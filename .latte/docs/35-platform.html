🔌 platform 驱动、设备树与 devm 资源管理

片上外设怎么被「认领」：设备树 → platform_device → probe → 资源自动回收 · 预计阅读 13 分钟

1. 它在解决什么问题

想象一栋写字楼：每个房间的水电接口位置都画在楼层的平面图上，工人拿着图纸进来，按图纸找到插座、接上线、装设备。图纸不会因为换了一栋楼就重画——楼的变化体现在图纸上，工人的操作流程不变。

Linux 内核面对的是同一件事。同一份内核要跑在无数块开发板上，板子上的 UART 在 0x9000000 还是 0x3f8、有没有 GPIO 控制芯片、中断号是多少，全都不一样。如果把这些差异写死在驱动代码里，就得为每块板子维护一个内核版本。内核的办法是：把硬件描述从代码里搬到数据里——这就是设备树（Device Tree, DT）。驱动只写「我是谁、我需要什么」，具体「我是谁」由设备树节点回答。

但设备树只是「图纸」。内核还需要一套机制把图纸上的节点和驱动对上号，并让驱动知道：我的寄存器在哪？中断号多少？用完怎么还回去？这套机制的主角叫 platform 总线——它是内核为「不可枚举的片上外设」准备的虚拟总线（PCI、USB 这些能自动枚举的设备不需要它）。

platform 总线只干三件事：

  • 造设备：把设备树里的一个节点变成一个 struct platform_device；
  • 配驱动：拿节点里的 compatible 字符串去和驱动声明的匹配表比对，命中就调用驱动的 probe()；
  • 发资源：把 reg（寄存器区）、interrupts（中断）、gpios（GPIO）交给驱动，并用 devm_* 机制保证「驱动解绑时资源自动归还」。

本篇就沿着这条链路走一遍：从设备树节点怎么变成 platform_device，到 compatible 怎么匹配打分，到 probe 里怎么拿寄存器、怎么用 devm 免手动释放，最后你在 qemu 的 -M virt 机器上写一个真正能 probe 成功的 platform 驱动。

为什么 x86 上很少讲设备树：x86 的硬件描述走的是 ACPI（固件提供），内核启动后由 ACPI 表生成设备。所以 x86 上 platform 设备多由板级代码或 ACPI 创建，而不是设备树。设备树是 ARM/RISC-V 等嵌入式平台的主流做法，QEMU 的 virt 机器恰好两种都支持，本文以设备树为主线。

3.2 compatible 匹配：不是「相等」而是「打分」

设备节点的 compatible 属性可以写多个字符串，从最具体到最笼统：


	pl011@9000000 {
		compatible = "arm,pl011", "primecell";
		...
	};

而驱动的匹配表也可以有多条。内核不会简单比较字符串是否相等，而是给每个候选打一个分，取最高分的那个。打分规则在 drivers/of/base.c 里写得很清楚：


 优先级（从高到低）：
   1. specific compatible && type && name
   2. specific compatible && type
   3. specific compatible && name
   4. specific compatible            ← 最常见的命中方式
   5. general compatible && type && name
   ...
  9. type && name
 10. type
 11. name

「specific（具体）」指的是 compatible 列表里靠前的字符串——越靠前越具体。所以一个驱动可以同时支持 "arm,pl011"（精确型号）和 "arm,primecell"（通用 IP），设备报哪个就匹配哪个。

3.4 devm：让「申请资源」和「释放资源」解耦

老式驱动在 probe 里申请资源，就必须在 remove 里一份份手动释放。写漏一个就是泄漏，写错顺序就是 use-after-free。内核给出的解法叫 devres（设备资源托管）：你把「资源」和「怎么释放它」一起登记到设备上，设备解绑时内核统一按逆序释放。


 probe 里：                          解绑时（自动，无需你写）：
 ─────────                          ──────────────────────────
 devm_kzalloc(dev, sz, gfp)      →   kfree(ptr)
 devm_ioremap_resource(dev, res) →   iounmap(ptr)
 devm_request_irq(dev, irq, ...) →   free_irq(irq, dev)
 devm_gpiod_get(dev, "reset")    →   gpiod_put(desc)
 devm_add_action_or_reset(dev, f, arg) → f(arg)

它的实现朴素得让人意外：每个设备有一个链表 dev->devres_head，登记时挂到链表头，释放时从头遍历逐个调用释放函数。逆序释放正好符合「后申请的先释放」的直觉。

4. 源码走读

4.1 设备树节点 → platform_device

这一步由 drivers/of/platform.c 完成：遍历设备树，为每个可用节点造一个 platform_device，并把节点里的属性翻译成内核认识的资源。

drivers/of/platform.c:166-199 of_platform_device_create_pdata

static struct platform_device *of_platform_device_create_pdata(
					struct device_node *np,
					const char *bus_id,
					void *platform_data,
					struct device *parent)
{
	struct platform_device *dev;

	if (!of_device_is_available(np) ||
	    of_node_test_and_set_flag(np, OF_POPULATED))
		return NULL;

	dev = of_device_alloc(np, bus_id, parent);
	if (!dev)
		goto err_clear_flag;

	dev->dev.coherent_dma_mask = DMA_BIT_MASK(32);
	if (!dev->dev.dma_mask)
		dev->dev.dma_mask = &dev->dev.coherent_dma_mask;
	dev->dev.bus = &platform_bus_type;
	dev->dev.platform_data = platform_data;
	of_msi_configure(&dev->dev, dev->dev.of_node);

	if (of_device_add(dev) != 0) {
		platform_device_put(dev);
		goto err_clear_flag;
	}

	return dev;

err_clear_flag:
	of_node_clear_flag(np, OF_POPULATED);
	return NULL;
}
  • of_device_is_available(np)：读节点的 status 属性。"okay"（或没有 status）才返回真；写成 "disabled" 就跳过——这是板级「暂时不用这个外设」的标准做法。
  • of_node_test_and_set_flag(np, OF_POPULATED)：给节点打标记，防止同一个节点被创建两次设备（设备树里一个节点可能同时被两条路径遍历到）。
  • dev->dev.bus = &platform_bus_type：这一行决定了它会走 platform 总线的匹配规则。
  • dev->dev.coherent_dma_mask = DMA_BIT_MASK(32)：默认只允许 32 位 DMA 地址；需要 64 位（ IOMMU 或大内存）的驱动会自己改。

真正的翻译工作（reg → resource、interrupts → IRQ）在 of_device_alloc()/of_device_add() 里完成，产出的资源就存在 pdev->resource[] 这个数组里。

4.2 platform_match：总线怎么决定「这个设备归你」

drivers/base/platform.c:1170-1193 platform_match

static int platform_match(struct device *dev, struct device_driver *drv)
{
	struct platform_device *pdev = to_platform_device(dev);
	struct platform_driver *pdrv = to_platform_driver(drv);

	/* When driver_override is set, only bind to the matching driver */
	if (pdev->driver_override)
		return !strcmp(pdev->driver_override, drv->name);

	/* Attempt an OF style match first */
	if (of_driver_match_device(dev, drv))
		return 1;

	/* Then try ACPI style match */
	if (acpi_driver_match_device(dev, drv))
		return 1;

	/* Then try to match against the id table */
	if (pdrv->id_table)
		return platform_match_id(pdrv->id_table, pdev) != NULL;

	/* fall-back to driver name match */
	return (strcmp(pdev->name, drv->name) == 0);
}

四条匹配路径，按优先级：

  • driver_override：强制指定。写 echo "mydrv" > /sys/bus/platform/devices/xxx/driver_override 就能手动指定驱动，调试神器。
  • 设备树匹配：of_driver_match_device() → of_match_device() → of_match_node()，也就是本文重点讲的 compatible 打分。
  • ACPI 匹配：x86 平台走这条路。
  • id_table 匹配：老式做法，驱动用 platform_device_id 数组按名字匹配。
  • 名字兜底：设备名和驱动名完全相同就算匹配。没有设备树的场景（比如内核里手工造平台设备）就靠这一条。

设备树匹配最终落到打分函数：

drivers/of/base.c:484-514 __of_device_is_compatible

static int __of_device_is_compatible(const struct device_node *device,
				     const char *compat, const char *type, const char *name)
{
	struct property *prop;
	const char *cp;
	int index = 0, score = 0;

	/* Compatible match has highest priority */
	if (compat && compat[0]) {
		prop = __of_find_property(device, "compatible", NULL);
		for (cp = of_prop_next_string(prop, NULL); cp;
		     cp = of_prop_next_string(prop, cp), index++) {
			if (of_compat_cmp(cp, compat, strlen(compat)) == 0) {
				score = INT_MAX/2 - (index << 2);
				break;
			}
		}
		if (!score)
			return 0;
	}

	/* Matching type is better than matching name */
	if (type && type[0]) {
		if (!__of_node_is_type(device, type))
			return 0;
		score += 2;
	}

	/* Matching name is a bit better than not */
	if (name && name[0]) {
		if (!of_node_name_eq(device, name))
    // ...（省略：返回 score）
  • INT_MAX/2 - (index << 2)：compatible 列表里越靠前的字符串（index 越小）分越高，每往后一个位置扣 4 分。
  • 匹配上 type 再加 2 分，匹配上 name 再加 1 分——这就是「compatible 优先于 type，type 优先于 name」的来源。
  • 返回 0 表示完全不匹配，直接出局。

4.3 platform_probe：总线把设备交给驱动

platform 总线在注册驱动时把自己的 probe 钩子挂上去，所以真正调用 drv->probe() 的是这段代码：

drivers/base/platform.c:746-773 platform_drv_probe

static int platform_drv_probe(struct device *_dev)
{
	struct platform_driver *drv = to_platform_driver(_dev->driver);
	struct platform_device *dev = to_platform_device(_dev);
	int ret;

	ret = of_clk_set_defaults(_dev->of_node, false);
	if (ret < 0)
		return ret;

	ret = dev_pm_domain_attach(_dev, true);
	if (ret)
		goto out;

	if (drv->probe) {
		ret = drv->probe(dev);
		if (ret)
			dev_pm_domain_detach(_dev, true);
	}

out:
	if (drv->prevent_deferred_probe && ret == -EPROBE_DEFER) {
		dev_warn(_dev, "probe deferral not supported\n");
		ret = -ENXIO;
	}

	return ret;
}
  • of_clk_set_defaults()：按设备树里的 clocks 属性把时钟框架准备妥当——所以你的 probe 里可以直接 devm_clk_get()。
  • dev_pm_domain_attach()：挂上电源域（PM domain），某些 SoC 上设备上电需要这个。
  • drv->probe(dev) 就是你的函数。返回 0 表示成功；返回负数表示失败，内核会解绑并释放所有 devm 资源。
  • 返回 -EPROBE_DEFER 表示「我依赖的另一个驱动还没就绪」，内核会把这个设备挂到延迟探测链表，等依赖满足后重试 probe。这是处理驱动间依赖的标准手法。

4.4 platform_get_resource 与 platform_get_irq

驱动拿到设备后，第一件事是问「我的寄存器在哪、中断是多少」。

drivers/base/platform.c:51-64 platform_get_resource

struct resource *platform_get_resource(struct platform_device *dev,
				       unsigned int type, unsigned int num)
{
	u32 i;

	for (i = 0; i < dev->num_resources; i++) {
		struct resource *r = &dev->resource[i];

		if (type == resource_type(r) && num-- == 0)
			return r;
	}
	return NULL;
}
EXPORT_SYMBOL_GPL(platform_get_resource);
  • type 是资源类型：IORESOURCE_MEM(0x200) 内存区、IORESOURCE_REG(0x300) 寄存器描述、IORESOURCE_IRQ(0x400) 中断。判断依据是 resource_type(r)，也就是 r->flags & IORESOURCE_TYPE_BITS。
  • num 是同类资源里的第几个。设备树里写了几个 reg，这里就用 0、1、2 依次取。
  • num-- == 0 这个写法很巧：命中第一个时 num 变 0 返回，第二个时 num 已是 -1 不等于 0……实际效果就是「数到第 num 个同类资源」。
  • 返回 NULL 表示没有这类资源，驱动必须检查。

中断号的获取多一层逻辑，因为要同时支持设备树和 ACPI：

drivers/base/platform.c:260-270 platform_get_irq

int platform_get_irq(struct platform_device *dev, unsigned int num)
{
	int ret;

	ret = platform_get_irq_optional(dev, num);
	if (ret < 0 && ret != -EPROBE_DEFER)
		dev_err(&dev->dev, "IRQ index %u not found\n", num);

	return ret;
}
EXPORT_SYMBOL_GPL(platform_get_irq);

而 platform_get_irq_optional() 里的顺序是：

  1. 如果设备有设备树节点，of_irq_get(dev->dev.of_node, num) 从 interrupts 属性解析出中断号；
  2. 否则退回从 IORESOURCE_IRQ 资源里取 r->start；
  3. 如果资源带了 IORESOURCE_BITS 里的触发类型标志，还会顺带设置 IRQ 的触发方式（边沿/电平）。

注意返回值语义：成功返回中断号（正数），失败返回负错误码。所以驱动里要写 if (irq < 0) return irq;，绝不能把负数当中断号传给 request_irq()。

4.5 devm_ioremap_resource：把寄存器变成能安全访问的指针

设备寄存器不能直接解引用物理地址，必须先 ioremap。而 devm_ioremap_resource() 把「申请 + 映射 + 自动回收」三件事打包了。

lib/devres.c:116-154 __devm_ioremap_resource

static void __iomem *
__devm_ioremap_resource(struct device *dev, const struct resource *res,
			enum devm_ioremap_type type)
{
	resource_size_t size;
	void __iomem *dest_ptr;
	char *pretty_name;

	BUG_ON(!dev);

	if (!res || resource_type(res) != IORESOURCE_MEM) {
		dev_err(dev, "invalid resource\n");
		return IOMEM_ERR_PTR(-EINVAL);
	}

	size = resource_size(res);

	if (res->name)
		pretty_name = devm_kasprintf(dev, GFP_KERNEL, "%s %s",
					     dev_name(dev), res->name);
	else
		pretty_name = devm_kstrdup(dev, dev_name(dev), GFP_KERNEL);
	if (!pretty_name)
		return IOMEM_ERR_PTR(-ENOMEM);

	if (!devm_request_mem_region(dev, res->start, size, pretty_name)) {
		dev_err(dev, "can't request region for resource %pR\n", res);
		return IOMEM_ERR_PTR(-EBUSY);
	}

	dest_ptr = __devm_ioremap(dev, res->start, size, type);
	if (!dest_ptr) {
		dev_err(dev, "ioremap failed for resource %pR\n", res);
		devm_release_mem_region(dev, res->start, size);
		dest_ptr = IOMEM_ERR_PTR(-ENOMEM);
	}

	return dest_ptr;
}
  • 先检查资源类型必须是 IORESOURCE_MEM，否则返回 -EINVAL——传错类型（比如把 IORESOURCE_REG 拿来）会在这里被挡住。
  • devm_request_mem_region()：向 I/O 资源管理器申请独占这段物理地址。别人已经占了就返回 -EBUSY。这一步能挡住「两个驱动乱映射同一段寄存器」。
  • __devm_ioremap()：真正做映射，并把「释放动作」登记到 devres 链上。
  • 映射失败时把刚申请的内存区退回去，错误码用 IOMEM_ERR_PTR() 包装。

对外的接口更简单：

lib/devres.c:175-180 devm_ioremap_resource

void __iomem *devm_ioremap_resource(struct device *dev,
				    const struct resource *res)
{
	return __devm_ioremap_resource(dev, res, DEVM_IOREMAP);
}
EXPORT_SYMBOL(devm_ioremap_resource);

platform 驱动还有两个「一步到位」的封装：devm_platform_ioremap_resource(pdev, 0)（自己取第 0 个内存资源再映射）和 devm_platform_get_and_ioremap_resource()（顺便把 resource 指针也返回给你）。

4.6 devm 资源是怎么被自动释放的

释放发生在驱动解绑时。内核先调用驱动的 remove，然后统一回收 devres。

drivers/base/dd.c:580-586 really_probe 的解绑路径

		if (dev->bus->remove)
			dev->bus->remove(dev);
		else if (drv->remove)
			drv->remove(dev);

		devres_release_all(dev);
		driver_sysfs_remove(dev);

drivers/base/devres.c:537-547 devres_release_all

int devres_release_all(struct device *dev)
{
	unsigned long flags;

	/* Looks like an uninitialized device structure */
	if (WARN_ON(dev->devres_head.next == NULL))
		return -ENODEV;
	spin_lock_irqsave(&dev->devres_lock, flags);
	return release_nodes(dev, dev->devres_head.next, &dev->devres_head,
			     flags);
}

release_nodes() 沿着链表挨个调用每个资源登记时留下的释放函数。链表是头插的，所以遍历顺序正好是「后申请的先释放」——这正是我们想要的顺序（比如先释放依赖别的东西的资源）。

如果你要加自己的清理逻辑（不是内核已有的 devm 类型），用 devm_add_action_or_reset()：

include/linux/device.h:257-267 devm_add_action_or_reset

static inline int devm_add_action_or_reset(struct device *dev,
					   void (*action)(void *), void *data)
{
	int ret;

	ret = devm_add_action(dev, action, data);
	if (ret)
		action(data);

	return ret;
}

or_reset 的意思是：如果登记动作本身失败了（比如内存不足），就立刻把 action 执行一遍做清理，避免漏掉资源。devm_add_action() 本身在 drivers/base/devres.c 里实现，也是用 devres 分配器分配的节点：

drivers/base/devres.c:739-754 devm_add_action

int devm_add_action(struct device *dev, void (*action)(void *), void *data)
{
	struct action_devres *devres;

	devres = devres_alloc(devm_action_release,
			      sizeof(struct action_devres), GFP_KERNEL);
	if (!devres)
		return -ENOMEM;

	devres->data = data;
	devres->action = action;

	devres_add(dev, devres);
	return 0;
}
EXPORT_SYMBOL_GPL(devm_add_action);

4.7 gpiod_get：拿 GPIO 的正确姿势

GPIO 在设备树里的描述是一个 <name>-gpios 属性，驱动用 gpiod_get() 按名字去要。

drivers/gpio/gpiolib.c:3817-3832 gpiod_get

/**
 * gpiod_get - obtain a GPIO for a given GPIO function
 * @dev:	GPIO consumer, can be NULL for system-global GPIOs
 * @con_id:	function within the GPIO consumer
 * @flags:	optional GPIO initialization flags
 *
 * Return: the GPIO descriptor corresponding to the function con_id of device
 * dev, -ENOENT if no GPIO has been assigned to the requested function, or
 * another IS_ERR() code if an error occurred while trying to acquire the GPIO.
 */
struct gpio_desc *__must_check gpiod_get(struct device *dev, const char *con_id,
					 enum gpiod_flags flags)
{
	return gpiod_get_index(dev, con_id, 0, flags);
}
EXPORT_SYMBOL_GPL(gpiod_get);

gpiod_get_index() 会依次尝试设备树、ACPI、平台数据三种来源，设备树这一路最终落到 of_find_gpio()：

drivers/gpio/gpiolib-of.c:492-517 of_find_gpio

struct gpio_desc *of_find_gpio(struct device *dev, const char *con_id,
			       unsigned int idx, unsigned long *flags)
{
	char prop_name[32]; /* 32 is max size of property name */
	enum of_gpio_flags of_flags;
	struct gpio_desc *desc;
	unsigned int i;

	/* Try GPIO property "foo-gpios" and "foo-gpio" */
	for (i = 0; i < ARRAY_SIZE(gpio_suffixes); i++) {
		if (con_id)
			snprintf(prop_name, sizeof(prop_name), "%s-%s", con_id,
				 gpio_suffixes[i]);
		else
			snprintf(prop_name, sizeof(prop_name), "%s",
				 gpio_suffixes[i]);

		desc = of_get_named_gpiod_flags(dev->of_node, prop_name, idx,
						&of_flags);

		if (!IS_ERR(desc) || PTR_ERR(desc) != -ENOENT)
			break;
	}

	// ...（省略：SPI/regulator/azona/usb 等特殊 GPIO 的兜底查找）
  • con_id 就是设备树属性的名字前缀：gpiod_get(dev, "reset") 找的是 reset-gpios 或 reset-gpio。
  • 返回值是 struct gpio_desc *（不透明描述符），不是 GPIO 编号——这样才能同时表达「哪个 GPIO 控制器 + 控制器里的第几根线」。
  • 用 gpiod_get_optional() 的场合，找不到时返回 NULL 而不是错误码，适合「有没有都行」的引脚。
  • 一定要用 devm_gpiod_get()，它会在设备解绑时自动 gpiod_put()。

4.8 一句话记住 DMA

驱动要一块「CPU 和设备都能直接访问、物理地址连续」的内存时，用 dma_alloc_coherent(dev, size, &dma_handle, gfp)：它返回的虚拟指针你可以直接解引用，返回的 dma_handle 是要写进设备寄存器的总线地址（设备通过 IOMMU 时它和物理地址不同）。释放用 dma_free_coherent()，或者用 devm_ 版本的托管接口。

{

			(gfp & __GFP_NOWARN) ? DMA_ATTR_NO_WARN : 0);
}

5.2 实验 A：自己造一个 platform 设备和驱动（任何 Linux 都能做）

这个实验不需要设备树，也不需要特殊硬件：我们在模块里造一个 platform_device（带一个假寄存器资源），再注册一个同名驱动，看内核如何自动匹配并调用 probe，最后看 devm 资源如何自动回收。

virt_demo.c：

// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/init.h>
#include <linux/platform_device.h>
#include <linux/ioport.h>
#include <linux/slab.h>

#define VIRT_DEV_NAME "virt-demo"
#define VIRT_REG_BASE 0x1000
#define VIRT_REG_SIZE 0x100

struct virt_demo {
	int counter;
};

/* 自定义的 devm 清理动作：设备解绑时自动调用 */
static void virt_demo_cleanup(void *data)
{
	struct virt_demo *v = data;
	pr_info("virt-demo: devm cleanup runs, counter=%d\n", v->counter);
}

static int virt_demo_probe(struct platform_device *pdev)
{
	struct virt_demo *v;
	struct resource *res;

	pr_info("virt-demo: probe, name=%s id=%d\n", pdev->name, pdev->id);

	/* 1) 私货：用 devm 分配，驱动解绑时自动释放 */
	v = devm_kzalloc(&pdev->dev, sizeof(*v), GFP_KERNEL);
	if (!v)
		return -ENOMEM;

	/* 2) 取资源：设备树 reg 或内核传进来的 resource 都在这里 */
	res = platform_get_resource(pdev, IORESOURCE_REG, 0);
	if (!res) {
		pr_err("virt-demo: no REG resource\n");
		return -ENODEV;
	}
	pr_info("virt-demo: reg 0x%llx..0x%llx\n",
		(unsigned long long)res->start,
		(unsigned long long)res->end);

	/* 3) 中断：真实设备里来自设备树的 interrupts 属性 */
	if (platform_get_irq(pdev, 0) < 0)
		pr_info("virt-demo: no irq (normal for a synthetic device)\n");

	/* 4) 自定义清理动作 */
	devm_add_action_or_reset(&pdev->dev, virt_demo_cleanup, v);

	platform_set_drvdata(pdev, v);
	v->counter = 42;
	pr_info("virt-demo: probed ok\n");
	return 0;
}

static int virt_demo_remove(struct platform_device *pdev)
{
	struct virt_demo *v = platform_get_drvdata(pdev);

	pr_info("virt-demo: remove, counter=%d\n", v ? v->counter : -1);
	return 0;
}

static struct platform_driver virt_demo_driver = {
	.probe	= virt_demo_probe,
	.remove	= virt_demo_remove,
	.driver = {
		.name = VIRT_DEV_NAME,
	},
};

static struct platform_device *virt_demo_dev;

static int __init virt_demo_init(void)
{
	struct resource res[1] = {
		{
			.start = VIRT_REG_BASE,
			.end   = VIRT_REG_BASE + VIRT_REG_SIZE - 1,
			.flags = IORESOURCE_REG,
			.name  = "regs",
		},
	};

	/* 先造设备 */
	virt_demo_dev = platform_device_register_simple(VIRT_DEV_NAME,
							PLATFORM_DEVID_NONE,
							res, ARRAY_SIZE(res));
	if (IS_ERR(virt_demo_dev))
		return PTR_ERR(virt_demo_dev);

	/* 再注册驱动：内核会立刻匹配并调用 probe */
	return platform_driver_register(&virt_demo_driver);
}

static void __exit virt_demo_exit(void)
{
	platform_driver_unregister(&virt_demo_driver);
	platform_device_unregister(virt_demo_dev);
	pr_info("virt-demo: bye\n");
}

module_init(virt_demo_init);
module_exit(virt_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("A synthetic platform device demo");

Makefile（和上一篇一样）：

obj-m := virt_demo.o
KDIR ?= /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

$ dmesg | tail -8

[ 12345.678902] virt-demo: reg 0x1000..0x10ff
[ 12345.678903] virt-demo: IRQ index 0 not found
[ 12345.678904] virt-demo: no irq (normal for a synthetic device)

预期输出说明（按出现顺序）：

  1. probe, name=virt-demo id=-1：驱动被调用了。注意 id=-1，因为我们传的是 PLATFORM_DEVID_NONE。
  2. reg 0x1000..0x10ff：platform_get_resource(pdev, IORESOURCE_REG, 0) 成功拿到了我们登记的资源。
  3. IRQ index 0 not found：platform_get_irq() 找不到中断时内核会打印这条错误——它内部调的是 platform_get_irq_optional()，找不到就返回 -ENXIO。真实设备的中断号来自设备树的 interrupts 属性。

5.3 实验 B：在 qemu -M virt 上写一个真正的设备树驱动

这个实验要走完整的设备树路线，需要一个 aarch64 内核（设备树是 ARM 平台的主场）和一个 busybox initramfs。

第 1 步：准备内核

$ make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- Image -j8

$ grep CONFIG_OF= .config
CONFIG_OF=y

第 2 步：导出 QEMU 的设备树并加一个自己的节点


$ qemu-system-aarch64 -M virt,dumpdtb=virt.dtb
$ dtc -I dtb -O dts -o virt.dts virt.dtb
$ less virt.dts

你会看到 QEMU 生成的设备树，里面有 pl011@9000000（串口，compatible = "arm,pl011"）、virtio_mmio@...、fw_cfg@9000000 等节点。现在编辑 virt.dts，在根节点的 / { ... } 里加入我们自己的设备：


	mydev@20000000 {
		compatible = "mycompany,mydev";
		reg = <0x0 0x20000000 0x0 0x1000>;
		interrupts = <0 1 100>;
		status = "okay";
	};
  • compatible 是我们驱动要匹配的关键字。
  • reg 是「地址 + 长度」。x86/arm64 的设备树里 #address-cells = <1>、#size-cells = <1>，所以 32 位地址写成 <0x0 0x20000000 0x0 0x1000>（每项 2 个 32 位字）。
  • interrupts = <0 1 100>：三元组「中断控制器号 / 类型 / 中断号」，这里 0=GIC、1=SPI、100=中断号。

$ dtc -I dts -O dtb -o virt-mydev.dtb virt.dts

第 3 步：写驱动（mydev.c）：

// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/io.h>

static int mydev_probe(struct platform_device *pdev)
{
	struct resource *res;
	void __iomem *base;
	int irq;

	res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
	if (!res) {
		pr_err("mydev: no reg resource\n");
		return -ENODEV;
	}
	pr_info("mydev: reg at 0x%llx size 0x%llx\n",
		(unsigned long long)res->start,
		(unsigned long long)resource_size(res));

	/* 取资源 + ioremap + 自动回收，一步到位 */
	base = devm_platform_ioremap_resource(pdev, 0);
	if (IS_ERR(base))
		return PTR_ERR(base);

	irq = platform_get_irq(pdev, 0);
	pr_info("mydev: base=%p irq=%d\n", base, irq);

	return 0;
}

static const struct of_device_id mydev_of_match[] = {
	{ .compatible = "mycompany,mydev" },
	{ }
};
MODULE_DEVICE_TABLE(of, mydev_of_match);

static struct platform_driver mydev_driver = {
	.probe = mydev_probe,
	.driver = {
		.name = "mydev",
		.of_match_table = mydev_of_match,
	},
};
module_platform_driver(mydev_driver);

MODULE_LICENSE("GPL");

不要真的去读写那个寄存器：0x20000000 在 QEMU 的 aarch64 virt 机器上并没有对应的设备，访问它会触发 QEMU 的「Invalid access」而让虚拟机abort。演示时只做 ioremap 和打印即可；如果你想真的读写，就把 reg 指向一个 QEMU 里真实存在且读起来无害的设备区域。
省事的替代方案：不想编译 arm64 内核的话，可以只做实验 A——它用纯软件造出 platform_device，把「匹配 → probe → 拿资源 → devm 自动释放」这条链路完整走了一遍，而这正是 platform 驱动的全部核心。设备树只是把「设备从哪来」换了个来源而已。

6. 自测

Q1. platform 总线存在的意义是什么？为什么不直接用 PCI 那种总线？因为片上外设（UART、I2C 控制器、GPIO 芯片）挂在芯片内部，没有 PCI 那种可枚举的总线，操作系统无法自动发现它们。platform 总线提供了一套统一的「设备—驱动」匹配框架，让这些设备的描述方式（设备树 / ACPI / 内核代码）和驱动的写法（probe/remove）都与 PCI 设备保持一致。
Q2. compatible 和驱动的名字必须完全一样吗？不一定。设备树路线下，匹配靠的是驱动 of_match_table 里的 compatible 串和节点 compatible 属性的字符串比较（带打分）。只有在没有设备树、也没有 id_table 时，才退化成「设备名 == 驱动名」的兜底匹配。设备名通常来自节点名（20000000.mydev），驱动名是自己取的，两者通常完全不同。
Q3. platform_get_resource(pdev, IORESOURCE_MEM, 0) 返回 NULL 怎么办？platform_get_irq() 返回负数又是什么意思？前者说明这个设备没有第 0 个内存资源：要么设备树里没写 reg，要么索引写错了。驱动必须检查返回值并返回错误码（如 -ENODEV），否则后面 devm_ioremap_resource() 会因为传进 NULL 而在 BUG_ON 处直接让内核崩溃。后者是错误码，常见的是 -ENXIO（这个设备没有第 0 个中断）——中断号本身是正数，所以驱动里必须写 if (irq < 0) return irq;，绝不能把负数传给 request_irq()。用 platform_get_irq_optional() 则不会打印错误日志，适合中断可选的设备。
Q4. devm_* 资源到底是谁释放的？驱动 remove 里还需要手动释放吗？不需要。devm 资源登记在 dev->devres_head 链表上，驱动解绑时内核在调用完 remove() 之后执行 devres_release_all()，按「后申请先释放」的逆序逐个调用释放函数。驱动自己 remove 里还要手动释放的，只有那些不是用 devm API 申请的普通资源。
Q5. probe 返回 -EPROBE_DEFER 是什么意思？设备树里 status = "disabled" 的节点会怎样？前者表示「我依赖的另一个设备/驱动还没准备好」，比如我要的时钟、电源域、IOMMU 还没注册。内核会把这个设备挂到延迟探测队列，等依赖满足后重新调用 probe——所以 probe 里遇到「资源暂时拿不到」时，返回 -EPROBE_DEFER 而不是 -ENODEV，是驱动之间正确排序的关键。后者则根本不会被创造成 platform_device：of_platform_device_create_pdata() 里的 of_device_is_available() 会跳过它。这给板级裁剪提供了手段：硬件在板上但这次不使能，就在设备树里关掉它。
