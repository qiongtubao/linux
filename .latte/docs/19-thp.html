📦 透明大页 THP：把 512 个页表项压成一个

用 2 MB 的"整块"映射换掉 512 次翻译，既省页表内存又省 TLB 压力，代价是内存放大和难预测的延迟抖动 · 预计阅读 42 分钟

1. 它在解决什么问题

先说清楚大页要解决的两个瓶颈。第 16 篇讲过，x86-64 的页表是四级的：一个进程的地址空间如果铺满 128 TB，光 PTE 那一级就要 128 TB / 4 KB = 340 亿个表项，按每项 8 字节算是 2.7 TB——当然实际用不到那么多，但只要程序碰过的地址是分散的，页表项的数量就会接近"碰过的页数"。每个页表项 8 字节，而它映射的页只有 4 KB 有效数据，页表本身比数据还稠密。

第二个瓶颈在 CPU 内部。CPU 里有个叫 TLB（Translation Lookaside Buffer）的缓存，专门存"最近用过的地址翻译结果"。它很快，但很小——典型只有 1536~2048 项。如果一个程序的工作集是 4 MB（1024 个 4 KB 页），TLB 装得下；但如果是 64 MB（16384 个页），就装不下了。装不下意味着TLB miss，CPU 必须去内存里查页表（四次访存），这比去数据缓存里拿数据慢得多。数据库、内存索引这类要扫大量内存的程序，TLB miss 就是致命的。

大页的思路非常直接：既然 4 KB 太小，那就用 2 MB 的页。2 MB = 512 个 4 KB 页。一个 PMD 表项就能覆盖整整 2 MB，于是：页表项数量除以 512，TLB 里能缓存的映射范围扩大 512 倍。这就是"大页"这个名字的全部含义。

那怎么用大页？Linux 有两条路子，区别很大：

  • hugetlbfs（显式大页）：你必须事先申请一大块（通常是 2 MB 或 1 GB）常驻物理内存，挂到一个特殊文件系统上，然后 mmap() 它。申请的页在启动时就被预留，不能被回收。你能精确控制"哪段地址用大页"，代价是要自己规划。
  • THP（透明大页）：不需要你申请。内核在普通的匿名内存缺页时，如果发现这个区域"适合大页"，就直接分配一个 2 MB 的大页来满足它；已经存在的小页，也可以被后台线程 khugepaged 合并成大页。所谓"透明"，就是应用程序完全无感——同一份代码，不需要改一行就能受益。

THP 的代价也很实在：①内存放大——你要 4 KB，内核可能给你 2 MB，剩下的 2 MB - 4 KB 被浪费（浪费的部分还是零页，但地址空间和 memcg 记账会按 2 MB 算）；②延迟抖动——分配 2 MB 需要一次 order-9 的连续内存分配，可能触发直接内存回收和内存整理，产生几百毫秒的停顿；③拆分——如果程序只碰了其中一个 4 KB 页，内核还得把这个大页拆回小页（__split_huge_pmd()），拆分的瞬间也会有延迟尖峰。本文会把这些代价的成因逐一对应到源码。

3. 整体结构

3.1 4 KB 映射 vs 2 MB 映射

  4 KB 页（普通映射）                        2 MB 大页（THP）

  PUD -> PMD -> PTE -> 页                     PUD -> PMD(=大页) -> 页
                    +------+                                  +--------+
   PTE[0]  -------->| 页 0 |                 PMD(PSE)  -------->| 页 0  |
   PTE[1]  -------->| 页 1 |                                  | 页 1  |
   PTE[2]  -------->| 页 2 |                                  | 页 2  |
     ...            |  ... |                                  |  ...  |
   PTE[511]-------->|页511 |                                  | 页 511|
                    +------+                                  +--------+

  映射 2 MB 需要：512 个 PTE (+ 1 个 PMD)      映射 2 MB 需要：1 个 PMD
  TLB 占 512 项                                TLB 占 1 项
  页表内存：512*8 = 4 KB                       页表内存：8 字节（+PMD 4KB 页）

收益一目了然：页表项少 512 倍，TLB 压力小 512 倍。代价是粒度变粗——只要用到大页里的任何一个字节，整个 2 MB 都被占着。

3.2 THP 的三条落地路径

  【路径 A：缺页时直接分配大页】
     程序第一次碰匿名内存 -> 缺页异常
        -> __handle_mm_fault() 发现 PMD 是空的
        -> create_huge_pmd()  (mm/memory.c)
        -> do_huge_pmd_anonymous_page()  (mm/huge_memory.c)
        -> 分配一个 order-9 复合页，清零，装进 PMD

  【路径 B：后台合并（khugepaged）】
     程序已经用小页跑了一阵 -> khugepaged 定期扫描
        -> 发现某个 VMA 里有一片连续的、够 2 MB 的小页
        -> collapse_huge_page()
        -> 申请 2 MB 连续内存 -> 拷贝内容 -> 换成 PMD 映射

  【路径 C：按需建议（MADV_HUGEPAGE）】
     程序调用 madvise(addr, len, MADV_HUGEPAGE)
        -> VMA 打上 VM_HUGEPAGE 标记
        -> khugepaged 把这个 mm 登记进扫描名单
        -> 之后走路径 A 或路径 B

路径 A 是"生下来就是大页"，路径 B 是"长大变成大页"，路径 C 是"给路径 A/B 开个许可证"。

3.3 三种系统级策略

  /sys/kernel/mm/transparent_hugepage/enabled

  always    : 所有合适的匿名 VMA 都用大页
  madvise  : 只有打了 VM_HUGEPAGE 标记的 VMA 才用大页  <-- 很多发行版的默认值
  never     : 完全禁用 THP（退回到全部 4 KB）

madvise 是最常用的折中：默认不打扰所有程序，需要大页的应用自己用 madvise() 申请。Debian/Ubuntu 历史上因为 THP 的延迟抖动问题，一度默认设成 madvise；而 RHEL/CentOS 系的 transparent_hugepage=never 曾经是默认，理由同样是数据库场景下的尾延迟问题。

3.4 大页 vs hugetlbfs

对比项THP（透明大页）hugetlbfs（显式大页）
谁决定用哪块内核自动挑（可以 madvise 建议）用户明确申请哪一块
物理内存来源普通 buddy 页临时拼成 order-9启动时预留的 hugepage 池
内存是否常驻否——用完可被回收是——预留后不能被回收
延迟抖动有（分配 2 MB 连续块、拆分大页）几乎没有（内存早就预留好了）
内存放大有无（要用多少申请多少）
典型用途通用、零改造数据库（Oracle/PostgreSQL）追求稳定尾延迟
配置方式/sys/kernel/mm/transparent_hugepage/*/proc/sys/vm/nr_hugepages + 挂载 hugetlbfs

3.5 THP 的三种开销，对应到源码

  ① 内存放大
     用户要 4 KB，内核给 2 MB
     -> add_mm_counter(mm, MM_ANONPAGES, HPAGE_PMD_NR)  按 2 MB 记账
     -> RSS 里显示 2 MB，实际用 4 KB
     -> memcg 限额也按 2 MB 扣

  ② 分配延迟（"延迟抖动"的根源）
     alloc_hugepage_vma(gfp, vma, haddr, HPAGE_PMD_ORDER)
     -> order-9 = 2 MB 连续
     -> buddy 系统里没有 2 MB 连续块？
        -> 触发 direct reclaim + compaction（内存整理）
        -> 可能几百毫秒的停顿
     -> /sys/kernel/mm/transparent_hugepage/defrag 控制要不要同步整理

  ③ 拆分延迟
     程序只碰了 2 MB 里的一个 4 KB 页
     -> __split_huge_pmd() 把大页拆成 512 个 PTE
     -> 内容不丢（复用同一批复合页），但页表操作变多
     -> 拆分点附近会出现延迟尖峰

这就是为什么很多数据库会明确把 THP 关掉或设成 madvise：它们宁可自己用 hugetlbfs 精确管理大页，也不要被内核"惊喜"地塞一个 order-9 分配。

4. 源码走读

4.1 大页的尺寸常量

include/linux/huge_mm.h:112-118 HPAGE_PMD_ORDER / HPAGE_PMD_NR

#define HPAGE_PMD_ORDER (HPAGE_PMD_SHIFT-PAGE_SHIFT)
#define HPAGE_PMD_NR (1<<HPAGE_PMD_ORDER)

#ifdef CONFIG_TRANSPARENT_HUGEPAGE
#define HPAGE_PMD_SHIFT PMD_SHIFT
#define HPAGE_PMD_SIZE	((1UL) << HPAGE_PMD_SHIFT)
#define HPAGE_PMD_MASK	(~(HPAGE_PMD_SIZE - 1))

HPAGE_PMD_SHIFT 就是 PMD_SHIFT（第 16 篇讲过是 21），所以 HPAGE_PMD_SIZE = 2 MB。HPAGE_PMD_ORDER = 21 - 12 = 9，是伙伴系统的阶数——order-9 意味着 2 MB 连续物理内存，这正是"大页分配可能触发内存整理"的根源。HPAGE_PMD_NR = 512，是一个大页包含的基础页数量。

4.2 缺页路径的入口：create_huge_pmd()

第 16 篇讲过，__handle_mm_fault() 在 PMD 为空时会尝试走大页路径：

mm/memory.c:4404-4412 create_huge_pmd

static inline vm_fault_t create_huge_pmd(struct vm_fault *vmf)
{
	if (vma_is_anonymous(vmf->vma) /* 检查是否为匿名VMA */)
		return do_huge_pmd_anonymous_page(vmf);
	if (vmf->vma->vm_ops->huge_fault)
		return vmf->vma->vm_ops->huge_fault(vmf, PE_SIZE_PMD);
	return VM_FAULT_FALLBACK;
}

三个出口：① 匿名 VMA → do_huge_pmd_anonymous_page()（THP 的主路径）；② 有 vm_ops->huge_fault 的 VMA（典型是 shmem/文件映射）→ 交给文件系统处理；③ 都不行 → VM_FAULT_FALLBACK，退回普通 4 KB 路径。"能退回去"是 THP 的基本礼貌——大页是优化，不是承诺。

4.3 do_huge_pmd_anonymous_page()：检查与分配

mm/huge_memory.c:695-716 do_huge_pmd_anonymous_page

vm_fault_t do_huge_pmd_anonymous_page(struct vm_fault *vmf)
{
	struct vm_area_struct *vma = vmf->vma;
	gfp_t gfp;
	struct page *page;
	unsigned long haddr = vmf->address & HPAGE_PMD_MASK;

	if (!transhuge_vma_suitable(vma, haddr))
		return VM_FAULT_FALLBACK;
	if (unlikely(anon_vma_prepare(vma)))
		return VM_FAULT_OOM;
	if (unlikely(khugepaged_enter(vma, vma->vm_flags)))
		return VM_FAULT_OOM;
	if (!(vmf->flags & FAULT_FLAG_WRITE) &&
			!mm_forbids_zeropage(vma->vm_mm) &&
			transparent_hugepage_use_zero_page()) {
		pgtable_t pgtable;
		struct page *zero_page;
		vm_fault_t ret;
		pgtable = pte_alloc_one(vma->vm_mm);
		if (unlikely(!pgtable))
			return VM_FAULT_OOM;

三个前置检查：transhuge_vma_suitable()（VMA 够不够大、地址对齐不对不对）、anon_vma_prepare()（准备反向映射）、khugepaged_enter()（把这个 mm 登记给 khugepaged）。然后是一个优化分支：如果只是读一个大页，而且内核允许用"全零大页"，那就不分配 2 MB 物理内存，直接把 PMD 指向一个共享的零页——零页的内容本来就是 0，而新分配的匿名内存也要求是 0，语义完全等价，却省掉了 2 MB 的分配。

mm/huge_memory.c:746-754 do_huge_pmd_anonymous_page（真正分配）

	gfp = alloc_hugepage_direct_gfpmask(vma);
	page = alloc_hugepage_vma(gfp, vma, haddr, HPAGE_PMD_ORDER);
	if (unlikely(!page)) {
		count_vm_event(THP_FAULT_FALLBACK);
		return VM_FAULT_FALLBACK;
	}
	prep_transhuge_page(page);
	return __do_huge_pmd_anonymous_page(vmf, page, gfp);
}

alloc_hugepage_vma(gfp, vma, haddr, HPAGE_PMD_ORDER) 就是那次 order-9 分配——THP 延迟抖动的主要来源就在这一行。alloc_hugepage_direct_gfpmask() 会根据 defrag 开关和 VMA 是否有 VM_HUGEPAGE 标记，决定 GFP 标志里带不带 __GFP_DIRECT_RECLAIM（允许直接回收）和 __GFP_COMP（允许同步内存整理）。分配失败就 VM_FAULT_FALLBACK 退回 4 KB 路径——所以 THP 永远不该把系统卡死。

4.4 __do_huge_pmd_anonymous_page()：把大页装进 PMD

mm/huge_memory.c:619-632 __do_huge_pmd_anonymous_page

		entry = mk_huge_pmd(page, vma->vm_page_prot);
		entry = maybe_pmd_mkwrite(pmd_mkdirty(entry), vma);
		page_add_new_anon_rmap(page, vma, haddr, true);
		lru_cache_add_inactive_or_unevictable(page, vma);

		set_pmd_at(vma->vm_mm, haddr, vmf->pmd, entry);
		add_mm_counter(vma->vm_mm, MM_ANONPAGES, HPAGE_PMD_NR);

逐行看：mk_huge_pmd() 造出 PMD 表项（带 PSE 位，指向复合页的 head page）；page_add_new_anon_rmap() 建立反向映射（第 16 篇讲的 anon_vma 机制）；lru_cache_add_inactive_or_unevictable() 把大页挂进 LRU 链表（第 18 篇）；set_pmd_at() 真正写进页表；最后 add_mm_counter(mm, MM_ANONPAGES, HPAGE_PMD_NR) 按 512 个基础页记账——这就是内存放大的账本：你只要了 4 KB，RSS 和 memcg 配额都按 2 MB 算。

4.5 __split_huge_pmd()：把大页拆回小页

当程序只碰了 2 MB 里的一个 4 KB 页，或者 VMA 的边界不在 2 MB 对齐位置，内核就必须拆页。

mm/huge_memory.c:2211-2237 __split_huge_pmd

repeat:
	if (pmd_trans_huge(*pmd)) {
		if (!page) {
			page = pmd_page(*pmd);
			if (unlikely(!trylock_page(page))) {
				get_page(page);
				_pmd = *pmd;
				spin_unlock(ptl);
				lock_page(page);
				spin_lock(ptl);
				if (unlikely(!pmd_same(*pmd, _pmd))) {
					unlock_page(page);
					put_page(page);
					page = NULL;
					goto repeat;
				}
				put_page(page);
			}
		}
		if (PageMlocked(page))
			clear_page_mlock(page);
	} else if (!(pmd_devmap(*pmd) || is_pmd_migration_entry(*pmd)))
		goto out;
	__split_huge_pmd_locked(vma, pmd, range.start, freeze);
out:
	spin_unlock(ptl);

trylock_page() 是并发保护：如果别的 CPU 正拿着这个大页（比如正在拆分或正在回收），就退出去拿阻塞锁，拿到后必须用 pmd_same() 复查页表项有没有被别人改过——这是典型的"读-改-写"竞态处理。

真正拆页的代码在 __split_huge_pmd_locked() 里：

mm/huge_memory.c:2113-2149 __split_huge_pmd_locked

	pgtable = pgtable_trans_huge_withdraw(mm, pmd);
	pmd_populate(mm, &_pmd, pgtable);

	for (i = 0, addr = haddr; i < HPAGE_PMD_NR; i++, addr += PAGE_SIZE) {
		pte_t entry, *pte;
		/*
		 * Note that NUMA hinting access restrictions are not
		 * transferred to avoid any possibility of altering
		 * permissions across VMAs.
		 */
		if (freeze || pmd_migration) {
			swp_entry_t swp_entry;
			swp_entry = make_migration_entry(page + i, write);
			entry = swp_entry_to_pte(swp_entry);
			if (soft_dirty)
				entry = pte_swp_mksoft_dirty(entry);
			if (uffd_wp)
				entry = pte_swp_mkuffd_wp(entry);
		} else {
			entry = mk_pte(page + i, READ_ONCE(vma->vm_page_prot));
			entry = maybe_mkwrite(entry, vma);
			if (!write)
				entry = pte_wrprotect(entry);
			if (!young)
				entry = pte_mkold(entry);
			if (soft_dirty)
				entry = pte_swp_mksoft_dirty(entry);
			if (uffd_wp)
				entry = pte_swp_mkuffd_wp(entry);
		}
		pte = pte_offset_map(&_pmd, addr);
		BUG_ON(!pte_none(*pte));

关键证据在 mk_pte(page + i, ...) 这个 page + i：拆出来的 512 个 PTE 指向的还是原来那个复合页里的第 i 个子页，一个字节都没有复制，物理内存也没变。5.10 的拆分只做两件事：把 PMD 表项撤下来（pgtable_trans_huge_withdraw），换成一张普通的 PTE 表（pmd_populate），然后逐个填 PTE。所以"拆分"本身并不慢——慢的是拆分前后的其他动作（比如为了对齐而把整个 VMA 重新布局）。

4.6 hugepage_vma_check()：谁有资格用大页

mm/khugepaged.c:440-461 hugepage_vma_check

static bool hugepage_vma_check(struct vm_area_struct *vma,
			       unsigned long vm_flags)
{
	if ((!(vm_flags & VM_HUGEPAGE) && !khugepaged_always()) ||
	    (vm_flags & VM_NOHUGEPAGE) ||
	    test_bit(MMF_DISABLE_THP, &vma->vm_mm->flags))
		return false;

	if (shmem_file(vma->vm_file) ||
	    (IS_ENABLED(CONFIG_READ_ONLY_THP_FOR_FS) &&
	     vma->vm_file &&
	     (vm_flags & VM_DENYWRITE))) {
		return IS_ALIGNED((vma->vm_start >> PAGE_SHIFT) - vma->vm_pgoff,
				HPAGE_PMD_NR);
	}
	if (!vma->anon_vma || vma->vm_ops)
		return false;
	if (vma_is_temporary_stack(vma))
		return false;
	return !(vm_flags & VM_NO_KHUGEPAGED);
}

逐条读这四个"否决项"：① 既没有 VM_HUGEPAGE 标记、系统又不是 always 模式 → 不行（这就是 madvise 模式的实现）；② 有 VM_NOHUGEPAGE 标记 → 不行（MADV_NOHUGEPAGE 可以给某块内存单独禁用）；③ !vma->anon_vma || vma->vm_ops → 不行（有 vm_ops 说明是有文件系统后备的映射，5.10 的 THP 只支持匿名内存和共享内存）；④ 临时栈 → 不行。

而 VM_HUGEPAGE 标记本身是这样设置和判断的：

include/linux/huge_mm.h:130-157 __transparent_hugepage_enabled

static inline bool __transparent_hugepage_enabled(struct vm_area_struct *vma)
{
	if (vma->vm_flags & VM_NOHUGEPAGE)
		return false;

	if (vma_is_temporary_stack(vma))
		return false;

	if (test_bit(MMF_DISABLE_THP, &vma->vm_mm->flags))
		return false;

	if (transparent_hugepage_flags & (1 << TRANSPARENT_HUGEPAGE_FLAG))
		return true;
	/*
	 * For dax vmas, try to always use hugepage mappings. If the kernel does
	 * not support hugepages, fsdax mappings will fallback to PAGE_SIZE
	 * mappings, and device-dax namespaces, that try to guarantee a given
	 * mapping size, will fail to enable
	 */
	if (vma_is_dax(vma))
		return true;

	if (transparent_hugepage_flags &
				(1 << TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG))
		return !!(vma->vm_flags & VM_HUGEPAGE);

	return false;
}

三个 if 依次对应系统级开关：always（TRANSPARENT_HUGEPAGE_FLAG）→ 直接返回 true；madvise（TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG）→ 看 VMA 有没有 VM_HUGEPAGE 标记；都不满足（never）→ 返回 false。

4.7 madvise(MADV_HUGEPAGE)：给某块内存开许可证

mm/khugepaged.c:345-382 hugepage_madvise

int hugepage_madvise(struct vm_area_struct *vma,
		     unsigned long *vm_flags, int advice)
{
	switch (advice) {
	case MADV_HUGEPAGE:
#ifdef CONFIG_S390
		/*
		 * qemu blindly sets MADV_HUGEPAGE on all allocations, but s390
		 * can't handle this properly after s390_enable_sie, so we simply
		 * ignore the madvise to prevent qemu from causing a SIGSEGV.
		 */
		if (mm_has_pgste(vma->vm_mm))
			return 0;
#endif
		*vm_flags &= ~VM_NOHUGEPAGE;
		*vm_flags |= VM_HUGEPAGE;
		/*
		 * If the vma become good for khugepaged to scan,
		 * register it here without waiting a page fault that
		 * may not happen any time soon.
		 */
		if (!(*vm_flags & VM_NO_KHUGEPAGED) &&
				khugepaged_enter_vma_merge(vma, *vm_flags))
			return -ENOMEM;
		break;
	case MADV_NOHUGEPAGE:
		*vm_flags &= ~VM_HUGEPAGE;
		*vm_flags |= VM_NOHUGEPAGE;
		break;
	}

	return 0;
}

注意那句注释："register it here without waiting a page fault that may not happen any time soon"——打上 VM_HUGEPAGE 标记后立刻把这个 mm 登记给 khugepaged，这样即使程序之后再也不碰这段内存，khugepaged 也会主动去合并它。

4.8 enabled 开关的实现

mm/huge_memory.c:162-199 enabled_show / enabled_store

static ssize_t enabled_show(struct kobject *kobj,
			    struct kobj_attribute *attr, char *buf)
{
	if (test_bit(TRANSPARENT_HUGEPAGE_FLAG, &transparent_hugepage_flags))
		return sprintf(buf, "[always] madvise never\n");
	else if (test_bit(TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG, &transparent_hugepage_flags))
		return sprintf(buf, "always [madvise] never\n");
	else
		return sprintf(buf, "always madvise [never]\n");
}

static ssize_t enabled_store(struct kobject *kobj,
			     struct kobj_attribute *attr,
			     const char *buf, size_t count)
{
	ssize_t ret = count;

	if (sysfs_streq(buf, "always")) {
		clear_bit(TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG, &transparent_hugepage_flags);
		set_bit(TRANSPARENT_HUGEPAGE_FLAG, &transparent_hugepage_flags);
	} else if (sysfs_streq(buf, "madvise")) {
		clear_bit(TRANSPARENT_HUGEPAGE_FLAG, &transparent_hugepage_flags);
		set_bit(TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG, &transparent_hugepage_flags);
	} else if (sysfs_streq(buf, "never")) {
		clear_bit(TRANSPARENT_HUGEPAGE_FLAG, &transparent_hugepage_flags);
		clear_bit(TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG, &transparent_hugepage_flags);
	} else
		ret = -EINVAL;

	if (ret > 0) {
		int err = start_stop_khugepaged();
		if (err)
			ret = err;
	}
	return ret;
}

实现就是两个 bit 的组合：TRANSPARENT_HUGEPAGE_FLAG（always）和 TRANSPARENT_HUGEPAGE_REQ_MADV_FLAG（madvise）。enabled_show() 用方括号标出当前值，所以 cat 出来的 [madvise] 表示"当前是 madvise 模式"。最后 start_stop_khugepaged() 会根据新策略启停 khugepaged 线程——切到 never 时 khugepaged 就被停掉了。

4.9 khugepaged：后台合并线程

mm/khugepaged.c:2243-2262 khugepaged

static int khugepaged(void *none)
{
	struct mm_slot *mm_slot;

	set_freezable();
	set_user_nice(current, MAX_NICE);

	while (!kthread_should_stop()) {
		khugepaged_do_scan();
		khugepaged_wait_work();
	}

	spin_lock(&khugepaged_mm_lock);
	mm_slot = khugepaged_scan.mm_slot;
	khugepaged_scan.mm_slot = NULL;
	if (mm_slot)
		collect_mm_slot(mm_slot);
	spin_unlock(&khugepaged_mm_lock);
	return 0;
}

一个非常朴素的循环：扫一遍 → 睡一会儿 → 再扫一遍。set_user_nice(current, MAX_NICE) 把线程的 nice 值降到最低优先级——khugepaged 是"后台做好事"，绝不能跟业务抢 CPU。扫描间隔由 khugepaged_scan_sleep_millisecs 控制（默认 10000 ms，即 10 秒一轮）。

扫描的核心是 khugepaged_do_scan() → khugepaged_scan_mm_slot() → khugepaged_scan_pmd()，最后落到 collapse_huge_page()：申请一块新的 2 MB 连续内存，把原来 512 个小页的内容拷进去，然后把 PMD 表项换成指向新的大页。合并的判定条件是：该 PMD 覆盖的 2 MB 范围内，所有 4 KB 页都已经驻留且没有在写——否则合并会丢数据。

hugetlbfs 是一个"用 RAM 当后备存储"的伪文件系统。挂载它、创建一个文件，mmap() 那个文件，得到的映射就是 hugetlb 映射——VMA 上会打上 VM_HUGETLB 标志（见 fs/hugetlbfs/inode.c:146），用 hugetlb_vm_ops。这些页是启动时就从伙伴系统预留出来的（/proc/sys/vm/nr_hugepages），不参与普通回收——这正是它尾延迟稳定的原因：分配时不需要现凑 2 MB 连续块。

defrag 的取值含义：

值含义
always任何 THP 分配都允许同步做内存整理（延迟最可控，但可能有停顿）
defer只在没有空闲大页时才做整理（常见默认）

6. 自测

Q1. THP 和 hugetlbfs 有什么区别？什么时候该用哪个？THP 是透明的：内核自动把合适的匿名内存用 2 MB 映射，程序无感，页是临时分配的（可被回收），存在内存放大和延迟抖动。hugetlbfs 是显式的：你在启动时通过 nr_hugepages 预留大页池，挂载后自己 mmap，页常驻不可回收，没有放大也没有抖动。追求尾延迟稳定的关键业务（Oracle、PostgreSQL 的大内存配置）通常用 hugetlbfs；希望零改造获得 TLB 收益的普通应用用 THP。
Q2. 为什么 THP 会造成"内存放大"？放大多少？因为一个大页是 2 MB，只要程序碰了其中一个 4 KB 页，整块 2 MB 就算被占用。内核按 add_mm_counter(mm, MM_ANONPAGES, HPAGE_PMD_NR) 记账（HPAGE_PMD_NR = 512），所以 RSS、memcg 配额都按 2 MB 计算，而实际有用的可能只有几 KB。最坏情况下放大 512 倍；如果程序均匀地碰过整个 2 MB，则没有浪费。
Q3. THP 的"延迟抖动"是怎么产生的？主要来自分配时刻：alloc_hugepage_vma(gfp, vma, haddr, HPAGE_PMD_ORDER) 要一次拿 order-9（2 MB 连续）的物理内存。如果 buddy 系统里没有现成的 2 MB 连续块，就要触发直接内存回收 + 内存整理（compaction）把碎片拼起来，这个过程可能耗时几十到几百毫秒，用户态表现为一次莫名的卡顿。缓解手段是设置 /sys/kernel/mm/transparent_hugepage/defrag = never（分配失败就退回 4 KB）或 madvise（只让明确申请大页的 VMA 承担这个代价）。
Q4. 把大页拆成小页会把数据复制一遍吗？不会。5.10 的 __split_huge_pmd_locked() 里，每个 PTE 指向的是 mk_pte(page + i, ...)——原复合页里的第 i 个子页。物理内存完全不动，拆分的动作只是把 PMD 表项换成一张普通的 PTE 表，再逐个填好 512 个 PTE。内容零拷贝。真正可能产生延迟的是拆分前后的其他工作（比如为了让 VMA 边界对齐而调整映射布局）。
Q5. enabled = madvise 模式下，怎么才能让我的程序用上大页？在 mmap() 之后调用 madvise(addr, len, MADV_HUGEPAGE)。内核会在 VMA 上打 VM_HUGEPAGE 标记（hugepage_madvise()，见 4.7 节），此后这个 VMA 走大页路径。反过来用 MADV_NOHUGEPAGE 可以给某段内存单独禁用大页。注意 madvise 只是建议——如果当前分配不到 2 MB 连续块，内核仍然会退回 4 KB，这是正常行为。
