🔋 电源管理：suspend、cpuidle、cpufreq

合盖后为什么还能收到邮件：四个层次的省电与唤醒 · 预计阅读 25 分钟

1. 它在解决什么问题

晚上合上笔记本，第二天打开，电池只掉了 3%，风扇没转，可手机推送居然同步过来了。若 CPU 一直满速空转，一夜能烧掉半块电池；若整机彻底断电，网卡就再也收不到数据。电源管理要解决的就是这个矛盾：在“深睡省电”和“随时能醒”之间分层取舍，并且对每个设备单独决定——屏幕可以立刻关，网卡不能。

从操作系统看，这里有四个层次，常被混为一谈：系统级睡眠（整机挂起 / 休眠，一次性的大动作）、CPU 空闲（这颗核此刻无事可做，进哪种低功耗状态）、频率调节（真要跑时用多快、多耗电）、运行时电源管理（单个设备空闲就关掉，常态发生）。它们串成一条链：设备各自挂起，CPU 再进深睡，最后整机断电或维持浅睡。

为什么必须分层？因为省电和响应是死对头。睡得越深唤醒越慢：CPU 从 C6 醒来要几十微秒，整机从 S3 醒来要几百毫秒。整个电源管理的工程学就两句话：尽可能深地睡，又在正确的时间醒。于是出现了“预测下次定时器还有多久”的 cpuidle 调节器、“跟着负载调频率”的 cpufreq 调节器、“谁在阻止我睡”的 wakeup source 记账——骨架全是预测与记账。

3. 整体结构

3.1 四个层次各管什么

用户动作（合盖 / 空闲 / 负载上升）
   │
   ├─► /sys/power/state ──► kernel/power/main.c  state_store ──► pm_suspend()
   │        系统级：freeze / mem / disk
   │             └─ suspend_enter(): 挂设备 → 关从核 → 停中断 → 固件睡
   │
   ├─► CPU 无事可做 ──► cpuidle governor（menu / teo）选 C 状态
   │        └─ 依据：下次定时器到期时间、退出延迟、PM QoS 约束
   │
   ├─► 负载变化 ──► cpufreq governor（schedutil）选频率
   │        └─ schedutil 在调度器更新利用率时被回调
   │
   └─► 设备空闲 ──► runtime PM（usage counter 归零 → rpm_idle → suspend 回调）
            └─ 驱动的 pm_runtime_get_sync() / pm_runtime_put_autosuspend()

3.2 /sys/power/state 的取值

写入值内核状态实际行为
freezePM_SUSPEND_TO_IDLEs2idle：冻结进程、挂起设备，CPU 只进 idle，不进固件睡眠。
standbyPM_SUSPEND_STANDBY浅睡，需平台 valid() 支持。
memPM_SUSPEND_MEMS3（挂起到内存），实际深度还由 /sys/power/mem_sleep 细分成 s2idle/shallow/deep。
diskPM_SUSPEND_MAX休眠，走 hibernate()。

这些字符串来自 kernel/power/suspend.c:36-40 的 pm_labels[]；mem_sleep 的三个取值来自同文件 42-46 行的 mem_sleep_labels[]。注意 freeze 与 mem_sleep 里的 s2idle 是同一个内核状态，两个文件的叫法不同。

3.3 一次 suspend 的步骤

核心是“层层递进、失败就逐层回滚”：

pm_suspend(state)
 ├─ suspend_console()
 ├─ dpm_suspend_start(PMSG_SUSPEND)     ← 普通设备 suspend 回调
 ├─ suspend_enter()
 │    ├─ platform_suspend_prepare()
 │    ├─ dpm_suspend_late()             ← late 阶段
 │    ├─ dpm_suspend_noirq()            ← 关中断后再挂
 │    ├─ suspend_disable_secondary_cpus()
 │    ├─ arch_suspend_disable_irqs()
 │    ├─ syscore_suspend()              ← 时钟 / 中断控制器
 │    └─ suspend_ops->enter(state)      ← 真正睡下去
 └─ 唤醒后原路反向 resume

顺序刻意“从外到内”：先停一般设备，再停需要中断的最后一批（noirq），最后才关 CPU 与系统核心。任何一步失败都反着回去，保证设备醒来时它的依赖（时钟、总线）还在。

3.4 谁在阻止我睡：wakeup source 与 QoS

设备驱动程序在收到可能唤醒系统的事件后调用 pm_stay_awake()，处理完再 pm_relax()。内核为每个设备维护一个 struct wakeup_source（include/linux/pm_wakeup.h:43-64），里面记着 total_time、max_time、event_count、wakeup_count——这就是 /sys/kernel/debug/wakeup_sources 与 powertop “谁最费电”的数据来源。只要还有 active 的 wakeup source，系统就认为不该进入深睡。

另一类约束来自 PM QoS：设备可以注册“我最多能忍受 50μs 唤醒延迟”，dev_pm_qos_add_request()（include/linux/pm_qos.h:170-173）登记后，所有请求按类型取最严值。这类约束会直接喂给 cpuidle 的 latency_req，也会限制 cpufreq 的 min/max frequency。

4. 源码走读

4.1 用户写 /sys/power/state 之后

sysfs 属性只做参数解析和分发：把 mem 换成当前选定的 mem 睡眠模式，把 disk 交给 hibernate。

kernel/power/main.c:638-666 state_store

static ssize_t state_store(struct kobject *kobj, struct kobj_attribute *attr,
			   const char *buf, size_t n)
{
	suspend_state_t state;
	int error;

	error = pm_autosleep_lock();
	if (error)
		return error;

	if (pm_autosleep_state() > PM_SUSPEND_ON) {
		error = -EBUSY;
		goto out;
	}

	state = decode_state(buf, n);
	if (state < PM_SUSPEND_MAX) {
		if (state == PM_SUSPEND_MEM)
			state = mem_sleep_current;

		error = pm_suspend(state);
	} else if (state == PM_SUSPEND_MAX) {
		error = hibernate();
	} else {
		error = -EINVAL;
	}

 out:
	pm_autosleep_unlock();
	return error ? error : n;
}
  • pm_autosleep_lock()：自动睡眠正在进行时，手写 state 返回 -EBUSY，两套机制不能同时驱动睡眠。
  • decode_state() 在 pm_states[] 里逐项比对字符串，不认识的值返回 PM_SUSPEND_ON，最终落到 -EINVAL。
  • state == PM_SUSPEND_MEM 时替换成 mem_sleep_current：写 mem 到底多深，取决于 /sys/power/mem_sleep 的选择。这是用户最常踩的“为什么写 mem 却是 s2idle”的原因。
  • 成功时返回写入长度 n，符合 sysfs 约定。

4.2 suspend 的最后一跳

真正“睡下去”只有一行 suspend_ops->enter()，前后是设备与中断的层层收拢。

kernel/power/suspend.c:389-440 suspend_enter（节选）

static int suspend_enter(suspend_state_t state, bool *wakeup)
{
	int error;

	error = platform_suspend_prepare(state);
	if (error)
		goto Platform_finish;

	error = dpm_suspend_late(PMSG_SUSPEND);
	if (error) {
		pr_err("late suspend of devices failed\n");
		goto Platform_finish;
	}
	// ... 省略 platform_suspend_prepare_late / dpm_suspend_noirq 及各回滚标签
	if (state == PM_SUSPEND_TO_IDLE) {
		s2idle_loop();
		goto Platform_wake;
	}

	error = suspend_disable_secondary_cpus();
	// ... 省略 suspend_test(TEST_CPUS) 分支

	arch_suspend_disable_irqs();
	BUG_ON(!irqs_disabled());

	system_state = SYSTEM_SUSPEND;

	error = syscore_suspend();
	if (!error) {
		*wakeup = pm_wakeup_pending();
		if (!(suspend_test(TEST_CORE) || *wakeup)) {
			trace_suspend_resume(TPS("machine_suspend"),
				state, true);
			error = suspend_ops->enter(state);
			trace_suspend_resume(TPS("machine_suspend"),
				state, false);
		}
	}
  • state == PM_SUSPEND_TO_IDLE 直接跳进 s2idle_loop()（同文件 120 行起）：不关从核、不进固件，只让 CPU 停在 idle 等唤醒——这就是“浅睡”的物理含义。
  • arch_suspend_disable_irqs() 之后才 syscore_suspend()，因为 syscore 要关的正是中断控制器本身。
  • pm_wakeup_pending() 是睡前最后一次检查：已有唤醒事件在排队就别睡了，直接返回，避免“刚睡下立刻醒”的抖动。
  • suspend_ops->enter() 是平台钩子，x86 上最终写 ACPI 睡眠寄存器；它返回即代表已经醒来。

4.3 cpuidle：选哪一层睡

先看状态结构：驱动只登记硬件事实，选哪个由调节器算。

include/linux/cpuidle.h:48-61 cpuidle_state

struct cpuidle_state {
	char		name[CPUIDLE_NAME_LEN];
	char		desc[CPUIDLE_DESC_LEN];

	u64		exit_latency_ns;
	u64		target_residency_ns;
	unsigned int	flags;
	unsigned int	exit_latency; /* in US */
	int		power_usage; /* in mW */
	unsigned int	target_residency; /* in US */

	int (*enter)	(struct cpuidle_device *dev,
			struct cpuidle_driver *drv,
			int index);

exit_latency_ns 是“出来要多久”，target_residency_ns 是“至少待多久才划算”，power_usage 供 powertop 之类工具估算功耗。menu 调节器的判断顺序最能体现取舍：

drivers/cpuidle/governors/menu.c:265-298 menu_select（节选）

static int menu_select(struct cpuidle_driver *drv, struct cpuidle_device *dev,
		       bool *stop_tick)
{
	struct menu_device *data = this_cpu_ptr(&menu_devices);
	s64 latency_req = cpuidle_governor_latency_req(dev->cpu);
	// ... 省略变量声明
	if (data->needs_update) {
		menu_update(drv, dev);
		data->needs_update = 0;
	}

	/* determine the expected residency time, round up */
	data->next_timer_ns = tick_nohz_get_sleep_length(&delta_next);

	nr_iowaiters = nr_iowait_cpu(dev->cpu);
	data->bucket = which_bucket(data->next_timer_ns, nr_iowaiters);

	if (unlikely(drv->state_count <= 1 || latency_req == 0) ||
	    ((data->next_timer_ns < drv->states[1].target_residency_ns ||
	      latency_req < drv->states[1].exit_latency_ns) &&
	     !dev->states_usage[0].disable)) {
		*stop_tick = !(drv->states[0].flags & CPUIDLE_FLAG_POLLING);
		return 0;
	}
  • tick_nohz_get_sleep_length() 返回“离最近一个定时器事件还有多久”，这就是本轮对空闲时长的预测；delta_next 带回精确值供后面校正。
  • latency_req 来自 PM QoS：cpuidle_governor_latency_req() 把设备请求与全局 cpu_latency_qos_limit() 取严，再换算成纳秒（drivers/cpuidle/governor.c:110-120）。音频驱动会把它压到几十微秒，强逼 CPU 别进深睡。
  • 那个 if 是“不值得深睡”的快速路径：状态不够、延迟约束为零、或预测时长连第二档的驻留时间与退出延迟都满足不了，直接返回状态 0。
  • 后面 337-420 行的循环按 target_residency_ns 从浅到深逐级试，选出“驻留时间不超过预测值的最深一档”，再按 exit_latency_ns 与 delta_next 回退校正。思路是压着预测值往上顶，但不越界。

teo 调节器的骨架相同（drivers/cpuidle/governors/teo.c:240 起），差别是它不做 interactivity 加成，而用“最近若干次空闲时长与本次预测的命中率”决定要不要退一档（teo.c:377-415）。两者靠 rating 竞争：menu 为 20、teo 为 19（drivers/cpuidle/governors/menu.c:558-564、teo.c:481-487），所以默认选中 menu；drivers/cpuidle/Kconfig:7-8 仅在开启 NO_HZ 且未启用 CPU_IDLE_GOV_TEO 时才自动选中 menu。

4.4 cpufreq：schedutil 跟着利用率走

调频的输入不是“负载百分比”，而是调度器算出的利用率，映射公式只有一行：

include/linux/sched/cpufreq.h:26-30 map_util_freq

static inline unsigned long map_util_freq(unsigned long util,
					unsigned long freq, unsigned long cap)
{
	return (freq + (freq >> 2)) * util / cap;
}

cap 是这颗 CPU 的最大算力，util 是当前需求，freq >> 2 预留 25% 余量，免得利用率估低了频率跟不上。本质就是按需求比例线性缩放。

kernel/sched/cpufreq_schedutil.c:159-172 get_next_freq

static unsigned int get_next_freq(struct sugov_policy *sg_policy,
				  unsigned long util, unsigned long max)
{
	struct cpufreq_policy *policy = sg_policy->policy;
	unsigned int freq = arch_scale_freq_invariant() ?
				policy->cpuinfo.max_freq : policy->cur;

	freq = map_util_freq(util, freq, max);

	if (freq == sg_policy->cached_raw_freq && !sg_policy->need_freq_update)
		return sg_policy->next_freq;

	sg_policy->cached_raw_freq = freq;
	return cpufreq_driver_resolve_freq(policy, freq);
}
  • arch_scale_freq_invariant() 为真时用 max_freq 做基准（硬件有频率无关计数器），否则退回 policy->cur，精度差一些。
  • cached_raw_freq 相同就直接返回上次结果，避免每次 tick 都惊动驱动——利用率每 tick 都在小幅变化，这层缓存是必需的。
  • cpufreq_driver_resolve_freq() 把连续频率对齐到驱动支持的档位（离散 P-state 或连续调节）。

调用者是谁？调度器每次更新利用率就回调 schedutil，单 CPU 策略如下：

kernel/sched/cpufreq_schedutil.c:439-469 sugov_update_single（节选）

static void sugov_update_single(struct update_util_data *hook, u64 time,
				unsigned int flags)
{
	struct sugov_cpu *sg_cpu = container_of(hook, struct sugov_cpu, update_util);
	struct sugov_policy *sg_policy = sg_cpu->sg_policy;
	unsigned long util, max;
	unsigned int next_f;
	unsigned int cached_freq = sg_policy->cached_raw_freq;

	sugov_iowait_boost(sg_cpu, time, flags);
	sg_cpu->last_update = time;

	ignore_dl_rate_limit(sg_cpu, sg_policy);

	if (!sugov_should_update_freq(sg_policy, time))
		return;

	util = sugov_get_util(sg_cpu);
	max = sg_cpu->max;
	util = sugov_iowait_apply(sg_cpu, time, util, max);
	next_f = get_next_freq(sg_policy, util, max);
	/*
	 * Do not reduce the frequency if the CPU has not been idle
	 * recently, as the reduction is likely to be premature then.
	 */
	if (sugov_cpu_is_busy(sg_cpu) && next_f < sg_policy->next_freq) {
		next_f = sg_policy->next_freq;

		/* Restore cached freq as next_freq has changed */
		sg_policy->cached_raw_freq = cached_freq;
	}
  • sugov_should_update_freq() 做速率限制（rate_limit_us），防止调频比硬件响应还快。
  • sugov_iowait_boost/apply：CPU 在等 IO 时利用率接近零，但马上就有活干，于是临时抬频率，显著降低唤醒后的延迟。
  • sugov_cpu_is_busy() 与后面的“只升不降”保护：最近没闲过就别降频，否则提前降频会立刻触发再升频，来回抖动。
  • sugov_get_util()（同文件 281 行）先取 CFS 利用率，再经 schedutil_cpu_util() 加上 RT/DL 的带宽需求，才是最终 util。

4.5 运行时 PM：带计数器的开关

驱动要用设备时先“取用”，用完“放回”。取用是同步的：计数加一并确保设备已上电。

include/linux/pm_runtime.h:373-387 pm_runtime_get_sync

/**
 * pm_runtime_get_sync - Bump up usage counter of a device and resume it.
 * @dev: Target device.
 *
 * Bump up the runtime PM usage counter of @dev and carry out runtime-resume of
 * it synchronously.
 *
 * The possible return values of this function are the same as for
 * pm_runtime_resume() and the runtime PM usage counter of @dev remains
 * incremented in all cases, even if it returns an error code.
 */
static inline int pm_runtime_get_sync(struct device *dev)
{
	return __pm_runtime_resume(dev, RPM_GET_PUT);
}

RPM_GET_PUT 是“同时操作 use_count”的标志（include/linux/pm_runtime.h:21 附近）。注释里那句“计数即使在出错时也已经增加”很关键：调用方无论成败都必须配一次 pm_runtime_put*()，否则计数永远不归零，设备再也不会自动休眠。

真正的恢复流程在 rpm_resume()，要点是先唤醒父设备：

drivers/base/power/runtime.c:805-857 rpm_resume（节选）

	if (!parent && dev->parent) {
		/*
		 * Increment the parent's usage counter and resume it if
		 * necessary.  Not needed if dev is irq-safe; then the
		 * parent is permanently resumed.
		 */
		parent = dev->parent;
		if (dev->power.irq_safe)
			goto skip_parent;
		spin_unlock(&dev->power.lock);

		pm_runtime_get_noresume(parent);

		spin_lock(&parent->power.lock);
		/*
		 * Resume the parent if it has runtime PM enabled and not been
		 * set to ignore its children.
		 */
		if (!parent->power.disable_depth
		    && !parent->power.ignore_children) {
			rpm_resume(parent, 0);
			if (parent->power.runtime_status != RPM_ACTIVE)
				retval = -EBUSY;
		}
		spin_unlock(&parent->power.lock);

		spin_lock(&dev->power.lock);
		if (retval)
			goto out;
		goto repeat;
	}
 skip_parent:

	if (dev->power.no_callbacks)
		goto no_callback;	/* Assume success. */

	__update_runtime_status(dev, RPM_RESUMING);

	callback = RPM_GET_CALLBACK(dev, runtime_resume);

	dev_pm_disable_wake_irq_check(dev);
	retval = rpm_callback(callback, dev);
  • 父设备先 pm_runtime_get_noresume()（只加计数、不同步恢复，避免递归死锁），再递归 rpm_resume()。级联顺序保证“子设备醒来时总线/控制器已就绪”。
  • goto repeat：唤醒父设备期间自己的状态可能变了，重新判断一遍。
  • dev->power.no_callbacks 表示该设备没有实现 runtime_resume 回调，直接假定成功。
  • __update_runtime_status(dev, RPM_RESUMING) 先置为“恢复中”，失败则回退为 RPM_SUSPENDED；成功才置 RPM_ACTIVE。中间态对外可见（/sys/devices/…/power/runtime_status），并让并发请求在 wait_queue 上排队（702-774 行）。
  • 反过来，pm_runtime_put_autosuspend() 递减计数；归零后 rpm_idle()（同文件 396 行）检查条件并发起 runtime_suspend 回调；有 autosuspend 延迟时用定时器等一会儿，避免频繁开关。
最底层还有两个常被忽略的子系统：clk（clk_prepare_enable() 打开时钟，关掉后寄存器都读写不了）和 regulator（调供电电压）。运行时 PM 的回调里经常只是“关时钟 + 关稳压器”，这两步才是真省电；PM 框架负责的只是“什么时候该做”。

4.6 休眠：hibernate 与 suspend 的分叉

kernel/power/hibernate.c:707-744 hibernate（节选）

int hibernate(void)
{
	bool snapshot_test = false;
	int error;

	if (!hibernation_available()) {
		pm_pr_dbg("Hibernation not available.\n");
		return -EPERM;
	}

	lock_system_sleep();
	/* The snapshot device should not be opened while we're running */
	if (!hibernate_acquire()) {
		error = -EBUSY;
		goto Unlock;
	}

	pr_info("hibernation entry\n");
	pm_prepare_console();
	error = pm_notifier_call_chain_robust(PM_HIBERNATION_PREPARE, PM_POST_HIBERNATION);
	if (error)
		goto Restore;

	ksys_sync_helper();

	error = freeze_processes();
	if (error)
		goto Exit;

	lock_device_hotplug();
	/* Allocate memory management structures */
	error = create_basic_memory_bitmaps();
	if (error)
		goto Thaw;

	error = hibernation_snapshot(hibernation_mode == HIBERNATION_PLATFORM);
  • ksys_sync_helper() 先把文件系统刷盘，镜像要写到干净的 swap 上。
  • freeze_processes() 把用户进程全部冻住——它们的堆栈不再变化，镜像才是一致的。
  • create_basic_memory_bitmaps() 标记哪些页必须保存、哪些是可丢弃的缓存，减小镜像体积。
  • hibernation_snapshot() 把镜像写入 swap 后，系统会用一次特殊的“关机”睡过去；下次开机 software_resume()（同文件 909 行）读回镜像并跳回原处。

6. 自测

Q1. “写 mem 结果只进了 s2idle”是怎么回事？state_store 对 PM_SUSPEND_MEM 做了替换：state = mem_sleep_current。所以 /sys/power/mem_sleep 选的是 s2idle 时，mem 就等价于浅睡。把它改成 deep 才真正走固件 S3。
Q2. cpuidle 的 target_residency 与 exit_latency 有什么区别？各自决定什么？exit_latency 是“退出要多久”，用来和延迟约束（PM QoS、latency_req）比较，决定“能不能睡这么深”；target_residency 是“待多久才划算”，用来和预测空闲时长比较，决定“睡了划不划算”。
Q3. 为什么 schedutil 要在 io-wait 时抬高频率？因为等 IO 的任务利用率显示接近零，但 IO 完成后会立刻占满 CPU。不提前提速，就会出现“醒来后先低频跑一段”的延迟尖峰；sugov_iowait_boost() 用临时 boost 补上这一段。
Q4. pm_runtime_get_sync() 失败了还要不要 pm_runtime_put()？要。原注释写明“counting remains incremented in all cases, even if it returns an error code”。漏掉 put 会导致计数永不归零，设备无法再自动挂起，属于常见驱动 bug。
Q5. 有设备还在 active 的 wakeup source 时，系统会进入深睡吗？不会。wakeup source 的语义就是“我正在处理可能唤醒系统的事件”，PM 核心据此判定不应进入深睡；它同时也是 powertop 统计“谁在阻止睡眠”的依据。pm_stay_awake/pm_relax 成对使用。
