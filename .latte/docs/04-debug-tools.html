🔧 04 · 内核调试与观测工具：给内核装上仪表盘

从"打一行日志"到"单步停在某个函数上"，一整套工具串起内核排障的完整武器库 · 预计阅读 28 分钟

1. 它在解决什么问题

内核是个"看不见摸不着"的东西：它跑在你看不见的地址空间里，出问题时屏幕上只有一个黑屏或一行 oops。修车师傅有举升机、有诊断仪、有示波器；内核工程师也需要仪表盘。这就是本章要讲的东西：printk 是仪表盘上的报警灯，/proc/kallsyms 是全车线路图，ftrace 是行车记录仪，perf 是性能分析仪，而 gdb 让你能把车拆开来逐个螺丝看。

从操作系统视角看，调试的核心矛盾是：bug 发生在内核态，而你的观察工具在用户态。内核必须主动"开窗"，把这些内部状态以文件（/proc、/sys、debugfs、tracefs）的形式暴露出来，用户态工具再去读这些"窗口"。本章讲的每一个工具，本质上都是一对"内核里的文件" + "用户态的读法"。

新手最常见的三个困惑，本章会逐一拆掉：

  • "为什么我改了代码，dmesg 里什么都没变？"——因为你没重新编译，或者你用的是运行时的日志级别过滤（/proc/sys/kernel/printk 把级别卡住了）。
  • "为什么 /proc/kallsyms 里的地址全是 0？"——因为 kptr_restrict 出于安全考虑把地址藏起来了，只有 root 能看。
  • "ftrace 和 perf 到底选哪个？"——ftrace 是"内核自己记录调用轨迹"，perf 是"用 PMU 硬件计数器采样"，两者可以叠加使用。

本章所有命令都可以在普通 Linux 机器上直接跑（需要 root 的会标出来）。需要编译内核的部分（gdb + qemu），会给出一套最小可用的步骤。

3.2 四种观测粒度：从粗到细

粒度工具回答什么问题开销
日志（事后）printk / dmesg"出事了/发生了某事"——只有你主动打印过才知道极低
统计（周期）/proc/stat、/proc/interrupts、/proc/slabinfo、perf stat"整体健康度如何"——CPU 用了多少、IRQ 打了几次低
轨迹（实时）ftrace（function/function_graph）、perf record"谁调用了谁、耗时多少、调用栈长什么样"中～高（需过滤）
断点（交互）gdb + qemu、kprobe、kgdb"此刻内核的变量到底是什么值"极高（会把机器拖停）

排障的正确顺序是从粗到细：先用统计确定"问题在 CPU 还是在 IO"，再用轨迹缩小到"哪个函数"，最后才上断点看变量。一上来就 gdb 单步是最慢的做法（每一步都可能几毫秒，而内核一次系统调用涉及的指令数以万计）。

3.3 ftrace 四件套：它们是怎么配合的

        /sys/kernel/debug/tracing/
        │
        ├── available_tracers        【只读】列出本内核支持的 tracer
        │       nop  function  function_graph  wakeup  ...
        │
        ├── current_tracer           【可写】当前用哪个 tracer
        │       echo function_graph > current_tracer
        │
        ├── set_ftrace_filter         【可写】只跟踪哪些函数
        │       echo do_sys_open > set_ftrace_filter
        │       echo 'do_sys_*' > set_ftrace_filter      (支持通配)
        │       echo '!do_sys_read' > set_ftrace_filter   (排除)
        │
        ├── available_filter_functions 【只读】列出所有可被过滤的函数
        │       grep do_sys_open available_filter_functions
        │
        ├── tracing_on                【可写】0/1 开关采集
        ├── trace                     【只读】采集到的内容（快照）
        └── trace_pipe                 【只读】流式输出（cat 会阻塞）

四件套的协作关系：

  1. 先 cat available_tracers 看看有哪些"镜头"可选（你要的是拍什么）。
  2. 把选中的名字写进 current_tracer（换镜头）。
  3. 用 set_ftrace_filter 限定拍摄范围（缩小视野）——不加过滤的话，内核每秒几万次函数调用会把缓冲区瞬间写满。
  4. echo 1 > tracing_on 开始录制，事后 cat trace 看快照，或 cat trace_pipe 实时跟着看。

available_filter_functions 是"字典"：它告诉你内核里到底有哪些函数名可以填进 filter。因为你得知道确切的符号名（还要注意 [module] 后缀表示该函数来自哪个模块）。

4. 源码走读

4.1 printk 的日志级别：为什么内核消息会"消失"

每条 printk() 消息前面都带一个"级别前缀"。老式写法是 printk(KERN_ERR "...")，现代写法是 pr_err("...")。这两者编译出来是同一个东西。

include/linux/kern_levels.h:5-17 级别宏定义

#define KERN_SOH	"\001"		/* ASCII Start Of Header */
#define KERN_SOH_ASCII	'\001'

#define KERN_EMERG	KERN_SOH "0"	/* system is unusable */
#define KERN_ALERT	KERN_SOH "1"	/* action must be taken immediately */
#define KERN_CRIT	KERN_SOH "2"	/* critical conditions */
#define KERN_ERR	KERN_SOH "3"	/* error conditions */
#define KERN_WARNING	KERN_SOH "4"	/* warning conditions */
#define KERN_NOTICE	KERN_SOH "5"	/* normal but significant condition */
#define KERN_INFO	KERN_SOH "6"	/* informational */
#define KERN_DEBUG	KERN_SOH "7"	/* debug-level messages */

#define KERN_DEFAULT	""		/* the default kernel loglevel

注意 KERN_SOH 是 ASCII 码 1（\001），后面跟一个数字字符。这是一个"带前缀的字符串"：KERN_ERR 展开成 "\0013"。内核靠这个约定在运行时反解出这条消息的级别——这样就不需要在消息结构体里额外存一个字段，代价是每条消息前面多两个字节。

include/linux/printk.h:19-45 printk_get_level（反解级别）

static inline int printk_get_level(const char *buffer)
{
	if (buffer[0] == KERN_SOH_ASCII && buffer[1]) {
		switch (buffer[1]) {
		case '0' ... '7':
		case 'c':	/* KERN_CONT */
			return buffer[1];
		}
	}
	return 0;
}

static inline const char *printk_skip_level(const char *buffer)
{
	if (printk_get_level(buffer))
		return buffer + 2;

	return buffer;
}

static inline const char *printk_skip_headers(const char *buffer)
{
	while (printk_get_level(buffer))
		buffer = printk_skip_level(buffer);

	return buffer;
}
  • printk_get_level()：看到 \001 + 数字就返回那个数字，否则返回 0（表示"没有级别前缀"）。
  • 注意 case 'c'：KERN_CONT（\001c）表示"这是一条续行"，不算独立日志级别。
  • printk_skip_headers()：连续跳过多层前缀——因为 printk() 可以把多条消息拼成一次调用。

include/linux/kern_levels.h:25-36 级别的整数值

/* integer equivalents of KERN_<LEVEL> */
#define LOGLEVEL_SCHED		-2	/* Deferred messages from sched code
					 * are set to this special level */
#define LOGLEVEL_DEFAULT	-1	/* default (or last) loglevel */
#define LOGLEVEL_EMERG		0	/* system is unusable */
#define LOGLEVEL_ALERT		1	/* action must be taken immediately */
#define LOGLEVEL_CRIT		2	/* critical conditions */
#define LOGLEVEL_ERR		3	/* error conditions */
#define LOGLEVEL_WARNING	4	/* warning conditions */
#define LOGLEVEL_NOTICE		5	/* normal but significant condition */
#define LOGLEVEL_INFO		6	/* informational */
#define LOGLEVEL_DEBUG		7	/* debug-level messages */

这套整数定义（LOGLEVEL_ERR 等）是给 C 代码用的，因为 pr_err() 这类宏需要在编译期就知道级别数字。

4.2 /proc/sys/kernel/printk：四个数字控制日志输出

你可能见过这个输出：4 4 1 7。这四个数字的含义经常被搞错，搞错了就会"日志怎么不打印"。

kernel/printk/printk.c:63-69 console_printk 数组

int console_printk[4] = {
	CONSOLE_LOGLEVEL_DEFAULT,	/* console_loglevel */
	MESSAGE_LOGLEVEL_DEFAULT,	/* default_message_loglevel */
	CONSOLE_LOGLEVEL_MIN,		/* minimum_console_loglevel */
	CONSOLE_LOGLEVEL_DEFAULT,	/* default_console_loglevel */
};
EXPORT_SYMBOL_GPL(console_printk);

四个槽位的含义：

位置名字含义
1console_loglevel当前控制台阈值：级别数字 > 它的消息不输出到控制台（但仍进环形缓冲区）。
2default_message_loglevel没写级别前缀的消息（printk("...")）默认按这个级别处理。
3minimum_console_loglevel下限：控制台阈值不能被设得比它更小（防止把关键错误也屏蔽掉）。
4default_console_loglevel开机时的默认控制台阈值。

kernel/sysctl.c:2206-2213 /proc/sys/kernel/printk 的注册

#if defined CONFIG_PRINTK
	{
		.procname	= "printk",
		.data		= &console_loglevel,
		.maxlen		= 4*sizeof(int),
		.mode		= 0644,
		.proc_handler	= proc_dointvec,
	},

.data = &console_loglevel 指向整个数组的第一个元素，.maxlen = 4*sizeof(int) 说明这是一个长度为 4 的整型数组，proc_dointvec 负责读写。所以 echo 4 4 1 7 > /proc/sys/kernel/printk 一次写 4 个数；只写一个数（如 echo 8）会只改第 1 个，其余保持不变。

注意：控制台阈值只影响"输出到屏幕/串口"，不影响环形缓冲区！你可以把控制台阈值调到 8（只显示 DEBUG），但 dmesg 依然能读出全部消息（受环形缓冲区和 dmesg 自身级别过滤影响）。这解释了那个经典现象：屏幕上啥也没有，但 dmesg | tail 全是日志。

4.3 /proc/kallsyms：内核符号表

要 gdb/perf 把地址翻译成函数名，靠的就是 kallsyms。

kernel/kallsyms.c:681-696 kallsyms_show_value（地址是否可见）

bool kallsyms_show_value(const struct cred *cred)
{
	switch (kptr_restrict) {
	case 0:
		if (kallsyms_for_perf())
			return true;
		fallthrough;
	case 1:
		if (security_capable(cred, &init_user_ns, CAP_SYSLOG,
				     CAP_OPT_NOAUDIT) == 0)
			return true;
		fallthrough;
	default:
		return false;
	}
}

kptr_restrict 的语义：

值谁能看到真实地址
0所有人
1有 CAP_SYSLOG 能力的用户（通常 root）
2没有人（连 root 也只看到 0）

fallthrough 是 C 的显式"贯穿"标注——告诉编译器"这里故意不 break，继续往下走"。所以 kptr_restrict=0 时，即使不是 root，只要 perf 被允许（kallsyms_for_perf()）也能看到地址。

kernel/kallsyms.c:739-751 /proc/kallsyms 的创建

static const struct proc_ops kallsyms_proc_ops = {
	.proc_open	= kallsyms_open,
	.proc_read	= seq_read,
	.proc_lseek	= seq_lseek,
	.proc_release	= seq_release_private,
};

static int __init kallsyms_init(void)
{
	proc_create("kallsyms", 0444, NULL, &kallsyms_proc_ops);
	return 0;
}
device_initcall(kallsyms_init);
  • proc_create("kallsyms", 0444, ...)：创建只读文件。注意 0444 权限——它是只读的，你不能通过写它来改符号表。
  • device_initcall(kallsyms_init)：用第 6 梯队 initcall 注册（见上一篇 03 的 3.3 节）。也就是说，/proc/kallsyms 在启动的"设备初始化"阶段就出现了，早于用户态 init。
  • 实现用 seq_file 接口（seq_read），这是内核里输出"可能很大"的文本文件的通用套路——分页生成，不会一次性把内容塞进内存。

4.4 debugfs：内核自报的内部状态

debugfs 是专门给调试用的伪文件系统。它的内容没有稳定性保证——内核升级后文件名可能就变了（所以它不能被用户态程序依赖）。

fs/debugfs/inode.c:447-457 debugfs_create_file

struct dentry *debugfs_create_file(const char *name, umode_t mode,
				   struct dentry *parent, void *data,
				   const struct file_operations *fops)
{

	return __debugfs_create_file(name, mode, parent, data,
				fops ? &debugfs_full_proxy_file_operations :
					&debugfs_noop_file_operations,
				fops);
}
EXPORT_SYMBOL_GPL(debugfs_create_file);

参数含义：

  • name：文件名。
  • mode：权限位（如 0644）。
  • parent：父目录 dentry，NULL 表示根目录。
  • data：内核私有数据指针。打开文件时它会出现在 file->private_data 里——这是 debugfs 的核心机制：你把一个结构体指针扔进去，读写回调函数就能拿回它。
  • fops：struct file_operations，定义 read/write 的行为。

如果 fops 为 NULL，内核会用 debugfs_noop_file_operations——文件能创建、能列出，但读写什么都不干。这就是为什么有些 debugfs 条目看着"空"：那个驱动只创建了占位文件，还没实现真正的输出。

debugfs 的三个常见 API：debugfs_create_dir() 建目录、debugfs_create_file() 建自定义文件、debugfs_create_u32() 建一个"读写的 32 位整数"快捷方式（实现在 fs/debugfs/file.c:510）。很多驱动还喜欢用 seq_file 自己分页输出。

4.5 tracefs 与 ftrace 四件套的文件是怎么造出来的

这些"文件"不是真的磁盘文件，而是内核在启动时用 trace_create_file() 动态创建的虚拟文件。写进去的内容会触发对应的回调函数。

kernel/trace/trace.c:8923-8948 init_tracer_tracefs（创建 tracer 控制文件）

static void
init_tracer_tracefs(struct trace_array *tr, struct dentry *d_tracer)
{
	struct trace_event_file *file;
	int cpu;

	trace_create_file("available_tracers", 0444, d_tracer,
			tr, &show_traces_fops);

	trace_create_file("current_tracer", 0644, d_tracer,
			tr, &set_tracer_fops);

	trace_create_file("tracing_cpumask", 0644, d_tracer,
			  tr, &tracing_cpumask_fops);

	trace_create_file("trace_options", 0644, d_tracer,
			  tr, &tracing_iter_fops);

	trace_create_file("trace", 0644, d_tracer,
			  tr, &tracing_fops);

	trace_create_file("trace_pipe", 0444, d_tracer,
			  tr, &tracing_pipe_fops);

	trace_create_file("buffer_size_kb", 0644, d_tracer,
			  tr, &tracing_entries_fops);
	// ... 省略后续若干 trace_create_file() 调用
}
  • available_tracers 用 0444（只读）——它是"菜单"，让你看有哪些选择。
  • current_tracer 用 0644（可写）——echo function_graph > current_tracer 就是"切换镜头"。
  • trace 是 0644：它竟然可写！但注意机制：真正起作用的是打开方式——用 > trace（或 : > trace）以截断方式打开它时，tracing_open()（kernel/trace/trace.c:4519）会先清空整个缓冲区；而往里写具体文字是无效的（写回调 tracing_write_stub() 什么也不做）。
  • trace_pipe 是 0444（只读），且是"流式"的：cat trace_pipe 会一直阻塞着不断输出新内容。

kernel/trace/ftrace.c:6073-6112 ftrace 的过滤器文件

void ftrace_create_filter_files(struct ftrace_ops *ops,
				struct dentry *parent)
{

	trace_create_file("set_ftrace_filter", 0644, parent,
			  ops, &ftrace_filter_fops);

	trace_create_file("set_ftrace_notrace", 0644, parent,
			  ops, &ftrace_notrace_fops);
}

// ... 省略 destroy_filter_files() 的说明性注释

static __init int ftrace_init_dyn_tracefs(struct dentry *d_tracer)
{

	trace_create_file("available_filter_functions", 0444,
			d_tracer, NULL, &ftrace_avail_fops);

	trace_create_file("enabled_functions", 0444,
			d_tracer, NULL, &ftrace_enabled_fops);

	ftrace_create_filter_files(&global_ops, d_tracer);

#ifdef CONFIG_FUNCTION_GRAPH_TRACER
	trace_create_file("set_graph_function", 0644, d_tracer,
				    NULL,
				    &ftrace_graph_fops);
	// ... 省略 set_graph_notrace / max_graph_depth 等文件
#endif

set_ftrace_filter 的 ops 参数是 &global_ops——全局 ftrace_ops，也就是"所有可被 ftrace 插桩的函数"。这解释了为什么 set_ftrace_filter 能过滤任意函数，而 set_graph_function（NULL）只对 function_graph tracer 生效。

kernel/trace/trace_functions_graph.c:1281-1297 function_graph tracer 的定义

4.6 kprobe：不改代码就能在任意函数上打点

kernel/trace/trace_kprobe.c:1928-1937 kprobe_events 文件

kprobe_events 是可写的：往里写一行文本就创建一个探针事件，比如：

# 语法：p[:[GRP/]EVENT] [MOD:]SYM[+offs]|MEMADDR [FETCHARGS]   (p=probe)
#       r[:[GRP/]EVENT] [MOD:]SYM[+offs]|MEMADDR [FETCHARGS]   (r=retprobe)
echo 'p:myprobe do_sys_open'   > /sys/kernel/debug/tracing/kprobe_events
echo 'r:myret  do_sys_open'    > /sys/kernel/debug/tracing/kprobe_events
echo 1 > /sys/kernel/debug/tracing/events/myprobe/enable
cat /sys/kernel/debug/tracing/trace

p: 是"进入函数时触发"，r: 是"函数返回时触发"。kprobe 的实现原理是把目标函数的第一条指令临时改成 int3（断点指令），命中后由调试异常处理程序执行回调，再把原指令恢复。这就是"不用重新编译就能加探针"的原因。

4.7 /proc/interrupts、/proc/stat、/proc/slabinfo

fs/proc/interrupts.c:12-40 /proc/interrupts 的实现

static void *int_seq_start(struct seq_file *f, loff_t *pos)
{
	return (*pos <= nr_irqs) ? pos : NULL;
}

static void *int_seq_next(struct seq_file *f, void *v, loff_t *pos)
{
	(*pos)++;
	if (*pos > nr_irqs)
		return NULL;
	return pos;
}

static void *int_seq_stop(struct seq_file *f, void *v)
{
	/* Nothing to do */
}

static const struct seq_operations int_seq_ops = {
	.start = int_seq_start,
	.next  = int_seq_next,
	.stop  = int_seq_stop,
	.show  = show_interrupts
};

static int __init proc_interrupts_init(void)
{
	proc_create_seq("interrupts", 0, NULL, &int_seq_ops);
	return 0;
}
fs_initcall(proc_interrupts_init);

它遍历 nr_irqs 个中断号，对每个号调用 show_interrupts() 输出各 CPU 的计数。注意 fs_initcall——它在 initcall 第 5 梯队（文件系统级）注册，比 kallsyms 的第 6 梯队早。

5.7 qemu + gdb：最小内核调试流程

这是唯一能"停住内核看变量"的手段。原理：QEMU 内置一个 gdb 服务器，gdb 通过串口协议连上去。

# ── 准备：编译一份带调试符号的内核 ──
cd /Users/zhouguodong/Documents/latte/linux_diff
make defconfig                       # 生成 .config
# 打开调试符号（内核默认 CONFIG_DEBUG_INFO=y，但检查一下）
grep -E "CONFIG_DEBUG_INFO=|CONFIG_GDB_SCRIPTS=" .config
# 期望：CONFIG_DEBUG_INFO=y
# 关掉 KASLR，否则地址每次都变，断点位置对不上
#   在 .config 里追加： CONFIG_RANDOMIZE_BASE=n
# 也可开机参数 nokaslr（但 -kernel 方式加载时更保险的是编进配置）

make -j$(sysctl -n hw.ncpu)          # 编译，产物：
ls -lh arch/x86/boot/bzImage vmlinux
# vmlinux 是带符号的 ELF，gdb 要用它

# ── 造一个最小 initramfs ──
mkdir -p /tmp/rootfs/bin /tmp/rootfs/proc /tmp/rootfs/sys
busybox --install -s /tmp/rootfs/bin
cat > /tmp/rootfs/init <<'EOF'
#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
exec /bin/sh
EOF
chmod +x /tmp/rootfs/init
cd /tmp/rootfs && find . | cpio -o -H newc 2>/dev/null | gzip > /tmp/initramfs.cpio.gz
cd -

# ── 启动 qemu，-s 开 gdb stub，-S 让 CPU 停在第一条指令 ──
qemu-system-x86_64 -m 512M \
  -kernel arch/x86/boot/bzImage \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init nokaslr" \
  -s -S -nographic
#   -s : 在 :1234 开 gdb 服务器
#   -S : 启动时冻结 CPU（等 gdb 说"go"才继续）
#   -nographic : 串口输出到当前终端

# ── 另开一个终端，gdb 连上去 ──
gdb ./vmlinux
# (gdb) target remote :1234
# (gdb) break start_kernel
# (gdb) continue
# → 命中！打印出 init/main.c:949 附近的源码和寄存器

# 常用命令：
# (gdb) bt              打印调用栈
# (gdb) info registers   打印所有寄存器
# (gdb) print command_line   打印变量（需要知道类型名）
# (gdb) p/x $rip         打印指令指针
# (gdb) x/10i $rip       反汇编当前指令
# (gdb) step / next / continue
# (gdb) finish           跑完当前函数
# (gdb) info threads     查看所有线程
# (gdb) thread 1 / bt   看某个线程的栈

# 内核自带的 gdb python 脚本（需要 CONFIG_GDB_SCRIPTS=y）
# (gdb) lx-symbols       加载 vmlinux 和所有模块符号
# (gdb) lx-dmesg         打印目标机的 dmesg
# (gdb) p $lx_current().pid   打印当前任务的 pid
# (gdb) p $lx_current().comm  打印当前任务名

# 退出 gdb 后，qemu 里按 Ctrl-A X 结束

为什么必须 -S？因为启动只有零点几秒，等你 gdb 连上去内核早就跑完了。-S 让 CPU 停在第一条指令，等你设好断点再 continue。nokaslr 则保证符号地址稳定，否则 break start_kernel 每次都会失败。

完整教程在源码树里：Documentation/dev-tools/gdb-kernel-debugging.rst（本仓库自带）。

6. 自测

Q1. cat /proc/sys/kernel/printk 输出 4 4 1 7，四个数分别是什么？我把它第一项改成 8，为什么 dmesg 里还是能看到 KERN_ERR 的消息？① console_loglevel=4：当前控制台阈值，级别 > 4（即 NOTICE/INFO/DEBUG）的消息不输出到屏幕；② default_message_loglevel=4：没写级别前缀的消息按 WARNING 处理；③ minimum_console_loglevel=1：控制台阈值不能被设到比 1 更低（防止屏蔽掉 ALERT）；④ default_console_loglevel=7：开机时的默认控制台级别。
改它不改变 dmesg 的内容，因为这四项只管控制台输出（屏幕/串口），不管环形缓冲区。dmesg 读的是环形缓冲区，那里按消息自身的级别全部保留（只受缓冲区容量和 dmesg 自己的 -l 过滤影响）。反过来，如果你改了内核代码但 dmesg 里没有新消息，那才是代码根本没执行到。
Q2. /proc/kallsyms 里地址全是 0，怎么修？看 /proc/sys/kernel/kptr_restrict：0=所有人可见、1=需要 CAP_SYSLOG（一般 root 即可）、2=谁都不显示。执行 sudo sysctl -w kernel.kptr_restrict=0 临时放开。代码层面由 kallsyms_show_value()（kernel/kallsyms.c:681）根据 kptr_restrict 和调用者的 capability 决定是否显示真实地址。
Q3. ftrace 的 current_tracer、set_ftrace_filter、available_filter_functions 三者分别管什么？current_tracer 决定"用什么方式记录"（function 只记调用、function_graph 记调用+嵌套+耗时、wakeup 记调度唤醒），对应 kernel/trace/trace.c 里 init_tracer_tracefs() 创建的可写文件；set_ftrace_filter 决定"记录哪些函数"，支持精确名、通配符（do_sys_*）和排除（!func）；available_filter_functions 则是"字典"——只读，列出内核里所有可填进 filter 的函数名（模块函数还带 [模块名] 后缀）。不设过滤就开录，缓冲区会瞬间被刷爆。
Q4. function_graph 的输出怎么读？每一行的格式是 CPU号) 耗时 函数名，缩进表示调用深度（越靠右越深），{ 是进入、} /* 函数名 */ 是返回，中间那列是被调用者。所以想找"哪里慢"，就看哪一行的耗时数字大——比如 do_dentry_open 那行明显比别的长，说明路径解析是瓶颈。
Q5. perf 和 ftrace 什么时候用哪个？问"CPU 时间花在哪了"（要覆盖大量函数、要低开销）用 perf top/perf record；问"这次调用的调用链长什么样、哪一层慢"用 ftrace 的 function_graph（需要精确的嵌套关系时 perf 的采样可能漏掉）。两者可以同时开：ftrace 给你结构，perf 给你全局热点。
