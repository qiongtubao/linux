📐 VMA 与进程地址空间布局：内核怎么记住"这块内存归谁"

用一棵红黑树把进程的虚拟地址切成带属性的区间，让"这段内存可读可写""这段是文件""这段会自己长"这些规则有地方可查 · 预计阅读 42 分钟

1. 它在解决什么问题

上一讲我们看到，CPU 只知道"虚拟地址 → 物理页"这条翻译链。但内核面对的问题远不止翻译：这段地址能不能写？背后是文件还是匿名内存？两个进程映射了同一个文件时，写入要怎么同步？这段内存该不该被换出？这些问题没法塞进页表项里（页表项只有 64 位，而且要留给硬件快速查询）。

于是内核换了个思路：页表只回答"在哪儿"，另建一套数据结构回答"是什么"。这套结构叫 VMA（Virtual Memory Area，虚拟内存区域）。类比一下：一栋写字楼里有不同的房间——总经理办公室有门禁，档案室归财务管，机房有空调且 24 小时不断电。房间号就是虚拟地址，而"这间房归谁管、能不能进、有什么特殊设备"就是 VMA 记录的内容。进程的一整个虚拟地址空间，就是被切分成若干个 VMA 的；没有对应 VMA 的地址就是"无效地址"，访问它会收到 SIGSEGV。

那 VMA 怎么组织？关键需求是：内核要能快速回答"地址 X 落在哪个 VMA 里"（缺页处理第 4 节的 find_vma()），还要能回答"给我一段长 L 的连续空闲地址"（mmap() 的 get_unmapped_area()）。这两个需求都是"在有序集合里做区间查询"，用红黑树正好合适：O(log n) 的查找，天然保持有序还能做区间剪枝。

这里要特别提醒一个版本细节：Linux 5.10 用的是红黑树（mm->mm_rb），不是 6.1 之后才引入的 maple tree。网上很多讲 VMA 的文章会说 mm_mt，那是新内核的做法；在 5.10 里你只会看到 mm_rb 和一条辅助的 vm_next/vm_prev 单链表。

本篇按"VMA 长什么样 → 怎么被创建（mmap）→ 怎么被拆开（munmap/mprotect）→ 怎么长大（栈扩展）→ VMA 上的回调钩子（vm_ops）"这条线展开，最后用两个动手实验：两进程共享同一块 mmap 缓冲区、以及观察栈增长与 RLIMIT_STACK 的作用。

3. 整体结构

3.1 进程地址空间的典型布局

在 x86-64 上，一个进程的虚拟地址空间大致是这样（地址从低到高）：

 0x0000000000000000
      |
      |  保留区（内核强制不可映射，mmap_min_addr 通常是 64 KB）
      |  防止 NULL 指针和低地址 exploit
      v
 0x0000000000010000
      |
      |  +------------------------------------------+
      |  |  程序代码段 .text   (r-xp)               |  可执行，不写
      |  +------------------------------------------+
      |  |  只读数据段 .rodata (r--p)               |
      |  +------------------------------------------+
      |  |  数据段 .data / .bss  (rw-p)            |  可读写
      |  +------------------------------------------+
      |  |  [heap]  堆（brk 分配区，向上长）         |  malloc 大块内存
      |  +------------------------------------------+
      |        <---- 未映射的空洞（mmap 可以在此挑地址） ---->
      |  +------------------------------------------+
      |  |  mmap 区：动态库、共享内存、文件映射      |  向下长
      |  |  /lib/x86_64-linux-gnu/libc.so.6 (r-xp)  |  (top-down)
      |  +------------------------------------------+
      |            <---- 巨大的空洞 ---->
      |  +------------------------------------------+
      |  |  [stack] 主线程栈 (rw-p)                |  向下长
      |  +------------------------------------------+
      |  |  [vvar] / [vdso] / [vvar_vclock]        |  内核给进程的
      |  +------------------------------------------+
 0x7ffffffffffff000  <-- TASK_SIZE (128 TB - 4KB)
      |
      |  以上是内核空间，用户态碰不到
      v
 0xffffffffffffffff

三个要点：① 堆（heap）在数据段之后，由 brk() 管理；② mmap 区在堆和栈之间，默认策略是"从上往下"分配（arch_get_unmapped_area_topdown），所以新 mmap 的地址通常比堆高、比栈低；③ 栈在最高处，向下生长，碰到极限就触发 expand_stack()。

你可以在自己的机器上用 cat /proc/self/maps 验证这个布局（见第 5 节）。

3.2 VMA 的数据结构

include/linux/mm_types.h:305-334 struct vm_area_struct（节选）

struct vm_area_struct {
	/* The first cache line has the info for VMA tree walking. */

	unsigned long vm_start;		/* Our start address within vm_mm. */
	unsigned long vm_end;		/* The first byte after our end address
					   within vm_mm. */

	/* linked list of VM areas per task, sorted by address */
	struct vm_area_struct *vm_next, *vm_prev;

	struct rb_node vm_rb;

	/*
	 * Largest free memory gap in bytes to the left of this VMA.
	 * Either between this VMA and vma->vm_prev, or between one of the
	 * VMAs below us in the VMA rbtree and its ->vm_prev. This helps
	 * get_unmapped_area find a free area of the right size.
	 */
	unsigned long rb_subtree_gap;

	/* Second cache line starts here. */

	struct mm_struct *vm_mm;	/* The address space we belong to. */

	pgprot_t vm_page_prot;
	unsigned long vm_flags;		/* Flags, see mm.h. */

几个字段值得单独说：

  • vm_start / vm_end：区间是左闭右开的，即 [vm_start, vm_end)。所以 vm_end 一定落在页边界上。
  • vm_next / vm_prev：按地址排序的双向链表，遍历全量时用。
  • vm_rb：红黑树节点。注释里特意写了"The first cache line has the info for VMA tree walking"——树遍历时访问的字段被刻意排在第一个缓存行里，为的就是减少 cache miss。
  • rb_subtree_gap：这棵树上的加速字段，记录"以该节点为根的子树里，最大的连续空洞有多长"。get_unmapped_area() 靠它剪枝：如果整棵子树的最大空洞都装不下你要的长度，就不用进去了。这让区间查找在"大段空洞"场景下也保持 O(log n)。
  • vm_page_prot：由 vm_flags 推导出的硬件页保护位（可读/可写/可执行/用户态）。

3.4 三种"改地址空间"的系统调用

系统调用干什么内核动作
mmap()新增一段映射找空洞 → 建 VMA → 挂进红黑树
munmap()删除一段映射切分 VMA（必要时）→ 摘出红黑树 → 清页表 + 刷 TLB → 释放 VMA
mprotect()改一段映射的权限切分/合并 VMA → 改 vm_flags/vm_page_prot → 重写对应页表项
brk()扩/缩堆调整 mm->brk，必要时新建/切分堆 VMA

它们都要拿 mmap_lock 的写锁，因为它们会修改地址空间的拓扑结构。而缺页处理拿的是读锁——缺页只"读"VMA 的属性，不改拓扑结构。这就是为什么 mmap 一个大文件不会阻塞其他进程的缺页处理（只要不切分 VMA）。

3.5 VMA 上的回调钩子：vm_ops

前面说过，页表项回答"在哪儿"，VMA 回答"是什么"。但缺页发生时，内核还需要知道"这个 VMA 背后的数据从哪来"——这就是 vm_ops（struct vm_operations_struct）的作用。它是一张函数指针表，挂在 vma->vm_ops 上，由"拥有这份数据的子系统"填写：

  缺页发生
      |
      v
  handle_pte_fault()
      |
      |  文件 VMA -> do_fault()  --> vma->vm_ops->fault(vmf)
      |                                |
      |                                +--> filemap_fault()  （通用文件系统）
      |                                     拿页缓存里的页；没有就读磁盘
      |                                |
      |                                +--> ext4 的 fault 变体（带 DIO/回退逻辑）
      |
      |  匿名 VMA -> do_anonymous_page()  （内核直接分配清零）
      |
      +-- 写只读页 -> do_wp_page()
             |
             +-- 文件 VMA -> vma->vm_ops->page_mkwrite(vmf)
             |     让文件系统知道"这个只读共享页要被写了"
             |     ext4 会在这里真正去掉 deny-write 标记
             |
             +-- 匿名 VMA -> 真正的写时复制（复制物理页）

关键点：文件映射的"写保护解除"不是内核直接改页表就完事的。因为这个文件可能被多个进程以不同方式映射，内核需要通过 page_mkwrite 通知文件系统，文件系统才能正确更新 inode 的写权限状态（deny_write_access）。这一步做完后，进程才能真的写进去（同一个文件的其他映射才看得到）。

4.2 get_unmapped_area()：在 VMA 树里找一块空洞

mm/mmap.c:2523-2563 get_unmapped_area

unsigned long
get_unmapped_area(struct file *file, unsigned long addr, unsigned long len,
		unsigned long pgoff, unsigned long flags)
{
	unsigned long (*get_area)(struct file *, unsigned long,
				  unsigned long, unsigned long, unsigned long);

	unsigned long error = arch_mmap_check(addr, len, flags);
	if (error)
		return error;

	/* Careful about overflows.. */
	if (len > TASK_SIZE)
		return -ENOMEM;

	get_area = current->mm->get_unmapped_area;
	if (file) {
		if (file->f_op->get_unmapped_area)
			get_area = file->f_op->get_unmapped_area;
	} else if (flags & MAP_SHARED) {
		pgoff = 0;
		get_area = shmem_get_unmapped_area;
	}

	addr = get_area(file, addr, len, pgoff, flags);
	if (IS_ERR_VALUE(addr))
		return addr;

	if (addr > TASK_SIZE - len)
		return -ENOMEM;
	if (offset_in_page(addr))
		return -EINVAL;

	error = security_mmap_addr(addr);
	return error ? error : addr;
}

这是个"派发器"：先问架构要一套默认实现（x86 的默认是 arch_get_unmapped_area_topdown），如果是文件映射且文件系统有自己的实现就优先用文件系统的，如果是 MAP_SHARED|MAP_ANONYMOUS（即共享内存）就用 tmpfs/shmem 的实现（因为它可能需要很大的连续空间）。拿到地址后还要做溢出检查、页对齐检查和安全钩子（security_mmap_addr，LSM 用它做策略）。

真正的搜索算法在 unmapped_area_topdown()（mm/mmap.c:2270）里，它在红黑树上从高往低找空洞，并用 rb_subtree_gap 剪枝：

static unsigned long unmapped_area_topdown(struct vm_unmapped_area_info *info)
{
	struct mm_struct *mm = current->mm;
	struct vm_area_struct *vma;
	unsigned long length, low_limit, high_limit, gap_start, gap_end;

	/* Adjust search length to account for worst case alignment overhead */
	length = info->length + info->align_mask;
	if (length < info->length)
		return -ENOMEM;

	/*
	 * Adjust search limits by the desired length.
	 */
	gap_end = info->high_limit;
	if (gap_end < length)
		return -ENOMEM;
	high_limit = gap_end - length;

	if (info->low_limit > high_limit)
		return -ENOMEM;
	low_limit = info->low_limit + length;

	/* Check highest gap, which does not precede any rbtree node */
	gap_start = mm->highest_vm_end;
	if (gap_start <= high_limit)
		goto found_highest;

	/* Check if rbtree root looks promising */
	if (RB_EMPTY_ROOT(&mm->mm_rb))
		return -ENOMEM;
	vma = rb_entry(mm->mm_rb.rb_node, struct vm_area_struct, vm_rb);
	if (vma->rb_subtree_gap < length)
		return -ENOMEM;

	while (true) {
		/* Visit right subtree if it looks promising */
		gap_start = vma->vm_prev ? vm_end_gap(vma->vm_prev) : 0;
		if (gap_start <= high_limit && vma->vm_rb.rb_right) {
			struct vm_area_struct *right =
				rb_entry(vma->vm_rb.rb_right,
					 struct vm_area_struct, vm_rb);
			if (right->rb_subtree_gap >= length) {
				vma = right;
				continue;
			}
		}

check_current:
		/* Check if current node has a suitable gap */
		gap_end = vm_start_gap(vma);
		if (gap_end < low_limit)
			return -ENOMEM;
		if (gap_start <= high_limit &&
		    gap_end > gap_start && gap_end - gap_start >= length)
			goto found;

		/* Visit left subtree if it looks promising */
		// ... (向左子树走，逻辑与上面镜像对称)
	}

逐段理解：length 加上对齐余量（align_mask）；high_limit 减掉 length 是为了让"区间尾部不越界"，low_limit 加上 length 是为了让"区间头部不越界"。然后先试最高处的空洞（mm->highest_vm_end 往上那段通常最大），再进红黑树。核心剪枝是 if (right->rb_subtree_gap >= length)：右子树里最大的空洞都装不下，就整棵右子树都不用进了。这正是 rb_subtree_gap 存在的意义。

			goto free_vma;
	} else {
		vma_set_anonymous(vma);
	}

	/* Allow architectures to sanity-check the vm_flags */
	if (!arch_validate_flags(vma->vm_flags)) {
		error = -EINVAL;
		if (file)
			goto unmap_and_free_vma;
		else
			goto free_vma;
	}

	vma_link(mm, vma, prev, rb_link, rb_parent);

三条分支决定 VMA 的"身份"：有文件 → 文件映射；无文件但 VM_SHARED → 共享内存（shmem_zero_setup() 给它造一个 tmpfs 文件）；无文件且私有 → vma_set_anonymous() 标记为匿名（这个标记很重要，第 16 篇的 handle_pte_fault() 就是靠 vma_is_anonymous() 决定走 do_anonymous_page() 还是 do_fault()）。

mm/mmap.c:795-814 vma_link

static void vma_link(struct mm_struct *mm, struct vm_area_struct *vma,
		struct vm_area_struct *prev, struct rb_node **rb_link,
		struct rb_node *rb_parent)
{
	struct address_space *mapping = NULL;

	if (vma->vm_file) {
		mapping = vma->vm_file->f_mapping;
		i_mmap_lock_write(mapping);
	}

	__vma_link(mm, vma, prev, rb_link, rb_parent);
	__vma_link_file(vma);

	if (mapping)
		i_mmap_unlock_write(mapping);

	mm->map_count++;
	validate_mm(mm);
}

vma_link() 是"挂进树"的动作，三步：① 如果 VMA 有文件，先锁住该文件 address_space 的 i_mmap 区间树（因为文件映射还要登记到文件那边去）；② __vma_link() 把 VMA 挂进 mm->mm_rb 红黑树和 mm->mmap 链表；③ mm->map_count++ 记账。rb_link / rb_parent 这两个参数是调用者提前算好的"插入点"——红黑树的插入位置是可以先算后插的，这样 munmap_vma_range() 顺手就把位置算好了。

4.4 __do_munmap()：拆 VMA、清页表

mm/mmap.c:3153-3186 __do_munmap（入口与查找）

int __do_munmap(struct mm_struct *mm, unsigned long start, size_t len,
		struct list_head *uf, bool downgrade)
{
	unsigned long end;
	struct vm_area_struct *vma, *prev, *last;

	if ((offset_in_page(start)) || start > TASK_SIZE || len > TASK_SIZE-start)
		return -EINVAL;

	len = PAGE_ALIGN(len);
	end = start + len;
	if (len == 0)
		return -EINVAL;

	/*
	 * arch_unmap() might do unmaps itself.  It must be called
	 * and finish any rbtree manipulation before this code
	 * runs and also starts to manipulate the rbtree.
	 */
	arch_unmap(mm, start, end);

	/* Find the first overlapping VMA */
	vma = find_vma(mm, start);
	if (!vma)
		return 0;
	prev = vma->vm_prev;
	/* we have  start < vma->vm_end  */

	/* if it doesn't overlap, we have nothing.. */
	if (vma->vm_start >= end)
		return 0;

入口检查很直白：起始地址必须页对齐、不能超过 TASK_SIZE。然后用第 16 篇讲过的 find_vma() 找第一个可能重叠的 VMA。

mm/mmap.c:3185-3217 __do_munmap（切分边界）

	/*
	 * If we need to split any vma, do it now to save pain later.
	 *
	 * Note: mremap's move_vma VM_ACCOUNT handling assumes a partially
	 * unmapped vm_area_struct will remain in use: so lower split_vma
	 * places tmp vma above, and higher split_vma places tmp vma below.
	 */
	if (start > vma->vm_start) {
		int error;

		if (end < vma->vm_end && mm->map_count >= sysctl_max_map_count)
			return -ENOMEM;

		error = __split_vma(mm, vma, start, 0);
		if (error)
			return error;
		prev = vma;
	}

	/* Does it split the last one? */
	last = find_vma(mm, end);
	if (last && end > last->vm_start) {
		int error = __split_vma(mm, last, end, 1);
		if (error)
			return error;
	}
	vma = vma_next(mm, prev);

这是 VMA 切分的核心逻辑：如果 munmap 的范围只覆盖了 VMA 的一部分，就把它切成两半——前半留在原地（__split_vma(mm, vma, start, 0)），后半被摘掉。尾部同理（__split_vma(mm, last, end, 1)）。切分之后，被 munmap 的区间就总是完整覆盖若干个 VMA，拆除逻辑就简单了——这也是为什么 mprotect、brk 都要学会切分。

4.5 mprotect_fixup()：改权限 = 切分 + 改 flags + 改页表

mm/mprotect.c:450-490 mprotect_fixup

	/*
	 * First try to merge with previous and/or next vma.
	 */
	pgoff = vma->vm_pgoff + ((start - vma->vm_start) >> PAGE_SHIFT);
	*pprev = vma_merge(mm, *pprev, start, end, newflags,
			   vma->anon_vma, vma->vm_file, pgoff, vma_policy(vma),
			   vma->vm_userfaultfd_ctx);
	if (*pprev) {
		vma = *pprev;
		VM_WARN_ON((vma->vm_flags ^ newflags) & ~VM_SOFTDIRTY);
		goto success;
	}

	*pprev = vma;

	if (start != vma->vm_start) {
		error = split_vma(mm, vma, start, 1);
		if (error)
			goto fail;
	}

	if (end != vma->vm_end) {
		error = split_vma(mm, vma, end, 0);
		if (error)
			goto fail;
	}

success:
	/*
	 * vm_flags and vm_page_prot are protected by the mmap_lock
	 * held in write mode.
	 */
	vma->vm_flags = newflags;
	dirty_accountable = vma_wants_writenotify(vma, vma->vm_page_prot);
	vma_set_page_prot(vma);

	change_protection(vma, start, end, vma->vm_page_prot,
			  dirty_accountable ? MM_CP_DIRTY_ACCT : 0);

顺序是：①先试合并（如果整个 VMA 都要改权限，就没必要拆，直接改；如果只是改一部分，合并会失败）；②再按边界切分；③改 vm_flags 和 vm_page_prot；④change_protection() 重写页表项，把对应的 PTE 权限位改掉并刷 TLB。

一个实践后果：mprotect() 一个 VMA 的中间一小段，会把原来那个 VMA 变成三个（前面一段、中间一段、后面一段），map_count 增加 2。这就是为什么大量 mprotect 调用会推高 mm->map_count，也是 vm.max_map_count 存在的原因之一。

4.6 find_extend_vma() 与栈的自动增长

mm/mmap.c:2893-2913 find_extend_vma

struct vm_area_struct *
find_extend_vma(struct mm_struct *mm, unsigned long addr)
{
	struct vm_area_struct *vma;
	unsigned long start;

	addr &= PAGE_MASK;
	vma = find_vma(mm, addr);
	if (!vma)
		return NULL;
	if (vma->vm_start <= addr)
		return vma;
	if (!(vma->vm_flags & VM_GROWSDOWN))
		return NULL;
	start = vma->vm_start;
	if (expand_stack(vma, addr))
		return NULL;
	if (vma->vm_flags & VM_LOCKED)
		populate_vma_page_range(vma, addr, start, NULL);
	return vma;
}

栈增长的判定链条：地址落在某个 VMA 之后（即在栈 VMA 的下方空洞里）→ 该 VMA 必须带 VM_GROWSDOWN → 调用 expand_stack() 真正扩展。

mm/mmap.c:2775-2798 expand_downwards

int expand_downwards(struct vm_area_struct *vma,
				   unsigned long address)
{
	struct mm_struct *mm = vma->vm_mm;
	struct vm_area_struct *prev;
	int error = 0;

	address &= PAGE_MASK;
	if (address < mmap_min_addr)
		return -EPERM;

	/* Enforce stack_guard_gap */
	prev = vma->vm_prev;
	/* Check that both stack segments have the same anon_vma? */
	if (prev && !(prev->vm_flags & VM_GROWSDOWN) &&
			vma_is_accessible(prev)) {
		if (address - prev->vm_end < stack_guard_gap)
			return -ENOMEM;
	}

	/* We must make sure the anon_vma is allocated. */
	if (unlikely(anon_vma_prepare(vma)))
		return -ENOMEM;

三道关卡：① 不能低于 mmap_min_addr（防止栈长到 NULL 附近）；② 不能侵入上一个 VMA 的 stack_guard_gap 保护区（这是防止栈溢出攻击覆盖相邻对象的安全带，默认 256 页 = 1 MB）；③ 必须能分配 anon_vma。

而"能不能长到这么大"最终由 acct_stack_growth() 判定，它会检查 RLIMIT_STACK：

static int acct_stack_growth(struct vm_area_struct *vma,
			     unsigned long size, unsigned long grow)
{
	struct mm_struct *mm = vma->vm_mm;
	unsigned long new_start;
	// ...
	if (is_vsyscall_vaddr(vma->vm_start))
		return -ENOMEM;

	new_start = vma->vm_start - size;
	// ...
	if (new_start < mm->map_base && stack_guard_gap)
		return -ENOMEM;

	/* Do we have enough space? */
	if (vma->vm_flags & VM_LOCKED) {
		// ...
	}
	return 0;
}

acct_stack_growth() 位于 mm/mmap.c:2639，它把新起始地址和 mm->total_vm 的增长量一起算，超出 RLIMIT_STACK 就返回 -ENOMEM，最终让缺页处理发 SIGSEGV。可以用 ulimit -s 调整这个限额（见第 5 节）。

4.7 vm_ops：VMA 的回调表

include/linux/mm.h:557-574 struct vm_operations_struct（节选）

struct vm_operations_struct {
	void (*open)(struct vm_area_struct * area);
	void (*close)(struct vm_area_struct * area);
	int (*split)(struct vm_area_struct * area, unsigned long addr);
	int (*mremap)(struct vm_area_struct * area);
	vm_fault_t (*fault)(struct vm_fault *vmf);
	vm_fault_t (*huge_fault)(struct vm_fault *vmf,
			enum page_entry_size pe_size);
	void (*map_pages)(struct vm_fault *vmf,
			pgoff_t start_pgoff, pgoff_t end_pgoff);
	unsigned long (*pagesize)(struct vm_area_struct * area);

	/* notification that a previously read-only page is about to become
	 * writable, if an error is returned it will cause a SIGBUS */
	vm_fault_t (*page_mkwrite)(struct vm_fault *vmf);

	/* same as page_mkwrite when using VM_PFNMAP|VM_MIXEDMAP */
	vm_fault_t (*pfn_mkwrite)(struct vm_fault *vmf);

四个最关键的成员：

  • fault：缺页时"这个 VMA 的页从哪来"。文件映射走它（进页缓存/读磁盘）；匿名映射不用它（内核直接分配清零）。
  • page_mkwrite："一个只读共享页即将被写"。文件映射用它通知文件系统去掉 deny-write 状态；返回错误会导致 SIGBUS。
  • huge_fault：大页缺页的专用路径（第 19 篇的 THP 会用到）。
  • open/close：VMA 被建立/销毁时的通知，典型用途是调整文件的引用计数和 deny_write_access 计数。
版本提醒：5.10 的 vm_operations_struct 没有 set_page_prot、map、unmap 这三个成员。设置页保护位改成了全局函数 vma_set_page_prot()（mm/mmap.c:152）；map/unmap 在 2.6 时代就被 address_space 的操作取代了。

5.3 实验：两个进程共享同一块 mmap 缓冲区

下面这个程序把同一个文件映射到 MAP_SHARED，父子进程各写各的，最后打印文件内容——你会看到两个进程的写入互相可见。

$ cat > shared_map.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <sys/wait.h>

#define SIZE 4096

int main(void)
{
	int fd = open("/tmp/shared_map.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
	char *buf;
	pid_t pid;

	setvbuf(stdout, NULL, _IONBF, 0);   /* 让父子进程的输出顺序稳定 */

	if (fd < 0) { perror("open"); return 1; }
	if (ftruncate(fd, SIZE) < 0) { perror("ftruncate"); return 1; }

	buf = mmap(NULL, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
	if (buf == MAP_FAILED) { perror("mmap"); return 1; }

	pid = fork();
	if (pid == 0) {
		sleep(1);
		printf("child  read  : %s", buf);      /* 读到父进程写的 */
		strcpy(buf, "hello from child\n");    /* 写回去 */
		printf("child  wrote : %s", buf);
		munmap(buf, SIZE);
		_exit(0);
	}

	strcpy(buf, "hello from parent\n");
	printf("parent wrote : %s", buf);
	waitpid(pid, NULL, 0);

	printf("parent read  : %s", buf);          /* 读到子进程写的 */
	printf("file content : ");
	system("cat /tmp/shared_map.bin");
	munmap(buf, SIZE);
	close(fd);
	return 0;
}
EOF
$ gcc -O0 -o shared_map shared_map.c && ./shared_map
parent wrote : hello from parent
child  read  : hello from parent
child  wrote : hello from child
parent read  : hello from child
file content : hello from child

这个实验演示了 MAP_SHARED 的三个关键性质：① 父子进程看到的是同一个物理页（不是两份拷贝）；② 一方的写入对另一方立即可见（无需额外同步机制）；③ 写入最终落到文件里（因为 MAP_SHARED 且文件可写，脏页会被回写）。

对照实验：把 MAP_SHARED 改成 MAP_PRIVATE，再跑一次——你会看到父子进程各写各的，文件内容也不会变。这就是"写时复制"的直观版本。

5.4 实验：mprotect 切分 VMA

$ cat > mprotect_demo.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <unistd.h>

static void show(const char *tag)

	FILE *f = fopen("/proc/self/maps", "r");
	char line[512];
	int n = 0;
	if (!f) { perror("/proc/self/maps"); exit(1); }

递归用了超过 1 MB，栈没法再扩展（acct_stack_growth() 拒绝了），内核给进程发 SIGSEGV。这就是"栈溢出"的真实机制——不是缓冲区写坏了，是内核拒绝再给栈发空间。可以用 ulimit -s unlimited 取消限制（但受 /proc/sys/vm/overcommit_memory 等其他因素约束）。

顺带一提，栈的实际增长是按页懒分配的：递归到第 100 层时，栈 VMA 可能只被扩展了几十 KB，其余页面直到被碰到才真正分配物理内存。

6. 自测

Q1. Linux 5.10 的 VMA 是用红黑树还是 maple tree 存的？用红黑树。5.10 的 struct mm_struct 里是 struct rb_root mm_rb;（include/linux/mm_types.h:391）和辅助的双向链表 struct vm_area_struct *mmap;（同文件 390 行）。maple tree 是 Linux 6.1 才引入的替代方案，5.10 里完全没有 mm_mt 字段。看老内核代码或 5.10 的资料时不要被新文章误导。
Q2. mmap() 明明申请了 1 GB，为什么不立刻占用 1 GB 内存？因为 mmap() 只建立 VMA（地址空间的"描述"），不建立页表项、更不分配物理页。物理页是在第一次访问该地址时，由缺页异常处理（do_anonymous_page() 或 do_fault()）按需分配的。这就是"懒分配"：虚拟地址空间是承诺，物理内存是兑现。所以 mmap 一块 1 TB 的空间不碰它，几乎不花物理内存，但 mm->total_vm 会涨 1 TB（受 RLIMIT_AS 约束）。
Q3. munmap 一段只覆盖了某个 VMA 一半的地址，会发生什么？会先切分那个 VMA：在 __do_munmap() 里，__split_vma(mm, vma, start, 0) 把 VMA 在 start 处切成两段（__split_vma(mm, last, end, 1) 处理尾部），然后被覆盖的那段才被完整摘除。切分的原因是：拆除逻辑要处理的是"完整覆盖某个 VMA 区间"的情况，先切分能让后续逻辑统一。同时 mm->map_count 会临时增加 1。
Q4. MAP_SHARED 和 MAP_PRIVATE 映射同一个文件，物理上有什么不同？MAP_SHARED 下多个进程（以及文件页缓存）用的是同一批物理页，任何一方的写入对其他方立即可见，最终回写到文件。MAP_PRIVATE 下，读取时共用同一批页（省内存），但一旦某个进程要写，就触发写时复制：内核复制一份新页给这个进程，从此各写各的，互不影响，也不会回写文件。这正是 5.5 节那个实验能演示出来的现象。
Q5. 递归太深导致"栈溢出"，为什么内核不干脆让栈无限增长？三个限制：① RLIMIT_STACK 限制（默认 8 MB），由 acct_stack_growth() 检查；② stack_guard_gap（默认 1 MB）保护带，栈不能长到侵占上一个 VMA，否则栈溢出就能覆盖相邻对象——这是安全机制；③ mmap_min_addr 防止栈长到 NULL 指针附近。三个条件任一不满足，内核就拒绝扩展并给进程发 SIGSEGV。另外栈本身也是懒分配的：只有被递归真正用到的页才分配物理内存。
