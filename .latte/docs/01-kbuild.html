🔨 01 · Kbuild：一套 Makefile 怎么编译两千多万行代码

从 make menuconfig 到 insmod——内核的"工厂流水线"是怎么设计和运转的 · 预计阅读 25 分钟

1. 它在解决什么问题

想象你要盖一栋有 3 万个房间的房子，但每个房间要不要盖、盖成什么样，都取决于一张可以随时改动的"需求清单"：今天要 100 个卧室、明天改要 2 个厨房。而且你不可能每次都推倒重建——你只想动那几间改过的房间。这就是 Linux 内核编译要面对的问题：源码有 2.8 万个文件、约 2000 万行 C 代码，可配置项（CONFIG 开关）有 上万种组合，而绝大多数用户只需要其中很小一部分。

如果做一个"所有文件全部编译"的傻瓜脚本，会有三个致命问题：① 编译时间从 10 分钟涨到数小时；② 每个驱动都被塞进内核镜像，一块 10 MB 的内核变成 300 MB，手机放不下；③ 一堆互斥的代码（比如同时给 Intel 和 ARM 编同一段汇编）根本编不过。所以内核必须有一套"先选、再编、只编选中的"的系统。

从操作系统视角看，这套系统叫 Kbuild，它由三个部件拼成：Kconfig（需求清单的描述语言，决定"要什么"）、Makefile 体系（施工队，决定"怎么盖"）、scripts/ 下的辅助工具（图纸校验、打包、生成头文件）。三者分工明确：Kconfig 只产出数据（.config），Makefile 只读数据做决策（要不要编某个 .o），绝不互相越界。理解这条边界，你就理解了 Kbuild 的一半。

对本篇的读者还有一个实际好处：写完一个内核模块，你得知道它该放哪、怎么让它被编出来、怎么单独编译它而不重编整个内核。这些都直接由 obj-y / obj-m 这几行决定。

3. 整体结构

3.1 三层 Makefile：递归下降

内核不是一个巨型 Makefile，而是每层目录一个 Makefile，逐层向下"串门"。一共三层的角色非常清楚：

第 1 层  顶层 Makefile（源码树根）
          职责：解析 ARCH/CROSS_COMPILE、检查 .config、决定要进哪些子目录
              （core-y / drivers-y / libs-y / head-y），最终调用
              scripts/link-vmlinux.sh 把各目录的 built-in.a 链成 vmlinux
              │
第 2 层  scripts/Makefile.build（每个目录都会被执行一次）
          职责：读取本目录的 Makefile/Kbuild，把它声明的 obj-y 编成 .o，
              打包成本目录 built-in.a；把 obj-m 变成 .mod 中间文件
              │
第 3 层  各级目录自己的 Makefile（如 fs/Makefile、drivers/char/Makefile）
          职责：只写本目录的 obj-y / obj-m / 子目录，不关心别人

顶层 Makefile 用一条"万能规则"下钻到所有子目录，子目录又用 scripts/Makefile.build 当成自己的"执行器"。这就是 Kbuild 被称为 recursive build（递归构建） 的原因。递归的好处是：每个目录只改自己的文件，别人不受影响，增量编译天然成立。

3.2 Kconfig：配置语言如何变成 .config

Kconfig 文件是一棵"菜单树"。顶层 Kconfig 只做一件事——source 各子系统的 Kconfig：

Kconfig:1-30 顶层配置入口

# SPDX-License-Identifier: GPL-2.0
#
# For a description of the syntax of this configuration file,
# see Documentation/kbuild/kconfig-language.rst.
#
mainmenu "Linux/$(ARCH) $(KERNELVERSION) Kernel Configuration"

source "scripts/Kconfig.include"

source "init/Kconfig"

source "kernel/Kconfig.freezer"

source "fs/Kconfig.binfmt"

source "mm/Kconfig"

source "net/Kconfig"

source "drivers/Kconfig"
// ... 省略 fs/Kconfig、security/Kconfig、crypto/Kconfig、lib/Kconfig 等
source "lib/Kconfig.debug"
  • mainmenu：菜单标题，编译时 $(ARCH)、$(KERNELVERSION) 由 Makefile 环境变量替换。
  • source：把另一个 Kconfig 文件的内容"内联"进来，没有 #include 那种物理拼接的坑，但效果一样。
  • 顺序有意义：先 init/Kconfig（里面有 MODULES），后面 fs/Kconfig 才能写 depends on MODULES。

一条配置项的标准写法（drivers/char/Kconfig 里的真实条目）：

drivers/char/Kconfig:10-23 TTY_PRINTK 的三态选项

config TTY_PRINTK
	tristate "TTY driver to output user messages via printk"
	depends on EXPERT && TTY
	default n
	help
	  If you say Y here, the support for writing user messages (i.e.
	  console messages) via printk is available.

	  // ... 省略中间 2 段说明文字

	  If unsure, say N.
  • config TTY_PRINTK：定义符号名，最终变成 CONFIG_TTY_PRINTK。
  • tristate：三态；如果是 bool 就只有 y/n。
  • depends on EXPERT && TTY：只有 EXPERT 和 TTY 都开着，这个选项才会出现在菜单里。
  • help：后面缩进的一段是帮助文本，menuconfig 里按 h/? 显示。
  • 答 m 时，符号值变成 CONFIG_TTY_PRINTK=m，Makefile 里的 obj-$(CONFIG_TTY_PRINTK) 就成了 obj-m += ttyprintk.o。

3.3 make menuconfig 到底写了什么文件

                你按键选择
                     │
                     ▼

                     │  退出时保存
                     ▼
                  .config          ← 人可读的答案清单，例如 CONFIG_TTY_PRINTK=y
                     │  下一步 make 检测到 .config 比 auto.conf 新
                     ▼
   顶层 Makefile 的 syncconfig 规则
                     │  实际执行：make -f Makefile syncconfig
                     ▼
   scripts/kconfig/conf --syncconfig
            │                    │
            ▼                    ▼
 include/config/auto.conf   include/generated/autoconf.h
 （给 Makefile 用）          （给 C 代码里的 #ifdef CONFIG_X 用）
            + 每个符号一个空文件 include/config/CONFIG_XXX（供依赖追踪）

关键点是：Makefile 从不直接读 .config。它读的是 include/config/auto.conf。这两份文件格式不同——.config 里有 # CONFIG_FOO is not set 这种注释，auto.conf 只保留等号形式，并且写进 Makefile 的语法域（CONFIG_X=y 就像 X=y）。

scripts/kconfig/confdata.c:220-232 配置文件名与 auto.conf 名

const char *conf_get_configname(void)
{
	char *name = getenv("KCONFIG_CONFIG");

	return name ? name : ".config";
}

static const char *conf_get_autoconfig_name(void)
{
	char *name = getenv("KCONFIG_AUTOCONFIG");

	return name ? name : "include/config/auto.conf";
}

两段代码一眼看懂：配置文件默认是 .config，但允许用环境变量 KCONFIG_CONFIG 改名（内核构建系统用这个机制做 O= 输出目录和多套配置）。auto.conf 同理，默认 include/config/auto.conf。这使得 O= 构建时所有路径都被"前缀化"，源码树零写入。

3.4 顶层 Makefile 与 scripts/Makefile.build 的分工

Makefile:648-654 顶层决定要下钻的目录

# Objects we will link into vmlinux / subdirs we need to visit
core-y		:= init/ usr/
drivers-y	:= drivers/ sound/
drivers-$(CONFIG_SAMPLES) += samples/
drivers-y	+= net/ virt/
libs-y		:= lib/
endif # KBUILD_EXTMOD

这 5 行是"总图"：core-y/drivers-y/libs-y 只有目录名和结尾斜杠。drivers-$(CONFIG_SAMPLES) 说明 CONFIG_SAMPLES 为 y 时才把 samples/ 加进来——这就是"配置驱动的目录裁剪"。注意 arch/ 不在这里，它由第 681 行 include arch/$(SRCARCH)/Makefile 注入，因为每个架构的下钻清单不同。

Makefile:1119-1127 把目录清单翻译成 built-in.a 清单

build-dirs	:= $(vmlinux-dirs)
clean-dirs	:= $(vmlinux-alldirs)

# Externally visible symbols (used by link-vmlinux.sh)
KBUILD_VMLINUX_OBJS := $(head-y) $(patsubst %/,%/built-in.a, $(core-y))
KBUILD_VMLINUX_OBJS += $(addsuffix built-in.a, $(filter %/, $(libs-y)))
ifdef CONFIG_MODULES
KBUILD_VMLINUX_OBJS += $(patsubst %/, %/lib.a, $(filter %/, $(libs-y)))
KBUILD_VMLINUX_LIBS := $(filter-out %/, $(libs-y))

$(patsubst %/,%/built-in.a, ...) 把 init/ 变成 init/built-in.a。head-y 来自 arch/x86/Makefile:225 的 head-y := arch/x86/kernel/head_$(BITS).o——它是 vmlinux 的"第一段代码"，必须排在最前面，因为它定义了内核入口地址。这就是为什么 head-y 单独列出来而不是混进 core-y。

3.5 obj-y / obj-m 的真实含义

先看 Kconfig 里 tristate 的取值如何流到 Makefile：

.config 里          auto.conf 里            Makefile 里
CONFIG_TTY_PRINTK=y   CONFIG_TTY_PRINTK=y   obj-y += ttyprintk.o
CONFIG_TTY_PRINTK=m   CONFIG_TTY_PRINTK=m   obj-m += ttyprintk.o
# CONFIG_TTY_PRINTK   （该行不存在）        （空，这一行整行变成 "obj-" 丢掉内容）
                                            → 结果：obj-  := ，不影响任何目标

第三行的技巧叫"变量名拼接"：obj-$(CONFIG_TTY_PRINTK) 在值为空时展开成 obj- += ttyprintk.o，GNU Make 里 obj- 是个合法（但没人用）的变量名，所以这一行什么也不做。这是 Kbuild 最经典的一招：不写 if，靠变量名拼接实现条件编译。

drivers/char/Makefile:6-11 真实的 obj-y/obj-$(CONFIG_X)

obj-y				+= mem.o random.o
obj-$(CONFIG_TTY_PRINTK)	+= ttyprintk.o
obj-y				+= misc.o
obj-$(CONFIG_ATARI_DSP56K)	+= dsp56k.o
obj-$(CONFIG_VIRTIO_CONSOLE)	+= virtio_console.o
obj-$(CONFIG_RAW_DRIVER)	+= raw.o
  • += 而不是 :=：因为 scripts/Makefile.build 第 14-15 行先做了 obj-y := ; obj-m := 清空，子 Makefile 必须用 += 追加，否则会覆盖之前的内容。
  • obj-y 与 obj-$(CONFIG_X) 可以混写，最终都汇集到同一个 obj-y。
  • agp/ 这种带斜杠的条目在第 39 行（obj-y += agp/）出现，会被 scripts/Makefile.lib 改写成 agp/built-in.a，并触发向下递归。

3.6 编译任意一个 .o 的规则只有一条

scripts/Makefile.build:153-154 唯一的编译命令

quiet_cmd_cc_o_c = CC $(quiet_modtag)  $@
      cmd_cc_o_c = $(CC) $(c_flags) -c -o $@ $<

所有 .c → .o 都走这条命令。$(c_flags) 是聚合了 KBUILD_CFLAGS、本目录的 ccflags-y、架构特有 flag 的"全家桶"；quiet_cmd_* 与 cmd_* 的成对约定是 Kbuild 的日志风格——正常只打 CC init/main.o，加 V=1 时打完整命令行。if_changed 会比对命令行与依赖文件的时间戳，只有真变了才重编。

scripts/Makefile.build:395-399 打包 built-in.a

quiet_cmd_ar_builtin = AR      $@
      cmd_ar_builtin = rm -f $@; $(AR) cDPrST $@ $(real-prereqs)

$(obj)/built-in.a: $(real-obj-y) FORCE
	$(call if_changed,ar_builtin)

$(AR) cDPrST 的 D 表示"不打符号表"（deterministic），P 用完整路径名——这是为了让 built-in.a 可以确定性地合并，不同机器编出同样的字节。

3.7 一次 make 的完整产物链

make menuconfig
   └─ .config
make -j$(nproc)
   ├─ 各目录 .c → .o
   │     └─ 各目录 .o → built-in.a（用 ar 打包，无符号表）
   ├─ scripts/link-vmlinux.sh 把 core-y/drivers-y/libs-y/head-y 的 .a 链起来
   │     ├─ vmlinux               （ELF，未压缩，带符号）
   │     └─ System.map            （nm 导出的符号表）
   └─ arch/x86/boot/compressed → vmlinux.bin → 加 boot 头 → bzImage
make modules
   └─ 各目录 .o → .mod（中间） → modpost 检查 → .ko
make modules_install
   └─ depmod -a 生成 /lib/modules/$(uname -r)/modules.dep

Makefile:1169-1170 vmlinux 由脚本链接

vmlinux: scripts/link-vmlinux.sh autoksyms_recursive $(vmlinux-deps) FORCE
	+$(call if_changed,link-vmlinux)

为什么链接要交给 shell 脚本而不是 Makefile？因为 kallsyms（内核内符号表）需要"链接 → 生成表 → 重新链接"两遍以上迭代，Makefile 的表达能力不够。脚本的 vmlinux_link() 会调用 ld 或 gcc 做最终链接。

scripts/link-vmlinux.sh:357-368 生成并校验 System.map

info SYSMAP System.map
mksysmap vmlinux System.map

# step a (see comment above)
if [ -n "${CONFIG_KALLSYMS}" ]; then
	mksysmap ${kallsyms_vmlinux} .tmp_System.map

	if ! cmp -s System.map .tmp_System.map; then
		echo >&2 Inconsistent kallsyms data
		echo >&2 Try "make KALLSYMS_EXTRA_PASS=1" as a workaround
		exit 1
	fi
fi

第一次 mksysmap 给调试工具用（System.map）；然后用带 kallsyms 的 vmlinux 再导出一份，如果两份地址不一致就报错——因为 kallsyms 表的大小会影响段布局，可能导致地址漂移。cmp -s 是"两次链接必须完全收敛"的判定。

3.8 模块：内置与可加载的区别

obj-m 的 .o 不走 built-in.a，走 .mod 中间文件（记录 .o 的路径），再经过 scripts/Makefile.modpost 与 modpost 工具生成 .ko。modpost 做两件事：① 检查模块是否用了内核未导出的符号（链接时才发现会太晚）；② 生成 __ksymtab/__kcrctab 相关内容。

Makefile:1690-1709 M= 外部模块的构建路径

// ... 省略上方注释（"only valid targets when building external modules"）
KBUILD_BUILTIN :=
KBUILD_MODULES := 1

build-dirs := $(KBUILD_EXTMOD)
PHONY += modules
modules: $(MODORDER)
	$(Q)$(MAKE) -f $(srctree)/scripts/Makefile.modpost

KBUILD_BUILTIN := 清空意味着"这次不编 vmlinux"；build-dirs 被替换成外部目录，递归只在那一个目录里发生。这就是 make M=path 能只编模块、秒级完成的原理。

3.9 initcall 与 module_init 在编译期的落点

模块的 module_init(fn) 在编译期被宏展开成一个指向函数指针、被放进特殊 section 的常量。当它是内置代码时，section 名叫 .initcall6.init（device 级），由链接脚本收集、启动时遍历。

include/linux/module.h:80-89 内置模块时的 module_init

#ifndef MODULE
/**
 * module_init() - driver initialization entry point
 * @x: function to be run at kernel boot time or module insertion
 *
 * module_init() will either be called during do_initcalls() (if
 * builtin) or at module insertion time (if a module).  There can only
 * be one per module.
 */
#define module_init(x)	__initcall(x);

注释把奥妙讲明了：同一个宏，在编进 vmlinux 时是 do_initcalls() 走一遍；在编成 .ko 时是 insmod 触发。这个分支由编译器的 -DMODULE 决定，而不是运行时。所以 samples/kobject/kobject-example.c:141 那一行 module_init(example_init) 在两种构建方式下都能正常工作。

4.2 架构与交叉编译入口

Makefile:369-375 ARCH 的默认值与归一化

ARCH		?= $(SUBARCH)

# Architecture as present in compile.h
UTS_MACHINE 	:= $(ARCH)
SRCARCH 	:= $(ARCH)
  • ?=：如果环境或命令行没给 ARCH，就用 $(SUBARCH)（Makefile 早先用 uname -m 算出来的值）。
  • 紧接着 375 行以后有一堆 ifeq ($(ARCH),i386) / x86_64 分支，把两者都归一成 SRCARCH := x86，因为 arch/x86/ 一个目录管两种位宽。
  • UTS_MACHINE 保留原始 ARCH 值，最终写进 utsrelease.h，uname -m 会显示它。

Makefile:351-369 交叉编译的官方说明

# Cross compiling and selecting different set of gcc/bin-utils
# ---------------------------------------------------------------------------
#
// ... 省略 3 行
ARCH can be set during invocation of make:
# make ARCH=ia64
# Another way is to have ARCH set in the environment.
# The default ARCH is the host where make is executed.

# CROSS_COMPILE specify the prefix used for all executables used
// ... 省略 4 行

这段注释是官方"手册"：ARCH=arm64 + CROSS_COMPILE=aarch64-linux-gnu- 就是交叉编译的标准姿势。前缀会拼到 CC/LD/AR/NM 前面，Makefile 不做别的事——它只是"传话筒"。

4.3 scripts/Makefile.build：每个目录的执行器

scripts/Makefile.build:36-44 读配置、找本目录 Kbuild

# Read auto.conf if it exists, otherwise ignore
-include include/config/auto.conf

include scripts/Kbuild.include

# The filename Kbuild has precedence over Makefile
kbuild-dir := $(if $(filter /%,$(src)),$(src),$(srctree)/$(src))
kbuild-file := $(if $(wildcard $(kbuild-dir)/Kbuild),$(kbuild-dir)/Kbuild,$(kbuild-dir)/Makefile)
include $(kbuild-file)
  • -include（减号前缀）：文件不存在也不报错。第一次构建时 auto.conf 可能还没生成。
  • $(wildcard .../Kbuild) 优先：如果目录里同时有 Kbuild 和 Makefile，用 Kbuild。所以纯 kbuild 项目可以只放 Kbuild。
  • $(src) 与 $(obj) 在全篇交替出现：src 是源文件所在目录，obj 是产物目录。用 O= 时两者不同，这是 O= 构建的核心机制。

scripts/Makefile.build:14-23 先把变量清空

# Init all relevant variables used in kbuild files so
# 1) they have correct type
# 2) they do not inherit any value from the environment
obj-y :=
obj-m :=
lib-y :=
// ... 省略 lib-m、always、always-y、always-m、targets、subdir-y/m 等

清空是必须的：否则 obj-y 会被父目录的值污染（GNU Make 变量默认向下继承），导致 drivers/char 的 obj-y 里混着 drivers/net 的东西。清空之后再 include $(kbuild-file)，就只包含本目录自己写的。

4.4 obj-y 如何变成 built-in.a：递归拼接

scripts/Makefile.lib:27-56 子目录与 built-in.a 的改写

# When an object is listed to be built compiled-in and modular,
# only build the compiled-in version
obj-m := $(filter-out $(obj-y),$(obj-m))
// ... 省略 lib-y / subdir-ym 计算（第 31-37 行）
ifdef need-modorder
obj-m := $(patsubst %/,%/modules.order, $(filter %/, $(obj-y)) $(obj-m))
else
obj-m := $(filter-out %/, $(obj-m))
endif

ifdef need-builtin
obj-y		:= $(patsubst %/, %/built-in.a, $(obj-y))
else
obj-y		:= $(filter-out %/, $(obj-y))
  • 第 29 行：同一个目标不能既内置又模块，优先内置。
  • 第 43-48 行：foo/ 在 obj-y 里时变成 foo/built-in.a（下拉目录并取回它的库）；在 obj-m 里时变成 foo/modules.order（只收集模块顺序，不取库）。
  • 这解释了为什么 drivers/char/Makefile 里能直接写 obj-y += agp/：Makefile.lib 会替你把斜杠翻译成库文件。

4.5 menuconfig 的实现：一个被编译出来的程序

scripts/kconfig/Makefile:28-29 menuconfig 只是跑 mconf

menuconfig: $(obj)/mconf
	$(Q)$< $(silent) $(Kconfig)

$(obj)/mconf 是 scripts/kconfig/mconf.c + lxdialog/ 编译出来的二进制。$(Kconfig) 是顶层 Kconfig 的路径（KBUILD_KCONFIG 可覆盖）。所以 menuconfig 的本质就是"编译并运行一个小工具"，跟 Makefile 体系没有别的耦合。

scripts/kconfig/Makefile:64-71 所有非交互式配置目标共享一条规则

simple-targets := oldconfig allnoconfig allyesconfig allmodconfig \
	alldefconfig randconfig listnewconfig olddefconfig syncconfig \
	helpnewconfig yes2modconfig mod2yesconfig

PHONY += $(simple-targets)

$(simple-targets): $(obj)/conf
	$(Q)$< $(silent) --$@ $(Kconfig)

--$@ 把目标名当参数名传给 conf，例如 make olddefconfig 执行 conf --olddefconfig Kconfig。一条规则覆盖十几种行为，conf.c 里再按 input_mode 枚举分派。

scripts/kconfig/conf.c:516-523 syncconfig 模式

		case syncconfig:
			/*
			 * syncconfig is invoked during the build stage.
			 * Suppress distracting "configuration written to ..."
			 */
			conf_set_message_callback(NULL);
			sync_kconfig = 1;
			break;

conf_set_message_callback(NULL) 关闭"配置已写入 xxx"的提示——因为构建阶段每次 make 都可能触发 syncconfig，吵人。sync_kconfig=1 后面会强制写 auto.conf。

scripts/kconfig/conf.c:705-724 写完 .config 再写 auto.conf

	} else if (input_mode != listnewconfig && input_mode != helpnewconfig) {
		if (!no_conf_write && conf_write(NULL)) {
			fprintf(stderr, "\n*** Error during writing of the configuration.\n\n");
			exit(1);
		}

		/*
		 * Create auto.conf if it does not exist.
		 // ... 省略 4 行注释
		 */
		if (conf_write_autoconf(sync_kconfig) && sync_kconfig) {
			fprintf(stderr,
				"\n*** Error during sync of the configuration.\n\n");
			return 1;
		}
	}

这是"两次写盘"：conf_write() 写 .config（人看的）；conf_write_autoconf() 写 auto.conf + autoconf.h（机器看的）。sync_kconfig 为 0 时若 auto.conf 已存在就跳过，这样 make menuconfig 之后普通 make 才不会重写。

scripts/kconfig/confdata.c:1041-1055 auto.conf 的生成

int conf_write_autoconf(int overwrite)
{
	struct symbol *sym;
	const char *name;
	const char *autoconf_name = conf_get_autoconfig_name();
	FILE *out, *out_h;
	int i;

	if (!overwrite && is_present(autoconf_name))
		return 0;

	conf_write_dep("include/config/auto.conf.cmd");

	if (conf_touch_deps())
		return 1;

	out = fopen(".tmpconfig", "w");
  • conf_write_dep("include/config/auto.conf.cmd")：写一份"auto.conf 依赖了哪些 Kconfig 文件"的 makefile 片段。这样改了某个 Kconfig，make 会自动重跑 syncconfig。
  • conf_touch_deps()：为每个 CONFIG_X=y 触碰一个空文件 include/config/X，让"某个头文件变了"能精确追踪到是哪个配置项导致的。

4.6 hello 模块：最小的可加载内核代码

仓库里没有 samples/hello/，但有更典型的 samples/kobject/——它既是一个模块，也演示了 init/exit 配对。我们节选其中真正决定"能不能加载"的部分：

samples/kobject/kobject-example.c:111-134 example_init

static int __init example_init(void)
{
	int retval;

	/*
	 * Create a simple kobject with the name of "kobject_example",
	 * located under /sys/kernel/
	//
	// ... 省略中间 5 行注释（说明为何不适合动态 kobject）
	 */
	example_kobj = kobject_create_and_add("kobject_example", kernel_kobj);
	if (!example_kobj)
		return -ENOMEM;

	/* Create the files associated with this kobject */
	retval = sysfs_create_group(example_kobj, &attr_group);
	if (retval)
		kobject_put(example_kobj);

	return retval;
}
  • __init：函数被放进 .init.text 段，启动完成后这段内存被释放——节省几百 KB 到几 MB 的常驻内存。
  • 返回 0 表示成功；返回负错误码（-ENOMEM）时，insmod 会打印 "insmod: ERROR: could not insert module ...: Cannot allocate memory"。
  • 失败路径里 kobject_put 是必须的，否则 sysfs 目录残留，再次 insmod 会因重名失败。

samples/kobject/kobject-example.c:136-143 exit 与注册

static void __exit example_exit(void)
{
	kobject_put(example_kobj);
}

module_init(example_init);
module_exit(example_exit);
MODULE_LICENSE("GPL v2");
  • __exit：放进 .exit.text；内置编译时这段会被丢弃（因为内置代码永不卸载），只有 CONFIG_MODULE_UNLOAD 且作为模块时才保留。
  • MODULE_LICENSE("GPL v2") 不是装饰：不写它，内核会打 "module verification failed: signature and/or required key missing - tainting kernel" 并标记内核被污染，而且拿不到 EXPORT_SYMBOL_GPL 的符号。

samples/kobject/Makefile:1-2 两行 Makefile 就够

# SPDX-License-Identifier: GPL-2.0-only
obj-$(CONFIG_SAMPLE_KOBJECT) += kobject-example.o kset-example.o

再配合 samples/Makefile:12 的 obj-$(CONFIG_SAMPLE_KOBJECT) += kobject/ 与 samples/Kconfig:41 的 config SAMPLE_KOBJECT / tristate "Build kobject examples"，一个目录的"配置—构建—产物"三元组就闭环了。答 m 得到 .ko，答 y 直接进 vmlinux。

如果你要写自己的最小模块，按同样的三元组做：

/* hello.c —— 不依赖 kobject，最小可加载模块 */
#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void)
{
	pr_info("hello: loaded, jiffies=%lu\n", jiffies);
	return 0;
}

static void __exit hello_exit(void)
{
	pr_info("hello: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL v2");
MODULE_DESCRIPTION("minimal hello module");

外部模块的 Makefile 必须写成"双人格"（源码里有官方范例，见 Documentation/kbuild/modules.rst:198-208）：

ifneq ($(KERNELRELEASE),)
# 被内核构建系统 include 时走这里
obj-m := hello.o
else
# 用户直接 make 时走这里
KDIR ?= /lib/modules/`uname -r`/build
default:
	$(MAKE) -C $(KDIR) M=$(PWD)
endif

KERNELRELEASE 是内核构建系统注入的环境变量。有这个变量说明"我被 Kbuild 调用了"，走 kbuild 语法；没有说明"我是用户在源码树外敲 make"，于是把自己转发给 M=$(PWD)。Documentation/kbuild/modules.rst:215-216 解释了这个检查的意义：同一个 Makefile 兼容两种入口。

6. 自测

Q1. obj-y 和 obj-m 最本质的区别是什么？obj-y 的目标文件被打进 built-in.a，最终链接进 vmlinux，代码常驻内核镜像，启动时就存在；obj-m 的目标文件走 .mod → modpost → .ko，运行时用 insmod/modprobe 才进内核，可卸载。同一个目标不允许同时在两者里（scripts/Makefile.lib:29 会用 filter-out 让 obj-y 获胜）。
Q2. 为什么 Makefile 里能写 obj-$(CONFIG_XXX) 而不写 if？因为 GNU Make 的变量名是"文本拼接"的：CONFIG_XXX 为空时整行变成 obj- += ...，而 obj- 是个没人用的变量名，追加进去也没人读，等价于"该行无效"。这是 Kbuild 最省事的条件编译手法。
Q3. 改了 .config 之后为什么必须重新 syncconfig？如果不做会怎样？因为 Makefile 读的不是 .config 而是 include/config/auto.conf 与 include/generated/autoconf.h。顶层 Makefile 第 709 行有"auto.conf 依赖 .config"的规则，make 会自动检测时间戳并触发 syncconfig；但如果你只改了 .config 又不跑 make，或者手工写错符号名，Kconfig 的依赖校验（depends on）不会被执行，可能编出"看起来成功但配置自相矛盾"的内核。
Q4. make M=dir 为什么快？因为 Makefile:1703-1708 在外部模块构建时把 KBUILD_BUILTIN 清空、把 build-dirs 换成 KBUILD_EXTMOD，于是递归只在你指定的目录发生，不产生 vmlinux，不遍历 drivers/。
Q5. 为什么要有 System.map，它和 vmlinux 里的符号表不是重复了吗？vmlinux 是带符号的 ELF，但很多符号地址在 KASLR（内核地址随机化）后会变化；System.map 是构建时生成的"链接期地址"快照，用于 nm/perf/崩溃解析工具在没有 vmlinux 的现场做符号化。而且 scripts/link-vmlinux.sh:364 的 cmp 校验保证 kallsyms 收敛，这是内核内自带的符号表能正确解码的前提。
