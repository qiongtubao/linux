🧱 块层：bio、请求队列与 blk-mq

把“读写某个文件的几页”翻译成“往某个设备发哪些扇区”，并排队排得聪明些 · 预计阅读 11 分钟

1. 它在解决什么问题

文件系统说的是“我要第 100 到 104 页”，却不懂设备说的是“第 2048 到 2051 号扇区、要不要 flush、优先级多少”。中间需要一层翻译与调度，这就是块层。它像快递公司的分拣中心：上游是各家网店（文件系统、swap、raw 设备），下游是各种运输工具（SATA 盘、NVMe、RAID 卡）。分拣中心要做的，是把大小不一的包裹（bio）合并成大件、按目的地装车（request），再交给司机（驱动）。

“排队排得聪明”就是 IO 调度器：机械盘怕随机寻道，所以要把相邻地址的读写排在一起（deadline、bfq）；SSD/NVMe 不怕寻道但怕队列饿着，所以要把请求尽快发出去（none、kyber）。5.10 已经没有老式单队列 elevator，全部是 blk-mq：每个 CPU 有软件队列，设备有若干硬件队列（hctx），请求在哪个 CPU 上产生就从哪个队列走，天然可扩展。

还有两个基础概念先分清：块设备以固定大小块（通常 512 或 4096 字节）随机访问，有页缓存、有文件系统，如 /dev/nvme0n1；字符设备按字节流，无缓存无寻址，如键盘、/dev/tty。本篇只讲块设备这条路。

2. 核心名词

术语英文一句话解释
基本 IO 单元bio一次块 IO 的描述：目标设备、起始扇区、长度、页向量、完成回调。
请求request调度单位：由一个或多个相邻 bio 合并而成，带 tag 号供硬件识别。
请求队列request_queue设备的 IO 队列，挂着 mq_ops、hctx 数组、调度器。
硬件队列hctxblk-mq 的每个硬件队列上下文，对应设备的一条提交通道。
软件队列blk_mq_ctx每 CPU 一个，暂存本 CPU 产生的请求，再派到 hctx。
标签tag请求在硬件队列中的槽位编号，队列深度决定最多同时多少请求。
plugplugging“先攒后发”：用 blk_start_plug 期间产生的 bio 先攒着，结束再一起下发，便于合并。
调度器elevator决定请求顺序的策略：mq-deadline、kyber、bfq、none。

3. 整体结构

文件系统 / swap / raw 读写
        │ submit_bio(bio)
        ▼
submit_bio_noacct：检查、防递归（current->bio_list）、IO 统计
        │
        ├─► __submit_bio_noacct_mq ─► blk_mq_submit_bio
        │                             │ 合并：plug 合并 / 调度器合并
        │                             │ 分配 request（tag）
        │                             ├─ 无调度器 → blk_mq_try_issue_directly
        │                             └─ 有调度器 → blk_mq_sched_insert_request
        │                                                     │
        ▼                                                     ▼
   驱动 .queue_rq(hctx, bd)  ◄── hctx dispatch ──►  硬件（SATA/NVMe/...）
        │
        ▼ 完成中断
   bio->bi_end_io → 文件系统回调（标页 Uptodate、end_page_writeback）

一次读的完整链条：页缓存未命中 → ext4 的 readpage 建 bio → submit_bio → 合并进已有 request 或新建 → 调度器排序 → 驱动把 request 变成硬件命令（SATA FIS / NVMe 命令）→ 完成中断 → bio_endio → 文件系统标 PageUptodate → 唤醒读线程。

“块设备 vs 字符设备”分辨方法：ls -l /dev/xxx 首字符 b 是块、c 是字符；块设备可 mount、能随机读写扇区，字符设备只能按字节流顺序使用。块层只管前者。

5.10 的调度器：mq-deadline（读写截止时间 + 排序，机械盘友好）、kyber（按延迟目标限流，快设备友好）、bfq（按进程公平分配带宽，桌面友好）、none（纯 FIFO，NVMe 默认）。多硬件队列时 elevator_get_default 直接返回 NULL（即 none），因为多队列下全局排序意义不大。

4. 源码走读

4.1 bio 里有什么

include/linux/blk_types.h:203-236 struct bio（节选）

struct bio {
	struct bio		*bi_next;	/* request queue link */
	struct gendisk		*bi_disk;
	unsigned int		bi_opf;		/* 低 bits 标志，高 bits REQ_OP */
	unsigned short		bi_flags;
	blk_status_t		bi_status;
	struct bvec_iter	bi_iter;	/* 当前扇区与剩余长度 */
	bio_end_io_t		*bi_end_io;	/* 完成回调 */
	void			*bi_private;
	unsigned short		bi_vcnt;	/* 有几个 bio_vec */
	unsigned short		bi_max_vecs;
	struct bio_vec		*bi_io_vec;	/* 页 + 页内偏移 + 长度 数组 */
	struct bio_set		*bi_pool;
	struct bio_vec		bi_inline_vecs[];   /* 小 bio 内联，省一次分配 */
};

关键在 bi_opf（操作类型读写/丢弃/flush + 标志）、bi_iter（当前处理到哪个扇区）、bi_io_vec（数据分布在哪些内存页）。bi_end_io 是完成时的回调，通常指向按页收尾的函数。

block/bio.c:437-460 bio_alloc_bioset（节选）

	if (!bs) {
		if (nr_iovecs > UIO_MAXIOV)
			return NULL;
		p = kmalloc(struct_size(bio, bi_inline_vecs, nr_iovecs), gfp_mask);
		front_pad = 0;  inline_vecs = nr_iovecs;
	} else {
		// ... 省略 mempool 分配与 rescuer 防死锁逻辑
		p = mempool_alloc(&bs->bio_pool, gfp_mask);
		front_pad = bs->front_pad;
		inline_vecs = BIO_INLINE_VECS;
	}
	bio = p + front_pad;

bio 从 bio_set（预分配的 mempool）里取，避免 IO 路径上因内存紧张失败；bi_inline_vecs 让少量页的 bio 与描述符一起分配，少一次 kmalloc。注释里还提到 rescuer workqueue：当上层在 submit_bio_noacct 之下递归分配 bio 时，防止把 mempool 耗尽而死锁。

4.2 提交与防递归

block/blk-core.c:1064-1087 submit_bio_noacct

	if (!submit_bio_checks(bio))
		return BLK_QC_T_NONE;

	if (current->bio_list) {
		/* 递归保护：已有 submit_bio 在处理，先收进队列 */
		bio_list_add(&current->bio_list[0], bio);
		return BLK_QC_T_NONE;
	}

	if (!bio->bi_disk->fops->submit_bio)
		return __submit_bio_noacct_mq(bio);  /* blk-mq 路径 */
	return __submit_bio_noacct(bio);         /* 传统单队列路径 */

current->bio_list 是“防递归栈”的替代品：设备栈叠（如 dm、md）时，每层都调 submit_bio 会把内核栈撑爆。做法是把后到的 bio 塞进链表，由最外层循环处理，把递归变成迭代。

block/blk-core.c:1014-1042 __submit_bio_noacct_mq

	struct bio_list bio_list[2] = { };
	blk_qc_t ret = BLK_QC_T_NONE;

	current->bio_list = bio_list;   /* 打开递归防护 */
	do {
		struct gendisk *disk = bio->bi_disk;
		if (unlikely(bio_queue_enter(bio) != 0))
			continue;
		if (!blk_crypto_bio_prep(&bio)) {
			blk_queue_exit(disk->queue);
			ret = BLK_QC_T_NONE;
			continue;
		}
		ret = blk_mq_submit_bio(bio);
	} while ((bio = bio_list_pop(&bio_list[0])));
	current->bio_list = NULL;
	return ret;

循环把本次提交期间新塞进来的 bio 也逐个处理。注意 bio_queue_enter 是队列“活跃引用”计数，防止提交途中队列被卸载。

4.3 blk_mq_submit_bio：合并与分派

block/blk-mq.c:2174-2245 blk_mq_submit_bio（节选）

	struct request_queue *q = bio->bi_disk->queue;
	// ...
	blk_queue_bounce(q, &bio);          /* DMA 地址受限时做 bounce */
	__blk_queue_split(&bio, &nr_segs);  /* 超过硬件上限就切分 */

	if (!bio_integrity_prep(bio))
		goto queue_exit;

	if (!is_flush_fua && !blk_queue_nomerges(q) &&
	    blk_attempt_plug_merge(q, bio, nr_segs, &same_queue_rq))
		goto queue_exit;                 /* 并进 plug 里的请求 */

	if (blk_mq_sched_bio_merge(q, bio, nr_segs))
		goto queue_exit;                 /* 并进调度器里的请求 */

	rq = __blk_mq_alloc_request(&data);  /* 从 tag 池取 request */
	// ...
	cookie = request_to_qc_t(data.hctx, rq);
	blk_mq_bio_to_request(rq, bio, nr_segs);
	// ... 省略 crypto 初始化

两条合并路径：plug 合并（本 CPU 攒着的请求里有地址相邻的就并进去）、调度器合并（已排队的请求里找相邻）。合并成功直接返回，cookie 即完成标识。合并失败才分配 request，分配失败时若带了 REQ_NOWAIT 就报 -EAGAIN，否则可能等待 tag。

block/blk-mq.c:2245-2280 blk_mq_submit_bio 的分派分支（节选）

	if (unlikely(is_flush_fua)) {
		blk_insert_flush(rq);              /* flush 直接特殊处理 */
		blk_mq_run_hw_queue(data.hctx, true);
	} else if (plug && (q->nr_hw_queues == 1 || q->mq_ops->commit_rqs ||
				!blk_queue_nonrot(q))) {
		// ... 省略：plug 累积，超过 BLK_MAX_REQUEST_COUNT 先 flush
		blk_add_rq_to_plug(plug, rq);
	} else if (q->elevator) {
		blk_mq_sched_insert_request(rq, false, true, true);   /* 进调度器 */
	} else if ((q->nr_hw_queues > 1 && is_sync) ||
			!data.hctx->dispatch_busy) {
		blk_mq_try_issue_directly(data.hctx, rq, &cookie);   /* 直接下发 */
	} else {
		blk_mq_sched_insert_request(rq, false, true, true);
	}

分派优先级：flush 请求走专门路径（需要等待前序写完成）；plug 存在且设备适合攒批（单队列、驱动支持批量提交、或机械盘）则先塞进 plug；有调度器就插进调度器；否则多队列同步请求或硬件不忙时直接下发给驱动，省一次派发延迟。

4.4 硬件队列与 CPU 的映射

block/blk-mq-cpumap.c:35-75 blk_mq_map_queues（节选）

	unsigned int *map = qmap->mq_map;
	unsigned int nr_queues = qmap->nr_queues;
	// ...
	for_each_present_cpu(cpu) {
		if (q >= nr_queues)
			break;
		map[cpu] = queue_index(qmap, nr_queues, q++);
	}
	for_each_possible_cpu(cpu) {
		if (map[cpu] != -1)
			continue;
		if (q < nr_queues) {
			map[cpu] = queue_index(qmap, nr_queues, q++);
		} else {
			first_sibling = get_first_sibling(cpu);
			if (first_sibling == cpu)
				map[cpu] = queue_index(qmap, nr_queues, q++);
			else
				map[cpu] = map[first_sibling];   /* 超线程共享队列 */
		}
	}

先把每个 present CPU 依次映射到不同队列，避免“死队列”（只被不可用 CPU 引用）；CPU 数多于队列数时，同一物理核上的超线程兄弟共享一个队列。驱动可提供自己的 map_queues（NVMe 就用 PCIe 的 NUMA 亲和映射），默认实现就是这一套。

设备的 request_queue（include/linux/blkdev.h:399）持有 queue_ctx（每 CPU 软件队列）、queue_hw_ctx（hctx 数组）、nr_hw_queues、elevator 与 mq_ops。hctx（include/linux/blk-mq.h:16）则持有派发链表、cpumask、sched_data。队列深度决定 tag 数，也就是“最多多少个请求同时在硬件里”。

4.5 调度器选谁

block/elevator.c:622-629 elevator_get_default

static struct elevator_type *elevator_get_default(struct request_queue *q)
{
	if (q->nr_hw_queues != 1)
		return NULL;                    /* 多硬件队列：默认 none */

	return elevator_get(q, "mq-deadline", false);
}

这一行解释了为什么新机器上 /sys/block/nvme0n1/queue/scheduler 常显示 [none]：NVMe 有几十个硬件队列，全局排序变成累赘。只有单队列设备（部分 SATA、virtio 单队列）才默认 mq-deadline。想换：echo bfq > /sys/block/sda/queue/scheduler，立即生效（部分调度器在切换时会重建队列）。

5. 动手验证

lsblk; ls -l /dev/nvme0n1 /dev/sda        # 首字符 b = 块设备
cat /sys/block/nvme0n1/queue/scheduler    # 形如 [none] mq-deadline kyber bfq
cat /sys/block/nvme0n1/queue/nr_requests  # 队列深度
cat /sys/block/nvme0n1/queue/rotational   # 1=机械 0=SSD/NVMe
ls /sys/block/nvme0n1/mq/                 # 每个 hctx 一个目录，内含 cpu_list

mq/0/cpu_list 显示这个硬件队列负责哪些 CPU 的提交，正是 blk_mq_map_queues 的结果。看 IO 统计：

iostat -x 1 3 | head -20          # 关注 r/s w/s, rkB/s, await, %util, aqu-sz
cat /proc/diskstats | grep nvme0n1

diskstats 每行字段依次是：主/次设备号、名字、读完成数、读合并数、读扇区数、读耗时(ms)、写完成数、写合并数、写扇区数、写耗时、IO 进行中、IO 总耗时、加权耗时。合并数高说明合并生效；aqu-sz（平均队列长度）接近队列深度说明打满。

压测并切换调度器：

sudo fio --name=randrw --filename=/tmp/fio.bin --size=1G --bs=4k \
  --rw=randread --iodepth=32 --numjobs=4 --runtime=20 --group_reporting
# 切换后重跑同一命令对比 IOPS
sudo sh -c 'echo none > /sys/block/<dev>/queue/scheduler'
grep -E '^nvme|^sda' /proc/diskstats

预期：NVMe 上 none 与 mq-deadline 差距不大；机械盘上随机读在 bfq/mq-deadline 下明显优于 none（后者会退化成几乎纯寻道）。fio 报告里的 iops、clat（完成延迟）、lat 分布就是调度器效果的量化。

6. 自测

Q1. bio 与 request 的区别？bio 描述“一段数据要读写到哪个设备的哪段扇区”；request 是调度与硬件提交单位，可由多个相邻 bio 合并，带 tag 号。
Q2. 为什么 submit_bio_noacct 要用 current->bio_list？设备栈叠时每层都调 submit_bio 会耗尽内核栈；把后续 bio 收进链表改由外层循环处理，把递归变成迭代。
Q3. blk-mq 的两个“队列”是什么关系？每 CPU 一个软件队列（blk_mq_ctx）收集本 CPU 请求，再按 map_queues 映射派发到硬件队列（hctx），每个 hctx 对应设备一条提交通道。
Q4. 5.10 中多队列设备为什么默认没有调度器？elevator_get_default 在 nr_hw_queues != 1 时返回 NULL（即 none）；多队列并行提交下全局排序收益低于开销。
Q5. diskstats 里的“合并数”说明什么？相邻 bio 被合并进同一 request 的次数。它高说明块层合并生效，能以更少的硬件命令传输更多数据。
