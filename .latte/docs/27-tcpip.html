🌐 27-tcpip TCP/IP 协议栈

一个字节如何从网卡爬到应用、又如何从应用掉回网卡；讲清 sk_buff 的指针戏法、TCP 握手状态机与拥塞控制 · 约 14 分钟

1. 它在解决什么问题

寄一封信，你不会只写正文就把它塞进邮筒。真实流程是：写信（应用数据）→ 装信封（TCP 段）→ 写收件地址（IP 包）→ 贴邮票、分拣、装车（以太网帧）→ 干线运输（网卡）。每一层只关心自己那层头的信息，下层把整包当"载荷"往上交，上层把载荷剥掉继续往上送。TCP/IP 协议栈干的就是这件事，只不过它不是比喻，而是真的在内存里一层层套头。

关键难点在效率。如果每加一层头就把整个包复制一遍，10 Gbps 网卡上每秒钟要做上亿次 memcpy，内核直接被拖垮。所以 Linux 用一个结构体 struct sk_buff 代表"一个包"，把整包数据放在一段连续的线性内存里，头部不是插进去的，而是在前面预留空地、各层用指针标记自己那份头的起点。剥头就是把 data 指针往后挪，插头就是把 data 指针往前挪——数据一个字节都不复制。

第二个难点是收包不能被慢速处理拖死。网卡每秒能收上百万帧，若每帧都同步走完整个协议栈，CPU 会被瞬间打满。Linux 的答案是 NAPI：中断只负责"打个招呼说我这儿有货"，真正的收包循环交给软中断（softirq）批量执行，还带一个预算（budget），一轮最多处理 N 个包，剩下的一半再排下一轮。这样即使某个包处理慢，也不会饿死其它 CPU。

第三个难点是TCP 是个状态机。同一段字节，在"连接还没建起来"和"连接已经建立"两种状态下含义完全不同：前者要拿来完成三次握手，后者是纯粹的数据。所以内核必须把收到的每个段先按状态分派（tcp_rcv_state_process），再走不同的处理逻辑。拥塞控制（cubic）则管的是"我该发多快"——发太快网络会堵死，发太慢带宽浪费。

3. 整体结构

3.1 报文头的嵌套

发送时一层层套头，接收时一层层剥头。以一个 HTTP 请求为例，最终上线的以太网帧长这样：

以太网帧 (Ethernet)
┌──────────────────────────────────────────────────────┐
│ 以太网头 (14B) │ IP 头 (20B) │ TCP 头 (20B) │ HTTP 数据 │
└──────────────────────────────────────────────────────┘
                    └────── IP 头 ──────┘
                            └──── TCP 头 ─────┘

内核里的内存布局（发送方向，data 指针在动）：

  head                data                 tail        end
   │                   │                    │          │
   ▼                   ▼                    ▼          ▼
   ┌───────────────────────────────────────────────────┐
   │ 预留区 │ 以太网头 │ IP头 │ TCP头 │ 负载数据      │  ← 一块连续内存
   └───────────────────────────────────────────────────┘
              ▲             ▲         ▲
              │             │         └── TCP 层数据起点（写入时）
              │             └──────────── IP 层认为的包起点
              └────────────────────────── 以太网层包起点

接收方向完全相反：网卡交付的 skb 里 data 指向以太网卡头，IP 层用 skb_pull 剥掉 14 字节以太头后 data 指向 IP 头；TCP 层再剥 20 字节 TCP 头，data 最终指向应用数据。剥头 = data 指针右移；插头 = data 指针左移，全程零拷贝。

为什么要分快慢两条路？ESTABLISHED 是绝大多数包的去处，那条路上只做必要校验、找 socket、入队；握手和拆除连接是罕见事件，逻辑复杂得多。走慢路径不影响快路径的吞吐。

注意这条链是自上而下、和接收完全相反。发送方向的头部是先申请空间再填内容（skb_push），接收方向是剥头（skb_pull），这就是"只挪指针不拷贝"的具体落地。

3.4 TCP 状态机与三次握手

  被动方（server）                主动方（client）
  ────────────────                ────────────────
  CLOSED ──listen()──► LISTEN
                          │                  CLOSED ──connect()──► SYN_SENT
                          │  ◄───── SYN ────────────────┐  发 SYN，seq=x
                          │                              │
                          │  ────── SYN+ACK ────────────►│  回 SYN+ACK，seq=y, ack=x+1
                          │        ack=x+1               │
                          │  ◄───── ACK ─────────────────┘  发 ACK，ack=y+1
                          ▼                              ▼
                      SYN_RECV                       ESTABLISHED
                          │  收到 ACK 后                 │
                          ▼                              ▼
                     ESTABLISHED ◄───────────────── ESTABLISHED
                       （收到第三次 ACK 后转正）

三次而不是两次，是为了让双方都确认对方的收发能力，同时交换初始序号（ISN）。服务端回 SYN+ACK 时其实已经把"我收到了你的 SYN"编码进了 ACK 号里，所以第三次 ACK 是客户端确认"我收到了你的 SYN+ACK"。ISN 随机化则防止旧连接的迟到报文污染新连接。

3.5 拥塞控制的位置

TCP 有两个独立的限速阀：接收窗口（对端告诉我能收多少，是被动的，由 TCP 协议栈自动通告）和拥塞窗口 cwnd（我自己判断网络能承受多少，是主动的，由拥塞控制算法维护）。实际在途字节数受两者较小值限制。Linux 默认的拥塞控制算法是 CUBIC（net/ipv4/tcp_cubic.c），它用一条三次方曲线代替 Reno 的线性增长，在高带宽时能更快铺满链路。

4. 源码走读

4.1 sk_buff：四个指针划出整块内存

这是全篇最重要的结构。sk_buff 本身不装数据，它只是一串"元数据 + 四个指针"，真正的数据在别处的内存里。

include/linux/skbuff.h:911-917

	/* These elements must be at the end, see alloc_skb() for details.  */
	sk_buff_data_t		tail;
	sk_buff_data_t		end;
	unsigned char		*head,
				*data;
	unsigned int		truesize;
	refcount_t		users;

head 是这块线性内存的最开头，end 是最末尾；tail 指向有效数据的最后一个字节的下一位，data 指向"当前协议层认为的数据起点"。发送时 data 往左跑（预留头部空间），接收时 data 往右跑（剥掉已处理的头）。truesize 是真实占用（含 slab 头等开销），用于内存统计；users 是引用计数，多个 skb 可能共享同一块数据（如 GSO 分割、skb_clone）。

这两个宏就是"零拷贝"的全部秘密：

include/linux/skbuff.h:2285-2299

void *skb_push(struct sk_buff *skb, unsigned int len);
static inline void *__skb_push(struct sk_buff *skb, unsigned int len)
{
	skb->data -= len;
	skb->len  += len;
	return skb->data;
}

void *skb_pull(struct sk_buff *skb, unsigned int len);
static inline void *__skb_pull(struct sk_buff *skb, unsigned int len)
{
	skb->len -= len;
	BUG_ON(skb->len < skb->data_len);
	return skb->data += len;
}

__skb_push 把 data 指针左移 len 字节（腾出头部空间），__skb_pull 把 data 指针右移（吃掉已解析的头）。两者都只改指针和长度计数，一个字节的数据都没动。BUG_ON(skb->len < skb->data_len) 是防呆：data_len 是分片到非线性区的部分，剥过头会让长度算错。

4.2 收包入口：NAPI 与 netif_receive_skb

网卡收包不是每个包一次中断。驱动在中断里只做"登记"，真正的批量取包在软中断里做。

net/core/dev.c:5583-5593

int netif_receive_skb(struct sk_buff *skb)
{
	int ret;

	trace_netif_receive_skb_entry(skb);

	ret = netif_receive_skb_internal(skb);
	trace_netif_receive_skb_exit(ret);

	return ret;
}

这是个薄壳，实质工作在 netif_receive_skb_internal（dev.c:5508）：先做时间戳处理，然后在 RCU 读侧临界区里调 __netif_receive_skb。RCU 的作用是让"当前挂在这个 hook 上的协议处理器列表"在遍历期间不会被释放——挂载/卸载 netfilter hook 时可以并发进行。

真正决定"这个包交给谁"的地方在 __netif_receive_skb_core：它遍历 ptype_all 链表，按 skb->protocol（以太网头里的 EtherType，0x0800 表示 IPv4）找到对应协议的处理函数。IPv4 对应的就是 ip_rcv。

net/core/dev.c:6740-6768

static int napi_poll(struct napi_struct *n, struct list_head *repoll)
{
	void *have;
	int work, weight;

	list_del_init(&n->poll_list);

	have = netpoll_poll_lock(n);

	weight = n->weight;

	work = 0;
	if (test_bit(NAPI_STATE_SCHED, &n->state)) {
		work = n->poll(n, weight);
		trace_napi_poll(n, work, weight);
	}

	if (unlikely(work > weight))
		pr_err_once("NAPI poll function %pS returned %d, exceeding its budget of %d.\n",
			    n->poll, work, weight);

	if (likely(work < weight))
		goto out_unlock;

n->weight 就是 NAPI 的预算：驱动一次 poll 最多交出 weight 个包。交满了说明网络很忙，NAPI 实例被放回 repoll 队列下一轮继续；没交满说明网络闲，可以歇着。这就是"用一半 CPU 处理千兆流量"的老办法。

4.3 IP 层入口：ip_rcv

net/ipv4/ip_input.c:527-542

/*
 * IP receive entry point
 */
int ip_rcv(struct sk_buff *skb, struct net_device *dev, struct packet_type *pt,
	   struct net_device *orig_dev)
{
	struct net *net = dev_net(dev);

	skb = ip_rcv_core(skb, net);
	if (skb == NULL)
		return NET_RX_DROP;

	return NF_HOOK(NFPROTO_IPV4, NF_INET_PRE_ROUTING,
		       net, NULL, skb, dev, NULL,
		       ip_rcv_finish);
}

ip_rcv_core（ip_input.c:435 起）干的是脏活：验证版本号和头长 ihl、做 IP 头校验和（ip_fast_csum）、按 tot_len 裁掉链路层填充、检查分片。校验和错了直接丢包并记 IPSTATS_MIB_CSUMERRORS。

NF_HOOK 是 netfilter 的第一个挂载点（NF_INET_PRE_ROUTING），包在这里会经过 iptables 的 mangle/raw 表再继续。防火墙细节见第 28 篇。

	int dif = inet_iif(skb);

		goto bad_packet;

	 * Packet length and doff are validated by header prediction,
	 * provided case of th->doff==0 is eliminated.
	 * So, we defer the checks. */

		goto csum_error;

几个关键动作：pskb_may_pull 保证 TCP 头已经在线性区（否则得先把分片搬过来）；skb_checksum_init 校验 TCP 校验和（伪首部含 IP 地址，所以函数名带 inet_compute_pseudo）；__inet_lookup_skb 用四元组（源 IP、源端口、目的 IP、目的端口）在哈希表里找对应的 socket。找不到就是 no_tcp_socket，通常回 RST。

__inet_lookup_skb 是这条路径上最贵的一步，所以内核专门为它做了头部预测（header prediction）：常见情况下（比如连接数不多）能直接猜出 socket 指针，省掉哈希计算。

4.5 状态分派：tcp_rcv_state_process

这是三次握手真正发生的地方。

net/ipv4/tcp_input.c:6303-6345

int tcp_rcv_state_process(struct sock *sk, struct sk_buff *skb)
{
	struct tcp_sock *tp = tcp_sk(sk);
	struct inet_connection_sock *icsk = inet_csk(sk);
	const struct tcphdr *th = tcp_hdr(skb);
	struct request_sock *req;
	int queued = 0;
	bool acceptable;

	switch (sk->sk_state) {
	case TCP_CLOSE:
		goto discard;

	case TCP_LISTEN:
		if (th->ack)
			return 1;

		if (th->rst)
			goto discard;

		if (th->syn) {
			if (th->fin)
				goto discard;
			/* It is possible that we process SYN packets from backlog,
			 * so we need to make sure to disable BH and RCU right there.
			 */
			rcu_read_lock();
			local_bh_disable();
			acceptable = icsk->icsk_af_ops->conn_request(sk, skb) >= 0;
			local_bh_enable();
			rcu_read_unlock();

			if (!acceptable)
				return 1;
			consume_skb(skb);
			return 0;
		}
		goto discard;

	case TCP_SYN_SENT:
		tp->rx_opt.saw_tstamp = 0;
		tcp_mstamp_refresh(tp);
		queued = tcp_rcv_synsent_state_process(sk, skb, th);

三个分支正好对应三次握手的三个角色：

  • TCP_LISTEN（被动方）：收到 SYN 就调 conn_request，即 tcp_conn_request（tcp_input.c:6743）。它会创建 request_sock（半连接对象）、协商 MSS/时间戳选项、算好 ISN，然后回 SYN+ACK。
  • TCP_SYN_SENT（主动方）：收到 SYN+ACK 时进 tcp_rcv_synsent_state_process（tcp_input.c:6032），校验 ACK 号合法性后转 ESTABLISHED，并回第三个 ACK。
  • TCP_SYN_RECV：服务端收到第三次 ACK 后转 ESTABLISHED，代码在 tcp_input.c:6388 起的 case TCP_SYN_RECV: 分支，末尾执行 tcp_set_state(sk, TCP_ESTABLISHED)。

注意 local_bh_disable()：conn_request 可能做路由查找等能睡眠的操作，而此时可能处在软中断上下文，必须显式禁止下半部抢占以免死锁。

4.6 发送路径：tcp_sendmsg → ip_queue_xmit → dev_queue_xmit

net/ipv4/tcp.c:1529-1539

int tcp_sendmsg(struct sock *sk, struct msghdr *msg, size_t size)
{
	int ret;

	lock_sock(sk);				/* 获取socket锁，防止软中断和其他进程并发访问 */
	ret = tcp_sendmsg_locked(sk, msg, size);	/* 调用核心发送函数 */
	release_sock(sk);			/* 释放socket锁 */

	return ret;
}

lock_sock 拿的是 socket 的自旋锁，保护 socket 状态机不被软中断并发修改。注意它不是互斥锁——发送路径不允许睡眠。

net/ipv4/ip_output.c:651-655

int ip_queue_xmit(struct sock *sk, struct sk_buff *skb, struct flowi *fl)

__ip_queue_xmit（ip_output.c:546）做三件事：查路由（ip_route_output_ports，决定从哪个网卡出去）、填 IP 头（skb_push(skb, sizeof(struct iphdr)) 后写版本、TTL、协议号、地址）、交给 netfilter（ip_local_out）。

net/ipv4/ip_output.c:605-619

	/* OK, we know where to send it, allocate and build IP header. */
	/* 在skb头部预留IP头部空间（20字节基本头部+可选IP选项） */
	skb_push(skb, sizeof(struct iphdr) + (inet_opt ? inet_opt->opt.optlen : 0));
	skb_reset_network_header(skb); /* 重置网络层头部指针 */
	iph = ip_hdr(skb);
	/* 设置IP头部：版本号(4) + 头部长度(5*4=20字节) + TOS字段 */
	*((__be16 *)iph) = htons((4 << 12) | (5 << 8) | (tos & 0xff));
	/* 设置分片标志：DF位禁止中间路由器分片（用于PMTU发现） */
	if (ip_dont_fragment(sk, &rt->dst) && !skb->ignore_df)
		iph->frag_off = htons(IP_DF);
	else
		iph->frag_off = 0;
	iph->ttl      = ip_select_ttl(inet, &rt->dst); /* TTL生存时间 */
	iph->protocol = sk->sk_protocol; /* 上层协议号（TCP=6, UDP=17） */
	ip_copy_addrs(iph, fl4); /* 拷贝源地址和目标地址 */

skb_push 把 data 指针左移 20 字节，腾出 IP 头的位置——数据本身一个字节没动。*((__be16 *)iph) = htons(...) 一行写了三个字段：版本号 4（高 4 位）、头长度 5（以 4 字节为单位，即 20 字节）、TOS。

__dev_queue_xmit（dev.c:4064）是发送的最后一站，它取出网卡对应的 qdisc 并把 skb 交给它排队：

qdisc（队列规则）是发送侧的交通管制器：pfifo_fast 是默认的简单 FIFO；sfq 做公平排队；htb/netem 能限速和模拟丢包。__dev_xmit_skb（dev.c:3742）里如果 qdisc 标记了 TCQ_F_CAN_BYPASS 且队列为空，就跳过排队直接发（work-conserving 直通），省一次入队出队。Linux 的 qdisc 全部在 net/sched/，注册表是 struct Qdisc_ops（net/sched/sch_api.c:130 的 register_qdisc）。

4.7 拥塞控制：cubic 是怎么被选中的

net/ipv4/tcp_cong.c:156-175

/* Assign choice of congestion control. */
void tcp_assign_congestion_control(struct sock *sk)
{
	struct net *net = sock_net(sk);
	struct inet_connection_sock *icsk = inet_csk(sk);
	const struct tcp_congestion_ops *ca;

	rcu_read_lock();
	ca = rcu_dereference(net->ipv4.tcp_congestion_control);
	if (unlikely(!bpf_try_module_get(ca, ca->owner)))
		ca = &tcp_reno;
	icsk->icsk_ca_ops = ca;
	rcu_read_unlock();

	memset(icsk->icsk_ca_priv, 0, sizeof(icsk->icsk_ca_priv));
	if (ca->flags & TCP_CONG_NEEDS_ECN)
		INET_ECN_xmit(sk);
	else
		INET_ECN_dontxmit(sk);
}

每个 socket 在创建时通过 tcp_assign_congestion_control 选定自己的拥塞控制算法，存进 icsk_ca_ops。选中的那个是网络命名空间级别的（net->ipv4.tcp_congestion_control），可以用 sysctl net.ipv4.tcp_congestion_control 改。找不到模块时降级到 tcp_reno。

算法本体是一张函数表：

net/ipv4/tcp_cubic.c:482-492

static struct tcp_congestion_ops cubictcp __read_mostly = {
	.init		= bictcp_init,
	.ssthresh	= bictcp_recalc_ssthresh,
	.cong_avoid	= bictcp_cong_avoid,
	.set_state	= bictcp_state,
	.undo_cwnd	= tcp_reno_undo_cwnd,
	.cwnd_event	= bictcp_cwnd_event,
	.pkts_acked     = bictcp_acked,
	.owner		= THIS_MODULE,
	.name		= "cubic",
};

.cong_avoid 是核心：每次收到 ACK 时被调用，按 CUBIC 公式算出新的 cwnd。.ssthresh 在检测到丢包时计算新的慢启动门限。编译期默认值由 Kconfig 决定（net/ipv4/Kconfig:733 是 default "cubic"）。

6. 自测

Q1. sk_buff 的 head/data/tail/end 四个指针分别指什么？head 是线性内存块的起点，end 是终点；data 是当前协议层认为的数据起点（发送时左移预留头，接收时右移剥头），tail 是有效数据末尾的下一位。
Q2. 为什么剥协议头不需要 memcpy？因为整个包的数据在一段连续内存里，各层头都靠 data 指针的位置来界定。__skb_pull 只做 skb->data += len 和长度计数，__skb_push 只做 skb->data -= len，一个字节的数据都不复制。
Q3. NAPI 的 weight 是什么概念？是单次 poll 的处理预算，驱动最多交出 weight 个包。交满说明网络忙，NAPI 实例被放回复处理队列下一轮继续；没交满说明空闲。这让内核能"用一半 CPU 处理千兆流量"。
Q4. tcp_v4_rcv 里为什么要先做 pskb_may_pull？保证 TCP 头完整落在 skb 的线性区内。若头部分散在分片区，必须先把数据搬过来才能安全读取头字段，否则会读到无效内存。
Q5. tcp_rcv_state_process 的 TCP_LISTEN 分支做了什么？收到 SYN 后调用 conn_request（tcp_conn_request），创建半连接 request_sock、协商选项、计算 ISN，并回发 SYN+ACK。整个过程在 local_bh_disable() 保护下进行，因为路由查找可能睡眠而此时可能处于软中断上下文。
Q6. cwnd 和接收窗口有什么区别？接收窗口是对端通告的，反映接收方缓冲能力，TCP 协议栈自动维护；cwnd 是本地拥塞控制算法根据网络拥塞状况估算的。实际在途数据受两者较小值限制。
Q7. __ip_queue_xmit 里 skb_push 的作用是什么？把 data 指针左移 20 字节（加上可选 IP 选项长度）在内存前方腾出空间，然后就地填写 IP 头。既不拷贝数据，也不需要预先精确分配每个头部的空间。
Q8. qdisc 位于发送路径的哪一步？在 IP 层填完头之后、驱动真正发包之前。__dev_queue_xmit 把 skb 交给网卡的 qdisc 排队，qdisc 决定排队顺序、限速、整形；队列为空且允许直通时会跳过排队直接发送。
