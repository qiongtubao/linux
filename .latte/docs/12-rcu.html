🔄 RCU：读多写少的无锁革命

用“复制 + 延迟回收”换掉读侧加锁：宽限期、静止态与 RCU 链表 · 预计阅读 24 分钟

1. 它在解决什么问题

图书馆要换一本旧杂志的封面。管理员不能一把抽走：也许正有读者捧着这一本，看到第 30 页。抽走的话，读者手里的纸页可能已经被扔进碎纸机——他再翻一页就等于读到了被回收的内存。管理员的做法是：把新杂志放上架，旧杂志照样留在架上，只是登记“旧的那本待回收”；等确认没有读者还在看旧的那本了，再把它扔掉。

内核里到处是这种“读多写少”的结构：路由表、进程表、目录项缓存、模块列表、网络设备的哈希桶……它们的共同特点是读操作远远多于写操作。传统做法是用读写锁（rwsem）：读者也要拿锁（一次原子操作 + 一次计数），写者要等所有读者退出才能改。读者那么多、写得那么少，这笔开销实在不划算。

RCU（Read-Copy-Update，读-拷贝-更新）的思路是把成本从读侧搬到写侧和回收侧，分成三步：

  1. 读侧完全不加锁。读者只做一件极轻的事：记一下“我正在读”（rcu_read_lock()）。它不是一把会互斥的锁，只是一个计数器加一条屏障。
  2. 写者复制一份再改。写者不原地修改共享结构，而是构造一份新的副本，在副本上改好，然后用一条带内存屏障的写（rcu_assign_pointer()）把“大家该看哪一份”的指针切换过去。
  3. 旧数据延迟回收。旧的那份不能立刻 kfree()——可能还有读者正捧着它。写者把它交给 RCU（call_rcu() 或 kfree_rcu()），RCU 等到“所有可能捧着旧数据的读者都放下”了，再执行真正的释放。

“所有可能捧着旧数据的读者都放下了”这个时刻，就是 RCU 的核心概念——宽限期（grace period）。宽限期怎么定义？答案是：等到每一颗 CPU 都至少报告过一次“静止态”（quiescent state）。静止态的含义是“此刻这颗 CPU 上没有正在进行的 RCU 读侧临界区”。一旦所有 CPU 都报告过静止态，说明没有任何读者可能还持有旧指针了，旧数据才可以安全释放。

RCU 不是免费的：写者变贵（要复制）、内存占用变大（老数据要等宽限期）、释放变成异步的（回调在软中断或内核线程上下文跑）、而且不能随手 free()（必须走 kfree_rcu()）。所以内核的规矩是：只有当更新率大约 10% 以下时才考虑用 RCU，否则老老实实用读写锁或普通锁。

3. 整体结构

3.1 三个阶段

  读侧（几乎零成本）                写侧                        回收侧
  ────────────────              ─────────                    ─────────
  rcu_read_lock()                复制一份新对象              call_rcu()/
    ↓ 标记“我在读”                在副本上修改                  kfree_rcu()
  ptr = rcu_dereference(p)         ↓                           挂进回调队列
    ↓ 读出当前指针               rcu_assign_pointer(p, new)    ↓
  ... 用 ptr ...                   ↓ 发布新指针              等一个宽限期
    ↓                           synchronize_rcu()  ← 可选       ↓
  rcu_read_unlock()                ↓ 等宽限期              宽限期结束
    ↓ 报告静止态                （此刻才能安全 free 旧对象）   ↓
                                                          真正 free(old)

3.2 宽限期与静止态（时序图）

时间 ───────────────────────────────────────────────────────────►

 CPU0            CPU1            CPU2         写者
  │               │               │            │
  │ rcu_read_lock │               │            │
  │ ptr = OLD     │               │            │  此刻 CPU0 手上有旧指针
  │ ... 用 OLD .. │               │            │
  │ rcu_read_unlock               │            │  ← CPU0 报告静止态(QS)
  │  → QS#1       │               │            │
  │               │               │            │  synchronize_rcu()
  │               │               │            │  ← 宽限期开始(GP start)
  │               │ rcu_read_lock │            │
  │               │ ptr = NEW     │            │  ← 发布之后进入的读者
  │               │ ... 用 NEW .. │            │     只会看到新指针
  │               │ rcu_read_unlock│            │
  │               │  → QS#2       │            │
  │               │               │ ← 一直空闲  │
  │               │               │  → QS#3     │  (空闲 CPU 立刻报告)
  │               │               │            │
  │        ┌──────────────────────────────────────────────┐
  │        │ 全部 CPU 都报告过 QS → 宽限期结束              │
  │        │ 现在 free(OLD) 是安全的：没有任何读者还握着它 │
  │        └──────────────────────────────────────────────┘
关键推论：CPU0 在写者发布新指针之前就进入了读侧临界区，它读到的是旧指针 OLD。只要宽限期覆盖了“CPU0 进入临界区”到“CPU0 报告静止态”这段路，写者就不能在宽限期内 free(OLD)。反过来，任何在发布之后才进入的读者都只会看到 NEW。这就是 RCU 正确性的全部。

3.3 读侧怎么报告静止态

“静止态”这个词听起来很玄，其实只取决于内核配置：

实现读者行为何时报告 QS
PREEMPT_RCU（抢占式）只做 ++current->rcu_read_lock_nesting最外层 rcu_read_unlock() 时报告；若中途被抢占，由上下文切换路径补报
TREE_RCU / TINY_RCU（非抢占式）preempt_disable()，读者期间不能被抢占退出临界区、重新允许抢占的那一刻

差别很大：抢占式 RCU 里读者可以被踢下 CPU，但代价是“报告静止态”的时机变复杂（被抢占的任务什么时候算 QS？答案是它重新被调度回来的时候）。非抢占式 RCU 里读者一退出临界区就立刻报告，简单得多，但读者期间不能被抢占（对延迟不利）。

3.4 RCU 链表：删除之后为什么不能马上 free

写者删除元素 B：
   list_del_rcu(&B->list);        ← B 从链表里摘掉了
   ...                                ← 但 B 本身还占着内存！
   kfree_rcu(B, rcu);                 ← 真正的释放推迟到宽限期之后

读者遍历链表：
   rcu_read_lock();
   list_for_each_entry_rcu(pos, &head, list) {
           use(pos);        ← 这个 pos 可能正指向 B！
   }
   rcu_read_unlock();

如果写者摘掉 B 之后立刻 kfree(B)：
   读者可能刚拿到 pos=&B，还没来得及 use(pos) → 访问已释放内存 → use-after-free。
如果用 kfree_rcu(B)：
   宽限期保证“所有可能在遍历 B 的读者都已退出”→ 此时 free(B) 才安全。

3.5 什么时候不该用 RCU

内核官方检查清单（Documentation/RCU/checklist.rst）第一条就写着：如果数据结构被更新的频率超过大约 10%，应该认真考虑别的方案，因为 RCU 是用写侧和内存的开销换读侧的开销。另外，RCU 读侧临界区里不能睡眠（非抢占式内核里绝对不行，抢占式也只允许阻塞那些支持优先级继承的锁），也不能做可能长时间等待的操作。

4. 源码走读

4.1 rcu_read_lock：读者的全部动作

include/linux/rcupdate.h:637-644 rcu_read_lock

static __always_inline void rcu_read_lock(void)
{
	__rcu_read_lock();
	__acquire(RCU);
	rcu_lock_acquire(&rcu_lock_map);
	RCU_LOCKDEP_WARN(!rcu_is_watching(),
			 "rcu_read_lock() used illegally while idle");
}

读者侧的“加锁”就这么点东西：__rcu_read_lock()（不同 RCU 实现不同）、给 sparse 用的注解、给 lockdep 用的记账。没有任何原子读-改-写，没有获取/释放语义，不会阻塞任何其他 CPU。这就是 RCU 读侧快的全部秘密。

抢占式实现里，__rcu_read_lock() 仅仅是个计数：

kernel/rcu/tree_plugin.h:374-383 __rcu_read_lock

void __rcu_read_lock(void)
{
	rcu_preempt_read_enter();
	if (IS_ENABLED(CONFIG_PROVE_LOCKING))
		WARN_ON_ONCE(rcu_preempt_depth() > RCU_NEST_PMAX);
	if (IS_ENABLED(CONFIG_RCU_STRICT_GRACE_PERIOD) && rcu_state.gp_kthread)
		WRITE_ONCE(current->rcu_read_unlock_special.b.need_qs, true);
	barrier();  /* critical section after entry code. */
}
EXPORT_SYMBOL_GPL(__rcu_read_lock);

rcu_preempt_read_enter() 就是 ++current->rcu_read_lock_nesting（见 kernel/rcu/tree_plugin.h:353-356）。最后那行 barrier() 是编译器屏障：保证“进入临界区”这条语句不会被编译器重排到临界区内部代码之后。这是第 13 篇要展开的话题。

4.2 rcu_read_unlock：报告静止态

include/linux/rcupdate.h:689-696 rcu_read_unlock

static inline void rcu_read_unlock(void)
{
	RCU_LOCKDEP_WARN(!rcu_is_watching(),
			 "rcu_read_unlock() used illegally while idle");
	__release(RCU);
	__rcu_read_unlock();
	rcu_lock_release(&rcu_lock_map); /* Keep acq info for rls diags. */
}

抢占式实现里，__rcu_read_unlock() 递减嵌套计数，只有最外层那次（计数减到 0）才算真正退出临界区：

kernel/rcu/tree_plugin.h:392-407 __rcu_read_unlock

void __rcu_read_unlock(void)
{
	struct task_struct *t = current;

	if (rcu_preempt_read_exit() == 0) {
		barrier();  /* critical section before exit code. */
		if (unlikely(READ_ONCE(t->rcu_read_unlock_special.s)))
			rcu_read_unlock_special(t);
	}
	if (IS_ENABLED(CONFIG_PROVE_LOCKING)) {
		int rrln = rcu_preempt_depth();

		WARN_ON_ONCE(rrln < 0 || rrln > RCU_NEST_PMAX);
	}
}
EXPORT_SYMBOL_GPL(__rcu_read_unlock);

rcu_read_unlock_special() 存在的理由是“任务在 RCU 读侧临界区里被抢占、切换走了”这种特殊情况——此时静止态要等到它被调度回来才报告。日常路径上它就是个空操作。

4.3 rcu_assign_pointer：发布

include/linux/rcupdate.h:414-423 rcu_assign_pointer

#define rcu_assign_pointer(p, v)					      \
do {									      \
	uintptr_t _r_a_p__v = (uintptr_t)(v);				      \
	rcu_check_sparse(p, __rcu);					      \
									      \
	if (__builtin_constant_p(v) && (_r_a_p__v) == (uintptr_t)NULL)	      \
		WRITE_ONCE((p), (typeof(p))(_r_a_p__v));		      \
	else								      \
		smp_store_release(&p, RCU_INITIALIZER((typeof(p))_r_a_p__v)); \
} while (0)

三个要点：

  • smp_store_release() 提供了 release 语义：保证“在调用 rcu_assign_pointer() 之前对副本做的所有修改，对之后读到该指针的读者都是可见的”。没有这条保证，读者可能拿到新指针却看到未初始化的新数据。
  • WRITE_ONCE() 只在赋值为 NULL 且是编译期常量时使用——那种情况下没有“发布顺序”需要保证。
  • rcu_check_sparse(p, __rcu) 让 sparse 静态检查器能验证“你确实用了 RCU 保护的指针”。

注意：rcu_assign_pointer() 只是发布，它不保证旧数据安全释放。旧数据的回收是另一件事。

4.4 rcu_dereference：读

include/linux/rcupdate.h:496-498 rcu_dereference_check

#define rcu_dereference_check(p, c) \
	__rcu_dereference_check((p), (c) || rcu_read_lock_held(), __rcu)

include/linux/rcupdate.h:550-556 rcu_dereference

/**
 * rcu_dereference() - fetch RCU-protected pointer for dereferencing
 * @p: The pointer to read, prior to dereferencing
 *
 * This is a simple wrapper around rcu_dereference_check().
 */
#define rcu_dereference(p) rcu_dereference_check(p, 0)

rcu_dereference() 做两件事：① 用正确的内存序读出指针（在 x86 上就是一条普通的 load，因为 x86 是强序模型；别的架构需要额外屏障）；② 顺便做一次合法性检查——c || rcu_read_lock_held() 表示“你要么持有某把更新侧的锁，要么正在 RCU 读侧临界区里”。如果两个条件都不满足（也就是在读侧临界区外裸读一个 RCU 指针），lockdep 会报 “rcu_dereference() used illegally”。

与之对称，写侧有一对 rcu_dereference_protected()（include/linux/rcupdate.h:546-547），用于“更新侧已经持有锁，值不会变”的场景，它连 READ_ONCE() 都省了。

4.5 synchronize_rcu：等一个宽限期

kernel/rcu/tree.c:3624-3637 synchronize_rcu

void synchronize_rcu(void)
{
	RCU_LOCKDEP_WARN(lock_is_held(&rcu_bh_lock_map) ||
			 lock_is_held(&rcu_lock_map) ||
			 lock_is_held(&rcu_sched_lock_map),
			 "Illegal synchronize_rcu() in RCU read-side critical section");
	if (rcu_blocking_is_gp())
		return;
	if (rcu_gp_is_expedited())
		synchronize_rcu_expedited();
	else
		wait_rcu_gp(call_rcu);
}
EXPORT_SYMBOL_GPL(synchronize_rcu);

逐行看：

  • 第一段是自我保护：如果你在 RCU 读侧临界区里调用 synchronize_rcu()，那是必死的（你在等所有读者退出，其中一个就是你自己）。lockdep 会提前抓住它并报 “Illegal synchronize_rcu() in RCU read-side critical section”。
  • rcu_blocking_is_gp()：如果当前这个 CPU 正在“阻塞式地参与宽限期”，直接返回即可。
  • rcu_gp_is_expedited()：加速宽限期（expedited grace period）是给“写者已经在等锁、必须尽快拿到结果”这种场景用的特殊路径（比如 rmmod 卸载模块时）。它不等待所有 CPU 报告静止态，而是直接让每个 CPU 执行一次上下文切换来强制报告。
  • wait_rcu_gp(call_rcu)：普通路径。发起宽限期，等待它结束，然后执行挂起的回调。

4.6 call_rcu：延迟回收

kernel/rcu/tree.c:3025-3029 call_rcu

void call_rcu(struct rcu_head *head, rcu_callback_t func)
{
	__call_rcu(head, func);
}
EXPORT_SYMBOL_GPL(call_rcu);

call_rcu() 把一个回调挂进当前 CPU 的回调链表，它会在下一个宽限期结束之后被执行（由 softirq 或 rcu_*_kthread 内核线程驱动）。执行时机是“回调所在的 CPU 恰好经历了一次宽限期结束”，所以它可能发生在你不期待的地方（比如中断上下文）——因此回调里不能睡眠。

4.7 RCU 链表：写侧

include/linux/rculist.h:85-95 __list_add_rcu

static inline void __list_add_rcu(struct list_head *new,
		struct list_head *prev, struct list_head *next)
{
	if (!__list_add_valid(new, prev, next))
		return;

	new->next = next;
	new->prev = prev;
	rcu_assign_pointer(list_next_rcu(prev), new);
	next->prev = new;
}

include/linux/rculist.h:113-116 list_add_rcu

static inline void list_add_rcu(struct list_head *new, struct list_head *head)
{
	__list_add_rcu(new, head, head->next);
}

关键在 rcu_assign_pointer(list_next_rcu(prev), new)：插入点的“next”指针是用发布语义写的。普通链表的 list_add() 直接写 prev->next = new，而 RCU 版本必须用 rcu_assign_pointer()，否则读者可能看到一个“半初始化”的新节点。

4.8 RCU 链表：读侧

include/linux/rculist.h:390-394 list_for_each_entry_rcu

#define list_for_each_entry_rcu(pos, head, member, cond...)		\
	for (__list_check_rcu(dummy, ## cond, 0),			\
	     pos = list_entry_rcu((head)->next, typeof(*pos), member);	\
		&pos->member != (head);					\
		pos = list_entry_rcu(pos->member.next, typeof(*pos), member))

读侧每走一步都用 list_entry_rcu()（内部是 READ_ONCE(ptr)）来取指针。配合 __list_check_rcu()，开了 CONFIG_PROVE_RCU_LIST 之后，如果你没有在 rcu_read_lock() 里就遍历 RCU 链表，内核会直接报 “RCU-list traversed in non-reader section!”。

4.9 kfree_rcu：为什么它比 call_rcu 更好用

include/linux/rcupdate.h:877-883 kfree_rcu

#define kfree_rcu(ptr, rhf)						\
do {									\
	typeof (ptr) ___p = (ptr);					\
									\
	if (___p)							\
		__kvfree_rcu(&((___p)->rhf), offsetof(typeof(*(ptr)), rhf)); \
} while (0)

很多 RCU 回调函数的内容就是一句 kfree()，但每个都要写一个独立的函数，还给模块卸载带来麻烦（模块卸载时必须调用高延迟的 rcu_barrier()）。kfree_rcu() 的聪明之处：它不存函数地址，而是存 rcu_head 在结构体里的偏移量。内核地址空间的低 4096 字节永远不会被分配，所以偏移量一定小于 4096，可以用一个整数塞进回调指针里——运行时再由 kvfree_call_rcu() 把它还原成偏移量并 free 掉。注释里写得很清楚：

 * The kfree_rcu() function handles this issue.  Rather than encoding a
 * function address in the embedded rcu_head structure, kfree_rcu() instead
 * encodes the offset of the rcu_head structure within the base structure.
 * Because the functions are not allowed in the low-order 4096 bytes of
 * kernel virtual memory, offsets up to 4095 bytes can be accommodated.

rcu_fanout_leaf   jiffies_till_first_fqs  rcu_min_cached_objs  rcu_resched_ns
dump_tree         rcu_kick_kthreads   use_softirq

$ cat /proc/sys/kernel/panic_on_rcu_stall
0

几个有用的：rcu_kick_kthreads（是否让宽限期内核线程忙轮询）、rcu_divisor（宽限期轮询频率）、use_softirq（回调在软中断还是内核线程里跑）。

关于 /sys/kernel/debug/rcu/：这个目录（含 stall_warnings）是 Linux 5.11 及以后才加进来的，5.10 没有。在 5.10 上想看 stall 警告，直接看 dmesg。

5.2 观察一个真实的宽限期

内核给 RCU 准备了一整套 tracepoint，开着 CONFIG_TRACEPOINTS（大多数发行版内核都开）就能看到宽限期的开始和结束：

# 列出可用的 RCU 事件
$ ls /sys/kernel/debug/tracing/events/rcu/
rcu_callback              rcu_invoke_callback
rcu_exp_grace_period      rcu_kvfree_callback
rcu_future_grace_period   rcu_nocb_wake
rcu_grace_period          rcu_preempt_task
rcu_grace_period_init     rcu_quiescent_state_report
rcu_invoke_kfree_bulk_callback  rcu_unlock_preempted_task
rcu_invoke_kvfree_callback

# 跟踪宽限期
$ cd /sys/kernel/debug/tracing
$ echo 1 > events/rcu/rcu_grace_period/enable
$ echo 1 > events/rcu/rcu_quiescent_state_report/enable
$ cat trace | head -40

典型输出会长这样：

              <...>-1409  [000] ...1 99999.999999: rcu_grace_period: ctxt=1
              <...>-1409  [000] ...1 99999.999999: rcu_quiescent_state_report: ctxt=1
              <...>-1409  [000] ...1 99999.999999: rcu_quiescent_state_report: ctxt=1
                 <idle>-0     [000] ...1 99999.999999: rcu_quiescent_state_report: ctxt=1
                 <idle>-0     [000] ...1 99999.999999: rcu_quiescent_state_report: ctxt=1
              <...>-1234   [002] ...1 99999.999999: rcu_quiescent_state_report: ctxt=1

读法：rcu_grace_period 是宽限期开始，rcu_quiescent_state_report 是每个 CPU 报告静止态。看到 N 颗 CPU 都报告了，宽限期就结束，之前挂起的 call_rcu 回调就会跑起来。

5.3 制造一次 RCU stall（可选，慎用）

# 一个 CPU 长时间不报告静止态 → 宽限期卡住
# 21 秒后内核会打印 stall 警告（默认值来自 CONFIG_RCU_CPU_STALL_TIMEOUT）
$ cat /proc/sys/kernel/panic_on_rcu_stall
0

# 把它设成 1，让 stall 直接 panic（调试用，会导致系统崩溃）
$ sudo sysctl -w kernel.panic_on_rcu_stall=1

典型的 stall 警告形如：

WARNING: RCU Stall Detected
detected stalls on CPUs/tasks:
	[0] rcu_preempt: 1-...: (rcu_read_lock_nesting) 49999 jiffies
	[1] kworker/1:1: (tasks) R

NMI backtrace for cpu 1
CPU: 1 PID: 0 Comm: swapper/1
Call Trace:
 <TASK>
 rcu_read_unlock_special+0x.../0x...

它会告诉你哪个 CPU、哪个任务卡在读侧临界区里出不来，以及它卡在哪一行调用栈上——这是排查“某个 CPU 长时间占着中断不放”类问题的利器。

5.4 用 rcutorture 给 RCU 做压力测试

RCU 自带一个“折磨测试”模块（kernel/rcu/rcutorture.c），它会开一堆读者线程和几个假的写者线程，不断地插入/删除/遍历，专门用来把 RCU 实现里的 bug 逼出来。Kconfig 名字是 CONFIG_RCU_TORTURE_TEST（kernel/rcu/Kconfig.debug:45）。

如果你的发行版内核带了这个模块，直接用：

$ sudo modprobe rcutorture
$ ls /sys/module/rcutorture/parameters/
extendables  fqs_duration  fqs_holdoff  fqs_stutter  fwd_progress  gp_cond
gp_exp  gp_normal  gp_sync  irqreader  leakpointer  n_barrier_cbs
nfakewriters  nreaders  object_debug  onoff_holdoff  onoff_interval
read_exit_delay  read_exit_burst  shuffle_interval  stall_cpu  stat_interval
stutter  test_boost  torture_type  verbose

$ cat /sys/module/rcutorture/parameters/nfakewriters
4
$ cat /sys/module/rcutorture/parameters/torture_type
rcu

$ dmesg | grep -i torture | tail -20
rcu: torture testing: fqs_duration=0 fqs_holdoff=0 fqs_stutter=3
rcu: Starting Rcupdate test with nreaders=4 nfakewriters=4
...

几个常用参数：nreaders（读者线程数，-1 表示每 CPU 一个）、nfakewriters（假写者数量）、torture_type（测 rcu 还是 srcu）、stutter（跑几秒停几秒）、stall_cpu（故意让某颗 CPU 卡住多少秒，用来验证 stall 检测器有效）。

如果没有这个模块，用 qemu + busybox 最小环境跑一个（这是编译内核的最小步骤）：

# 1) 在源码树里打开相关配置
$ scripts/config --enable DEBUG_KERNEL \
                  --enable RCU_TORTURE_TEST=m \
                  --enable RCU_CPU_STALL_TIMEOUT \
                  --disable MODULE_SIG \
                  --enable MODULE_SIG_FORCE
$ make olddefconfig
$ make -j$(nproc) bzImage modules

# 2) 准备一个 busybox 根文件系统
$ wget https://busybox.net/downloads/binaries/1.31.0-defconfig-multiarch-musl/busybox
$ chmod +x busybox
$ mkdir -p rootfs/{bin,dev,proc,sys,lib/modules}
$ cp busybox rootfs/bin/ && ln -s busybox rootfs/bin/sh
$ (cd rootfs && find . | cpio -o -H newhdr | gzip) > initramfs.cpio.gz

# 3) 用 qemu 启动
$ qemu-system-x86_64 -kernel arch/x86/boot/bzImage \
    -initrd initramfs.cpio.gz \
    -append "console=ttyS0 rdinit=/bin/sh" \
    -m 1024 -smp 4 -nographic

# 4) 在 busybox shell 里
/ # modprobe rcutorture
/ # cat /sys/module/rcutorture/parameters/nreaders
/ # dmesg | tail -30

为了让 torture 更有压力，可以调大读者数并加上“故意卡住某 CPU”的场景：

/ # echo 8 > /sys/module/rcutorture/parameters/nreaders
/ # echo 1 > /sys/module/rcutorture/parameters/stall_cpu
/ # echo 30 > /sys/module/rcutorture/parameters/stall_cpu_holdoff

6. 自测

Q1. RCU 和读写锁（rwsem）到底差在哪？读写锁的读者要拿锁：一次原子读-改-写 + 计数 + 屏障，多核读者之间虽然可以并发，但仍有写者要等所有读者退出。RCU 的读者完全不加锁，只做一个嵌套计数加一条编译器屏障；写者复制一份、改好、发布新指针；旧数据延迟到宽限期之后再释放。所以 RCU 的读侧几乎零成本，代价全在写侧（复制）和内存（老数据不能立刻回收）以及回收侧（异步回调）。
Q2. 什么是宽限期和静止态？宽限期是从写者发起 synchronize_rcu() 开始、到“所有可能持有旧指针的读者都退出”为止的一段时间。静止态（quiescent state）指“某颗 CPU 上此刻没有 RCU 读侧临界区”的一个瞬间。宽限期结束的判据是：每颗 CPU 都至少报告过一次静止态。非抢占式 RCU 在读者退出临界区、重新允许抢占时报告；抢占式 RCU 在最外层 rcu_read_unlock() 时报告，被抢占的情况由上下文切换路径补报。
Q3. 为什么 rcu_assign_pointer() 和 rcu_dereference() 不能用普通的赋值和读取代替？两个都是内存序问题。rcu_assign_pointer() 用 release 语义发布指针，保证“副本里的所有初始化对看到该指针的读者可见”；rcu_dereference() 用 acquire 语义读指针，保证“读到指针之后的读取不会被重排到指针读取之前”。用普通赋值/读取，编译器或 CPU 可能重排，读者就可能拿到“新指针 + 未初始化内容”，也就是经典的 release/acquire 失效。此外 rcu_dereference() 还带 lockdep 检查，会验证你确实在读侧临界区里。
Q4. list_del_rcu() 之后为什么必须用 kfree_rcu() 而不是直接 kfree()？因为读者可能正拿着刚被摘掉的节点的指针在遍历：list_for_each_entry_rcu() 逐步用 list_entry_rcu() 取 next，读者可能刚拿到指向 B 的指针，还没来得及用，B 就被 kfree() 掉了 → use-after-free。kfree_rcu() 把释放推迟到宽限期之后，保证那时已经没有读者能碰到 B。它的实现很巧：不在回调里存函数地址，而是存 rcu_head 在结构体中的偏移量（内核地址空间低 4096 字节不可分配，所以偏移量必然小于 4096），省掉了为每个类型写一个回调函数的开销。
Q5. 什么时候不该用 RCU？官方检查清单第一条：更新率超过大约 10% 就别用，因为 RCU 是拿写侧开销和内存开销换读侧开销，读写比例不悬殊时这笔买卖不划算。另外读侧临界区里不能睡眠（非抢占式内核里绝对禁止），也不能做可能长时间等待的操作。如果数据结构简单、访问不频繁，一把普通的 mutex 或 rwsem 往往更省事。
Q6. RCU stall 警告是什么意思？该找谁？意思是“某个 CPU 太久没有报告静止态，导致宽限期无法结束”，最常见的原因是某个任务在 RCU 读侧临界区里死循环、或者长时间关着中断/关着抢占。警告里会列出卡住的 CPU 号和任务名，还可能附带 NMI backtrace 指出它卡在哪一行。它的用途是定位“某个 CPU 长时间占着不放”这类问题（比如驱动里忘了开中断）。在 5.10 上这个警告通过 dmesg 查看；/sys/kernel/debug/rcu/stall_warnings 是 5.11 才加的。
