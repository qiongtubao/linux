🗺️ 02 · 内核源码树：3 万个文件怎么找你要的那一个

把 23 个顶层目录当成一座城市的行政区划——先会看地图，再动手挖路 · 预计阅读 22 分钟

1. 它在解决什么问题

假设你被骗到一座陌生的巨型城市，没有导航，只知道"我要找到供水公司的一个阀门"。你会怎么办？先看城市总图（有哪些行政区），再看区的职能（哪个区管供水），再看那个区里的街道门牌。内核源码也是这个道理：Linux 5.10 的源码树里约有 7 万个文件、3 万个 C 文件，谁也不可能记住每个文件在哪。你唯一能依靠的，是一套稳定的"空间组织逻辑"。

这套逻辑其实极其朴素：按"功能模块"划顶层目录，比如内存管理全在 mm/、文件系统全在 fs/、驱动全在 drivers/。然后在每个目录内部，再按"子系统—子系统内再分"递归切分。这就是操作系统视角下的"模块化内核"：内核不是一坨代码，而是几十个半独立子系统用少量公共接口缝合起来的整体。

学会这棵树有三个直接收益：① 看到一个函数名，能猜它大概在哪个目录（kmalloc 一定在 mm/，tcp_sendmsg 一定在 net/）；② 遇到 bug 时能找到"该看谁"（网络问题不看 fs/）；③ 知道该向谁提交补丁——这直接对应 MAINTAINERS 里的维护者机制。

本篇还会解决一个新手最常见的困惑：include/linux/ 和 include/uapi/ 到底有什么区别？搞错这一层，你会在写驱动时遇到"结构体字段对不上"的诡异问题。

3. 整体结构

3.1 一张"行政区划图"

linux/  (源码根)
├── arch/         CPU 架构相关：x86、arm64、riscv…（每个架构一套启动代码、中断、页表）
├── block/        块设备层：把"读写扇区"抽象成 bio 请求，供 ext4/NVMe 使用
├── certs/        内核签名用的证书（模块签名、安全启动）
├── crypto/       加密算法实现（AES、SHA、ChaCha20）与 crypto API
├── Documentation/ 文档（80+ 子目录，见 3.3）
├── drivers/      所有硬件驱动（2.87 万个文件，占源码树的 1/3）
├── fs/           文件系统：vfs 抽象层 + ext4/xfs/btrfs/overlayfs…
├── include/      头文件：linux/(内部) + uapi/(用户态) + asm-generic/…
├── init/         启动入口：main.c（start_kernel）、do_mounts.c
├── ipc/          进程间通信：信号量、共享内存、消息队列
├── kernel/       核心：调度器、中断管理、时间、锁、模块加载、trace
├── lib/          通用库函数：字符串、位图、红黑树、排序、CRC
├── mm/           内存管理：页分配器、slab、页表、回收、swap
├── net/          网络协议栈：socket 层、TCP/IP、netfilter、各种协议族
├── samples/      示例代码（kobject、kprobes、bpf、seccomp 的小 demo）
├── scripts/      构建/辅助脚本：Kbuild 规则、kconfig、checkpatch、dtc
├── security/     安全框架：LSM、SELinux、AppArmor、seccomp
├── sound/        音频子系统（ALSA 核心 + 各种声卡驱动）
├── tools/        用户态工具源码：perf、bpftool、selftests（不编进内核）
├── usr/          initramfs 的生成与打包（usr/initramfs_data.cpio）
└── virt/         虚拟化：KVM 的架构无关部分
    （另有 Kconfig / Makefile / MAINTAINERS / README / COPYING 等根文件）

这个划分有一个贯穿全局的隐喻：越靠上的目录越"抽象"，越靠下的越"具体"。fs/ 的 VFS 层不知道底下是 ext4 还是 xfs；mm/ 不知道调用它的是进程还是内核线程；block/ 不知道底下是 NVMe 还是 U 盘。这种"抽象层 + 具体实现"的分层，是内核能在 30 年里换掉无数硬件实现而接口不崩的根本原因。

3.2 每个顶层目录干什么（附文件数）

目录文件数职责你会因为什么进来
arch/15947架构相关代码。arch/x86/ 管 x86（含 32/64 位），arch/arm64/ 管 ARM 64 位。启动汇编、页表布局、中断控制器、SMP 启动都在这。看 head_64.S、查某个寄存器的定义、写架构相关驱动。

fs/1994文件系统：fs/open.c 是 open 系统调用实现，fs/ext4/ 是 ext4 全部实现，fs/proc/ 是 /proc。调文件系统 bug、理解 path walk、写新 FS。
include/5417头文件：linux/（1357 个内部头）、uapi/（544 个用户态头）、asm-generic/、net/、trace/ 等。找结构体定义、找函数声明、写模块时 include。
init/12启动：main.c（start_kernel）、do_mounts.c（挂根）、initramfs.c（解包 initramfs）。追启动流程、改 initcall、看 rootfs 挂载。
ipc/13老式 IPC：System V 信号量/共享内存/消息队列，以及 POSIX mqueue。查 shmget/msgget 实现。
kernel/492核心子系统：sched/ 调度、irq/ 中断、time/ 时钟、locking/ 锁、trace/ 追踪、events/ perf、bpf/。理解调度/中断/锁、ftrace、perf、kprobe。
lib/448通用库：字符串、位图、rbtree、排序、lib/Kconfig.debug（调试选项都在这定义）。看某个 helper 实现、开 debug 选项。
mm/127内存管理：page_alloc.c 伙伴系统、slab.c/slub.c、mmap.c、vmscan.c 回收、swap。调 OOM、看内存分配路径、理解 page cache。
net/1859网络：socket.c 是 socket 系统调用、ipv4/、ipv6/、netfilter/、wireless/。排查网络问题、看 TCP 状态机、写 netfilter 规则。
samples/248可编译的示例模块（kobject/kprobes/bpf/seccomp/ftrace 等），是学写模块最好的起点。照抄模板、做实验。
scripts/426构建脚本：Kbuild 规则本体、kconfig/ 配置工具、checkpatch.pl、get_maintainer.pl、dtc/ 设备树编译器。看编译规则、提交补丁前自查。
security/226安全框架：security.c 是 LSM 钩子总入口，selinux/、apparmor/、keys/、integrity/。研究权限模型、写 LSM 模块。
sound/2279ALSA 核心（sound/core/）+ 各声卡驱动（sound/pci/、sound/usb/、sound/soc/）。调音频驱动、理解 PCM 通路。
tools/4582用户态工具源码：tools/perf、tools/bpf、tools/testing/selftests、tools/power。默认不参与内核编译。编 perf、跑 selftest、写自己的测试工具。
usr/9把 initramfs 打包成 .cpio.gz 并编进内核镜像的那段逻辑。做最小化嵌入式镜像。
virt/14KVM 的架构无关部分：kvm_main.c、kvm/ 子目录。看虚拟化实现。

注意 drivers/ 一个目录就占了 2.87 万个文件、接近全部源码的 40%，而 ipc/ 只有 13 个文件。这个比例本身就是一堂课：内核的主体是驱动，核心机制其实相当紧凑。如果你刚开始学，不要从 drivers/ 开始读——先读 init/、kernel/、mm/、fs/ 这四块。

3.3 include/linux 与 include/uapi 的分界线

这条线是内核代码里最重要的"海关"：

                    内核内部                         用户态
   ┌──────────────────────────────┐   ┌──────────────────────────┐
   │ include/linux/  (1357 个)     │   │ include/uapi/ (544 个)   │
   │  - struct task_struct        │   │  - struct sockaddr       │
   │  - struct file               │   │  - struct ifreq          │
   │  - 内核函数声明               │   │  - #define SIOCGIFHWADDR │
   │  - 依赖 __user / spinlock_t   │   │  - 只用基本类型 __u32     │
   └───────────┬──────────────────┘   └────────────┬─────────────┘
               │  内核代码同时看到两边               │
               │  include <linux/socket.h>          │
               │      └─ 第 11 行 #include <uapi/linux/socket.h>
               ▼                                    ▼
   编译内核（用内核头）                 make headers_install 导出到 /usr/include

include/linux/socket.h:1-11 内部头是如何"包含" uapi 头的

/* SPDX-License-Identifier: GPL-2.0 */
#ifndef _LINUX_SOCKET_H
#define _LINUX_SOCKET_H


#include <asm/socket.h>			/* arch-dependent defines	*/
#include <linux/sockios.h>		/* the SIOCxxx I/O controls	*/
#include <linux/uio.h>			/* iovec support		*/
#include <linux/types.h>		/* pid_t			*/
#include <linux/compiler.h>		/* __user			*/
#include <uapi/linux/socket.h>

这就是标准模式：uapi 头是"干净"的那一半，只放用户态能看懂的东西（struct sockaddr、常量定义、ioctl 号）；内部头在最后 include 它，再加内核专有的东西（struct socket、struct file 指针、spinlock_t）。

include/uapi/linux/if_link.h:1-11 uapi 头长什么样

/* SPDX-License-Identifier: GPL-2.0 WITH Linux-syscall-note */
#ifndef _UAPI_LINUX_IF_LINK_H
#define _UAPI_LINUX_IF_LINK_H

#include <linux/types.h>
#include <linux/netlink.h>

/* This struct should be in sync with struct rtnl_link_stats64 */
struct rtnl_link_stats {
	__u32	rx_packets;
	__u32	tx_packets;

三个特征：① SPDX 是 GPL-2.0 WITH Linux-syscall-note——这一行让用户态程序可以自由使用这些头文件而不被 GPL 传染；② 文件名前缀 _UAPI_ 防重复包含；③ 类型只用 __u32/__s64 这类固定宽度类型，绝不用 unsigned long（32/64 位宽度不同）。

第 8 行的注释 "should be in sync with struct rtnl_link_stats64" 揭示了一个痛苦现实：同一个网卡统计结构在 uapi（rtnl_link_stats）和内部（rtnl_link_stats64）各有一份，必须手工保持一致。改 uapi 结构 = 改 ABI = 不能随便改，这是内核"永不破坏用户态"承诺的代价。

make headers_install 的作用就是把 uapi 目录按 include/uapi/Kbuild 的规则导出成 usr/include/linux/，供 glibc 和你的 C 程序 include。所以 #include <linux/if_link.h> 在用户态程序里能编过，是因为那个头来自 uapi；而 #include <linux/sched.h> 在用户态会失败，因为它不在 uapi 里（内部头）。

改了一个文件，不知道发给谁？看 MAINTAINERS。它是一份结构化文本，每个子系统一段：

MAINTAINERS:6619-6627 EXT4 文件系统条目

字段含义（MAINTAINERS:83-119 有官方解释）：

  • M: maintainer，补丁要发给的人（可以有多个）。
  • L: mailing list，邮件列表。
  • S: status，Maintained（有人管）/ Supported（有人专职管）/ Odd Fixes（偶尔修）/ Orphan（没人管）。

  • F: file pattern，文件通配模式，F: drivers/net/ 表示该目录及子目录全部归他。
  • X: 排除模式（F: net/ + X: net/ipv6/ 表示除了 ipv6 都归他）。

3.6 建索引：让 3 万个文件可搜索

光有目录结构不够，你需要"按符号跳转"的能力。内核自带三个目标：

Makefile:1836-1837 tags / cscope 目标

tags TAGS cscope gtags: FORCE
	$(call cmd,tags)

$(call cmd,tags) 会调用 scripts/tags.sh，根据目标名决定跑 ctags 还是 cscope。三个命令的区别：

  • make cscope：生成 cscope.out（约 100-300 MB），能在 vim 里 :cs find c func 查"谁调用了它"。
  • make tags：生成 tags（约 30-60 MB），vim 里 Ctrl-] 跳到定义。
  • make TAGS：emacs 用。

scripts/tags.sh:123-126 cscope 的生成方式

docscope()
{
	(echo \-k; echo \-q; all_target_sources) > cscope.files
	cscope -b -f cscope.out
}

all_target_sources 函数（脚本前面定义）根据 arch/ 和配置筛选出所有真正会被编译的源文件——不是全树。-k 关闭默认的 /usr/include 索引（内核自带 include 就够），-q 生成反向索引加速查询，-b 只建库不启动交互界面。

对新手更现代的选择：clangd / ccls + compile_commands.json。make compile_commands.json（内核脚本 scripts/clang-tools/gen_compile_commands.py 会用到）能生成供 LSP 使用的编译数据库，VS Code + clangd 就有了完整的跳转与补全。

3.7 git log：把"谁改的、为什么改"当成第二份文档

源码树是 .git 仓库（本仓库确实是）。注释只解释"现在是什么"，git log 解释"为什么变成这样"。常用姿势：

git log --oneline -20 fs/open.c                 # 这个文件最近 20 次改动
git log -p --follow mm/mmap.c | less            # 带 diff 的历史，跟改名
git log -S 'kvmalloc' --oneline | head          # 搜索"哪个提交引入了这个字符串"
git log --author='Linus' --since=2020-01-01     # 按作者/时间过滤
git blame -L 1316,1320 fs/open.c                # 这 5 行分别是谁何时改的
git show HEAD~3 --stat                          # 看某个提交改了哪些文件

精髓是 git log -S（俗称 "pickaxe"）：它不看 diff 文本，而是统计"某字符串出现次数变了"的提交。想找"某个函数是什么时候被删的"，这是唯一靠谱的办法。git blame 加上 -C 参数还能跨文件追踪代码搬移。

4. 源码走读

4.1 fs/Makefile：VFS 核心文件一览

想知道"文件系统抽象层"有哪些核心组件？看一个 Makefile 就够了——obj-y 的清单就是该目录直接参与 vmlinux 的组件名单。

fs/Makefile:9-14 VFS 核心对象

obj-y :=	open.o read_write.o file_table.o super.o \
		char_dev.o stat.o exec.o pipe.o namei.o fcntl.o \
		ioctl.o readdir.o select.o dcache.o inode.o \
		attr.o bad_inode.o file.o filesystems.o namespace.o \
		seq_file.o xattr.o libfs.o fs-writeback.o \
		pnode.o splice.o sync.o utimes.o d_path.o

逐个数一遍就是 VFS 的全家福：open.o（open 系统调用）、read_write.o（read/write）、namei.o（路径解析，即"name to inode"）、dcache.o（目录项缓存）、inode.o（inode 缓存）、super.o（superblock 管理）、exec.o（execve 加载 ELF）、pipe.o（管道）、select.o（select/poll）、fs-writeback.o（脏页回写）。

这些是所有文件系统共享的代码，没有一行与 ext4 有关。这就是"抽象层"的具体体现：ext4 只提供 file_operations 和 inode_operations 的具体实现，其余的通用流程都在这里。

4.2 block/Makefile：块层的 10 个核心文件

block/Makefile:6-11 块层对象清单

obj-$(CONFIG_BLOCK) := bio.o elevator.o blk-core.o blk-sysfs.o \
			blk-flush.o blk-settings.o blk-ioc.o blk-map.o \
			blk-exec.o blk-merge.o blk-timeout.o \
			blk-lib.o blk-mq.o blk-mq-tag.o blk-stat.o \
			blk-mq-sysfs.o blk-mq-cpumap.o blk-mq-sched.o ioctl.o \
			genhd.o ioprio.o badblocks.o partitions/ blk-rq-qos.o

读法：bio.o 是 IO 的最小单位（bio = block IO），blk-core.o 是请求队列主逻辑，blk-merge.o 把相邻读写合并，blk-mq.o 是多队列实现（NVMe 必备），genhd.o 管"通用磁盘"（/dev/sda 这种设备节点），partitions/ 是分区表解析（DOS/GPT）。

注意这里用 obj-$(CONFIG_BLOCK) := 而不是 +=，因为这是第一条赋值，后面还有 block/Makefile:13 起的其它 += 追加。obj-y := 与 obj-y += 的区分，是读 Makefile 的基本功。

Kconfig:6-30 顶层配置的 source 顺序（完整）

mainmenu "Linux/$(ARCH) $(KERNELVERSION) Kernel Configuration"

4.4 目录与配置的联动：drivers/ 如何按配置裁剪

drivers/Kconfig:1-9 menu "Device Drivers" 下的 source 清单

# SPDX-License-Identifier: GPL-2.0
#

每一行 source 对应一个子目录的 Kconfig，而每个子目录的 Makefile 里又有 obj-$(CONFIG_X) += ...。于是"你要的驱动"在三个地方同时登记：Kconfig（选项）、Makefile（编译规则）、C 文件（实现）。如果只动了后两者而没加 Kconfig 项，用户就永远选不到它。

4.5 samples/Kconfig + samples/Makefile：最小三元组

	  You can build and test sample kernel code here.

menuconfig 是"带菜单的 config"：在 menuconfig 界面里它是一行可展开的菜单标题，而不是叶子选项。if SAMPLES ... endif 包住整个文件，意味着关掉 SAMPLES 后，里面的所有子选项都不可见。

obj-$(CONFIG_X) += foo/（带斜杠）与 subdir-$(CONFIG_X) += foo（不带斜杠）有什么区别？前者表示"foo 是个 kbuild 子目录，递归进去取 built-in.a"，后者表示"只是下钻，不取产物"（用于 host program / 只做测试的目录）。Documentation/kbuild/makefiles.rst 有完整解释，新手记一条：要产物就用 obj-，只是去子目录干活用 subdir-。

注意 samples/Makefile:9 那行 FTRACE_DIRECT 与 TRACE_ARRAY 都指向 ftrace/，因为两个配置项控制同一目录下的不同目标，允许的重复没有人会去合并它。

4.6 一个目录的内部结构：drivers/char 与 fs/ext4

drivers/char/                 fs/ext4/
├── Makefile   (obj-y/obj-m)  ├── Makefile   (ext4-y := ...)
├── Kconfig    (选项定义)      ├── Kconfig    (CONFIG_EXT4_FS)
├── mem.c      (/dev/mem)     ├── inode.c    (inode 操作)
├── random.c   (/dev/random)   ├── super.c    (挂载/卸载)
├── misc.c     (杂项设备注册)   ├── file.c     (读写路径)
├── ttyprintk.c                ├── ext4.h      (内部头)
└── ...                        └── ...

规律清晰：每个"设备/文件系统"一组文件，文件名按"主题"切分（inode.c 管 inode，super.c 管 superblock）。想找 ext4 的写路径？fs/ext4/file.c → fs/ext4/inode.c（页映射）。想找 ttyprintk 怎么注册？drivers/char/ttyprintk.c 里搜 register_。

4.7 arch/x86 的布局：一个架构目录怎么组织

arch/x86/Makefile:225-233 架构 Makefile 注入全局变量

head-y := arch/x86/kernel/head_$(BITS).o
head-y += arch/x86/kernel/head$(BITS).o
head-y += arch/x86/kernel/ebda.o
head-y += arch/x86/kernel/platform-quirks.o

libs-y  += arch/x86/lib/

# drivers-y are linked after core-y
core-y += arch/x86/

这三行把 arch/x86 的代码"注入"到顶层 vmlinux 的链接清单里。注意拼装方式：head-y 是 vmlinux 的第一段（内核入口）、libs-y 是库（memcpy 等）、core-y 是其余。这个顺序决定了内核二进制文件里"哪段代码在最前面"，启动时的 _text 符号地址就由它决定。

$(BITS) 是 32 或 64，由配置的 CONFIG_64BIT 决定。所以 x86 用同一个目录同时支撑 32/64 位，文件名里带位数后缀是常见惯例（head_32.S、head_64.S）。

4.8 Documentation 文档如何编译成网页

Makefile:1615-1616 help 把文档目标委托出去 · Documentation/Makefile:89-91,134-136

    # 顶层 Makefile：只负责转发
    'Documentation targets:'
    $(MAKE) -f $(srctree)/Documentation/Makefile dochelp

    # Documentation/Makefile：真正的实现
    htmldocs:
          @$(srctree)/scripts/sphinx-pre-install --version-check
          @+$(foreach var,$(SPHINXDIRS),$(call loop_cmd,sphinx,html,$(var),,$(var)))

    cleandocs:
          $(Q)rm -rf $(BUILDDIR)
          $(Q)$(MAKE) BUILDDIR=$(abspath $(BUILDDIR)) $(build)=Documentation/userspace-api/media clean

所以 make htmldocs 的实质是：先跑脚本检查 Sphinx 依赖是否齐全，再对每个列在 SPHINXDIRS 里的文档子目录分别调一次 sphinx-build，产物落在 Documentation/output/。make pdfdocs 走 latexdocs 目标生成 LaTeX，再调用 pdflatex。

Sphinx 读 Documentation/conf.py（Python 配置）和各个 index.rst 的 toctree 来组织页面。每个 .rst 文件都能独立阅读，toctree 只是决定"在网站上谁挂在谁下面"。对新手，直接 grep .rst 比看网页快：grep -rn "kmalloc" Documentation/core-api/ | head。

4.9 本仓库的 git 状态：学会区分"上游代码"和"本地改动"

本仓库是 Linux 5.10 加上少量本地修改（git diff --stat 显示 26 个文件被改）。这是一个真实的"读源码"场景：你看到的代码可能不是 Linus 的原始版本。任何时候怀疑某个行为，先跑 git log -1 --format=%H 确认基线提交，再 git diff -- 某文件 看本地改了啥。这是读源码树的基本纪律。

6. 自测

Q1. 为什么 include/linux/socket.h 要 include include/uapi/linux/socket.h，而不是反过来？因为 uapi 头是"用户态也能看"的净版，只能依赖基本类型和别的 uapi 头；内部头包含内核专属类型（struct socket、spinlock_t），用户态根本编译不了。所以依赖方向必须是"内部 → uapi"，反过来会把内核内部结构泄漏给用户态，破坏 ABI 稳定性。
Q2. 我看到一个函数 tcp_sendmsg，去哪个目录找它的定义？为什么不是 fs/？net/ipv4/tcp.c。命名约定：tcp_ 前缀 → TCP 协议 → net/ipv4/；ext4_ → fs/ext4/；kvm_ → virt/kvm/ 或 arch/x86/kvm/；kmalloc → mm/slab_common.c。函数前缀就是最好的"目录提示"。
Q3. MAINTAINERS 的 F: 匹配了某个文件，但同一路径也被另一条 F: 匹配，会怎样？get_maintainer.pl 会把所有匹配条目的维护者都列出来（可能有多组）。X:（排除）优先级高于 F:，所以可以用 F: net/ + X: net/ipv6/ 把某子目录从某位维护者名下摘掉。实际提交补丁时，"发给谁"以输出的 (maintainer:XXX) 标注为准，不要自己猜。
Q4. 为什么 make cscope 要先有 .config？因为 scripts/tags.sh 的 all_target_sources 只收集"当前配置下真正会被编译的源文件"，这样索引更小、更精确。没有 .config 时脚本要么报错要么退回全树扫描。代价：索引里不会有你未启用的驱动代码。
Q5. 想读一个陌生的子系统，你的前 3 步是什么？① 读该目录的 Makefile（看清有哪些组件）；② 读该目录的 Kconfig（看清它和哪些子系统互相依赖）；③ 读 Documentation/ 下对应的 rst（比如 Documentation/filesystems/vfs.rst、Documentation/networking/netdev-FAQ.rst）；最后才 git log 看最近改了什么、为什么改。
