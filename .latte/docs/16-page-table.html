🗺️ 页表与缺页异常：MMU 怎么把虚拟地址翻译成物理地址

让每个进程都以为自己独占一整台电脑的内存，代价是一张多级"地址翻译表"和一次"翻译失败就现场补页"的缺页异常 · 预计阅读 40 分钟

1. 它在解决什么问题

先想象一个四合院，院里住了老王、老张、小李三家。每户人家寄快递，收件地址写的都是"XX 路 3 号 201 室"——同一个门牌号，送信的快递员不用知道哪家是哪家，因为三家各自都有��己的信箱柜。老王家的柜子只归老王开，老张家的是老张的。快递员把包裹按地址送进来，柜子怎么分、包裹谁签收，外人（甚至快递员本人）都看不出一丝差别。这就是虚拟内存的核心思想：把物理内存切成一块块 4 KB 的"物理页"，然后给每个进程发一套"虚拟页号"，让所有进程都用同一套虚拟地址写代码，但各自映射到不同的物理页上，互不干扰。

但"各发一套虚拟页号"这个动作本身有成本。CPU 拿到的只是一串地址，它并不知道这串地址属于哪个进程，也不该为每个进程分别准备一份翻译表。于是硬件（x86 上是 MMU，Memory Management Unit，内存管理单元）采用了一个折中方案：把翻译表本身也做成虚拟的。翻译表放在内存里，CPU 手里只握一个"翻译表在哪"的指针——x86 上就是 CR3 寄存器。CPU 翻译一个地址时，会自动去内存里查那张表；如果查不到，CPU 抛出一个异常（x86 的 #PF，Page Fault），把这个"我翻译不了"的问题交给内核处理。

为什么一定要做成"多级"的表？因为虚拟地址空间是巨大的（x86-64 上用户空间 128 TB），如果用一张平铺的大表，就算只用了一个字节也要为整个地址空间分配表项。所以硬件把地址切成几段，每段当"目录索引"，像"省 → 市 → 区 → 小区 → 门牌号"一样逐级往下查。x86-64 上是 PGD → PUD → PMD → PTE 四级，每级 512 项（9 位索引），最后 12 位是页内偏移。这样，一次翻译最多查四次表，代价恒定，与实际用了多少内存无关。

内核这一侧要做的事情是三件：一是维护每个进程的页表（mm_struct->pgd，切换进程时装进 CR3）；二是在缺页异常到来时，判断"这个地址本来该有什么"，然后现场把缺的页补上——这就是缺页处理路径 handle_mm_fault → __handle_mm_fault → handle_pte_fault；三是提供反向映射：从"某个物理页"能查出"哪些进程的哪个虚拟地址映射着它"，这样才能做页面回收、COW、迁移等操作。本文按这三条主线展开。

2. 核心名词

术语英文一句话解释
虚拟地址virtual address进程（和用户态程序）能看见的地址；由"页号 + 页内偏移"组成，页号部分要翻译，偏移部分原样加到物理地址上。
物理地址physical address内存条上真实的地址；只有 CPU 和内核看得见。
页page / frame内存管理的最小单位，x86-64 上是 4 KB（PAGE_SIZE）。虚拟侧叫"页"，物理侧叫"页框"。
页表page table存放"虚拟页 → 物理页"映射关系的表，每张表正好占一个 4 KB 页（512 个 8 字节表项）。
PGDPage Global Directory页表第 1 级（全局目录），索引 9 位，一个表项管 512 GB。
PUDPage Upper Directory页表第 2 级（上层目录），索引 9 位，一个表项管 1 GB。
PMDPage Middle Directory页表第 3 级（中间目录），索引 9 位，一个表项管 2 MB。
PTEPage Table Entry页表第 4 级（末级表项），索引 9 位，一个表项管 4 KB；真正存放物理页帧号。
CR3Control Register 3x86 的页表基址寄存器，存放当前进程 PGD 的物理地址；切换地址空间就是换 CR3。
mm_structstruct mm_struct进程的内存描述符，定义整个地址空间；里面挂着 pgd、VMA 红黑树、内存统计计数。
缺页异常page fault / #PFCPU 翻译地址失败时抛出的异常，Linux 用它实现"按需分页"和"写时复制"。
缺页处理fault handler内核处理缺页异常的代码路径：找到 VMA、判断缺页类型、补上页表项、返回用户态重试那条指令。
VMAVirtual Memory Area地址空间中一段有相同权限和属性的连续区间，是内核描述地址空间的基本单位（第 17 篇专题）。
匿名页anonymous page没有文件做后备的页，内容由内核提供（读零页或新分配的内存）。
文件映射页file-backed page由文件内容填充的页，通常同时存在于页缓存里。
写时复制Copy-On-Write, COWfork 时不真复制物理页，而是把写权限去掉；被写的那个进程触发缺页时才真正复制一份。
换出页swapped-out page内容被写入 swap 区、页表项被标记为"不在内存"的页；访问它触发缺页并从 swap 读回。
反向映射reverse mapping, rmap从物理页反查"哪些进程的哪些虚拟地址映射着它"的索引；匿名页靠 anon_vma，文件页靠 address_space 的区间树。
TLBTranslation Lookaside BufferCPU 内部缓存地址翻译结果的“小抽屉”，页表没改时翻译不必走内存。

3. 整体结构

3.1 一张虚拟地址的"位域切片"

在 x86-64（未开启 5 级分页）上，一个 48 位虚拟地址被切成 5 段：4 段 9 位的"目录索引" + 12 位的"页内偏移"。CPU 从最高位开始逐级查表。

 虚拟地址（48 位有效，bit 47..0）

  47        39        30        21        12         0
 +----------+----------+----------+----------+----------+
 |  PGD 9位 |  PUD 9位 |  PMD 9位 |  PTE 9位 | 页内偏移 |
 |  索引    |  索引    |  索引    |  索引    |  12 位   |
 +----------+----------+----------+----------+----------+
   CR3 --> [PGD 表] --> [PUD 表] --> [PMD 表] --> [PTE 表] --> 物理页框号
                                                  |
                                          页内偏移原样相加
                                                  v
                                        物理地址 = (页框号 << 12) | 偏移

 每一级覆盖范围：
   PGD 项 -> 512 GB      PUD 项 -> 1 GB
   PMD 项 -> 2 MB        PTE 项 -> 4 KB（1 个物理页）

反过来看"每级 512 项"意味着什么：一个 PGD 表项覆盖 512 GB，一个 PUD 表项覆盖 1 GB，一个 PMD 表项覆盖 2 MB，一个 PTE 表项覆盖 4 KB。所以"一个进程把 128 TB 用户空间全映射上"只需要 512 个 PGD 项；"把 1 GB 内存映射上"只需要 512 个 PMD 表项。这就是多级页表的全部意义：用固定的 4 次访存代价，支持稀疏的、巨大的地址空间。

3.2 CR3、mm_struct 与"进程切换"

  进程 A 的地址空间                    进程 B 的地址空间
  +--------------------+               +--------------------+
  | mm_struct A        |               | mm_struct B        |
  |  pgd ----+         |               |  pgd ----+         |
  +----------|---------+               +----------+---------+
             |                                       |
        [PGD A 表]                              [PGD B 表]
             |                                       |
   CR3 寄存器 --> PGD A 物理地址          CR3 寄存器 --> PGD B 物理地址

   switch_mm() 时：把 mm->pgd 的物理地址写进 CR3，
   CPU 之前的翻译缓存（TLB）被标记为失效。

所以"进程隔离"在硬件层面是靠一件东西实现的：每个进程一份独立的 PGD。地址串本身在两个进程里可以一模一样，但查表得到的结果完全不同。

3.4 四种缺页，分别意味着什么

缺页类型触发条件内核动作你看到的现象
匿名缺页访问一块从没碰过的匿名内存（malloc 堆、栈）do_anonymous_page()：分配一个物理页并清零第一次读写这块内存会慢一点；mincore 报"不在内存"
文件缺页访问一个 mmap 进来的文件区域，页还没进内存do_fault()：从页缓存取页，或从磁盘读进来首次读文件内容慢（major fault）
COW 缺页写一个"共享的只读"页（fork 出来的子进程写父进程的数据）do_wp_page()：复制一份物理页，把当前进程的可写位打开fork 后子进程写内存会突然变慢
换出缺页访问被换到 swap 里的页do_swap_page()：从 swap 读回冷启动后第一次访问旧程序会卡一下

其中 minor fault（次要缺页）和 major fault（主要缺页）是按"是否需要真的读磁盘"来分的：匿名缺页、COW 缺页（复制已在内存的页）都是 minor；文件缺页如果页缓存里没有、要真去读磁盘，就是 major。统计在 /proc/vmstat 的 pgmajfault / pgminfault 里。

3.5 反向映射：回收与 COW 的前提

正向映射是"虚拟地址 → 物理页"，页表天然提供。但内核还有一类需求是反过来的：我要把这块物理内存回收了，谁在用它？这需要"物理页 → 虚拟地址"的索引，叫 rmap。

  • 匿名页：靠 struct anon_vma。一句话：一个 anon_vma 代表"一份共享的匿名内存"，多个进程的 VMA 挂在它的链表上，于是从物理页可以顺藤摸瓜找到所有映射它的地址空间。
  • 文件页：靠 struct address_space 里的区间树（i_mmap），文件页都指向同一份页缓存，映射它的 VMA 都登记在这棵树上。

4. 源码走读

4.1 从地址算出各级索引：pgd_index / pte_index

翻译的第一步是把地址切段。x86 没有自己实现这组宏，用的是内核通用版本 include/linux/pgtable.h，规则简单到可以背下来：先右移，屏蔽掉低一级能管的位数。

include/linux/pgtable.h:43-67 pte_index / pmd_index / pud_index / pgd_index

static inline unsigned long pte_index(unsigned long address)
{
	return (address >> PAGE_SHIFT) & (PTRS_PER_PTE - 1);
}

#ifndef pmd_index
static inline unsigned long pmd_index(unsigned long address)
{
	return (address >> PMD_SHIFT) & (PTRS_PER_PMD - 1);
}
#define pmd_index pmd_index
#endif

#ifndef pud_index
static inline unsigned long pud_index(unsigned long address)
{
	return (address >> PUD_SHIFT) & (PTRS_PER_PUD - 1);
}
#define pud_index pud_index
#endif

#ifndef pgd_index
/* Must be a compile-time constant, so implement it as a macro */
#define pgd_index(a)  (((a) >> PGDIR_SHIFT) & (PTRS_PER_PGD - 1))
#endif

逐行看：pte_index 把地址右移 12 位（PAGE_SHIFT，丢掉页内偏移），再 & (PTRS_PER_PTE - 1)。因为 PTRS_PER_PTE 是 512，512 - 1 = 0x1FF，正好是 9 个 1，所以这一步等价于"取第 20..12 位"。pmd_index 右移 21 位后取 9 位，就是"取第 29..21 位"。pgd_index 特别注明"必须是编译期常量"，因为它被用在 KERNEL_PGD_BOUNDARY 这种数组维度里，所以写成了宏而不是函数。

4.2 各级表的宽度与覆盖范围

arch/x86/include/asm/pgtable_64_types.h:79-96 PUD_SHIFT / PMD_SHIFT / PTRS_PER_*

/*
 * 3rd level page
 */
#define PUD_SHIFT	30
#define PTRS_PER_PUD	512

/*
 * PMD_SHIFT determines the size of the area a middle-level
 * page table can map
 */
#define PMD_SHIFT	21
#define PTRS_PER_PMD	512

/*
 * entries per page directory level
 */
#define PTRS_PER_PTE	512

这就是位域图的源码依据：PUD_SHIFT=30 表示"PUD 索引占第 30..38 位"，PMD_SHIFT=21 表示"PMD 索引占第 21..29 位"，往下 PAGE_SHIFT=12（在 arch/x86/include/asm/page_types.h:10）是页内偏移。三个 PTRS_PER_* 都是 512，说明每一级页表正好填满一个 4 KB 页——每项 8 字节 × 512 项 = 4096 字节。这一点在第 14 篇（buddy）讲过：页表页本身就是从伙伴系统里申请的普通页。

4.3 CR3：CPU 手里的那根"目录指针"

arch/x86/include/asm/processor.h:242-258 read_cr3_pa / load_cr3

/*
 * Friendlier CR3 helpers.
 */
static inline unsigned long read_cr3_pa(void)
{
	return __read_cr3() & CR3_ADDR_MASK;
}

static inline unsigned long native_read_cr3_pa(void)
{
	return __native_read_cr3() & CR3_ADDR_MASK;
}

static inline void load_cr3(pgd_t *pgdir)
{
	write_cr3(__sme_pa(pgdir));
}

注意 load_cr3(pgd_t *pgdir) 的参数类型：传进来的不是物理地址，而是 PGD 的内核虚拟地址指针。因为在 x86-64 上内核地址和物理地址是"恒等映射"（偏移量固定），所以 __sme_pa() 拿到的就是物理地址。掩码 CR3_ADDR_MASK（在 arch/x86/include/asm/processor-flags.h:38，值为 0x7FFFFFFFFFFFF000）会把低 12 位的 PCID 和 SME 加密位清掉——因为 CR3 里塞的不止一个地址。

4.5 缺页的第一站：x86 层的 do_user_addr_fault

CPU 抛出 #PF 后进入内核态的缺页入口。我们看它做的第一件实事——找到这个地址属于哪个 VMA。

arch/x86/mm/fault.c:1333-1346 do_user_addr_fault

	vma = find_vma(mm, address);
	if (unlikely(!vma)) {
		bad_area(regs, hw_error_code, address);
		return;
	}
	if (likely(vma->vm_start <= address))
		goto good_area;
	if (unlikely(!(vma->vm_flags & VM_GROWSDOWN))) {
		bad_area(regs, hw_error_code, address);
		return;
	}
	if (unlikely(expand_stack(vma, address))) {
		bad_area(regs, hw_error_code, address);
		return;
	}

find_vma(mm, address) 返回的是"第一个 vm_end > address 的 VMA"。三种情况：找不到（地址完全不在任何合法区间）→ 发 SIGSEGV；找到了但 vm_start > address（落在某个 VMA 之前的空洞里）→ 只有当这个 VMA 带 VM_GROWSDOWN（栈）时才尝试 expand_stack() 往下扩展栈，否则也是 SIGSEGV；地址落在 VMA 内部 → good_area，继续检查权限。

4.6 handle_mm_fault：通用入口

mm/memory.c:4758-4787 handle_mm_fault

vm_fault_t handle_mm_fault(struct vm_area_struct *vma, unsigned long address,
			   unsigned int flags, struct pt_regs *regs)
{
	vm_fault_t ret;

	__set_current_state(TASK_RUNNING);

	count_vm_event(PGFAULT);
	count_memcg_event_mm(vma->vm_mm, PGFAULT);

	/* do counter updates before entering really critical section. */
	check_sync_rss_stat(current);

	if (!arch_vma_access_permitted(vma, flags & FAULT_FLAG_WRITE,
					    flags & FAULT_FLAG_INSTRUCTION,
					    flags & FAULT_FLAG_REMOTE))
		return VM_FAULT_SIGSEGV;

	/*
	 * Enable the memcg OOM handling for faults triggered in user
	 * space.  Kernel faults are handled more gracefully.
	 */
	if (flags & FAULT_FLAG_USER)
		mem_cgroup_enter_user_fault();

	if (unlikely(is_vm_hugetlb_page(vma)))
		ret = hugetlb_fault(vma->vm_mm, vma, address, flags);
	else
		ret = __handle_mm_fault(vma, address, flags);

这个函数本身很短，做三件事：①把进程从"睡眠中"标成运行中并做计数（PGFAULT 事件就是 /proc/vmstat 里缺页计数的来源）；②用 arch_vma_access_permitted() 做一次架构相关的权限检查（比如 x86 上内核态访问用户页受 SMAP 限制）；③分诊：如果是 hugetlb 映射走 hugetlb_fault()，否则交给通用的 __handle_mm_fault()。

4.7 __handle_mm_fault：逐级定位页表

mm/memory.c:4602-4626 __handle_mm_fault

vm_fault_t __handle_mm_fault(struct vm_area_struct *vma,
		unsigned long address, unsigned int flags)
{
	struct vm_fault vmf = {
		.vma = vma,
		.address = address & PAGE_MASK,
		.flags = flags,
		.pgoff = linear_page_index(vma, address),
		.gfp_mask = __get_fault_gfp_mask(vma),
	};
	unsigned int dirty = flags & FAULT_FLAG_WRITE;
	struct mm_struct *mm = vma->vm_mm;
	pgd_t *pgd;
	p4d_t *p4d;
	vm_fault_t ret;

	pgd = pgd_offset(mm, address);
	p4d = p4d_alloc(mm, pgd, address);
	if (!p4d)
		return VM_FAULT_OOM;

	vmf.pud = pud_alloc(mm, p4d, address);
	if (!vmf.pud)
		return VM_FAULT_OOM;

先看 .address = address & PAGE_MASK：把地址向下取整到页边界——因为 PTE 是按页对齐的，页内偏移在查表阶段要丢掉。

然后是核心三行：pgd_offset(mm, address) 用第 4.1 节那套位运算算出 PGD 里的第几项；p4d_alloc() 顺着 PGD 往下走一级，如果那一项是空的，就当场申请一页内存来建这张下级表（这就是"懒分配页表"——没人碰过的地址空间，页表页根本不占内存）；pud_alloc() 同理。返回 VM_FAULT_OOM 表示连页表页都申请不出来（内存耗尽），这会一路传上去变成 OOM。

再往下（mm/memory.c:4654-4657）还有 vmf.pmd = pmd_alloc(mm, vmf.pud, address);，以及专门处理透明大页的分支：if (pmd_none(*vmf.pmd) && __transparent_hugepage_enabled(vma)) → create_huge_pmd(&vmf)。这就是第 19 篇讲的 THP 在缺页路径上的入口。

4.8 handle_pte_fault：分诊四种缺页

这是整个缺页处理的核心分诊台。注意本仓库的源码里已经带了中文注释，可以对照着读。

mm/memory.c:4498-4544 handle_pte_fault

static vm_fault_t handle_pte_fault(struct vm_fault *vmf)
{
	pte_t entry;

	if (unlikely(pmd_none(*vmf->pmd /* 故障地址对应的PMD指针 */))) {
		/*
		 * 延迟到稍后调用__pte_alloc()：因为vm_ops->fault可能
		 * 想要分配巨页，如果我们瞬间暴露页表，将很难从
		 * 并发错误和rmap查找中撤回
		 */
		vmf->pte /* 故障地址对应的PTE指针 */ = NULL;
	} else {
		/* 参见pte_alloc_one_map()中的注释 */
		if (pmd_devmap_trans_unstable(vmf->pmd /* 故障地址对应的PMD指针 */))
			return 0;
		/*
		 * 常规PMD已建立，在此点之后不能再变形为巨PMD，
		 * 因为我们持有mmap_lock读模式，而khugepaged以写模式获取它。
		 * 所以现在运行pte_offset_map()是安全的。
		 */
		vmf->pte /* 故障地址对应的PTE指针 */ = pte_offset_map(vmf->pmd /* 故障地址对应的PMD指针 */, vmf->address /* 故障发生的虚拟地址 */);
		vmf->orig_pte /* 原始PTE值 */ = *vmf->pte /* 故障地址对应的PTE指针 */; /* 保存原始PTE值 */

		barrier();
		if (pte_none(vmf->orig_pte /* 原始PTE值 */)) {
			pte_unmap(vmf->pte /* 故障地址对应的PTE指针 */); /* PTE为空，取消映射 */
			vmf->pte /* 故障地址对应的PTE指针 */ = NULL;
		}
	}

	if (!vmf->pte /* 故障地址对应的PTE指针 */) {
		/* PTE不存在，根据VMA类型选择处理方式 */
		if (vma_is_anonymous(vmf->vma) /* 检查是否为匿名VMA */)
			return do_anonymous_page(vmf); /* 匿名页面错误 */
		else
			return do_fault(vmf); /* 文件页面错误 */
	}

	if (!pte_present(vmf->orig_pte /* 原始PTE值 */))
		return do_swap_page(vmf); /* 页面已换出，处理swap错误 */

分诊逻辑一目了然：

  • PTE 不存在（pte_none）→ 看 VMA 有没有文件后备：匿名 VMA 走 do_anonymous_page()（新分配一页并清零）；文件 VMA 走 do_fault()（从页缓存/磁盘取页）。
  • PTE 存在但 !pte_present → 页被换出了，走 do_swap_page() 从 swap 读回。
  • PTE 存在、present，但写访问时 !pte_write → 走 do_wp_page() 做写时复制（见 4.9）。
  • 一切正常 → 补上 accessed / dirty 位，刷新 TLB。

注意代码里的 barrier()：这里读到 PTE 只是一份"一致的快照"，用来做分支判断；真正要改 PTE 时，会在 vmf->ptl（页表锁）保护下再检查一次 pte_same()，防止和并发的缺页处理互相踩踏。

4.9 find_vma：地址空间的红黑树查询

mm/mmap.c:2581-2612 find_vma

struct vm_area_struct *find_vma(struct mm_struct *mm, unsigned long addr)
{
	struct rb_node *rb_node;
	struct vm_area_struct *vma;

	/* Check the cache first. */
	vma = vmacache_find(mm, addr);
	if (likely(vma))
		return vma;

	rb_node = mm->mm_rb.rb_node;

	while (rb_node) {
		struct vm_area_struct *tmp;

		tmp = rb_entry(rb_node, struct vm_area_struct, vm_rb);

		if (tmp->vm_end > addr) {
			vma = tmp;
			if (tmp->vm_start <= addr)
				break;
			rb_node = rb_node->rb_left;
		} else
			rb_node = rb_node->rb_right;
	}

	if (vma)
		vmacache_update(addr, vma);
	return vma;
}

先查 vmacache——一个每线程 4 槽的"VMA 查找缓存"。缺页处理是高频操作，绝大多数缺页都发生在"刚刚访问过的那个 VMA"里，缓存命中率极高，命中就是 O(1)。未命中才走红黑树：因为 VMA 按地址有序排列，所以"找第一个 vm_end > addr 的节点"就是一次标准的 BST 查找，O(log n)。

红黑树遍历的逻辑值得逐行体会：tmp->vm_end > addr 说明这个节点在目标地址右边（它的范围可能包含 addr），要往左找更靠前的候选；如果 tmp->vm_start <= addr 说明 addr 确实落在它里面，直接命中；否则 addr 在这个 VMA 之前的空洞里，继续往左子树找更早的 VMA。

4.10 anon_vma：匿名页的反向映射锚点

include/linux/rmap.h:29-39 struct anon_vma

struct anon_vma {
	struct anon_vma *root;		/* Root of this anon_vma tree */
	struct rw_semaphore rwsem;	/* W: modification, R: walking the list */
	/*
	 * The refcount is taken on an anon_vma when there is no
	 * guarantee that the vma of page tables will exist for
	 * the duration of the operation. A caller that takes
	 * the reference is responsible for clearing up the
	 * anon_vma if they are the last user on release
	 */
	atomic_t refcount;

root 指向这棵 anon_vma 树的根（fork 出来的多个进程共享同一个 root），rwsem 保护遍历与修改，refcount 管生命周期。物理页的 struct page 里有一个 anon_vma 指针指向它，于是"给定物理页 → 找到所有映射它的 VMA"就变成了：读 page->anon_vma → 沿 anon_vma_chain 链表遍历 → 每个 chain 上挂着一个 struct vm_area_struct *vma。这条链是第 18 篇内存回收和 COW 的基础设施。

4.11 /proc/[pid]/maps 是怎么生成的

fs/proc/task_mmu.c:165-180 m_next

static void *m_next(struct seq_file *m, void *v, loff_t *ppos)
{
	struct proc_maps_private *priv = m->private;
	struct vm_area_struct *next, *vma = v;

	if (vma == priv->tail_vma)
		next = NULL;
	else if (vma->vm_next)
		next = vma->vm_next;
	else
		next = priv->tail_vma;

	*ppos = next ? next->vm_start : -1UL;

	return next;
}

/proc/[pid]/maps 走的是 seq_file 框架：m_start 用 find_vma() 找到第一个 VMA，m_next 顺着 vm_next 链表走，show_map 负责格式化每一行。值得注意的是它用的是 VMA 单链表（vm_next）而不是红黑树——因为遍历全部时链表更省缓存。

5.1 看自己进程的地址空间

$ cat /proc/self/maps
55a8b0a00000-55a8b0a02100 r--p 00000000 08:01 1234567    /usr/bin/cat
55a8b0a02100-55a8b0a02400 r-xp 00002100 08:01 1234567    /usr/bin/cat

每一行的格式是：起始地址-结束地址 权限 偏移 设备号 inode 路径。权限那 4 个字符依次是 r 可读、w 可写、x 可执行、p 私有（s 则表示共享）。起始地址一定是 4 KB 的整数倍——因为 VMA 的边界必须落在页边界上，这就是第 4.7 节 address & PAGE_MASK 的原因。

5.2 看页表占多少内存

$ grep -E "PageTables|Active\(file\)|AnonPages" /proc/meminfo
PageTables:      24448 kB
AnonPages:      123456 kB
Active\(file\):   23456 kB

PageTables 就是当前所有页表页占用的内存总量（第 14 篇讲过页表页本身也是普通页）。它的开销和"映射了多少虚拟地址范围"成正比，而不是和"实际用了多少数据"成正比——这也是为什么给一个程序 mmap 一块 1 TB 的空间（不碰它）几乎不花内存，但页表还是会有零星开销。

$ sudo gdb -p $(pidof sleep 1000)

CR3 里那个地址就是该进程 PGD 表的物理地址。用 info proc mappings 拿到 VMA 列表后，可以手工验证一下：随便挑一个 VMA 里的地址 A，按第 3.1 节的位域切片算出 PGD/PUD/PMD/PTE 四个索引，就能推出这个地址对应哪几张物理页。

5.4 mincore + mmap：亲眼看到"懒分配"

下面这个小程序映射 4 MB 匿名内存，然后用 mincore() 查询"哪些页真的在内存里"。注意 mincore 报的是"物理驻留状态"，不是"页表项是否存在"——这正是懒分配的直接证据。

$ cat > mincore_demo.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <unistd.h>

int main(void)
{
	size_t len = 4UL * 1024 * 1024;          /* 4 MB */
	long   pages = len / sysconf(_SC_PAGESIZE);
	unsigned char *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
				MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	unsigned char *vec;
	int resident, i;

	if (p == MAP_FAILED) { perror("mmap"); return 1; }
	vec = malloc(pages);
	if (!vec) { perror("malloc"); return 1; }
	printf("mapped  at %p  (%ld pages)\n", (void *)p, pages);

	if (mincore(p, len, vec) != 0) { perror("mincore"); return 1; }
	resident = 0;
	for (i = 0; i < pages; i++) resident += (vec[i] & 1);
	printf("before touch: resident = %d / %ld\n", resident, pages);

	p[0] = 1;                               /* 只碰第一个页 */
	mincore(p, len, vec);
	resident = 0;
	for (i = 0; i < pages; i++) resident += (vec[i] & 1);
	printf("after  touch: resident = %d / %ld\n", resident, pages);
	return 0;
}
EOF
$ gcc -O0 -o mincore_demo mincore_demo.c && ./mincore_demo
mapped  at 0x7f5b4c000000  (1024 pages)
before touch: resident = 0 / 1024
after  touch: resident = 1 / 1024

预期输出就是上面那样：映射了 1024 个页，但一个都没在内存里；只有碰过第一个页之后，驻留数才变成 1。这说明 mmap() 只建立 VMA 和页表结构（甚至连 PTE 都还没建），真正分配物理页是在第一次访问时由缺页异常完成的。整段程序只 touch 了 1 个字节，物理内存开销也只有 1 页。

5.5 观察缺页计数

$ grep -E "pgmajfault|pgminfault" /proc/vmstat
$ ./mincore_demo
$ grep -E "pgmajfault|pgminfault" /proc/vmstat

两次采样相减，pgminfault 会增加几十（每个新碰的页一次缺页，加上程序本身的加载缺页），而 pgmajfault 通常不变——因为这些页都是匿名页，不需要读磁盘。如果换成读一个刚创建的大文件，pgmajfault 就会明显跳上去。

6. 自测

Q1. 为什么虚拟地址要设计成"多级页表"，而不是一张平铺的大表？因为地址空间巨大（x86-64 用户空间 128 TB）。平铺表需要为每个虚拟页都准备一个表项，哪怕你只用了一个字节，也要按整个地址空间分配合页表内存。多级表把地址分段，每一级只对"真正用到的区间"分配下级表：PTE 那一级是按需分配的（没碰过的页连 PTE 都没有），上几级也只在需要时才建立。结果是：映射 1 GB 内存的页表开销大约是几 MB 量级，而不是几百 GB。
Q2. 缺页处理完成后，为什么是"返回用户态重试指令"，而不是在内核里把这次访存做完？因为缺页处理的职责只是"把路修通"——补上缺失的页表项。它并不知道这条指令后续要怎么用数据、要不要跨页、要不要处理对齐。如果内核替用户态执行完这条指令，就得在用户地址空间里模拟访存的全部语义（字节序、原子性、信号、可被观测的时序），复杂且易错。返回用户态重试，硬件会重新走一遍完整的访存流程，语义天然正确。代价是多一次异常往返，这也是"缺页"在性能分析里值得关注的原因。
Q3. COW 缺页和匿名缺页有什么区别？两者都会新建一个物理页吗？都会新建物理页，但来源不同。匿名缺页是"这个地址从来没被映射过"，新页的内容由内核清零提供（因为语义上要求新内存是零）。COW 缺页是"这个地址有映射，但页表项是只读的"——只读是因为它被多个进程共享（典型是 fork 出来的父子进程）。内核这时把原页复制一份给当前进程使用，原页保持不变给其他进程用。COW 的关键在于：复制发生在"真的有人要写"的那一刻，而不是 fork 的那一刻，这让 fork 变得非常廉价。
Q4. find_vma() 返回的 VMA 一定包含查询的地址吗？不一定。它返回的是"第一个满足 vm_end > addr 的 VMA"。如果 addr 落在两个 VMA 之间的空洞里，返回的是后面那个 VMA（它的 vm_start > addr）。所以调用者必须自己判断：x86 的缺页路径里就是先看 vma->vm_start <= address，成立才算命中；不成立则根据 VM_GROWSDOWN 判断能否扩栈，否则发 SIGSEGV。
Q5. 为什么 /proc/meminfo 里的 PageTables 会比"实际用到的页数 × 8 字节"大不少？因为页表是分级的、且每级都固定占 4 KB。映射 4 KB 数据需要：1 个 PTE（4 KB 页）+ 沿途的 PMD/PUD/PGD（如果之前没建，还要各占 4 KB）。所以摊到每个数据页上，页表开销可能是几十字节甚至更多。此外 PageTables 是全系统的统计，包含内核自身页表、每个进程的页表、以及为预留地址空间而建立的空表。内核在 mm->pgtables_bytes 里单独统计每个进程的页表开销。
