🧬 进程描述符 task_struct

内核用一个 C 结构体记住每个进程的一切：它是谁、在等什么、占着哪些内存和文件 · 预计阅读 25 分钟

1. 它在解决什么问题

想象一家大型酒店。住客有几百上千人，前台需要随时回答：这位客人住哪间房、房卡什么时候到期、他订的早餐送到哪、他欠多少钱、他是不是正在等洗衣机。前台不会把每个客人的信息塞进房卡里，而是在电脑里为每位客人建一条档案，房卡上只写一个编号，其余信息一查档案就有。

Linux 内核面对的是同一类问题。CPU 只有几个，可运行的“进程”有几百个，而且每秒要切换上千次。内核必须为每个执行流（一个进程，或者进程里的一个线程）维护一份完整的档案：它在什么状态、它的内核栈在哪、它的地址空间是什么、打开的文件表是哪一份、凭据（uid/gid）是什么、父子关系是谁。这份档案就是 task_struct，中文通常叫“进程描述符”（process descriptor）。

从操作系统视角看，task_struct 是内核里唯一“代表一个执行流”的对象。Linux 并不区分“进程”和“线程”两种数据结构——二者都是 task_struct，区别只在于若干指针是共享还是复制（这正是下一篇 fork 要讲的事）。你看到的 ps、top、/proc、调度器、信号、内存管理，全部围绕这个结构体运转。

理解 task_struct 的关键不是背字段，而是理解三件事：状态字段如何描述“我在等什么”、内核如何用 current 在 O(1) 时间找到“我自己”、哪些字段是共享的、哪些是私有的。这三点决定了后面 fork、调度、信号、内存几篇文章的所有行为。

3. 整体结构

3.1 一个 task 的全部家当

把 task_struct 想成一张“人物卡”，卡上按主题分区：身份区（pid/tgid/comm）、关系区（parent/children/sibling/group_leader）、状态区（state/flags/exit_state）、资源区（mm/files/fs/nsproxy/signal/sighand/cred）、调度区（prio/sched_class/se）、硬件区（thread）。下面这张图说明它与内核栈、地址空间的关系：

注意一个 5.10 的细节：thread_info 不再放在内核栈底部，而是放在 task_struct 的第一个字段（CONFIG_THREAD_INFO_IN_TASK）。这是为了防止内核栈溢出时改坏 thread_info 里的标志位——老内核把两者放一起，溢出会静默篡改 TIF_NEED_RESCHED 之类的位，非常难查。

3.2 状态机：state 的位不是枚举

state 的注释写着 “-1 unrunnable, 0 runnable, >0 stopped”，但 5.10 实际上把它当位掩码用。真正决定“现在能不能被调度”的是：state == TASK_RUNNING 且该 task 在运行队列上（on_rq）。常见状态：

宏值ps 显示含义

TASK_INTERRUPTIBLE0x0001S睡眠，可被信号唤醒（如 read 等待数据）
TASK_UNINTERRUPTIBLE0x0002D睡眠，不响应信号（等磁盘 IO 典型）

__TASK_TRACED0x0008t被 ptrace 调试器停住

     ▲                            │

TASK_RUNNING ──SIGSTOP──► TASK_STOPPED ──SIGCONT──► TASK_RUNNING

关键区分：state 管“睡眠原因”，flags（PF_*）管“这个 task 的属性”，exit_state 管“退出阶段”。三个字段各司其职，读代码时不要混。比如 PF_EXITING（正在退出）是 flags 位，不是 state 值。

3.3 current 如何 O(1) 找到自己

内核代码里到处出现 current，比如 current->pid。如果每次都要靠“当前栈指针减某个偏移”来推算，会很脆弱。5.10 的 x86_64 做法是：每个 CPU 有一个 percpu 变量 current_task，切换进程时（switch_to）就地更新它，读的时候用 %gs 段基址 + 固定偏移，一条指令级别完成。

老式做法（32 位内核常见）是让内核栈底存放 thread_info，再把栈指针按 THREAD_SIZE 对齐后取到它，再 thread_info->task 拿到 task_struct。5.10 里 current_thread_info() 直接就是 (struct thread_info *)current——因为 thread_info 已经是 task_struct 的第一个成员，两者地址相同，零成本强制转换。

3.4 内核栈与 thread_struct

每个 task 有自己私有的内核栈，x86_64 上是 THREAD_SIZE = PAGE_SIZE << 2 = 16KB（THREAD_SIZE_ORDER = 2）。为什么是 16KB 而不是更大？因为内核栈不能像用户栈那样按需增长（没有缺页机制支撑栈扩张的复杂判定），一旦溢出就是静默踩内存，所以它必须足够小以限制每个 task 的内存开销（几百个 task × 16KB 已经不小），又足够大以容纳最深的调用链（文件系统 + 网络 + 驱动嵌套）。5.10 有 CONFIG_VMAP_STACK，栈在 vmalloc 区且两页之间有 guard page，溢出会触发缺页而不是静默破坏内存。

thread_struct 保存“CPU 硬件视角”的私有状态：内核栈指针 sp（切换时由 __switch_to 写进 TSS）、FS/GS 基址（TLS）、浮点/AVX 状态 fpu、调试寄存器、cr2（上次缺页地址）等。它是 task_struct 的最后一个字段（在 randomized_struct_fields_end 之后），因为切换路径要按固定偏移直接访问它。

4. 源码走读

4.1 开头三个字段：state / stack / flags

这是 task_struct 的头部。thread_info 必须在最前（注释写了原因），紧接着是 state，然后才是“可随机化区域”。内核用 GCC 的 -frandomize-layout 打乱中间字段的顺序，用来对抗内核漏洞利用——但调度关键字段必须固定位置，所以被放在随机化标记之外。

include/linux/sched.h:640-662 struct task_struct（头部）

struct task_struct {
#ifdef CONFIG_THREAD_INFO_IN_TASK
	/*
	 * For reasons of header soup (see current_thread_info()), this
	 * must be the first element of task_struct.
	 */
	struct thread_info		thread_info;
#endif
	/* -1 unrunnable, 0 runnable, >0 stopped: */
	volatile long			state; /*进程状态*/

	/*
	 * This begins the randomizable portion of task_struct. Only
	 * scheduling-critical items should be added above here.
	 */
	randomized_struct_fields_start

	void				*stack; /*进程内核栈 ... */
	refcount_t			usage; /*进程描述符的使用计数 ... */
	/* Per task flags (PF_*), defined further below: */
	unsigned int			flags; /*进程标志 ... */
	unsigned int			ptrace;
  • thread_info 放在第一位，使 current_thread_info() 可以零成本把 task_struct * 转成 thread_info *；thread_info 里只有 flags（TIF_* 位）和 status 两个域，是汇编入口代码要快速访问的部分。
  • volatile long state：volatile 防止编译器把它缓存进寄存器，因为别的 CPU（唤醒路径）会在锁保护下直接写它。
  • void *stack：指向该 task 的 16KB 内核栈。进入内核时 entry_SYSCALL_64 从 percpu 的 cpu_current_top_of_stack 取栈顶，那个值就是在切换时从这个字段写过去的。
  • refcount_t usage：结构体自身的引用计数，get_task_struct()/put_task_struct() 操作它，归零才 free_task()。
  • flags（PF_*）：PF_KTHREAD（内核线程）、PF_EXITING（正在退出）、PF_MEMALLOC（允许动用内存保留区）等。

4.2 身份与亲属关系

pid 与 tgid 是整个“进程/线程”模型的骨架。real_parent 与 parent 平时相同，但被 ptrace 附加后，parent 会指向调试器（谁该收到 SIGCHLD 就发给谁）。

include/linux/sched.h:835-859 pid / tgid / 父子链表

	pid_t				pid;
	pid_t				tgid;

#ifdef CONFIG_STACKPROTECTOR
	/* Canary value for the -fstack-protector GCC feature: */
	unsigned long			stack_canary;
#endif
	/* ... */
	/* Real parent process: */
	struct task_struct __rcu	*real_parent; /*指向创建了P的进程描述符 ... */

	/* Recipient of SIGCHLD, wait4() reports: */
	struct task_struct __rcu	*parent; /*如果指向P当前父进程 ... */

	/*
	 * Children/sibling form the list of natural children:
	 */
	struct list_head		children; /*子进程列表的头节点。*/
	struct list_head		sibling; /*在父进程的 children 链表中的节点。...*/
	struct task_struct		*group_leader; /*线程组的领导者。...*/
  • pid 是 task 级 ID，每个线程都不同；tgid 是线程组级 ID，同组线程相同，等于组长（主线程）的 pid。你 ps 看到的“进程号”是 tgid。
  • children 是链表头，sibling 是挂在这个链表里的节点——这是内核经典的侵入式链表用法：父进程遍历 children，每个子进程通过自己的 sibling 串起来，不需要额外分配节点。
  • parent 才是 SIGCHLD 与 wait4() 的接收者。孤儿进程会被 reparent 到 init 或最近的 subreaper，改的就是这两个指针。

4.3 资源指针：mm / active_mm / cred / files / nsproxy

这一段是“共享还是私有”的核心。mm 是进程的地址空间，线程共享同一个 mm；active_mm 是“当前 CPU 上真的装着的页表”，内核线程没有 mm，就借用上一个用户进程的 active_mm（lazy TLB）。

include/linux/sched.h:755-758 地址空间指针

	struct mm_struct		*mm;
	struct mm_struct		*active_mm;

	/* Per-thread vma caching: */
	struct vmacache			vmacache;

include/linux/sched.h:920-969 cred / fs / files / nsproxy

	/* Process credentials: */

	/* Tracer's credentials at attach: */
	const struct cred __rcu		*ptracer_cred;

	/* Objective and real subjective task credentials (COW): */
	const struct cred __rcu		*real_cred;

	/* Effective (overridable) subjective task credentials (COW): */
	const struct cred __rcu		*cred;
	/* ... 此处省略 comm/nameidata/sysvsem 等字段 ... */
	/* Filesystem information: */
	struct fs_struct		*fs;

	/* Open file information: */
	struct files_struct		*files;
	/* ... 此处省略 io_uring/signal 之外的若干字段 ... */
	/* Namespaces: */
	struct nsproxy			*nsproxy;

	/* Signal handlers: */
	struct signal_struct		*signal;
	struct sighand_struct __rcu	*sighand;
  • cred 是 const 的，且注释写着 COW：要改 uid 不能原地改（别的线程可能共享同一份），必须先 prepare_creds() 复制一份新的，改完再 commit_creds() 挂上去。这是“读多写少 + 无锁读”的经典设计。
  • files 是 fd 表。fork() 默认复制一份，clone(CLONE_FILES) 则共享同一份并加引用计数——这就是“一个线程 close 了 fd，另一个线程也看不到”的原因。
  • fs 存 cwd、root、umask；nsproxy 存 mount/pid/net/uts/ipc/cgroup/time 命名空间指针，容器就是靠它隔离的；signal 是整个线程组共享的信号状态（pending 位图、nr_threads），sighand 是处理函数表（sigaction 装的东西，线程间共享）。
  • 注意 signal 是普通指针，sighand 带 __rcu。因为信号处理函数表会被 sigaction() 替换，读侧要靠 RCU 保护；而 signal_struct 在线程组内永久共享，生命周期跟组绑定。

4.4 current：一条 percpu 读取指令

x86_64 不再用“栈指针取整”那套。它把当前 task 的指针放进每个 CPU 自己的变量里，current 展开成 this_cpu_read_stable(current_task)，编译后基本就是 mov %gs:current_task, %rax。

arch/x86/include/asm/current.h:10-18 取当前 task

struct task_struct;

DECLARE_PER_CPU(struct task_struct *, current_task);

static __always_inline struct task_struct *get_current(void)
{
	return this_cpu_read_stable(current_task);
}

#define current get_current()

include/linux/thread_info.h:15-23 current_thread_info() 的真相

#ifdef CONFIG_THREAD_INFO_IN_TASK
/*
 * For CONFIG_THREAD_INFO_IN_TASK kernels we need <asm/current.h> for the
 * definition of current, but for !CONFIG_THREAD_INFO_IN_TASK kernels,
 * including <asm/current.h> can cause a circular dependency on some platforms.
 */
#include <asm/current.h>
#define current_thread_info() ((struct thread_info *)current)
#endif
  • DECLARE_PER_CPU 定义的是“每个 CPU 一份”的变量。写它的人必须在关抢占/关中断的上下文里，比如 __switch_to 两侧；读它则不用加锁，因为读的永远是“本 CPU 当前任务”，不会读到别的 CPU 的值。
  • __always_inline 保证不会生成函数调用——current 在内核里出现频率极高，一次多余的 call 都不可接受。
  • current_thread_info() 只是把同一个指针换个类型：因为 thread_info 是 task_struct 的第一个成员，偏移为 0。老内核那套“栈底找 thread_info”的代码在 5.10 x86_64 上已经不存在了。

4.5 thread_info 与内核栈大小

arch/x86/include/asm/thread_info.h:56-59 x86 的 thread_info

struct thread_info {
	unsigned long		flags;		/* low level flags */
	u32			status;		/* thread synchronous flags */
};

arch/x86/include/asm/page_64_types.h:13-16 栈大小

#define THREAD_SIZE_ORDER	(2 + KASAN_STACK_ORDER)
#define THREAD_SIZE  (PAGE_SIZE << THREAD_SIZE_ORDER)
  • flags 里是 TIF_* 位：TIF_NEED_RESCHED（该重新调度了）、TIF_SIGPENDING（有信号待处理）、TIF_NOTIFY_RESUME（返回用户态前要做点事）。它们被“远程写”的频率很高（别的 CPU 唤醒你），所以放在 task_struct 里、单独一个 cache line 附近。
  • PAGE_SIZE 通常是 4KB，THREAD_SIZE_ORDER = 2 表示连续 4 页 = 16KB。打开 KASAN（内核地址消毒器）时再 +1 个 order，变成 32KB，因为 KASAN 需要影子内存来标记栈变量。
  • 16KB 意味着内核调用链深度大概 1000 多层帧，超过就溢出。所以内核代码严禁深递归，也严禁在栈上放大数组（char buf[4096] 在内核里是危险动作）。

4.6 状态如何变成 ps 里的一个字母

state 和 exit_state 都可能是“位”，但 ps 只能显示一个字母。内核用 task_state_index() 把位或成一个 TASK_REPORT 掩码，再取 fls()（最高有效位位置）当数组下标。

fs/proc/array.c:129-139 状态字母表

static const char * const task_state_array[] = {

	/* states in TASK_REPORT: */
	"R (running)",		/* 0x00 */
	"S (sleeping)",		/* 0x01 */
	"D (disk sleep)",	/* 0x02 */
	"T (stopped)",		/* 0x04 */
	"t (tracing stop)",	/* 0x08 */
	"X (dead)",		/* 0x10 */
	"Z (zombie)",		/* 0x20 */
	"P (parked)",		/* 0x40 */

数组下标与位值一一对应：fls(0x20) = 6，正好是 "Z (zombie)"。state == 0（R）时 fls(0) = 0，落在第 0 项。这个技巧让“判断状态”和“打印状态”共用同一套位定义，避免两处枚举不同步。

5. 动手验证

下面所有命令在普通 x86_64 Linux 上都能跑，不需要编译内核。内核版本建议 5.10 附近，输出字段名一致。

实验一：看自己的状态字段。

$ cat /proc/self/status | head -12
Name:	cat
Umask:	0022
State:	R (running)
Tgid:	4242
Ngid:	0
Pid:	4242
PPid:	4001
TracerPid:	0
Uid:	1000	1000	1000	1000
Gid:	1000	1000	1000	1000
FDSize:	256

预期：State 是 R，因为 cat 正在跑（虽然它大部分时间在 sleep，但读取自己的 status 这一刻在 CPU 上）。Tgid == Pid 说明它是单线程进程；开一个多线程程序再对比，会看到 Tgid 相同而 Pid 不同。

实验二：state 的“位”特性。

$ sleep 100 &
$ ps -o pid,stat,comm -p $!
  PID STAT COMMAND
 4321 S    sleep
$ grep State /proc/$!/status
State:	S (sleeping)

sleep 在等定时器，处于 TASK_INTERRUPTIBLE（0x1），所以显示 S。再看一个不可中断的例子：

$ dd if=/dev/zero of=/tmp/x bs=1M count=200 &
$ while :; do ps -o stat= -p $!; done | grep -m1 D || echo "没抓到 D（磁盘太快）"

D 状态（TASK_UNINTERRUPTIBLE）通常出现在等块设备 IO 时，转瞬即逝；抓不到很正常，这正说明它是一种“短暂但不可被信号打断”的等待。

实验三：观察僵尸与父进程关系。

$ bash -c 'sleep 0.1 & exit 0' &
$ ps -o pid,ppid,stat,comm -C sleep
  PID  PPID STAT COMMAND
 4401     1  Z    sleep

子进程先退出、父进程（bash）已退出，于是它被 reparent 到 PID 1（或 systemd 的 subreaper），此时处于 EXIT_ZOMBIE（0x20）。ps 的 STAT 显示 Z，且 PPID 变成 1——这对应源码里的 real_parent/parent 被重写。Z 进程不能 kill -9 掉，只能等父进程 wait 或系统重新挂载父进程。

实验四：核对源码里的常量。

$ grep -n "THREAD_SIZE_ORDER" arch/x86/include/asm/page_64_types.h
15:#define THREAD_SIZE_ORDER	(2 + KASAN_STACK_ORDER)
$ getconf PAGESIZE
4096
$ echo $((4096 << 2))
16384

预期 16384 字节 = 16KB，与文档中“内核栈 16KB”一致。如果你的机器开了 KASAN 或 CONFIG_THREAD_INFO_IN_TASK 关闭，数字会变，但推导过程不变。

实验五：current 与内核态。选做：用 perf 观察切换，或直接读 /proc/self/wchan：

$ cat /proc/self/wchan; echo
0

wchan 显示“睡眠时内核停在哪个函数”，R 状态下是 0。用 ps -o pid,stat,wchan 看一个 S 状态的进程，会看到它停在 do_wait、ep_poll 之类，这就是 state 与内核栈内容的对应关系。

6. 自测

Q1. 为什么 5.10 x86_64 的 current_thread_info() 可以只是把 current 强转？因为 thread_info 被放进了 task_struct 的第一个字段（CONFIG_THREAD_INFO_IN_TASK），偏移为 0，两个指针值相同。老内核把 thread_info 放在内核栈底，才需要“栈指针按 THREAD_SIZE 对齐再取”。
Q2. state == TASK_RUNNING 就一定能被调度吗？不一定。还要看它是否在运行队列上（on_rq != 0）。一个刚被 wake_up_process() 唤醒的 task，state 已是 RUNNING，随后由 activate_task() 挂进 rq；而正在 schedule() 里执行、已经 deactivate_task() 的 task 可能 state 还是 RUNNING 但不在队列上。
Q3. mm 与 active_mm 有什么区别？mm 是“这个 task 拥有的地址空间”（用户态 task 必有，内核线程为 NULL）；active_mm 是“当前 CPU 上真正加载的页表”。内核线程没有自己的地址空间，为了不做无谓的 CR3 切换，它会借用上一个用户 task 的 active_mm，这叫 lazy TLB。
Q4. 为什么 cred 是 const 的？因为多个 task（同组线程、甚至 fork 后的父子）可能共享同一份 cred，读侧需要无锁并发访问。要修改权限（如 setuid()）必须 prepare_creds() 复制一份新的再改，最后 commit_creds() 替换指针。这样不是“给字段加锁”，而是“改指针不改变旧对象”。
Q5. pid 与 tgid 谁是你 ps 看到的进程号？tgid。一个三线程进程的 ps -eLf 会列出 3 行，PID 各不同，但 TGID 相同；内核调度的是每个 task（每个线程），而信号、/proc/<pid> 目录、wait() 大多以 tgid 为单位。
