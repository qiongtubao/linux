🔌 设备模型：bus / device / driver

内核怎么「发现」硬件、怎么找到对的驱动、怎么把两者绑起来 · 预计阅读 11 分钟

1. 它在解决什么问题

搬家时最烦的不是搬东西，而是「这箱东西该放哪个房间」。如果所有箱子都堆在客厅，你每次找锅都要翻一遍全部家当。聪明的做法是：每个房间门口挂一块牌子写「厨房」「书房」，箱子外面贴着用途标签，你只要把标签和门口牌子对上一放——各就各位。

Linux 内核面对的问题一模一样：机器上可能有 PCI 网卡、USB 键盘、I2C 温度传感器、platform 串口……如果每个驱动都在启动时挨个探测「这个设备是不是我的」，代码会乱到无法维护。于是内核抽象出一个统一的设备模型（device model）：

  • bus（总线）是「房间」，负责定义这套设备的匹配规则（match）；
  • device（设备）是「箱子」，描述自己是什么（名字、资源、设备树节点）；
  • driver（驱动）是「管家」，声明自己能照顾哪类箱子，并提供 probe/remove。

三者一旦对上，内核就调用驱动的 probe()，把设备的所有权交出去。这个过程叫绑定（bind）。此外这个模型还统一解决了热插拔、电源管理、sysfs 呈现（/sys/bus/pci/devices/...）、驱动延迟探测依赖等横切需求。

为什么必须有它？因为设备种类与驱动数量是「多对多」：一块网卡芯片可能被两个驱动支持，一个驱动可能服务几十种型号。没有统一的匹配框架，就只能写死判断链，既不能并行探测，也无法在设备热插入时自动找到驱动。

                              └─ 失败时 devres_release_all() 释放 devm_* 资源

关键设计：设备注册和驱动注册是两条独立的路径，任何一方先到都会主动去找对方。设备先到，device_add 会遍历该总线上的所有驱动；驱动先到，driver_register 会遍历已有设备。这样驱动可以编成模块按需加载，不必关心加载顺序。

3.3 sysfs 呈现

每注册一个对象，就在 /sys 里多出一套目录和符号链接，让用户态能看见「谁绑了谁」：


/sys/bus/platform/
├── devices/              ← 所有平台设备（含到 /sys/devices/... 的链接）
├── drivers/              ← 所有平台驱动
│   ├── sbsa-uart/
│   │   ├── bind          ← echo 设备名 > bind  可手动绑定
│   │   ├── unbind        ← 手动解绑
│   │   └── a0010000.uart -> ../../../../devices/platform/a0010000.uart
└── drivers_autoprobe     ← 1：注册即自动匹配

4.1 三个结构体的骨架

struct my_chip *chip = devm_kzalloc(&pdev->dev, sizeof(*chip), GFP_KERNEL);
platform_set_drvdata(pdev, chip);   /* 等价于 dev_set_drvdata(&pdev->dev, chip) */
/* 之后任何拿到 device 的地方： */
struct my_chip *chip = dev_get_drvdata(dev);

4.2 驱动注册：先挂到总线下，再广播

driver_register 做四件事：检查总线是否已初始化、防止旧式 API 混用、查重名，然后 bus_add_driver 把它挂上总线，最后 kobject_uevent 通知 udev。

drivers/base/driver.c:147-182 driver_register

int driver_register(struct device_driver *drv)
{
	int ret;
	struct device_driver *other;

	if (!drv->bus->p) {
		pr_err("Driver '%s' was unable to register with bus_type '%s' because the bus was not initialized.\n",
			   drv->name, drv->bus->name);
		return -EINVAL;
	}

	if ((drv->bus->probe && drv->probe) ||
	    (drv->bus->remove && drv->remove) ||
	    (drv->bus->shutdown && drv->shutdown))
		pr_warn("Driver '%s' needs updating - please use "
			"bus_type methods\n", drv->name);

	other = driver_find(drv->name, drv->bus);
	if (other) {
		pr_err("Error: Driver '%s' is already registered, "
			"aborting...\n", drv->name);
		return -EBUSY;
	}

	ret = bus_add_driver(drv);
	if (ret)
		return ret;
	ret = driver_add_groups(drv, drv->groups);
	if (ret) {
		bus_remove_driver(drv);
		return ret;
	}
	kobject_uevent(&drv->p->kobj, KOBJ_ADD);

	return ret;
}

bus_add_driver 是关键：它把驱动加入 bus->p->klist_drivers，若 drivers_autoprobe 为真就立刻调 driver_attach(drv)，遍历该总线所有设备尝试绑定。drv->bus->p 为 NULL 的报错非常常见——那通常意味着驱动的 bus 字段没填，或总线本身还没 bus_register。

4.3 总线注册：sysfs 的目录骨架

bus_register 先把一个 subsys_private 塞进 bus->p，再注册 sysfs 的 subsystem 目录，并创建 devices/ 与 drivers/ 两个子 kset。

4.4 设备注册与 really_probe 的实质

device_register 只是 device_initialize + device_add 的两步包装（后者做 kobject_add、uevent、属性、symlink，并触发与驱动的匹配）。真正把「设备交给驱动」的是 really_probe：

drivers/base/dd.c:494-562 really_probe（节选）

static int really_probe(struct device *dev, struct device_driver *drv)
{
	int ret = -EPROBE_DEFER;
	int local_trigger_count = atomic_read(&deferred_trigger_count);
	bool test_remove = IS_ENABLED(CONFIG_DEBUG_TEST_DRIVER_REMOVE) &&
			   !drv->suppress_bind_attrs;

	if (defer_all_probes) {
		/* ...（省略：device_block_probing() 时强制延迟） */
		dev_dbg(dev, "Driver %s force probe deferral\n", drv->name);
		driver_deferred_probe_add(dev);
		return ret;
	}

	ret = device_links_check_suppliers(dev);
	if (ret == -EPROBE_DEFER)
		driver_deferred_probe_add_trigger(dev, local_trigger_count);
	if (ret)
		return ret;

	atomic_inc(&probe_count);
	pr_debug("bus: '%s': %s: probing driver %s with device %s\n",
		 drv->bus->name, __func__, drv->name, dev_name(dev));
	if (!list_empty(&dev->devres_head)) {
		dev_crit(dev, "Resources present before probing\n");
		ret = -EBUSY;
		goto done;
	}

re_probe:
	dev->driver = drv;

	/* If using pinctrl, bind pins now before probing */
	ret = pinctrl_bind_pins(dev);
	if (ret)
		goto pinctrl_bind_failed;
    // ...（省略：dma_configure、driver_sysfs_add、pm_domain activate）
	if (dev->bus->probe) {
		ret = dev->bus->probe(dev);
		if (ret)
			goto probe_failed;
	} else if (drv->probe) {
		ret = drv->probe(dev);
		if (ret)
			goto probe_failed;
	}

几个值得记住的点：

  • device_links_check_suppliers 检查「供电/时钟等供应商设备」是否已就绪，未就绪就返回 -EPROBE_DEFER。
  • !list_empty(&dev->devres_head) 的 dev_crit：probe 开始前不该有任何 devm 资源，否则说明上次清理不干净。
  • 优先调用 bus->probe，其次 drv->probe。新式写法用 bus 层统一包装（例如 platform bus 的 platform_drv_probe 会先做 clk defaults、PM domain），旧式驱动直接给 drv->probe。
  • 失败后统一走 devres_release_all(dev) —— devm_* 分配的资源和 iounmap 等都在此自动撤销，这是「错误路径不必写一堆 goto 清理」的基石。

probe 成功后 driver_bound(dev) 把设备挂到驱动的设备链表、清掉延迟探测标记，并广播 BUS_NOTIFY_BOUND_DRIVER。

4.5 匹配：platform bus 的优先级

不同总线各有各的匹配算法。平台总线（虚拟总线）的 platform_match 依次尝试四种方式，先命中先绑定：

drivers/base/platform.c:1170-1190 platform_match

static int platform_match(struct device *dev, struct device_driver *drv)
{
	struct platform_device *pdev = to_platform_device(dev);
	struct platform_driver *pdrv = to_platform_driver(drv);

	/* When driver_override is set, only bind to the matching driver */
	if (pdev->driver_override)
		return !strcmp(pdev->driver_override, drv->name);

	/* Attempt an OF style match first */
	if (of_driver_match_device(dev, drv))
		return 1;

	/* Then try ACPI style match */
	if (acpi_driver_match_device(dev, drv))
		return 1;

	/* Then try to match against the id table */
	if (pdrv->id_table)
		return platform_match_id(pdrv->id_table, pdev) != NULL;

	/* fall-back to driver name match */
	return (strcmp(pdev->name, drv->name) == 0);
}

顺序有意义：设备树/ACPI 是「固件给出的权威描述」，优先于平台 id 表，最后才退化为「名字相同就算匹配」这条兼容旧驱动的兜底规则。driver_override 是给用户态调试用的（echo foo > /sys/bus/platform/devices/X/driver_override）。

4.6 compatible 匹配的打分机制

of_driver_match_device 只是一层壳：of_match_device(drv->of_match_table, dev)，后者取设备的 of_node 后调 of_match_node。真正的比较在 __of_match_node，它不是「第一个相等就返回」，而是给每个候选打分，取最高分：

drivers/of/base.c:1082-1100 __of_match_node

const struct of_device_id *__of_match_node(const struct of_device_id *matches,
					   const struct device_node *node)
{
	const struct of_device_id *best_match = NULL;
	int score, best_score = 0;

	if (!matches)
		return NULL;

	for (; matches->name[0] || matches->type[0] || matches->compatible[0]; matches++) {
		score = __of_device_is_compatible(node, matches->compatible,
						  matches->type, matches->name);
		if (score > best_score) {
			best_match = matches;
			best_score = score;
		}
	}

	return best_match;
}

打分规则（来自 __of_device_is_compatible）：compatible 命中得 INT_MAX/2 - (index << 2)，即在设备节点 compatible 列表里越靠前，分数越高；type 命中加 2 分；name 命中加 1 分。这就实现了设备树的「从最具体到最通用」的层次匹配：一个节点可以写 compatible = "vendor,chip-v2", "vendor,chip", "generic-uart";，专为 v2 写的驱动优先胜出。

4.7 一个真实的平台驱动：SBSA UART

看一个架构里真实存在的例子。它挂在 platform 总线上，用 of_match_table 按 compatible 匹配，probe 里取资源、映射寄存器、把上下文存进 drvdata：

drivers/tty/serial/amba-pl011.c:2786-2808 sbsa_uart_of_match / arm_sbsa_uart_platform_driver

static const struct of_device_id sbsa_uart_of_match[] = {
	{ .compatible = "arm,sbsa-uart", },
	{},
};
MODULE_DEVICE_TABLE(of, sbsa_uart_of_match);

static struct platform_driver arm_sbsa_uart_platform_driver = {
	.probe		= sbsa_uart_probe,
	.remove		= sbsa_uart_remove,
	.driver	= {
		.name	= "sbsa-uart",
		.pm	= &pl011_dev_pm_ops,
		.of_match_table = of_match_ptr(sbsa_uart_of_match),
		.acpi_match_table = ACPI_PTR(sbsa_uart_acpi_match),
		.suppress_bind_attrs = IS_BUILTIN(CONFIG_SERIAL_AMBA_PL011),
	},
};

细节：of_match_table 是嵌在 driver 子结构里的，因为 struct platform_driver 把通用的 struct device_driver driver 当作成员（而非指针），to_platform_driver() 用 container_of 反向转换。末尾的空 {} 是哨兵项，__of_match_node 的循环靠它判断「表结束」。suppress_bind_attrs 在内建时禁用 /sys/.../bind 文件，避免用户把正在用的串口 unbind 掉。

再看 probe 的主体，注意它怎么把「设备描述」翻译成「驱动私有状态」：

drivers/tty/serial/amba-pl011.c:2715-2775 sbsa_uart_probe

static int sbsa_uart_probe(struct platform_device *pdev)
{
	struct uart_amba_port *uap;
	struct resource *r;
	int portnr, ret;
	int baudrate;

	if (pdev->dev.of_node) {
		struct device_node *np = pdev->dev.of_node;

		ret = of_property_read_u32(np, "current-speed", &baudrate);
		if (ret)
			return ret;
	} else {
		baudrate = 115200;
	}

	portnr = pl011_find_free_port();
	if (portnr < 0)
		return portnr;

	uap = devm_kzalloc(&pdev->dev, sizeof(struct uart_amba_port),
			   GFP_KERNEL);
	if (!uap)
		return -ENOMEM;

	ret = platform_get_irq(pdev, 0);
	if (ret < 0)
		return ret;
	uap->port.irq	= ret;
    // ...（省略：vendor 选择、fifo/iotype/ops 填充、type 字符串）
	r = platform_get_resource(pdev, IORESOURCE_MEM, 0);

	ret = pl011_setup_port(&pdev->dev, uap, r, portnr);
	if (ret)
		return ret;

	platform_set_drvdata(pdev, uap);

	return pl011_register_port(uap);
}
  • pdev->dev.of_node 就是设备树里那个节点；of_property_read_u32 读取固件写的属性——这是「硬件描述」与「驱动逻辑」分离的典型做法。
  • devm_kzalloc 让内核记得这块内存在设备卸载时自动释放，probe 失败也自动回收，不需要手写 kfree 的 goto 链。
  • platform_get_irq/platform_get_resource 从 pdev->resource[] 里取中断号和 MMIO 区间——这些资源由设备树或板级代码在创建设备时填入。
  • platform_set_drvdata(pdev, uap) 把 uap 存进 dev.driver_data，sbsa_uart_remove 里 platform_get_drvdata(pdev) 就能取回来——这是 remove 与 probe 之间唯一的约定。
「probe 成功」的含义不是「初始化函数返回 0」，而是「驱动能把设备当作自己的私有类型操作」。所以每个 probe 几乎都以 set_drvdata + 注册到某个框架（uart、netdev、input）结尾。顺序颠倒会导致中断先来、状态还没准备好。

5. 动手验证

(1) 在 /sys/bus 下看清三角关系与符号链接的方向：

$ ls /sys/bus/
acpi  amba  clockevents  clocksource  container  cpu  edac  event_source
gpio  i2c  isa  mdio_bus  mmc  module  nvme  pci  pci_express  platform
scsi  serio  spi  usb  virtio  ...  workqueue

$ ls /sys/bus/platform/devices/ | head -5
LNXPWRBN:00  PNP0000:00  PNP0103:00  alarmtimer  efi-framebuffer.0

$ ls -l /sys/bus/platform/devices/serial8250
... -> ../../../devices/platform/serial8250

$ ls /sys/bus/platform/drivers/
...  sbsa-uart  serial8250

$ ls -l /sys/bus/platform/drivers/serial8250/
bind  serial8250 -> ../../../../devices/platform/serial8250  unbind

设备先出现在 devices/；绑定后 drivers/<drv>/ 下多一个指向设备的符号链接。两个目录里的同名项只是链接，真实目录在 /sys/devices/platform/serial8250。

(2) 手动解绑/绑定（在虚拟机或测试机上做，别动真机的根磁盘控制器）：

# 看某设备当前挂的驱动
$ basename $(readlink -f /sys/bus/platform/devices/serial8250/driver 2>/dev/null)
serial8250

# 解绑（写入的是设备名，不是驱动名）
$ echo serial8250 | sudo tee /sys/bus/platform/drivers/serial8250/unbind
serial8250

# 重新绑定
$ echo serial8250 | sudo tee /sys/bus/platform/drivers/serial8250/bind
serial8250

写入后 dmesg 里能看到 probe/remove 的痕迹；解绑时 /sys/devices/platform/serial8250/driver 目录消失，说明 dev->driver 已被置空、devm 资源已回收。

(3) 观察 probe 顺序与延迟探测：

$ dmesg | grep -i 'probe.*defer'
platform serial8250: Driver serial8250 requests probe deferral

$ cat /sys/bus/platform/drivers_autoprobe   # 1 = 自动匹配
$ echo 0 | sudo tee /sys/bus/platform/drivers_autoprobe   # 之后注册的驱动不再自动探测

(4) 查看设备的资源与 driver_data 之外的信息（sysfs 属性）：

$ ls /sys/devices/platform/serial8250/
driver  driver_override  modalias  power  subsystem  uevent
$ cat /sys/devices/platform/serial8250/modalias
platform:serial8250
$ cat /sys/devices/platform/serial8250/uevent
DRIVER=serial8250
MODALIAS=platform:serial8250

modalias 正是 udev 做「模块自动加载」时用来匹配 MODULE_DEVICE_TABLE 的字符串；uevent 是热插拔事件的载荷内容。

6. 自测

Q1. 设备和驱动谁先注册会漏匹配吗？不会。两条路径都在自己的末尾主动遍历对方：device_add 里 bus_probe_device(dev) 遍历该总线所有驱动；driver_register 里 bus_add_driver 调 driver_attach 遍历所有设备。只要匹配函数返回正数就会 probe。
Q2. probe 返回 -EPROBE_DEFER 后发生了什么？设备被挂在总线延迟探测链表上，每次有新驱动/设备成功绑定，内核会触发重试列表。常用于「我的时钟供应商驱动还没 probe」「我的 regulator 还没就绪」这类顺序依赖。
Q3. 驱动为什么要保存 driver_data？因为 probe 与 remove（以及中断处理、sysfs 属性回调）是不同函数、不同时机调用的，需要一个地方存放「这次绑定的私有状态」。dev_set_drvdata 是唯一的官方入口，别自己写全局变量。
Q4. 设备树里的 compatible 字符串为什么可以写多个？表示「兼容性从最具体到最通用」。驱动匹配时按分数选最优表项（compatible 在设备节点中越靠前分数越高），从而让专用驱动赢过通用驱动，也让旧驱动能兜底。
Q5. /sys/bus/platform/devices/foo 是真目录吗？不是，是指向 /sys/devices/platform/foo 的符号链接。/sys/devices/ 是按「设备拓扑」组织的树（父设备下面挂子设备），/sys/bus/<bus>/devices/ 是按「总线归属」组织的视图，两者靠链接交叉引用。
