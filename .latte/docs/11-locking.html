🔒 内核锁：多核世界的交通规则

竞态、临界区、自旋锁、互斥锁、死锁与 lockdep：内核如何让几十个 CPU 同时跑而不互相踩脚 · 预计阅读 26 分钟

1. 它在解决什么问题

想象一个小区只有一个快递柜，物业规定“取件时把柜门关上”。但某天来了两个人：A 伸手去取件，B 同时也伸手去取件。A 刚把门拉开一半，B 就把门往外一拽——柜子里的东西掉地上摔坏了。这就是竞态（race condition）：结果取决于两个动作谁先谁后，而不是取决于代码的意图。

操作系统里的竞态要严重得多。你的内核跑在 16 个 CPU 上，同一段代码（比如“把网络包挂进接收队列”）可能同时在 16 个核上执行；而且内核随时可能把任务抢占下去、切换到另一个任务，等它再回来时世界已经变了。用一句话概括内核必须解决的并发问题：保护一小段代码，使得这段代码执行期间，不会有另一个 CPU（或另一个任务）插进来破坏它的中间状态。这段代码叫临界区（critical section），临界区里操作的共享数据叫临界资源。

那“插进来”具体怎么发生？三种方式：一是真并行——两个核真的同时执行；二是抢占——CPU 0 正在临界区里，调度器把它踢下核，CPU 1 接着跑同一段代码；三是中断——CPU 0 正在临界区里，硬件中断来了，中断处理程序也想操作同一份数据。前两种靠“关抢占/加锁”解决，第三种则引出了本篇最重要的一个坑：spin_lock_irqsave 为什么必须关中断。

解决竞态的办法只有两类，生活中都见过。第一类是站着等：锁被占着我就原地转圈等（自旋锁 spinlock），适合“等的时间只有几百纳秒”的场景；第二类是排队等：锁被占着我就去排队睡觉，等持锁人 release 时把我叫醒（互斥锁 mutex），适合“可能要等几毫秒甚至更久”的场景。选错了会要命：在中断处理程序里睡眠是禁止的（中断上下文不能调用调度器），在持有自旋锁时睡眠也是禁止的（会死锁）。

最后，内核还自带了一个“交警”——lockdep。锁的用法看起来简单，写错一两个字母就变成“中断里拿同一把锁导致死锁”这种极难复现的 bug。lockdep 会把每一次加锁/解锁记成一张有向图，一旦发现环（A→B→A）或者顺序反了（A→B 同时又有 B→A），立刻在 dmesg 里甩出一大段带调用栈的警告。本篇最后会带你写一个故意死锁的内核模块，亲眼看到这份报告。

3. 整体结构

3.1 锁家族总览

内核里的锁不是一种东西，而是按“等待时能不能睡觉”“中断里能不能用”两个维度分出来的一族。选错的典型后果不是性能下降，而是 panic 或整机卡死。

类型抢不到时中断上下文可用典型场景
spinlock_t原地自旋（忙等）可以（用 _irq/_irqsave 变体）保护短小的内核数据结构，如 slab 链表
raw_spinlock_t原地自旋可以lockdep 自身代码、不想付 lockdep 开销的热路径
mutex睡眠进等待队列不可以进程上下文里保护稍长的临界区（inode、文件操作）
rw_semaphore睡眠（读者可并发）不可以VFS 的 inode 锁：读多写少
seqlock_t读者重试；写者用锁串行化读侧可以读多写极少的统计值、时间戳
completion睡眠不可以“I/O 完成”“子进程退出”的一次性通知
一句话选择法：临界区只有几十条指令 → 自旋锁；临界区可能睡眠或做 I/O → mutex；读远多于写 → rwsem 或 seqlock；只是通知“做完了” → completion。

3.2 自旋锁的 ticket（排队号）思路

最简单的自旋锁就是一个标志位：test_and_set。但它有个致命缺点——不公平。CPU 0 反复失败又反复成功，CPU 1 可能一直抢不到，理论上可以饿死。Linux 5.10 的 x86 用的是 qspinlock（queued spinlock），继承了经典 ticket 锁“先来先得，按号排队”的思路：

一个 32 位原子字，被拆成 4 个字节来看：

  31        18 17    16 15   9 8  7      0
 +------------+-----+----+-----+--+----------+
 |  tail cpu  |tail |   不用 |P|  locked  |   <- P = pending 位
 +------------+-----+----+-----+--+----------+
   发放的号（谁该上）      等待标记   锁是否被占

抢锁流程（快路径）：
   1. 读出 val
   2. 如果 locked 字节为 0 -> 用 cmpxchg 把 val 改成 _Q_LOCKED_VAL -> 抢到
   3. 否则走慢路径 queued_spin_lock_slowpath()：
        - 给自己发一个号：tail = encode_tail(我的 CPU 号, 我的排队序号)
        - 把自己的 MCS 节点挂到等待队列尾部（挂进别人 CPU 的缓存行 -> 缓存行乒乓）
        - 轮询等待，直到“锁里记录的 tail == 我手里的 tail” → 我是队首 -> 拿锁

比“谁抢到谁拿”多出来的好处：FIFO 公平，不饿死；每个等待者只碰自己的缓存行，减少 cache line 争抢。

3.3 为什么 spin_lock_irqsave 必须关中断

这是全篇最重要的一张图。假设驱动代码在进程上下文里用 spin_lock_irqsave(&lock, flags) 保护设备寄存器，而中断处理程序里也用 spin_lock(&lock)（不关中断版）保护同一份数据。问题出在关中断只挡住了别人抢锁，挡不住“我自己被中断”——不对，恰恰相反：irqsave 关中断正是为了防止下面这个局面。

时间轴（CPU 0）：

 进程上下文                        中断处理程序
 ------------                     -----------------
 spin_lock_irqsave(&lock)          （此刻中断是开着的！）
   关中断 ✓
   拿到锁 ✓
   ├──── 访问设备寄存器 ────┐
   │                       │
   │  ◄── 中断来了！        │  中断处理程序启动（同一 CPU）
   │       中断处理程序 spin_lock(&lock)
   │       → 发现锁被进程上下文持有 → 自旋等待
   │       （中断处理程序此刻不能睡眠，只能一直转）
   │
   └─ 进程上下文要访问设备寄存器
      → 但中断处理程序正占着 CPU，中断没返回，
        进程上下文根本拿不到 CPU 去执行下面的代码
        → 进程上下文永远等不到中断返回
        → 中断处理程序永远等不到锁被释放
        ══════════════════════════════════════► 死锁！

结论：进程上下文必须用 spin_lock_irqsave（或 _irq），
      关中断，保证“持锁期间不会被自己打断”。
      中断处理程序里如果也要这把锁，用普通 spin_lock 即可
      （中断上下文本来就没开中断）。
反过来的坑同样致命：如果中断处理程序用 spin_lock_irqsave，而进程上下文用普通 spin_lock，lockdep 会报 “irq-unsafe lock acquired by irq-safe lock” 类警告。规则是：同一把锁，在越"高"的上下文里必须用越强的关中断版本（进程 → irqsave，中断 → irq 或普通）。

3.4 mutex 的三级尝试

mutex_lock() 不是一上来就睡眠，它按成本从低到高试三招：

mutex_lock(&m)
   │
   ├─ 招式一：__mutex_trylock_fast()   —— 一个 cmpxchg 抢锁
   │      成功？ ── 是 ──▶ 完事，函数返回（绝大多数情况走这条）
   │      否 ↓
   │
   ├─ 招式二：mutex_optimistic_spin()  —— 乐观自旋一小会儿
   │      反复 trylock；失败就 cpu_relax() 让出流水线
   │      为什么划算：持锁者可能马上就释放了，
   │      自旋几微秒比"睡下→被唤醒→再调度回来"快得多
   │      注意：要判断持锁者是不是在"睡眠"，睡眠者就不值得等
   │      否 ↓
   │
   └─ 招式三：__mutex_lock_slowpath()  —— 把自己挂到 wait_list 尾部
          set_current_state(TASK_UNINTERRUPTIBLE); schedule();
          → 真正睡下，等持锁者 mutex_unlock() 时把自己唤醒
          → FIFO 排队，不插队（ww_mutex 除外）
为什么 mutex 允许睡眠而自旋锁不允许？睡眠意味着让出 CPU，而让出 CPU 意味着调度器要选下一个任务、可能要处理中断、要拿运行队列锁……这一整套动作在持锁临界区里做非常危险（甚至不可能，因为运行队列锁自己也是自旋锁）。自旋锁则全程不离开 CPU，绝不会“睡着”，因此适合任何上下文，包括中断处理程序。

3.5 另外三种锁的定位

  • rwsem（读写信号量）：像图书馆的“借阅区”。一堆读者可以同时进借阅区（down_read），但写管理员要改架子上时，所有人必须先出来（down_write）。写者之间互斥、写者优先，读者之间共享。它可睡眠，所以只能在进程上下文用。内核里最典型的是 VFS 的 inode->i_rwsem。
  • seqlock（顺序锁）：读者完全不加任何锁，只读一个序号，读完数据后再看序号变没变；变了说明读到了写者改动中的中间状态，丢掉重来。写者用序号（奇数=正在写，偶数=写完了）和一把普通锁把写者串行化。适合“读极多、写极少、数据本身可以容忍撕裂”的场景，比如时钟、统计计数。
  • completion（完成量）：只有一个计数器和一个等待队列。complete() 把计数加一并唤醒等待者，wait_for_completion() 睡到计数不为 0。它表达的是“一次性的事件通知”，而不是互斥。

4. 源码走读

4.1 spin_lock 只是 raw_spin_lock 的壳

spinlock_t 内部包了一个 raw_spinlock_t；两者唯一的区别是前者多了 lockdep 用来画依赖图的 dep_map（见 include/linux/spinlock_types.h:71-83）。真正干活的是 raw_spin_lock()。

include/linux/spinlock.h:352-355 spin_lock

static __always_inline void spin_lock(spinlock_t *lock)
{
	raw_spin_lock(&lock->rlock);
}

也就是说 spin_lock() 就是取内部裸锁加锁。raw_spin_lock() 本身在 include/linux/spinlock.h:225 被定义成 _raw_spin_lock(lock)。

4.2 __raw_spin_lock：关抢占 + 记账 + 真加锁

include/linux/spinlock_api_smp.h:139-144 __raw_spin_lock

static inline void __raw_spin_lock(raw_spinlock_t *lock)
{
	preempt_disable();
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
}
  • preempt_disable()：关掉抢占，保证持锁期间不会被踢下 CPU（关的是“任务级抢占”，不是关硬件中断）。
  • spin_acquire()：告诉 lockdep“当前任务现在持有这把锁”。没开 CONFIG_DEBUG_LOCK_ALLOC 时它是个空宏。
  • LOCK_CONTENDED(lock, trylock, lock)：真正去抢锁。它是个包装宏：先试 do_raw_spin_trylock，失败就进入 do_raw_spin_lock（在 x86 上最终落到 arch_spin_lock）。同时把“等待”这件事报告给 lockdep，让它能检测锁等待时间过长。

当内核把 CONFIG_INLINE_SPIN_LOCK 关掉（省代码体积）时，会走 out-of-line 版本：

kernel/locking/spinlock.c:148-154 _raw_spin_lock

#ifndef CONFIG_INLINE_SPIN_LOCK
void __lockfunc _raw_spin_lock(raw_spinlock_t *lock)
{
	__raw_spin_lock(lock);
}
EXPORT_SYMBOL(_raw_spin_lock);
#endif

只是一层转发。真正的“排队号”逻辑在架构层。

4.3 排队锁的快路径：queued_spin_lock

include/asm-generic/qspinlock.h:78-86 queued_spin_lock

static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
	u32 val = 0;

	if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
		return;

	queued_spin_lock_slowpath(lock, val);
}

atomic_try_cmpxchg_acquire 就是那条 x86 的 lock cmpxchg：如果我读到的 val 还是 0（没人占），就原子地把它改成 _Q_LOCKED_VAL（locked 字节置 1）。成功即拿到锁。失败说明有人占着，走慢路径去排队领号。

那 4 个字节长什么样？看类型定义：

include/asm-generic/qspinlock_types.h:14-44 arch_spinlock_t

typedef struct qspinlock {
	union {
		atomic_t val;

#ifdef __LITTLE_ENDIAN
		struct {
			u8	locked;
			u8	pending;
		};
		struct {
			u16	locked_pending;
			u16	tail;
		};
#else
		struct {
			u16	tail;
			u16	locked_pending;
		};
		...
#endif
	};
} arch_spinlock_t;

小端机器上：locked（第 0 字节）表示锁是否被占；pending（第 1 字节）表示“已经有人在排队了”；tail（第 2-3 字节）就是发放的号。号由 encode_tail(cpu, idx) 编码成“高 14 位是 CPU 号，低 2 位是序号”，所以锁本身就能记住“现在该第几号上场”，这就是 ticket 思想在现代实现里的样子。

4.4 spin_lock_irqsave：关中断的版本

include/linux/spinlock_api_smp.h:104-122 __raw_spin_lock_irqsave

static inline unsigned long __raw_spin_lock_irqsave(raw_spinlock_t *lock)
{
	unsigned long flags;

	local_irq_save(flags);
	preempt_disable();
	spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
	/*
	 * On lockdep we dont want the hand-coded irq-enable of
	 * do_raw_spin_lock_flags() code, because lockdep assumes
	 * that interrupts are not re-enabled during lock-acquire:
	 */
#ifdef CONFIG_LOCKDEP
	LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
#else
	do_raw_spin_lock_flags(lock, &flags);
#endif
	return flags;
}

关键在第 108 行 local_irq_save(flags)：把当前 CPU 的中断标志位存进 flags 并关掉中断。flags 返回给调用者，配对的 spin_unlock_irqrestore(&lock, flags) 会在释放锁后把中断状态恢复成原样（而不是无脑打开）——这就是为什么 API 叫 “irqsave” 而不是 “irqdisable”。

对外的宏在 include/linux/spinlock.h:382-385：

include/linux/spinlock.h:382-385 spin_lock_irqsave

#define spin_lock_irqsave(lock, flags)				\
do {								\
	raw_spin_lock_irqsave(spinlock_check(lock), flags);	\
} while (0)
三个变体的区别一句话版：spin_lock 不动中断状态（只能用在本来就关了中断的地方，比如中断处理程序）；spin_lock_irq 关中断、释放时打开；spin_lock_irqsave 关中断并保存原状态、释放时恢复。进程上下文用 irqsave，中断上下文用 irq 或裸 spin_lock。

4.5 mutex_lock：快路径与慢路径

kernel/locking/mutex.c:279-286 mutex_lock

void __sched mutex_lock(struct mutex *lock)
{
	might_sleep();

	if (!__mutex_trylock_fast(lock))
		__mutex_lock_slowpath(lock);
}
EXPORT_SYMBOL(mutex_lock);

might_sleep() 在 lockdep 开启时会检查当前是不是原子上下文（关着中断/关着抢占）——如果有人在中断处理程序里调 mutex_lock，这里直接 panic，而不是让你在几秒后收到一个莫名其妙的 oops。

kernel/locking/mutex.c:1361-1365 __mutex_lock_slowpath

static noinline void __sched
__mutex_lock_slowpath(struct mutex *lock)
{
	__mutex_lock(lock, TASK_UNINTERRUPTIBLE, 0, NULL, _RET_IP_);
}

noinline 是故意把慢路径踢出热路径；TASK_UNINTERRUPTIBLE 表示“睡下去不可被信号打断”（普通 mutex_lock 的语义；mutex_lock_killable 用 TASK_KILLABLE）。

kernel/locking/mutex.c:1099-1104 __mutex_lock

static int __sched
__mutex_lock(struct mutex *lock, long state, unsigned int subclass,
	     struct lockdep_map *nest_lock, unsigned long ip)
{
	return __mutex_lock_common(lock, state, subclass, nest_lock, ip, NULL, false);
}

真正的逻辑在 __mutex_lock_common()，把三种尝试串起来（下面是节选，省略了 ww_mutex 相关分支）：

kernel/locking/mutex.c:925-966 __mutex_lock_common

static __always_inline int __sched
__mutex_lock_common(struct mutex *lock, long state, unsigned int subclass,
		    struct lockdep_map *nest_lock, unsigned long ip,
		    struct ww_acquire_ctx *ww_ctx, const bool use_ww_ctx)
{
	struct mutex_waiter waiter;
	bool first = false;
	/* ... ww_mutex 相关判断略 ... */

	might_sleep();

	preempt_disable();
	mutex_acquire_nest(&lock->dep_map, subclass, 0, nest_lock, ip);

	if (__mutex_trylock(lock) ||
	    mutex_optimistic_spin(lock, ww_ctx, use_ww_ctx, NULL)) {
		/* got the lock, yay! */
		lock_acquired(&lock->dep_map, ip);
		preempt_enable();
		return 0;
	}

	spin_lock(&lock->wait_lock);
	/*
	 * After waiting to acquire the wait_lock, try again.
	 */
	if (__mutex_trylock(lock)) {
		goto skip_wait;
	}

	lock_contended(&lock->dep_map, ip);

	if (!use_ww_ctx) {
		/* add waiting tasks to the end of the waitqueue (FIFO): */
		__mutex_add_waiter(lock, &waiter, &lock->wait_list);
	}
	waiter.task = current;

	set_current_state(state);
	/* ... 睡进等待队列，等 mutex_unlock() 唤醒 ... */
}

注意两个细节：① 真正排队前还要抢一把内部自旋锁 lock->wait_lock 保护等待队列——因为等待队列是共享数据，不能裸着改；② 排队是 FIFO（list_add_tail），后来的不能插队。

4.6 乐观自旋：mutex_optimistic_spin

kernel/locking/mutex.c:637-684 mutex_optimistic_spin

static __always_inline bool
mutex_optimistic_spin(struct mutex *lock, struct ww_acquire_ctx *ww_ctx,
		      const bool use_ww_ctx, struct mutex_waiter *waiter)
{
	if (!waiter) {
		/* 持锁者可能正睡着，睡着就不值得等 */
		if (!mutex_can_spin_on_owner(lock))
			goto fail;

		/*
		 * In order to avoid a stampede of mutex spinners trying to
		 * acquire the mutex all at once, the spinners need to take a
		 * MCS (queued) lock first before spinning on the owner field.
		 */
		if (!osq_lock(&lock->osq))
			goto fail;
	}

	for (;;) {
		struct task_struct *owner;

		/* Try to acquire the mutex... */
		owner = __mutex_trylock_or_owner(lock);
		if (!owner)
			break;			/* 抢到了！ */

		if (!mutex_spin_on_owner(lock, owner, ww_ctx, waiter))
			goto fail_unlock;		/* 持锁者在睡觉，去睡吧 */

		/*
		 * The cpu_relax() call is a compiler barrier which forces
		 * everything in this loop to be re-loaded.
		 */
		cpu_relax();
	}

	if (!waiter)
		osq_unlock(&lock->osq);

	return true;

fail_unlock:
	if (!waiter)
		osq_unlock(&lock->osq);
fail:
	if (need_resched()) {
		__set_current_state(TASK_RUNNING);
		schedule_preempt_disabled();
	}
	return false;
}

三个设计要点：

  • mutex_can_spin_on_owner()：如果持锁者处于不可睡眠的状态（比如它正在跑用户态、或者正在忙），那它很快就可能释放锁，值得等；如果持锁者自己睡下了（比如它正阻塞在 I/O 上），那我等它毫无意义，应该立刻去睡。这是乐观自旋能提高性能的核心判据。
  • osq_lock(&lock->osq)：Optimization Spinlock Queue。一个 MCS 排队锁，保证同一时刻只有一个自旋者在盯 owner 字段，避免“一窝蜂全冲上去读 owner”造成缓存行抖动。
  • cpu_relax()：在 x86 上是 pause 指令，提示 CPU “我这步没活干，别浪费流水线”；在 ARM 上是 yield。它不是内存屏障（注释里也说了，这里不需要内存屏障，因为最终会看到正确的值）。

4.7 rwsem：读多写少

kernel/locking/rwsem.c:1489-1496 down_read

void __sched down_read(struct rw_semaphore *sem)
{
	might_sleep();
	rwsem_acquire_read(&sem->dep_map, 0, 0, _RET_IP_);

	LOCK_CONTENDED(sem, __down_read_trylock, __down_read);
}
EXPORT_SYMBOL(down_read);

__down_read_trylock 是快路径：给 sem->count 加一个 RWSEM_READER_BIAS（读者偏置），读者可以并发持有；写者则要把 count 减到 0 才能进去。__down_read 是慢路径，会真的睡下等写者。

4.8 seqlock：读者不拿锁，只看序号

include/linux/seqlock.h:329-338 __read_seqcount_begin

#define __read_seqcount_begin(s)					\
({									\
	unsigned seq;							\
									\
	while ((seq = __seqcount_sequence(s)) & 1)			\
		cpu_relax();						\
									\
	kcsan_atomic_next(KCSAN_SEQLOCK_REGION_MAX);			\
	seq;								\
})

include/linux/seqlock.h:346-352 raw_read_seqcount_begin

#define raw_read_seqcount_begin(s)					\
({									\
	unsigned seq = __read_seqcount_begin(s);			\
									\
	smp_rmb();							\
	seq;								\
})

include/linux/seqlock.h:450-454 read_seqcount_t_retry

static inline int read_seqcount_t_retry(const seqcount_t *s, unsigned start)
{
	smp_rmb();
	return __read_seqcount_t_retry(s, start);
}

串起来看：序号为奇数 = 写者正在改（读者必须等）；__read_seqcount_begin 自旋到序号变偶数，记住这个偶数 start；读完数据后 read_seqcount_retry() 比较当前序号和 start，不等就说明中途有写者来过，这份数据作废、重读。两处 smp_rmb() 保证“读序号”和“读数据”之间的顺序（详见第 13 篇）。

4.9 completion：一次性事件通知

include/linux/completion.h:26-29 struct completion

struct completion {
	unsigned int done;
	struct swait_queue_head wait;
};

简单到不可思议：一个计数 + 一个可睡眠等待队列。complete() 把 done 加一并唤醒全部等待者；wait_for_completion() 睡到 done != 0。它不提供互斥，只提供“等一件事发生”。

4.10 lockdep 抓死锁：一张有向图

lockdep 记录每一次“持有 A 的同时去拿 B”，形成边 A → B。如果新加的边让图里出现了环，就报“可能存在循环锁依赖”。

kernel/locking/lockdep.c:1880-1896 print_circular_bug

	pr_warn("\n");
	pr_warn("======================================================\n");
	pr_warn("WARNING: possible circular locking dependency detected\n");
	print_kernel_ident();
	pr_warn("------------------------------------------------------\n");
	pr_warn("%s/%d is trying to acquire lock:\n",
		curr->comm, task_pid_nr(curr));
	print_lock(check_src);

	pr_warn("\nbut task is already holding lock:\n");

	print_lock(check_tgt);
	pr_warn("\nwhich lock already depends on the new lock.\n\n");
	pr_warn("\nthe existing dependency chain (in reverse order) is:\n");

	print_circular_bug_entry(entry, depth);
}

而 print_lock()（kernel/locking/lockdep.c:725-748）负责把每把锁的“实例地址 + 名字 + 获取位置”打出来：

	printk(KERN_CONT "%px", hlock->instance);
	print_lock_name(lock);
	printk(KERN_CONT ", at: %pS\n", (void *)hlock->acquire_ip);

%pS 会把裸地址解析成 函数名+偏移 的形式，这正是报告末尾那些 at: spin_lock+0x1a/0x30 的来源——它直接告诉你锁是在哪一行被拿走的。

文件看什么

5.3 亲手制造一次死锁，让 lockdep 报警

下面这个模块让两个内核线程以相反顺序获取两把 mutex：A→B 和 B→A。经典 AB-BA 死锁，lockdep 会在第一次发现环时就报告（不用真等到卡死）。

// deadlock_demo.c
#include <linux/module.h>
#include <linux/mutex.h>
#include <linux/kthread.h>
#include <linux/delay.h>

static DEFINE_MUTEX(lock_a);
static DEFINE_MUTEX(lock_b);

static int worker_ab(void *arg)
{
	mutex_lock(&lock_a);       /* 先拿 A */
	msleep(500);                 /* 拉长窗口，等对方拿到 B */
	mutex_lock(&lock_b);       /* 再拿 B —— 这里死锁 */
	mutex_unlock(&lock_b);
	mutex_unlock(&lock_a);
	return 0;
}

static int worker_ba(void *arg)
{
	mutex_lock(&lock_b);       /* 先拿 B */
	msleep(500);
	mutex_lock(&lock_a);       /* 再拿 A —— 这里死锁 */
	mutex_unlock(&lock_a);
	mutex_unlock(&lock_b);
	return 0;
}

static int __init dd_init(void)
{
	struct task_struct *t1, *t2;

	t1 = kthread_run(worker_ab, NULL, "dd_ab");
	if (IS_ERR(t1))
		return PTR_ERR(t1);

	t2 = kthread_run(worker_ba, NULL, "dd_ba");
	if (IS_ERR(t2))
		return PTR_ERR(t2);

	pr_info("deadlock demo: two threads, opposite lock order\n");
	return 0;
}

static void __exit dd_exit(void)
{
	/* 两个线程都卡住了，正常路径退不出来 */
}

module_init(dd_init);
module_exit(dd_exit);
MODULE_LICENSE("GPL");

配套的 Makefile：

obj-m := deadlock_demo.o
KDIR ?= /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

$ make -C /lib/modules/$(uname -r)/build M=$PWD modules
$ sudo insmod deadlock_demo.ko
$ dmesg | tail -40

 -> {other:3/3}   (lock_a)
    -> {other:3/3}   (lock_b)

报告会告诉你：哪两个任务、谁正在拿哪把锁、依赖链是什么、以及拿锁的调用栈（worker_ba+0x40/0x80）——最后这条最值钱，直接指向你代码里的问题行。

6. 自测

Q1. 进程上下文里能不能用普通 spin_lock？不能，或者说“能但不安全”。普通 spin_lock 不动中断状态，进程持锁期间可能来中断，中断处理程序若拿同一把锁就会死锁（见 3.3 的时序图）。进程上下文必须用 spin_lock_irqsave（或 _irq），把中断关掉；释放时用 spin_unlock_irqrestore 恢复原状态。
Q2. raw_spinlock_t 和 spinlock_t 到底差在哪？差在 spinlock_t 内嵌的 lockdep_map dep_map（include/linux/spinlock_types.h:71-83）。它让 lockdep 知道这把锁的名字、类型和获取位置，从而画出依赖图、发现死锁。raw_spinlock_t 没有这块元数据，所以 lockdep 看不见它——代价是省掉 lockdep 的记账开销，代价的代价是你写错了也不会有人提醒。spin_lock() 的实现就是 raw_spin_lock(&lock->rlock)。
Q3. mutex 和 spinlock 都能保护共享数据，差在哪？什么时候用哪个？核心差别是“抢不到时做什么”。自旋锁抢不到就原地忙等，全程占着 CPU，绝不睡眠，因此可以在中断上下文用；mutex 抢不到就把自己挂进等待队列睡眠，让出 CPU，代价是唤醒 + 调度开销，但可以等很久（几毫秒以上）。规则：临界区只有几十条指令 → 自旋锁；临界区可能耗时或需要睡眠（做 I/O）→ mutex。
Q4. 什么是“乐观自旋”？它凭什么能提速？mutex 慢路径上，在真正睡下之前先原地自旋一小段时间，反复尝试 trylock。因为“自旋 → 唤醒 → 调度回本 CPU”的往返成本大约几微秒，而持锁者如果本来就在运行，很可能几百纳秒后就释放了锁，自旋直接拿到就省掉了整个睡眠/唤醒流程。判断能不能自旋的关键是 mutex_can_spin_on_owner()：如果持锁者自己也睡下了，自旋就没意义，应当直接去睡。mutex_optimistic_spin() 里还用 osq_lock 保证同一时刻只有一个自旋者，避免缓存行抖动。
Q5. lockdep 是怎么发现死锁的？它报的“circular locking dependency”是什么意思？lockdep 维护一张有向图：每次“持有 A 的同时申请 B”就加一条边 A→B。当新边让图里出现环（A→B→A）时，它判定存在循环锁依赖并打印报告，报告里包含：涉及的进程名和 PID、每把锁的实例地址与名字、锁是在哪一行被拿到的（at: %pS 打出来的调用点），以及完整的调用栈。它报的“possible”是保守措辞——在真实硬件上这确实会死锁，但报告本身不足以证明，因为时序可能刚好错开。
Q6. seqlock 的读者到底加锁了吗？没有加任何锁。读者只读一个序号（偶数表示当前没有写者），读完数据后再次读序号并比较，不一致就丢弃重来（read_seqcount_retry()）。写者则把序号置为奇数表示“正在写”，改完后置为偶数，并用一把普通锁把多个写者串行化。代价是读者可能白读一次，但换来了读者侧零锁开销。注意它只适用于“数据本身允许不一致”的场景，绝不能用来保护指针（写者可能让读者手里的指针失效）。
