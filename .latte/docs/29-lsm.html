🛡️ 29-lsm 安全模块框架

当"属主可读写"不足以描述安全时，用 LSM 钩子把 SELinux/AppArmor 插进内核的每个关键决策点 · 约 13 分钟

1. 它在解决什么问题

先看一个真实场景。公司给每个员工一个共享目录，权限是 rw。按传统的 DAC（Discretionary Access Control，自主访问控制）模型，任何属主都能改任何文件——因为权限位就写在那儿。这套模型的隐含假设是：文件属主值得信任。

但在真实的企业环境里这个假设常常不成立。财务部希望：只有财务应用能读 salary.db，即便是属主本人用文本编辑器打开也要被拒绝；日志进程可以追加日志但不能删除；nginx 可以读静态目录但不能读配置里的私钥。SELinux 的做法是给每个进程和每个文件打一个安全标签（比如 system_u:system_r:httpd_t 和 unconfined_t），然后用策略表规定"哪种标签的进程，对哪种标签的文件，能做什么操作"。

问题来了：内核的权限检查散落在几百个地方——打开文件、读目录、创建进程、发信号、绑定端口……如果每加一种安全策略就往内核里塞一次判断，代码会烂掉。LSM 的解法是先在所有关键决策点埋一个"钩子"，再让外部模块往钩子上挂函数。协议栈/文件系统完全不知道自己被检查了，它们只是调用 security_xxx() 这个壳，壳内部遍历一串模块的回调，任一模块说"不行"就整体拒绝。

这本质上是第 28 篇 netfilter 的同一套思想在"安全"领域的翻版：把策略与机制分离。netfilter 管网络包，LSM 管系统对象。

第二个问题是能力（capability）。传统 UNIX 里只有 root 和非 root 两档，root 能干的事太多了。Linux 把 root 的权力拆成 40 多项能力（CAP_NET_ADMIN、CAP_SYS_ADMIN、CAP_KILL……），可以按需授予某个子进程。这就是 capability 这个 LSM 干的事——它其实不"管"，只是提供了这个机制的挂载点。

第三个问题是多个 LSM 同时存在。SELinux 和 AppArmor 是两种风格迥异的策略系统，都可能装在同一台机器上。LSM 框架的答案是：所有已注册的模块按顺序依次被询问，第一个给出非默认返回的说了算。同时提供 lsm=... 启动参数和 /sys/kernel/security/lsm 文件来选择启用哪些、什么顺序。

3. 整体结构

3.1 钩子表的组织方式

  内核代码（fs/open.c 等）
        │
        ▼
  security_file_open(file)
        │
        ▼
  call_int_hook(file_open, 0, file)
        │
        ├──► security_hook_heads.file_open  (链表头)
        │        │
        │        ├─► [capability]  （若实现了该钩子）
        │        ├─► [selinux]     selinux_file_open
        │        └─► [apparmor]    apparmor_file_open
        │
        ▼
   任一回调返回非 0 → 整体拒绝，错误码上抛
   全部返回 0     → 放行

3.2 LSM 之间的优先级

  内核启动参数：lsm=capability,selinux,yama,apparmor
       ↓
  ordered_lsms[] = [capability, selinux, yama, apparmor]
       ↓
  每个钩子的链表按这个顺序排列
       ↓
  call_int_hook 遍历时，先问 capability，再问 selinux……

  特殊规则：
   · capability 永远排第一（LSM_ORDER_FIRST）
   · 某些 LSM 标了 LSM_FLAG_EXCLUSIVE（如 SELinux），
     它一旦启用，其它 LSM 就都不启用了
   · "security=selinux" 这种老写法只影响 Legacy Major 类 LSM

为什么要给 LSM 排序？因为它们的语义会互相影响。SELinux 的 capable 钩子会检查进程是否被策略允许使用某项能力；capability 模块则只回答"能力位有没有"。顺序不同结果可能不同。

3.4 LSM 与其它安全机制的分工

┌──────────────────────────────────────────────────────────┐
│  用户态策略引擎                                          │
│    SELinux policy  /  AppArmor profile                    │
└──────────────┬───────────────────────────────────────────┘
               │ 决策
┌──────────────▼───────────────────────────────────────────┐
│  LSM 框架（security/security.c）                          │
│    call_int_hook → 遍历各模块回调                        │
└──────────────┬───────────────────────────────────────────┘
               │ 询问
┌──────────────▼───────────────────────────────────────────┐
│  内核机制                                                │
│    DAC 权限位 → capability → namespace 隔离 → seccomp    │
└──────────────────────────────────────────────────────────┘

它们是叠加而非替代关系：DAC 先看（文件权限位），LSM 再看（策略），seccomp 最后看（能不能发起这个系统调用）。任何一层拒绝就整体拒绝。

4. 源码走读

4.1 钩子定义：一个头文件生成三份清单

LSM 最巧妙的设计在 include/linux/lsm_hook_defs.h：整个文件只是一串 LSM_HOOK(...) 声明，不同代码 include 它时用不同的 LSM_HOOK 宏展开成完全不同的东西。

include/linux/lsm_hook_defs.h:166-176

LSM_HOOK(int, 0, file_lock, struct file *file, unsigned int cmd)
LSM_HOOK(int, 0, file_fcntl, struct file *file, unsigned int cmd,
	 unsigned long arg)
LSM_HOOK(void, LSM_RET_VOID, file_set_fowner, struct file *file)
LSM_HOOK(int, 0, file_send_sigiotask, struct task_struct *tsk,
	 struct fown_struct *fown, int sig)
LSM_HOOK(int, 0, file_receive, struct file *file)
LSM_HOOK(int, 0, file_open, struct file *file)
LSM_HOOK(int, 0, task_alloc, struct task_struct *task,
	 unsigned long clone_flags)
LSM_HOOK(void, LSM_RET_VOID, task_free, struct task_struct *task)

每行的格式是 LSM_HOOK(返回值类型, 默认值, 钩子名, 参数...)。这个文件被 include 三次，每次得到不同结果：

include/linux/lsm_hooks.h:1536-1546

union security_list_options {
	#define LSM_HOOK(RET, DEFAULT, NAME, ...) RET (*NAME)(__VA_ARGS__);
	#include "lsm_hook_defs.h"
	#undef LSM_HOOK
};

struct security_hook_heads {
	#define LSM_HOOK(RET, DEFAULT, NAME, ...) struct hlist_head NAME;
	#include "lsm_hook_defs.h"
	#undef LSM_HOOK
} __randomize_layout;

第一次展开得到一个函数指针联合体：每个钩子对应一个函数指针成员，模块的回调表就长这样。第二次展开得到钩子链表头数组：每个钩子对应一个 hlist_head，用来挂所有模块的回调。

第三次展开在 security/security.c 里，生成每个钩子的默认值常量：

security/security.c:672-689

/*
 * The default value of the LSM hook is defined in linux/lsm_hook_defs.h and
 * can be accessed with:
 *
 *	LSM_RET_DEFAULT(<hook_name>)
 *
 * The macros below define static constants for the default value of each
 * LSM hook.
 */
#define LSM_RET_DEFAULT(NAME) (NAME##_default)
#define DECLARE_LSM_RET_DEFAULT_void(DEFAULT, NAME)
#define DECLARE_LSM_RET_DEFAULT_int(DEFAULT, NAME) \
	static const int LSM_RET_DEFAULT(NAME) = (DEFAULT);
#define LSM_HOOK(RET, DEFAULT, NAME, ...) \
	DECLARE_LSM_RET_DEFAULT_##RET(DEFAULT, NAME)

#include <linux/lsm_hook_defs.h>
#undef LSM_HOOK

所以 LSM_RET_DEFAULT(file_open) 就是 0。这种"单一定义、多处生成"的做法，让新增一个钩子只需要改一行声明，三处代码自动跟上——避免了内核里几百个钩子各写一遍的维护噩梦。

钩子链表项本身：

include/linux/lsm_hooks.h:1550-1584

/*
 * Security module hook list structure.
 * For use with generic list macros for common operations.
 */
struct security_hook_list {
	struct hlist_node		list;
	struct hlist_head		*head;
	union security_list_options	hook;
	char				*lsm;
} __randomize_layout;

/*
 * LSM_RET_VOID is used as the default value in LSM_HOOK definitions for void
 * LSM hooks (in include/linux/lsm_hook_defs.h).
 */
#define LSM_RET_VOID ((void) 0)

/*
 * Initializing a security_hook_list structure takes
 * up a lot of space in a source file. This macro takes
 * care of the common case and reduces the amount of
 * text involved.
 */
#define LSM_HOOK_INIT(HEAD, HOOK) \
	{ .head = &security_hook_heads.HEAD, .hook = { .HEAD = HOOK } }

LSM_HOOK_INIT 是给模块用的初始化宏：LSM_HOOK_INIT(file_open, selinux_file_open) 展开成 { .head = &security_hook_heads.file_open, .hook = { .file_open = selinux_file_open } }——一行搞定"我注册在哪个钩子上、我提供哪个函数"。

4.2 模块注册：security_add_hooks

security/security.c:468-494

/**
 * security_add_hooks - Add a modules hooks to the hook lists.
 * @hooks: the hooks to add
 * @count: the number of hooks to add
 * @lsm: the name of the security module
 *
 * Each LSM has to register its hooks with the infrastructure.
 */
void __init security_add_hooks(struct security_hook_list *hooks, int count,
				char *lsm)
{
	int i;

	for (i = 0; i < count; i++) {
		hooks[i].lsm = lsm;
		hlist_add_tail_rcu(&hooks[i].list, hooks[i].head);
	}

	/*
	 * Don't try to append during early_security_init(), we'll come back
	 * and fix this up afterwards.
	 */
	if (slab_is_available()) {
		if (lsm_append(lsm, &lsm_names) < 0)
			panic("%s - Cannot get early memory.\n", __func__);
	}
}

hlist_add_tail_rcu 把回调插到链表尾部——这保证了执行顺序就是模块的注册顺序，而注册顺序由启动时的 ordered_lsm[] 决定（不是编译进内核的顺序）。用 RCU 版本是因为遍历侧（call_int_hook）在 RCU 读侧临界区里，不能被阻塞。

lsm_append(lsm, &lsm_names) 把模块名字追加到全局字符串 lsm_names，这正是 /sys/kernel/security/lsm 显示的内容。

4.3 调用侧：call_int_hook

security/security.c:701-721

#define call_void_hook(FUNC, ...)				\
	do {							\
		struct security_hook_list *P;			\
								\
		hlist_for_each_entry(P, &security_hook_heads.FUNC, list) \
			P->hook.FUNC(__VA_ARGS__);		\
	} while (0)

#define call_int_hook(FUNC, IRC, ...) ({			\
	int RC = IRC;						\
	do {							\
		struct security_hook_list *P;			\
								\
		hlist_for_each_entry(P, &security_hook_heads.FUNC, list) { \
			RC = P->hook.FUNC(__VA_ARGS__);		\
			if (RC != 0)				\
				break;				\
		}						\
	} while (0);						\
	RC;							\
})

关键点在 if (RC != 0) break;：任何一个模块返回非 0，遍历立刻停止，该值就是最终结果。所以 LSM 的返回值约定是"0 = 我不反对，非 0 = 拒绝"。这与 netfilter 的"verdict"风格不同——netfilter 里 ACCEPT 是 1，LSM 里放行是 0。

IRC 参数是"初始返回码"，用于那些默认值不是 0 的钩子（比如 fs_context_parse_param 默认是 -ENOPARAM）。它是 statement expression（({ ... })），整个块的值就是最后一个表达式的值。

call_void_hook 是无返回值版本，遍历完所有模块，没有"否决权"。

4.4 一个具体钩子：security_file_open

security/security.c:1571-1580

int security_file_open(struct file *file)
{
	int ret;

	ret = call_int_hook(file_open, 0, file);
	if (ret)
		return ret;

	return fsnotify_perm(file, MAY_OPEN);
}

两步：先问所有 LSM 能不能开这个文件；通过了再通知文件系统监听器（inotify/fanotify）"有文件被打开了"。这个顺序很重要——被拒绝的操作不应该产生"文件被打开"的审计事件。

SELinux 的实现：

security/selinux/hooks.c:3850-3875

static int selinux_file_open(struct file *file)
{
	struct file_security_struct *fsec;
	struct inode_security_struct *isec;

	fsec = selinux_file(file);
	isec = inode_security(file_inode(file));
	/*
	 * Save inode label and policy sequence number
	 * at open-time so that selinux_file_permission
	 * can determine whether revalidation is necessary.
	 * Task label is already saved in the file security
	 * struct as its SID.
	 */
	fsec->isid = isec->sid;
	fsec->pseqno = avc_policy_seqno(&selinux_state);
	/*
	 * Since the inode label or policy seqno may have changed
	 * between the selinux_inode_permission check and the saving
	 * of state above, recheck that access is still permitted.
	 * Otherwise, access might never be revalidated against the
	 * new inode label or new policy.
	 * This check is not redundant - do not remove.
	 */
	return file_path_has_perm(file->f_cred, file, open_file_to_av(file));
}

这里体现了 SELinux 的一个重要设计：打开文件时保存 inode 的 SID 和策略版本号，后续的权限检查（file_permission）可以据此判断"策略或标签有没有变过"，变了就重新验证（revalidate）。注释还特意强调最后那次检查"不是冗余的，不要删"——因为它防的是 TOCTOU：检查通过之后、真正读之前，标签被换掉了。

4.5 capability 模块：cap_capable

capability 这个 LSM 很特殊——它不做策略，只提供"能力位"这套机制的实现。

security/commoncap.c:65-101

int cap_capable(const struct cred *cred, struct user_namespace *targ_ns,
		int cap, unsigned int opts)
{
	struct user_namespace *ns = targ_ns;

	/* See if cred has the capability in the target user namespace
	 * by examining the target user namespace and all of the target
	 * user namespace's parents.
	 */
	for (;;) {
		/* Do we have the necessary capabilities? */
		if (ns == cred->user_ns)
			return cap_raised(cred->cap_effective, cap) ? 0 : -EPERM;

		/*
		 * If we're already at a lower level than we're looking for,
		 * we're done searching.
		 */
		if (ns->level <= cred->user_ns->level)
			return -EPERM;

		/* 
		 * The owner of the user namespace in the parent of the
		 * user namespace has all caps.
		 */
		if ((ns->parent == cred->user_ns) && uid_eq(ns->owner, cred->euid))
			return 0;

		/*
		 * If you have a capability in a parent user ns, then you have
		 * it over all children user namespaces as well.
		 */
		ns = ns->parent;
	}

	/* We never get here */
}

这个循环体现的是 namespace 的层级语义：判断进程是否拥有某能力时，要沿着目标 user namespace 往上走：

  • 如果目标 ns 就是自己的 ns，看 cap_effective 里有没有这个位；
  • 如果目标的 ns 层级比自己还低（更"内层"），直接拒绝；
  • 如果自己是目标 ns 的直接父 namespace 的属主，那么拥有全部能力（这是创建 user namespace 的人天然具备的权限）；
  • 否则往上一级继续找——在父 namespace 里有该能力，就对所有子 namespace 都有效。

这就是为什么容器里的进程默认拿不到 CAP_SYS_ADMIN（除非用 --privileged 或 cap_add），而容器里的 root 对它自己那个 user namespace 里的操作是有全部能力的。

5.1 查看当前启用的 LSM

5.2 SELinux

getenforce
# Enforcing   ← 严格执行，拒绝违规操作
# Permissive  ← 只记录日志不拒绝（调试用）

sestatus
# SELinux status: enabled
# Current mode:  enforcing
# Loaded policy name: local
# ...

# 查看某个进程的标签
ps -eZ | head -5
# system_u:system_r:init_t:s0      1 ?        0      0 48 ?        0 0 ?       0 ?        init
# unconfined_u:unconfined_r:unconfined_t:s0 1000 ?  0 ...

# 查看文件的标签
ls -Z /etc/passwd
# system_u:object_r:passwd_file_t:s0 /etc/passwd

# 看审计日志
sudo ausearch -m avc -ts recent
# 或
sudo dmesg | grep -i avc

# 临时切到 permissive
sudo setenforce 0
sudo setenforce 1

标签格式是 user:role:type:level，最重要的是第三段 type（类型）——策略表规定的正是"某 type 的进程对某 type 的对象能做什么"。unconfined_t 表示未受限。

5.3 AppArmor

sudo aa-status
# apparmor module is loaded.
# 48 profiles are loaded.
# AppArmor profiles:
# /usr/lib/firefox/firefox
# /usr/bin/man
# ...
# /etc/apparmor.d/usr.man
# /etc/apparmor.d/usr.sshd

# 看某个 profile
cat /etc/apparmor.d/usr.sshd | head -20

# 某个进程在哪个 profile 里
cat /proc/$(pgrep -n sshd)/attr/current
# /usr/sbin/sshd (enforce)

# 临时禁用
sudo aa-disable /etc/apparmor.d/usr.man
sudo aa-enforce /etc/apparmor.d/usr.man
sudo aa-complain /etc/apparmor.d/usr.man

# 审计日志
sudo journalctl -k | grep apparmor="DENIED"

AppArmor 只给进程打 profile（路径规则写在 profile 里），不用给文件打标签，所以上手比 SELinux 简单，但表达力弱一些。

5.4 capability 实操

# 看当前进程的 capability 位
capsh --print
# Current: =, cap_chown, dac_override, fowner, fsetid, kill, setgid, setuid,
#          setpcap, net_bind_service, net_raw, sys_chroot, mknod, audit_write,
#          setfcap

# 完整列表
cat /proc/sys/kernel/cap_last_cap
# 40   ← 最后一个能力的编号，共 41 项（0~40）

# 给某个二进制文件加能力（这样普通用户也能执行）
sudo setcap cap_net_bind_service+ep /usr/local/bin/myserver
getcap /usr/local/bin/myserver
# /usr/local/bin/myserver cap_net_bind_service=ep

# 在文件里运行
sudo capsh --drop=cap_sys_admin -- -c 'ls /proc/1/'

# 容器里
docker run --rm --cap-add=NET_ADMIN ubuntu ip link add dummy0 type dummy
docker run --rm ubuntu ip link add dummy0 type dummy   # 权限不够

capability 位共 41 项（cap_last_cap = 40）。setcap ... +ep 的 e 是 effective、p 是 permitted。文件能力让非 root 程序在执行时获得特定能力——这是给服务程序最小权限的常用手法。

5.5 观察 LSM 钩子被调用

cd /sys/kernel/debug/tracing
# LSM 有专门的 tracepoint
ls events/lsm/
# lsm_capable  lsm_file_alloc  lsm_file_open  lsm_inode_permission ...

echo 1 > events/lsm/lsm_file_open/enable
echo 1 > events/lsm/lsm_inode_permission/enable
cat trace_pipe
# 然后 cat /etc/passwd，能看到 lsm_file_open 事件

每个 LSM 钩子都有对应的 tracepoint，能直接看到"某个钩子被调用了，返回值是多少"。这是验证 LSM 是否生效的最直接手段。

5.6 qemu + busybox 最小实验

make defconfig
scripts/config --enable CONFIG_SECURITY --enable CONFIG_SECURITYFS \
               --enable CONFIG_SECURITY_SELINUX
make -j$(nproc)

wget https://busybox.net/downloads/binaries/1.31.0-defconfig-multiarch-musl/busybox
chmod +x busybox && ./busybox --install -h initramfs
qemu-system-x86_64 -kernel arch/x86/boot/bzImage -initrd initramfs \
  -append "console=ttyS0 lsm=capability,selinux" -nographic

# 客控台里
mount -t securityfs securityfs /sys/kernel/security   # 挂上 securityfs
cat /sys/kernel/security/lsm
# capability,selinux
grep Cap /proc/self/status
# CapInh: 0000000000000000
# CapPrm: 0000003fffffffff
# CapEff: 0000003fffffffff

用 lsm= 启动参数指定顺序，串口控制台里挂上 securityfs 后就能看到生效的模块列表和当前进程的 capability 位。

6. 自测

Q1. DAC 和 MAC 有什么区别？DAC（自主访问控制）是传统 UNIX 权限位模型，文件属主可以随意修改权限，隐含假设属主可信；MAC（强制访问控制）由中央安全策略决定，绕不开，SELinux/AppArmor 属于此类。
Q2. call_int_hook 里 RC != 0 时会发生什么？立即停止遍历链表，该非零值作为整个钩子的结果返回。LSM 的约定是 0 表示"不反对"，非 0（通常是负 errno）表示拒绝，协议栈据此返回错误。
Q3. lsm_hook_defs.h 被 include 三次分别生成什么？第一次生成函数指针联合体 union security_list_options（模块回调表用）；第二次生成钩子链表头数组 struct security_hook_heads；第三次生成每个钩子的默认值常量（LSM_RET_DEFAULT(name)）。
Q4. /sys/kernel/security/lsm 里的内容是怎么来的？由 security_add_hooks 里的 lsm_append 按模块注册顺序追加到全局字符串 lsm_names，securityfs 用 lsm_read 原样输出。顺序即执行顺序即优先级。
Q5. 为什么 LSM 链表用 hlist_add_tail_rcu？tail 保证执行顺序等于注册顺序（由启动参数 lsm= 决定）；RCU 保证遍历侧（call_int_hook 在 RCU 读侧临界区）不会被注册/卸载操作阻塞。
Q6. cap_capable 里的 namespace 遍历逻辑是什么？沿目标 user namespace 逐级向上：目标即自己则看 cap_effective；目标层级比自己低则拒绝；自己是目标直接父 ns 的属主则拥有全部能力；在父 ns 有该能力则对所有子 ns 有效。
Q7. 为什么说 LSM 框架是"策略与机制分离"？内核只在固定位置调用 security_xxx() 壳，壳内遍历模块回调；具体的策略判断全在模块里（SELinux 的策略引擎、AppArmor 的路径匹配）。新增策略不需要改内核代码。
Q8. SELinux 的 selinux_file_open 为什么要保存策略版本号并做二次检查？防止 TOCTOU：前一次权限检查通过后，inode 的标签或策略本身可能已被修改，保存的 pseqno/isid 让后续检查能判断是否需要重新验证（revalidate），否则被撤销的授权将永远生效。
