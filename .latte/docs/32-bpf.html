🧪 eBPF：内核里的安全虚拟机

不写内核模块、不重启、不冒崩溃风险，把自定义程序插进内核热点路径执行 · 预计阅读 13 分钟

1. 它在解决什么问题

假设你在一栋大楼里做安全检查：想查清所有包裹的流向、想拦住可疑物品、想统计每个电梯的使用频率。传统做法是「改造大楼」——加装固定管道、改结构（这相当于编译并加载内核模块），一旦设计错了，整栋楼可能塌。

另一个做法是在楼里放一台「可编程的安检机器人」：管理员随时可以给它换一套规则，但机器人被严格限制——只能看不能砸墙、只能在指定房间活动、不能打电话出去、运行时间超了就自动停。eBPF（extended Berkeley Packet Filter）就是这台机器人：一段由你写、由内核先审查再执行的小程序。

从操作系统角度看，内核一直缺一块「安全的可编程性」：性能观测、包过滤、安全策略、流量整形都需要在内核里看数据、改行为，但每个需求都编一个模块代价太高，而且任意模块都能让内核 panic。eBPF 用三件事解决：受限指令集（只能执行经过验证的指令）、静态验证器（加载前证明程序不会越界/死循环/泄露指针）、JIT 编译（验证通过后翻译成机器码，性能接近原生）。

它最初只是 tcpdump 用的包过滤器，2014 年重写后扩展成通用执行引擎，如今 bpftrace、Cilium、XDP 抗 DDoS、容器安全策略都建在它上面。理解 eBPF，等于理解现代 Linux 可观测与网络加速的公共底座。

4. 源码走读

4.1 系统调用入口：用 cmd 分派

bpf() 只有一个 union bpf_attr 参数，靠第一个参数 cmd 分派到不同操作。注意开头的 sysctl_unprivileged_bpf_disabled：默认非特权用户不能随便加载程序。

kernel/bpf/syscall.c:4357-4386 SYSCALL_DEFINE3(bpf)

SYSCALL_DEFINE3(bpf, int, cmd, union bpf_attr __user *, uattr, unsigned int, size)
{
	union bpf_attr attr;
	int err;

	if (sysctl_unprivileged_bpf_disabled && !bpf_capable())
		return -EPERM;

	err = bpf_check_uarg_tail_zero(uattr, sizeof(attr), size);
	if (err)
		return err;
	size = min_t(u32, size, sizeof(attr));

	/* copy attributes from user space, may be less than sizeof(bpf_attr) */
	memset(&attr, 0, sizeof(attr));
	if (copy_from_user(&attr, uattr, size) != 0)
		return -EFAULT;

	err = security_bpf(cmd, &attr, size);
	if (err < 0)
		return err;

	switch (cmd) {
	case BPF_MAP_CREATE:
		err = map_create(&attr);
		break;
	case BPF_MAP_LOOKUP_ELEM:
		err = map_lookup_elem(&attr);
		break;
    // ...（省略：UPDATE/DELETE/GET_NEXT_KEY、BPF_PROG_LOAD 等数十个分支）
  • bpf_check_uarg_tail_zero 防「用户态传了比内核期望更长的结构、尾部长不为零」的兼容性陷阱——允许旧结构，但多出的字节必须清零。
  • security_bpf 是 LSM 钩子（例如 lockdown 模式会在此拒绝）。
  • 每个 case 最终返回一个 fd（-1 到 n），用户态拿到 fd 就能 attach 或操作对象。

4.2 一次程序加载的完整流程

BPF_PROG_LOAD 落到 bpf_prog_load。它先做权限与配额检查，再拷贝指令，最后交给验证器。验证器是整个 eBPF 安全模型的守门人。

kernel/bpf/syscall.c:2119-2160, 2208-2212 bpf_prog_load（节选）

	if (attr->insn_cnt == 0 ||
	    attr->insn_cnt > (bpf_capable() ? BPF_COMPLEXITY_LIMIT_INSNS : BPF_MAXINSNS))
		return -E2BIG;
	if (type != BPF_PROG_TYPE_SOCKET_FILTER &&
	    type != BPF_PROG_TYPE_CGROUP_SKB &&
	    !bpf_capable())
		return -EPERM;

	if (is_net_admin_prog_type(type) && !capable(CAP_NET_ADMIN) && !capable(CAP_SYS_ADMIN))
		return -EPERM;
	if (is_perfmon_prog_type(type) && !perfmon_capable())
		return -EPERM;
    // ...（省略：license 检查、attach 类型校验、bpf_prog_alloc）

	err = -EFAULT;
	if (copy_from_user(prog->insns, u64_to_user_ptr(attr->insns),
			   bpf_prog_insn_size(prog)) != 0)
		goto free_prog;

    // ...（省略：find_prog_type、prog_name 拷贝、btf 处理）

要点：非特权用户只允许 socket filter / cgroup skb 这两类（历史上最安全的两类），且指令数上限只有 BPF_MAXINSNS（4096）；带 CAP_BPF/CAP_SYS_ADMIN 才有更高上限。网络型程序还要 CAP_NET_ADMIN，跟踪型程序要 CAP_PERFMON。权限分权设计得很细，正是为了不把「能跑内核代码」这个能力随手送人。

4.3 验证器主循环 do_check

验证器分两遍：第一遍 check_cfg 用 DFS 检查程序是合法的有向无环图（无越界跳转、无不可达指令、无回边循环），第二遍 do_check 沿所有路径模拟执行。看 do_check 的骨架：

kernel/bpf/verifier.c:9280-9312 do_check（节选，主循环开头）

		insn = &insns[env->insn_idx];
		class = BPF_CLASS(insn->code);

		if (++env->insn_processed > BPF_COMPLEXITY_LIMIT_INSNS) {
			verbose(env,
				"BPF program is too large. Processed %d insn\n",
				env->insn_processed);
			return -E2BIG;
		}

		err = is_state_visited(env, env->insn_idx);
		if (err < 0)
			return err;
		if (err == 1) {
			/* found equivalent state, can prune the search */
			if (env->log.level & BPF_LOG_LEVEL) {
				verbose(env, "\nfrom %d to %d%s: safe\n",
					env->prev_insn_idx, env->insn_idx,
					env->cur_state->speculative ?
					" (speculative execution)" : "");
				// ...（省略：日志格式细节）
			}
			goto process_bpf_exit;
		}

		if (signal_pending(current))
			return -EAGAIN;

		if (need_resched())
			cond_resched();

四个关键点：BPF_COMPLEXITY_LIMIT_INSNS 限制「验证工作量」而不是指令条数——聪明的程序能用少量指令展开大量分支，这个计数器保证验证不会把 CPU 耗死。is_state_visited 是状态剪枝：如果到达某条指令时寄存器/栈状态与之前某次相同，这条路就不用再分析（返回 1 表示已证明安全）。signal_pending/cond_resched 则让长时间验证可被中断、可让出 CPU，避免用户态被挂住。

4.4 每类指令的类型检查

接着是真正的分派：按指令大类（ALU、LDX、STX、ST、JMP）分别检查。以 BPF_LDX（读内存）为例，它要求源寄存器是一个已初始化且类型可读的指针，再检查 reg + off 这段内存是否在所属对象（map 值、栈、ctx）的合法范围内。

		if (class == BPF_ALU || class == BPF_ALU64) {

				return err;

					       BPF_READ, insn->dst_reg, false);
			if (err)
				return err;

而 check_reg_arg 对「类型」的把关是这样：

kernel/bpf/verifier.c:1717-1748 check_reg_arg（节选）

static int check_reg_arg(struct bpf_verifier_env *env, u32 regno,
			 enum reg_arg_type t)
{
	struct bpf_verifier_state *vstate = env->cur_state;
	struct bpf_func_state *state = vstate->frame[vstate->curframe];
	struct bpf_insn *insn = env->prog->insnsi + env->insn_idx;
	struct bpf_reg_state *reg, *regs = state->regs;
	bool rw64;

	if (regno >= MAX_BPF_REG) {
		verbose(env, "R%d is invalid\n", regno);
		return -EINVAL;
	}

	reg = &regs[regno];
	rw64 = is_reg64(env, insn, regno, reg, t);
	if (t == SRC_OP) {
		/* check whether register used as source operand can be read */
		if (reg->type == NOT_INIT) {
			verbose(env, "R%d !read_ok\n", regno);
			return -EACCES;
		}
		/* We don't need to worry about FP liveness because it's read-only */
		if (regno == BPF_REG_FP)
			return 0;

reg->type == NOT_INIT 这条检查极其重要：它把「读未初始化的栈内存」变成一条硬错误（R3 !read_ok）。因为 eBPF 程序能直接读内核栈，如果不限制，就能把内核栈里的残留数据通过 map 泄露给用户态——这正是历史上真实出现过的漏洞类型。mark_reg_read 则记录「这个寄存器/栈槽在后续某条路径会被读」，用于分析未初始化。

4.5 指针算术的边界追踪

eBPF 里指针可以加常量或变量，但不能被随意「造出来」。验证器给每个指针寄存器维护固定的 off 和可变范围 {smin,smax,umin,umax}。加常量时直接把偏移累加，但要求不溢出 s32 的 off 字段：

kernel/bpf/verifier.c:5536-5557 adjust_ptr_min_max_vals（BPF_ADD 分支）

	case BPF_ADD:
		ret = sanitize_ptr_alu(env, insn, ptr_reg, dst_reg, smin_val < 0);
		if (ret < 0) {
			verbose(env, "R%d tried to add from different maps or paths\n", dst);
			return ret;
		}
		/* We can take a fixed offset as long as it doesn't overflow
		 * the s32 'off' field
		 */
		if (known && (ptr_reg->off + smin_val ==
			      (s64)(s32)(ptr_reg->off + smin_val))) {
			/* pointer += K.  Accumulate it into fixed offset */
			dst_reg->smin_value = smin_ptr;
			dst_reg->smax_value = smax_ptr;
			dst_reg->umin_value = umin_ptr;
			dst_reg->umax_value = umax_ptr;
			dst_reg->var_off = ptr_reg->var_off;
			dst_reg->off = ptr_reg->off + smin_val;
			dst_reg->raw = ptr_reg->raw;
			break;
		}

sanitize_ptr_alu 防的是 Spectre-v1 型侧信道：指针加变量时插入掩码让非法分支的偏移被夹住。smin/smax/umin/umax 的四元组让验证器能做「区间推理」：比如已知 i < 8（分支条件收窄），那么 buf[i] 访问就被证明不越界。这就是「eBPF 不需要运行时检查也能保证安全」的来源。

4.6 验证通过之后：JIT 还是解释器

验证成功后 bpf_prog_select_runtime 决定执行方式：先装好解释器入口，再尝试 JIT 编译；若 JIT 失败（或架构不支持）就回退到解释器。

kernel/bpf/core.c:1796-1813 bpf_prog_select_runtime（节选）

struct bpf_prog *bpf_prog_select_runtime(struct bpf_prog *fp, int *err)
{
	/* In case of BPF to BPF calls, verifier did all the prep
	 * work with regards to JITing, etc.
	 */
	if (fp->bpf_func)
		goto finalize;

	bpf_prog_select_func(fp);

	/* eBPF JITs can rewrite the program in case constant
	 * blinding is active. However, in case of error during
	 * blinding, bpf_int_jit_compile() must always return a
	 * valid program, which in this case would simply not
	 * be JITed, but falls back to the interpreter.
	 */
	if (!bpf_prog_is_dev_bound(fp->aux)) {
		*err = bpf_prog_alloc_jited_linfo(fp);
		if (*err)
			return fp;

		fp = bpf_int_jit_compile(fp);
        // ...（省略：JIT 失败且 CONFIG_BPF_JIT_ALWAYS_ON 时的处理）

解释器本体在 core.c 的 ___bpf_prog_run，它用 GCC 的「计算 goto」把 256 种 opcode 映射成标签，每个标签就是一段 C 代码——比朴素 switch 快，但仍远不如 JIT。CONFIG_BPF_JIT_ALWAYS_ON 打开时（多数发行版默认）只允许 JIT，避免解释器被用于绕过 Spectre 缓解措施。

6. 自测

Q1. 为什么 eBPF 程序不需要每次访问内存都做越界检查？因为验证器在加载时已沿所有路径证明「此访问必然落在合法对象范围内」，并把结论固化到程序里。运行时的代价只是一条普通指令。
Q2. BPF 程序能否调用任意内核函数？不能。只能调用该程序类型白名单里的 helper（由 env->ops->get_func_proto 决定），且 helper 参数会按 bpf_func_proto 声明的类型再检查一遍。普通内核函数地址对程序不可见。
Q3. map 为什么必须由内核和用户态共享？程序在内核跑、结果要交给用户态读。map 是双方都可访问的受控容器，用户态用 BPF_MAP_LOOKUP_ELEM 读、程序用 bpf_map_lookup_elem 读，避免程序直接往用户内存写。
Q4. 状态剪枝（is_state_visited）解决什么问题？分支多的程序路径数指数爆炸。若两条路径到达同一指令时寄存器/栈状态等价，后续行为必然相同，已验证过一次就够了，可剪掉整棵子树。
Q5. XDP 为什么比 iptables 快？XDP 在驱动收包的最早期执行，此时还没分配 sk_buff、没走协议栈，可以直接 XDP_DROP。普通 netfilter 钩子已经在 skb 分配和部分解析之后，成本高得多。
