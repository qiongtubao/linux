🖥️ KVM 虚拟化

让一个 Linux 内核同时「租」出多个独立的 CPU 和内存给别的操作系统 · 预计阅读 12 分钟

1. 它在解决什么问题

想象你有一栋自建楼，自己想住，但空房间太多。最省事的做法不是另建一栋，而是在原有结构上加装一层「可拆卸夹层」：楼还是那栋楼，水电总管线还是那套，但每个夹层里可以住进一户完全独立的租客，他们有自己的门牌、自己的家具，甚至不知道自己住在夹层里。住户之间互不相见，房东（你）随时能上楼查看。

KVM（Kernel-based Virtual Machine）就是这层夹层。它不改变 Linux 内核的本质，而是把这个内核变成 hypervisor（虚拟机监控器）：宿主机内核照常跑进程、管内存、调度 CPU，同时在 CPU 硬件提供的「隔离模式」里再跑若干个完整的客户操作系统（guest）。

从操作系统视角看，问题是这样：一个内核默认认为自己独占 CPU 的所有特权指令（改页表基址、关中断、读写控制寄存器）。若让第二个内核也直接执行这些指令，必然互相踩踏。解决办法只有两条：一是全虚拟化——靠硬件在每次执行特权指令时把控制权交回宿主机，「骗」客户机它仍是老大；二是半虚拟化——改客户机代码，把敏感操作改成主动「敲门」调用宿主机（hypercall）。KVM 走第一条路，依赖 Intel VT-x / AMD-V 这样的硬件扩展。

而 KVM 在内核里只做「最硬的那部分」：创建 vCPU、进入/退出客户机、处理退出原因、维护客户机内存映射。剩下的设备模拟（网卡、磁盘、显示器、BIOS）全部交给用户态的 QEMU。所以「KVM 加速的虚拟机」其实是 KVM + QEMU 的合体。

3. 整体结构

先看硬件模式。CPU 加电后处于 VMX root；执行 VMLAUNCH/VMRESUME 指令就切入 non-root 跑客户机，遇到「被截获的事件」再自动回到 root 的固定入口 vmx_vmexit。


             ┌──────────── VMX root operation（宿主机内核）────────────┐
             │ 普通 Linux 代码：调度、中断、文件系统、KVM 模块        │
             │                                                        │
             │   vmx_vcpu_run() ──► vmx_vmenter ──┐                   │
             │                                   │ VMLAUNCH/VMRESUME │
             │   vmx_vmexit ◄────────────────────┼── 硬件 VM-exit    │
             └───────────────────────────────────┼────────────────────┘
                                                 │
             ┌──────────── VMX non-root operation（客户机）──────────┐
             │ 客户机内核执行普通指令；遇到敏感操作被硬件「截获」      │
             │ 例：out 指令、写 CR3、访问 EPT 里没有的页面、CPUID      │
             └───────────────────────────────────────────────────────┘

再看软件分层与一次 KVM_RUN 的生命周期：


QEMU（用户态）
  │  open("/dev/kvm") → KVM_CREATE_VM（得到 VM fd）
  │  → KVM_CREATE_VCPU（得到 vCPU fd）→ mmap(kvm_run 共享页)
  │
  ├─ ioctl(vcpu_fd, KVM_RUN, 0)  ───────────────┐
  │                                             │ 内核态
  │                        kvm_vcpu_ioctl()     │
  │                          └ kvm_arch_vcpu_ioctl_run()
  │                              └ vcpu_run() ──► vcpu_enter_guest()
  │                                   └ kvm_x86_ops.run() = vmx_vcpu_run()
  │                                        └ __vmx_vcpu_run()  ← 汇编，真正 VMENTER
  │                                             …客户机运行…
  │                                        ◄── VM-EXIT（硬件跳回 vmx_vmexit）
  │                              vcpu_enter_guest() 里 kvm_x86_ops.handle_exit()
  │                                   └ vmx_handle_exit() → 退出原因分发表
  │
  └─ KVM_RUN 返回，读 kvm_run->exit_reason，QEMU 据此模拟设备/注入中断
     然后再次 KVM_RUN，循环往复

关键点：一次 KVM_RUN 只处理「一次进入 + 一次退出」或一个内部小循环。I/O 端口访问、MMIO、HLT 这些设备行为由 QEMU 处理；EPT 缺页、CPUID、CR 访问这类由内核直接处理，用户态无感知。

4. 源码走读

4.1 KVM_RUN 的入口

用户态 ioctl 落到通用层 kvm_vcpu_ioctl。这里先校验调用者 mm 与创建 VM 时是否一致（防止跨进程偷跑别人 VM 的 vCPU），再在 KVM_RUN 分支里记录「当前是哪个线程在跑这个 vCPU」，最后交给架构层。

virt/kvm/kvm_main.c:3213-3237 kvm_vcpu_ioctl

	switch (ioctl) {
	case KVM_RUN: {
		struct pid *oldpid;
		r = -EINVAL;
		if (arg)
			goto out;
		oldpid = rcu_access_pointer(vcpu->pid);
		if (unlikely(oldpid != task_pid(current))) {
			/* The thread running this VCPU changed. */
			struct pid *newpid;

			r = kvm_arch_vcpu_run_pid_change(vcpu);
			if (r)
				break;

			newpid = get_task_pid(current, PIDTYPE_PID);
			rcu_assign_pointer(vcpu->pid, newpid);
			if (oldpid)
				synchronize_rcu();
			put_pid(oldpid);
		}
		r = kvm_arch_vcpu_ioctl_run(vcpu);
		trace_kvm_userspace_exit(vcpu->run->exit_reason, r);
		break;
	}

逐点说明：

  • if (arg) —— KVM_RUN 不接受参数，传了就是错的；所有状态通过 kvm_run 共享页传递。
  • vCPU 可以被不同的用户态线程执行（QEMU 允许迁移线程绑定），换了线程要通知架构层（比如重设 FPU/APIC 相关状态）。
  • 用 RCU 指针 + synchronize_rcu() 安全地替换 vcpu->pid，因为其他路径可能在 RCU 读侧查看它。
  • kvm_arch_vcpu_ioctl_run 就是进入 x86 专有逻辑的门；返回时 vcpu->run->exit_reason 已经填好。

4.2 vCPU 的主循环

架构无关的「跑一轮」由 vcpu_run 负责。它是一个 for(;;)：只要还能继续（返回 > 0），就反复进出客户机，直到需要把控制权交还用户态。

arch/x86/kvm/x86.c:9082-9107 vcpu_run

static int vcpu_run(struct kvm_vcpu *vcpu)
{
	int r;
	struct kvm *kvm = vcpu->kvm;

	vcpu->srcu_idx = srcu_read_lock(&kvm->srcu);
	vcpu->arch.l1tf_flush_l1d = true;

	for (;;) {
		if (kvm_vcpu_running(vcpu)) {
			r = vcpu_enter_guest(vcpu);
		} else {
			r = vcpu_block(kvm, vcpu);
		}

		if (r <= 0)
			break;

		kvm_clear_request(KVM_REQ_PENDING_TIMER, vcpu);
		if (kvm_cpu_has_pending_timer(vcpu))
			kvm_inject_pending_timer_irqs(vcpu);
        // ...（省略：中断窗口检查、guest-mode 工作处理）
	}
	srcu_read_unlock(&kvm->srcu, vcpu->srcu_idx);
	return r;
}

srcu_read_lock 保护的是客户机内存槽表：运行期间不能让内存槽被并发删掉。kvm_vcpu_running() 为假说明 vCPU 处于 HLT 等阻塞态，此时走 vcpu_block 睡眠等待事件。返回值 <= 0 是「要回用户态了」的信号，最常见的 0 就是 I/O 或 MMIO 需要 QEMU 处理。

4.3 vcpu_enter_guest 的后半段：从硬件退回到事件处理

前面一大段在处理各类 KVM_REQ_* 请求（刷新 TLB、同步时钟、注入 NMI……），真正的「进客户机」是 kvm_x86_ops.run(vcpu)。返回后 CPU 已经回到 root 模式，接着要做的是恢复宿主机上下文、处理退出原因。

arch/x86/kvm/x86.c:8979-9028 vcpu_enter_guest（节选）

	vcpu->arch.last_vmentry_cpu = vcpu->cpu;
	vcpu->arch.last_guest_tsc = kvm_read_l1_tsc(vcpu, rdtsc());

	vcpu->mode = OUTSIDE_GUEST_MODE;
	smp_wmb();

	kvm_x86_ops.handle_exit_irqoff(vcpu);

	/*
	 * Consume any pending interrupts, including ... any ticks that occur
	 * between VM-Exit and now.
	 */
	kvm_before_interrupt(vcpu);
	local_irq_enable();
	++vcpu->stat.exits;
	local_irq_disable();
	kvm_after_interrupt(vcpu);
    // ...（省略：LAPIC 定时器延迟统计）
	vcpu->srcu_idx = srcu_read_lock(&vcpu->kvm->srcu);
    // ...（省略：exit RIP profiling、时钟请求、vapic 同步）

	r = kvm_x86_ops.handle_exit(vcpu, exit_fastpath);
	return r;
  • vcpu->mode = OUTSIDE_GUEST_MODE 是「我已经不在客户机里」的公开标志，配合写屏障，让其他 CPU 上的 IPI/请求能看到状态切换。
  • VM-exit 后中断是关的（硬件保证），这里短暂 local_irq_enable() 把宿主机积压的中断消化掉，再关上继续处理，避免软中断/定时器饿死。
  • srcu_read_lock 重新拿锁，因为 handle_exit 里可能访问内存槽（如 MMIO 地址翻译）。
  • 最后一次调用 kvm_x86_ops.handle_exit —— 这是转到厂商实现的钩子（Intel 走 vmx_handle_exit）。

4.4 真正的 VMENTER 是一条汇编指令

vmx_vcpu_run 里最终调用 __vmx_vcpu_run，它先把客户机通用寄存器装好，再 call vmx_vmenter。切换之所以能「一条指令完成」，是因为 CPU 自动从 VMCS 里加载客户机状态、并从 VMCS 的 HOST_RIP 找到退出后的落脚点。

arch/x86/kvm/vmx/vmenter.S:47-65 vmx_vmenter

SYM_FUNC_START(vmx_vmenter)
	/* EFLAGS.ZF is set if VMCS.LAUNCHED == 0 */
	je 2f

1:	vmresume
	ret

2:	vmlaunch
	ret

3:	cmpb $0, kvm_rebooting
	je 4f
	ret
4:	ud2

	_ASM_EXTABLE(1b, 3b)
	_ASM_EXTABLE(2b, 3b)

SYM_FUNC_END(vmx_vmenter)

VMLAUNCH 用于从未启动过的 VMCS，VMRESUME 用于已经启动过的。两者「成功时不返回」：CPU 直接跳进客户机；只有 VM-Fail（比如 VMCS 配置非法）才落到 ret。_ASM_EXTABLE 把异常路径指向 3:，那里检查 kvm_rebooting 后 ud2，属于「不可能发生但必须兜底」的处理。vmx_vmexit（同文件 73 行起）是 HOST_RIP 指向的落点，它要在 ret 前用 FILL_RETURN_BUFFER 填充 RSB，防 Spectre 类攻击。

4.5 EPT 缺页：客户机以为自己缺页，其实是 KVM 缺页

客户机访问一个没建立 EPT 映射的 GPA 时，硬件产生 EXIT_REASON_EPT_VIOLATION。KVM 的 handler 把硬件给的「退出资格」（exit qualification）翻译成类似 x86 缺页错误码的格式，再交给 MMU 层去建立映射。

arch/x86/kvm/vmx/vmx.c:5304-5342 handle_ept_violation

static int handle_ept_violation(struct kvm_vcpu *vcpu)
{
	unsigned long exit_qualification;
	gpa_t gpa;
	u64 error_code;

	exit_qualification = vmx_get_exit_qual(vcpu);

	/* ...（省略：从 NMI 中 iret 时设置 GUEST_INTR_STATE_NMI 的勘误处理） */

	gpa = vmcs_read64(GUEST_PHYSICAL_ADDRESS);
	trace_kvm_page_fault(gpa, exit_qualification);

	/* Is it a read fault? */
	error_code = (exit_qualification & EPT_VIOLATION_ACC_READ)
		     ? PFERR_USER_MASK : 0;
	/* Is it a write fault? */
	error_code |= (exit_qualification & EPT_VIOLATION_ACC_WRITE)
		      ? PFERR_WRITE_MASK : 0;
	/* Is it a fetch fault? */
	error_code |= (exit_qualification & EPT_VIOLATION_ACC_INSTR)
		      ? PFERR_FETCH_MASK : 0;
	/* ept page table entry is present? */
	error_code |= (exit_qualification &
		       (EPT_VIOLATION_READABLE | EPT_VIOLATION_WRITABLE |
			EPT_VIOLATION_EXECUTABLE))
		      ? PFERR_PRESENT_MASK : 0;
    // ...（省略：PFERR_GUEST_FINAL / PFERR_GUEST_PAGE 的选择）
	return kvm_mmu_page_fault(vcpu, gpa, error_code, NULL, 0);
}

GUEST_PHYSICAL_ADDRESS 是出错的 GPA，也就是「客户机以为的物理地址」；kvm_mmu_page_fault 会去查内存槽，找到这段 GPA 对应的宿主机虚拟地址（HVA），再用 __pa() 换成 HPA 写进 EPT 表项。若这段 GPA 根本没有内存槽，KVM 就会产生 MMIO 退出，把控制权交回 QEMU 模拟设备——这就是「访问设备寄存器」的底层实现。目录 arch/x86/kvm/mmu/ 中 mmu.c 管软件遍历，tdp_mmu.c 是 EPT/NPT 专用的两维页表遍历器，spte.c 负责 EPT 表项位的组装与检查。

4.6 退出原因分发表

VM-exit 的原因是一个整数，所以 Intel 侧的处理就是一张函数指针表 + 一次数组索引。注意 array_index_nospec：防止推测执行把越界的 exit_reason 用作索引。

arch/x86/kvm/vmx/vmx.c:5628-5636, 6063-6068 kvm_vmx_exit_handlers / vmx_handle_exit

static int (*kvm_vmx_exit_handlers[])(struct kvm_vcpu *vcpu) = {
	[EXIT_REASON_EXCEPTION_NMI]           = handle_exception_nmi,
	[EXIT_REASON_EXTERNAL_INTERRUPT]      = handle_external_interrupt,
	[EXIT_REASON_TRIPLE_FAULT]            = handle_triple_fault,
	[EXIT_REASON_NMI_WINDOW]	      = handle_nmi_window,
	[EXIT_REASON_IO_INSTRUCTION]          = handle_io,
	[EXIT_REASON_CR_ACCESS]               = handle_cr,
	[EXIT_REASON_DR_ACCESS]               = handle_dr,
	[EXIT_REASON_CPUID]                   = kvm_emulate_cpuid,
    // ...（省略：其余几十个表项，如 EPT_VIOLATION、HLT、MSR 读写、INVLPG）

	exit_reason = array_index_nospec(exit_reason,
					 kvm_vmx_max_exit_handlers);
	if (!kvm_vmx_exit_handlers[exit_reason])
		goto unexpected_vmexit;

	return kvm_vmx_exit_handlers[exit_reason](vcpu);

以 handle_io 为例：它解析端口号、宽度、in/out 方向，调用 kvm_fast_pio。如果该端口在 KVM 内部有模拟器（比如串口、PIC），内核直接完成；否则填好 vcpu->run->exit_reason = KVM_EXIT_IO 并带着端口信息返回 0，让 QEMU 去处理。

5. 动手验证

(1) 先确认硬件与内核支持：

$ ls -l /dev/kvm
crw------- 1 root root 10, 232  8月 20 09:11 /dev/kvm
$ egrep -c '(vmx|svm)' /proc/cpuinfo   # ≥1 表示 CPU 有虚拟化扩展

(4) 观察 vCPU 线程和统计：

$ ps -T -p $(pgrep -f qemu-system) | grep CPU
  PID  SPID TTY   TIME CMD
 1234  1240 ?    00:00:01 CPU 0/KVM
 1234  1241 ?    00:00:01 CPU 1/KVM
$ sudo perf kvm stat live           # 需要 root，展示各 exit_reason 的占比
$ ls /sys/module/kvm_intel/parameters/
nested  ept  unrestricted_guest  ...

预期：-smp 2 对应两个名为 CPU N/KVM 的线程；perf kvm stat 里 EXTERNAL_INTERRUPT、MSR_WRITE、EPT_VIOLATION 往往排前列，说明「大部分时间客户机在跑，退出是稀疏事件」——这正是硬件虚拟化高效的原因。

不要在生产机上随意给 /dev/kvm 全局可读写。任何拿到该 fd 的进程都能创建 VM，配合 KVM_SET_USER_MEMORY_REGION 可读写任意物理内存。

6. 自测

Q1. 为什么 KVM 的 VM-exit 对性能影响不大？因为客户机大部分指令是「非敏感」的，直接在 non-root 模式执行，不需要陷入；只有 I/O、缺页、CPUID 这类操作才产生 VM-exit。硬件负责保存/恢复状态，退出成本约几千个周期，不是每条指令都付。
Q2. EPT 解决了影子页表的什么问题？影子页表要为每个客户机进程维护一份「GVA→HPA」的合成页表，客户机改页表时软件必须同步，开销大且易错。EPT 让硬件做第二级翻译（GPA→HPA），客户机维护自己的页表完全不受干扰，KVM 只补 EPT 表项。
Q3. 一次 KVM_RUN 返回 0 且 exit_reason=KVM_EXIT_IO，谁来完成这次 I/O？QEMU。内核只在 kvm_run 里填好端口、方向、宽度和 data_offset；QEMU 读那个偏移处的数据、模拟设备响应，然后再次 KVM_RUN。
Q4. vCPU 为什么能对应一个普通 Linux 线程？因为宿主机内核仍在线程里调度它；KVM_RUN 期间该线程阻塞在 ioctl 里，但可被信号打断（-EINTR 加 KVM_EXIT_INTR），也可被宿主机调度器抢占，因此 vCPU 与线程是一一绑定的执行上下文。
Q5. 半虚拟化和全虚拟化在代码里怎么体现？全虚拟化走 VM-exit 后由 KVM/QEMU 模拟；半虚拟化引入 KVM_EXIT_IO/hypercall 页（如 KVM_HC_*），客户机装 virtio 驱动，主动发起请求，避免昂贵的设备寄存器陷入。
