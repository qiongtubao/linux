📦 38-cgroup 资源控制

把"一群进程"当作一个整体来限制 CPU、内存、IO 与进程数；容器资源限制的实现底座 · 约 14 分钟

1. 它在解决什么问题

想象一栋公寓楼，每户人家有自己的电表和水量表。物业想给某户设定"每月用电不超过 200 度"，超额就自动断电；同时也要保证整栋楼的总用电不超过变压器容量。这套"按住户而不是按电线计量和限流"的机制，就是 cgroup。

在没有 cgroup 的年代，Unix 只有"用户"这一个资源计量单位——setrlimit() 限制的是单个进程的地址空间和文件大小。但真实需求是"一组进程共享一份配额"：一个 Java 应用有几十个线程加上若干子进程，它们应该合起来不超过 1 GB 内存，而不是每个进程各自 1 GB。cgroup 提供的正是这个"进程组"概念。

第二个需求是分层。不能只有"一组进程"，还需要"组里的子组"：整台机器 16 GB → 交给"测试环境" 8 GB → 测试环境里的"单个用例" 2 GB。资源用量自底向上汇总，限制自顶向下传递。这和容器的 image 层级、namespace 的嵌套是同构的设计。

第三个需求是资源控制器的可插拔。CPU 限速、内存上限、磁盘 IO 限速、进程数上限——这些是完全不同的机制，但都遵循同一个模式：内核在关键路径上问一句"这个进程组现在用了多少？超了吗？"。cgroup 框架提供这个提问机制和记账框架，各控制器（controller）自己去实现。

第四个需求是与 namespace 配合。namespace 负责"隔离视野"（这个容器只能看到自己的进程、自己的网络、自己的文件系统），cgroup 负责"限制资源"。两者合起来才构成完整的容器：namespace 是围墙，cgroup 是配额表。Docker 的 docker run --memory=512m 就是往 cgroup 里写一个 memory.max = 536870912。

最后一个现实问题是历史包袱。cgroup v1 为每个控制器单独做一套层级：内存一套、CPU 一套、IO 一套……同一个进程在每套层级里各有一个位置。结果是"进程属于哪个组"这个问题有多个答案，容器要同时配好几套。cgroup v2 把所有控制器合并成一棵统一的树，一个进程在整棵树里只有一个位置，简单得多。v1 在 5.10 里仍然完整保留，但新系统默认用 v2。

3. 整体结构

3.1 一棵树的形状

  cgroup v2 统一层级（挂载在 /sys/fs/cgroup）

  /sys/fs/cgroup/                     ← 根 cgroup
  ├── user.slice/                     ← systemd 的用户切片
  │   ├── user-1000.slice/
  │   │   ├── user-1000.slice.scope/  ← 一个服务
  │   │   └── session-3.scope/
  │   └── user-1001.slice/
  ├── system.slice/
  │   ├── sshd.service/
  │   │   ├── 1234/                  ← 进程迁入这里
  │   │   └── ...
  │   └── docker-abc.scope/
  └── machine.slice/

  每个节点下都有这些文件（片段）：
    cgroup.procs          该组里的进程 PID 列表
    cgroup.threads        该组里的线程 TID 列表
    cgroup.controllers    本节点可用的控制器
    cgroup.subtree_control  已下发给子组的控制器
    cgroup.type           domain / threaded / threaded-domain
    memory.max            内存上限
    memory.current        当前用量
    memory.events         low/high/max/oom/oom_kill 计数
    cpu.max               CPU 配额
    pids.max              进程数上限

3.2 v1 与 v2 的差别

  v1：每个控制器一棵独立的树
  ─────────────────────────────
  /sys/fs/cgroup/memory/         ← 内存树
      ├── docker/
      │   └── abc/
      └── user.slice/
  /sys/fs/cgroup/cpu/            ← CPU 树（跟内存树完全无关）
      ├── docker/
      │   └── abc/
      └── user.slice/
  /sys/fs/cgroup/cpuset/         ← 第三棵树
  ...
  同一个进程在每棵树里各有一个位置，容器要配 N 遍。

  v2：所有控制器共用一棵树
  ─────────────────────────────
  /sys/fs/cgroup/                 ← 唯一的树
      ├── docker/
      │   └── abc/                ← 这里同时管内存、CPU、IO、pids
      └── user.slice/
  一个进程在整棵树里只有一个位置。
维度v1v2
层级数每个控制器一棵全部控制器共用一棵
挂载mount -t cgroup -o memory 等，每控制器挂一次mount -t cgroup2 none /sys/fs/cgroup
限制文件位置在控制器自己的目录下，如 memory/memory.limit_in_bytes统一在节点下，如 memory.max
内部进程允许（有进程和子组并存）默认禁止（no internal process）
CPU 限制cpu.cfs_quota_us + cpu.cfs_period_uscpu.max = "quota period"
内存限制memory.limit_in_bytes（软硬两级）memory.max（硬）+ memory.high（软）
启用子组控制器不用显式开（各树独立）要往 cgroup.subtree_control 里写 "+cpu"
状态仍在维护，但已冻结新功能当前推荐

3.3 内部对象关系

  task_struct
      │
      │ current->cgroups ──► css_set（每个进程一个）
      │                          │
      │                          ├── subsys[0] ──► cgroup_subsys_state (memory)
      │                          ├── subsys[1] ──► cgroup_subsys_state (cpu)
      │                          ├── subsys[2] ──► cgroup_subsys_state (io)
      │                          └── subsys[3] ──► cgroup_subsys_state (pids)
      │                                    │
      │                                    └── cgroup ──► struct cgroup
      │                                                        │
      │                                                        └── kn ──► kernfs_node
      │                                                                     │
      └── cg_list ◄────────── tasks 链表（每个 css_set 一条）        └── 子 cgroup 树

  为什么用 css_set？
  一个进程可能在 4 棵控制器树里各有一个状态指针。
  打包成一个 css_set 后，fork 时只要 refcount++ 和 list_add 一次，
  而不是对每个控制器各做一遍 —— 大幅加快 fork/exit。

css_set 是本篇最关键的设计。它把"一个进程在所有控制器上的位置"打包成一个对象，进程只持有这一个指针。

3.4 内存限制的生效路径

  进程 malloc/mmap 缺页 → 分配物理页
        │
        ▼
  mem_cgroup_charge(page, mm, gfp)      ← mm/memcontrol.c:6766
        │
        ▼
  try_charge(memcg, gfp_mask, nr_pages) ← mm/memcontrol.c:2681
        │
        ├── page_counter_try_charge(&memcg->memory, ...)
        │        │
        │        ├── 成功 → 返回 0，继续
        │        │
        │        └── 失败（超过 memory.max）
        │                 │
        │                 ▼
        │           try_to_free_mem_cgroup_pages()   ← 尝试在本组内回收
        │                 │
        │                 ├── 回收够了 → retry 成功
        │                 │
        │                 └── 回收不出来
        │                          │
        │                          ▼
        │                    mem_cgroup_out_of_memory()
        │                          │
        │                          ▼
        │                    OOM killer 杀进程
        │                    （本组里内存占用最大的那个）
        │
        └── 内存不够且不许阻塞 → 返回 -ENOMEM / -ENOMEM


  路径对应关系：
    memory.max    → memcg->memory.max     ← 上限
    memory.current → page_counter_read(&memcg->memory) * PAGE_SIZE
    memory.high   → memcg->memory.high    ← 软限制，触发回收不杀进程

4. 源码走读

4.1 创建一个 cgroup

kernel/cgroup/cgroup.c:5180-5217

static struct cgroup *cgroup_create(struct cgroup *parent, const char *name,
				    umode_t mode)
{
	struct cgroup_root *root = parent->root;
	struct cgroup *cgrp, *tcgrp;
	struct kernfs_node *kn;
	int level = parent->level + 1;
	int ret;

	/* allocate the cgroup and its ID, 0 is reserved for the root */
	cgrp = kzalloc(struct_size(cgrp, ancestor_ids, (level + 1)),
		       GFP_KERNEL);
	if (!cgrp)
		return ERR_PTR(-ENOMEM);

	ret = percpu_ref_init(&cgrp->self.refcnt, css_release, 0, GFP_KERNEL);
	if (ret)
		goto out_free_cgrp;

	if (cgroup_on_dfl(parent)) {
		ret = cgroup_rstat_init(cgrp);
		if (ret)
			goto out_cancel_ref;
	}

	/* create the directory */
	kn = kernfs_create_dir(parent->kn, name, mode, cgrp);
	if (IS_ERR(kn)) {
		ret = PTR_ERR(kn);
		goto out_stat_exit;
	}
	cgrp->kn = kn;

	init_cgroup_housekeeping(cgrp);

	cgrp->self.parent = &parent->self;
	cgrp->root = root;
	cgrp->level = level;

创建顺序很清楚：先分配 cgroup 对象 → 初始化引用计数 → 建 kernfs 目录 → 挂到父节点。用 kernfs 而不是自己实现文件系统，是因为 kernfs 提供了"每个目录带一组自定义文件"的机制（正是 cgroup.procs、memory.max 这些控制文件的载体）。

struct_size(cgrp, ancestor_ids, (level + 1)) 是变长数组技巧：ancestor_ids 是个 flexible array member，要按层级深度分配——每个 cgroup 记住自己所有祖先的 ID，这样从任意节点都能 O(1) 查到根路径。

4.2 把进程迁入 cgroup

往 cgroup.procs 里写 PID 就触发迁移，代码路径是 cgroup_procs_write → cgroup_attach_task。

kernel/cgroup/cgroup.c:2717-2747

int cgroup_attach_task(struct cgroup *dst_cgrp, struct task_struct *leader,
		       bool threadgroup)
{
	DEFINE_CGROUP_MGCTX(mgctx);
	struct task_struct *task;
	int ret = 0;

	/* look up all src csets */
	spin_lock_irq(&css_set_lock);
	rcu_read_lock();
	task = leader;
	do {
		cgroup_migrate_add_src(task_css_set(task), dst_cgrp, &mgctx);
		if (!threadgroup)
			break;
	} while_each_thread(leader, task);
	rcu_read_unlock();
	spin_unlock_irq(&css_set_lock);

	/* prepare dst csets and commit */
	ret = cgroup_migrate_prepare_dst(&mgctx);
	if (!ret)
		ret = cgroup_migrate(leader, threadgroup, &mgctx);

	cgroup_migrate_finish(&mgctx);

	if (!ret)
		TRACE_CGROUP_PATH(attach_task, dst_cgrp, leader, threadgroup);

	return ret;
}

整个迁移分四步，这是 cgroup 里最需要小心的并发逻辑：

  1. 收集源（cgroup_migrate_add_src）：在 css_set_lock + RCU 读侧保护下，把进程当前的 css_set 记到迁移上下文里。while_each_thread 遍历整个线程组（threadgroup 为真时），保证多线程进程整体搬迁。
  2. 准备目标（cgroup_migrate_prepare_dst）：算出目标 cgroup 对应的 css_set（可能已存在，find_existing_css_set 会复用），并做合法性检查。
  3. 提交（cgroup_migrate → cgroup_migrate_execute）：真正把进程从旧 css_set 的链表移到新的。这是最关键的一步——先调各控制器的 can_attach（任何一个拒绝就整体取消），全部通过后才在 css_set_lock 下真正移动任务，并调用各控制器的 attach 回调。
  4. 收尾（cgroup_migrate_finish）：释放迁移期间临时持有的引用。

关键性质：要么全成功，要么全失败（cgroup_migrate_execute 里 can_attach 失败会调 cancel_attach 回滚）。这保证不会出现"进程在内存控制器里搬了、在 CPU 控制器里没搬"的半吊子状态。

4.3 css_set：进程持有的那一个指针

include/linux/cgroup-defs.h:188-218

/*
 * A css_set is a structure holding pointers to a set of
 * cgroup_subsys_state objects. This saves space in the task struct
 * object and speeds up fork()/exit(), since a single inc/dec and a
 * list_add()/del() can bump the reference count on the entire cgroup
 * set for a task.
 */
struct css_set {
	/*
	 * Set of subsystem states, one for each subsystem. This array is
	 * immutable after creation apart from the init_css_set during
	 * subsystem registration (at boot time).
	 */
	struct cgroup_subsys_state *subsys[CGROUP_SUBSYS_COUNT];

	/* reference count */
	refcount_t refcount;

	/*
	 * For a domain cgroup, the following points to self.  If threaded,
	 * to the matching cset of the nearest domain ancestor.  The
	 * dom_cset provides access to the domain cgroup and its csses to
	 * which domain level resource consumptions should be charged.
	 */
	struct css_set *dom_cset;

	/* the default cgroup associated with this css_set */
	struct cgroup *dfl_cgrp;

	/* internal task count, protected by css_set_lock */
	int nr_tasks;

注释说得很清楚：这个结构是为了省 task_struct 的空间、加速 fork/exit 而存在的。subsys[] 数组在创建后不可变（除了启动时的 init_css_set），所以能放心地被多个进程共享。

dom_cset 是 threaded 模式的关键：普通 cgroup 指向自己；threaded cgroup 指向最近的 domain 祖先的 css_set，这样资源记账总是算到 domain 层级去。

4.5 memory.max 的写入与读取

mm/memcontrol.c:6358-6387

static ssize_t memory_max_write(struct kernfs_open_file *of,
				char *buf, size_t nbytes, loff_t off)
{
	struct mem_cgroup *memcg = mem_cgroup_from_css(of_css(of));
	unsigned int nr_reclaims = MAX_RECLAIM_RETRIES;
	bool drained = false;
	unsigned long max;
	int err;

	buf = strstrip(buf);
	err = page_counter_memparse(buf, "max", &max);
	if (err)
		return err;

	xchg(&memcg->memory.max, max);

	for (;;) {
		unsigned long nr_pages = page_counter_read(&memcg->memory);

		if (nr_pages <= max)
			break;

		if (signal_pending(current))
			break;

		if (!drained) {
			drain_all_stock(memcg);
			drained = true;
			continue;
		}

写 memory.max 时内核不只存下这个值，还会立刻检查当前用量：如果当前用量已经超过新设的上限，就进入回收循环（try_to_free_mem_cgroup_pages），回收不出来就触发 OOM（mem_cgroup_out_of_memory）。这解释了为什么"把 memory.max 改小"可能当场杀掉进程。

xchg 是原子交换，保证并发写时的可见性。

读 memory.current：

mm/memcontrol.c:6248-6254

static u64 memory_current_read(struct cgroup_subsys_state *css,
			       struct cftype *cft)
{
	struct mem_cgroup *memcg = mem_cgroup_from_css(css);

	return (u64)page_counter_read(&memcg->memory) * PAGE_SIZE;
}

就是 page_counter 的当前值乘以页大小。page_counter 是内核里的通用"带上限的计数器"，用 per-CPU 的批量记账 + 原子汇总来减少争用——高并发下这个计数器的性能是关键。

4.6 "无内部进程"规则

v2 的一条重要约束：一个要启用控制器的 cgroup 节点，自己不能直接放进程，否则父组的控制器和子组的控制器会争抢同一份资源，记账就乱了。

kernel/cgroup/cgroup.c:3173-3211

static int cgroup_vet_subtree_control_enable(struct cgroup *cgrp, u16 enable)
{
	u16 domain_enable = enable & ~cgrp_dfl_threaded_ss_mask;

	/* if nothing is getting enabled, nothing to worry about */
	if (!enable)
		return 0;

	/* can @cgrp host any resources? */
	if (!cgroup_is_valid_domain(cgrp->dom_cgrp))
		return -EOPNOTSUPP;

	/* mixables don't care */
	if (cgroup_is_mixable(cgrp))
		return 0;

	if (domain_enable) {
		/* can't enable domain controllers inside a thread subtree */
		if (cgroup_is_thread_root(cgrp) || cgroup_is_threaded(cgrp))
			return -EOPNOTSUPP;
	} else {
		/*
		 * Threaded controllers can handle internal competitions
		 * and are always allowed inside a (prospective) thread
		 * subtree.
		 */
		if (cgroup_can_be_thread_root(cgrp) || cgroup_is_threaded(cgrp))
			return 0;
	}

	/*
	 * Controllers can't be enabled for a cgroup with tasks to avoid
	 * child cgroups competing against tasks.
	 */
	if (cgroup_has_tasks(cgrp))
		return -EBUSY;

	return 0;
}

cgroup_has_tasks(cgrp) 返回 -EBUSY 就是这条规则的实现：这个节点里还有进程，就不能往下发控制器。所以 v2 里正确的用法是"root → 建子组 → 把进程放进子组"，而不是"root → 放进程 → 建子组"。

threaded 模式是官方给的例外：cgroup.type 写成 threaded 后，节点内部可以再放进程和线程组，用于"把一个多线程进程的线程拆开分别限制"的场景。

struct cftype 就是"控制文件描述符"：seq_show 是读回调，write 是写回调，seq_start/seq_next 是遍历时的迭代钩子。cgroup.procs 的写回调 cgroup_procs_write 就是第 4.2 节那条迁移路径的入口。

写 cgroup.subtree_control 的实现：

kernel/cgroup/cgroup.c:3214-3250

static ssize_t cgroup_subtree_control_write(struct kernfs_open_file *of,
					    char *buf, size_t nbytes,
					    loff_t off)
{
	u16 enable = 0, disable = 0;
	struct cgroup *cgrp, *child;
	struct cgroup_subsys *ss;
	char *tok;
	int ssid, ret;

	/*
	 * Parse input - space separated list of subsystem names prefixed
	 * with either + or -.
	 */
	buf = strstrip(buf);
	while ((tok = strsep(&buf, " "))) {
		if (tok[0] == '\0')
			continue;
		do_each_subsys_mask(ss, ssid, ~cgrp_dfl_inhibit_ss_mask) {
			if (!cgroup_ssid_enabled(ssid) ||
			    strcmp(tok + 1, ss->name))
				continue;

			if (*tok == '+') {
				enable |= 1 << ssid;
				disable &= ~(1 << ssid);
			} else if (*tok == '-') {
				disable |= 1 << ssid;
				enable &= ~(1 << ssid);
			} else {
				return -EINVAL;
			}
			break;
		} while_each_subsys_mask();
		if (ssid == CGROUP_SUBSYS_COUNT)
			return -EINVAL;
	}

解析 "+cpu +memory" 这样的字符串，转换成位掩码。enable 是要新增的，disable 是要移除的。之后会检查"这个控制器在本节点可用吗"（cgroup_control(cgrp)）、"子节点是否还在用要禁用的控制器"（会返回 -EBUSY），最后才真正应用。

5.2 用 memory.max 限制内存并观察 OOM

# 1. 建一个组，并启用 memory 控制器
sudo mkdir /sys/fs/cgroup/mytest
echo "+memory" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

# 2. 设一个很小的上限：32 MiB
echo $((32*1024*1024)) | sudo tee /sys/fs/cgroup/mytest/memory.max
cat /sys/fs/cgroup/mytest/memory.max
# 33554432

# 3. 把当前 shell 放进去
echo $$ | sudo tee /sys/fs/cgroup/mytest/cgroup.procs
# 此时你的 shell 已经在 mytest 组里了

# 4. 在另一个终端启动一个吃内存的程序
python3 -c "
a = []
while True:
    a.append(bytearray(10*1024*1024))
    import time; time.sleep(0.1)"

# 5. 观察：另一个终端
watch -n1 'cat /sys/fs/cgroup/mytest/memory.current; cat /sys/fs/cgroup/mytest/memory.events'
# 当前用量会一路涨到 33554432 附近
# memory.events 里：
#   low 0
#   high 3       ← 超过 memory.high 触发了回收
#   max 1        ← 超过 memory.max
#   oom 1        ← 触发了 OOM
#   oom_kill 1   ← 杀了进程

# 6. 看内核日志
sudo dmesg | tail -20
# Memory cgroup out of memory: Killed process 12345 (python3)
#   total-vm:..., anon-rss:..., file-rss:..., shmem-rss:..., ...
#   Memory cgroup stats for /mytest: ...
#   inactive_anon:..., active_anon:..., inactive_file:..., active_file:...

# 7. 清理
echo $$ | sudo tee /sys/fs/cgroup/cgroup.procs   # 先把自己移出来
sudo rmdir /sys/fs/cgroup/mytest

关键观察点：memory.current 涨到 memory.max 附近就不再涨（内核强制回收），回收不出来时 oom_kill 计数增加、进程被 SIGKILL 掉。dmesg 里的 "Memory cgroup out of memory: Killed process" 就是证据。

5.3 memory.high 与 memory.max 的区别

# 设一个软限制：24 MiB
echo $((24*1024*1024)) | sudo tee /sys/fs/cgroup/mytest/memory.high
# 再跑吃内存的程序
# 观察：程序会明显变慢（大量时间花在回收上），
#       但不会被杀
# memory.events 里 high 计数猛增，oom_kill 保持 0

memory.high 是"软限制"：超过就开始疯狂回收，进程变慢但活着。memory.max 是"硬限制"：超过就 OOM kill。memory.low 则是保护线——本组内存紧张时，内核会优先回收其它组的页面，而不是动本组低于 low 的部分。

6. 自测

Q1. cgroup v1 和 v2 最本质的区别是什么？v1 每个控制器一棵独立的树，一个进程在每棵树里各有一个位置；v2 所有控制器共用一棵统一的树，一个进程在整棵树里只有一个位置。v2 还引入了"无内部进程"约束和统一的 memory.max / cpu.max 文件接口。
Q2. 什么是"no internal process"约束？v2 规定：一个要向下启用控制器的 cgroup 节点，自己不能直接放进程（否则父组控制器和子组控制器会争抢资源）。实现见 cgroup_vet_subtree_control_enable 里 cgroup_has_tasks() 返回 -EBUSY。threaded 模式是官方例外。
Q3. css_set 这个结构解决什么问题？把一个进程在所有控制器上的状态指针打包成一个对象，进程只持有这一个指针。好处是 task_struct 变小，且 fork/exit 时只需一次 refcount++ 和 list_add，而不是对每个控制器各做一遍。
Q4. 往 cgroup.procs 里写 PID 发生了什么？触发 cgroup_procs_write → cgroup_attach_task：收集源 css_set、准备目标 css_set、提交迁移（先 can_attach 后 attach，全成功或全失败）、收尾释放引用。过程中会遍历整个线程组。
Q5. 把 memory.max 改小为什么可能立刻杀掉进程？memory_max_write 存下新值后会进入循环检查当前用量，若已超限就先回收（try_to_free_mem_cgroup_pages），回收不出来就调 mem_cgroup_out_of_memory 触发 OOM killer。
Q6. memory.high 和 memory.max 有什么区别？high 是软限制：超过就开始激进回收，进程变慢但不会被杀（memory.events 里 high 计数增长）；max 是硬限制：超过触发 OOM kill（oom / oom_kill 计数增长）。low 则是保护线，本组低于 low 的内存优先不被回收。
Q7. cpu.max 的两个数字是什么意思？quota 和 period。每 period 微秒的调度周期内，该 cgroup 最多使用 quota 微秒的 CPU 时间。超出后被挂起到下个周期。默认 period 是 100000 微秒（100ms），cpu.max = "50000 100000" 即 50% CPU。
Q8. cgroup namespace 是什么？让容器内的进程看到"以容器自身为根"的 cgroup 视图，而不是宿主机的完整 cgroup 树。clone 时带 CLONE_NEWCGROUP 即可创建，是容器隔离方案的一部分。
