⚖️ 调度器：谁该用 CPU

CFS 用一个会“记账”的红黑树，让每个可运行 task 分到的 CPU 时间与它的权重成正比 · 预计阅读 30 分钟

1. 它在解决什么问题

一家只有 4 个灶台的餐厅，同时来了 20 桌客人。怎么安排？如果按“先到先服务”，一个点了 50 道菜的大订单会让后面所有等着喝汤的客人等到发火。于是老板发明了一种记账法：每桌都有一个看不见的“欠账计数器”，谁被服务得越多，欠账值越大；每次只挑欠账最少的桌子上灶。点菜多的桌子上得快（权重高），欠账涨得慢，所以能被多照顾；只点一碗面的桌子上得慢但欠账涨得快，很快又能轮到它。所有人的等待比例趋于公平，而不是服务次数相等。

Linux 的 CFS（Completely Fair Scheduler，完全公平调度器） 用的就是这套记账法。那个“欠账计数器”叫 vruntime（virtual runtime，虚拟运行时间）。每次挑下一个要运行的 task，就选 vruntime 最小的那个——它欠账最少，最该被照顾。而 vruntime 的增长速度取决于 task 的“权重”：权重高（优先级高）的 task，跑同样长的真实时间，vruntime 涨得慢，于是它更容易再次成为最小者，从而分到更多 CPU。

但 Linux 不是只有一种“公平”需求。硬实时任务（控制电机、音频中断处理）必须尽快跑，不能等记账；deadline 任务要在截止时间前跑完；完全无事可做的 idle task 只在没别的事时才跑。所以内核没有“一个万能调度器”，而是把调度拆成若干个 调度类（sched_class），按优先级从高到低排队：stop → deadline → RT → fair → idle。先问 stop 有没有活，没有才问 deadline，依次下滑。CFS 只是 fair 这个类内部的实现。

本仓库是 Linux 5.10，fair 类就是 CFS + 红黑树。要理解调度，必须读懂三件事：vruntime 如何算、红黑树如何选出最小值、什么时候从用户代码切到另一段代码（need_resched 与 __schedule）。

3.2 vruntime 的记账公式

真实运行 delta_exec 纳秒后，vruntime 增加 delta_exec × (NICE_0_LOAD / weight)。nice 0 的权重是 1024，所以 nice 0 的 task 跑 1ms，vruntime 也涨 1ms（1:1）。nice -20 的权重约 88761，跑 1ms 只涨约 0.0115ms——要过很久才“欠账”。nice 19 的权重只有 15，跑 1ms 涨约 68ms——很快就欠账最多，被换下去。

于是“谁 vruntime 最小谁跑”自动导致“CPU 时间按权重比例分配”。这就是 “completely fair” 的含义：公平的是比例，不是绝对时长。

从“决定该切换”到“真的切换”之间有一个延迟窗口：内核代码里很多地方暂时不能切换（持锁、关抢占、中断上下文）。所以 resched_curr() 只是置标志，真正的切换在最近的抢占点发生。这就是 why Linux 是“可抢占内核”而不是“随时抢占”——安全点由 preempt_count 控制。

3.4 调度类优先级链

五个调度类按链接顺序排在一段特殊 section 里，for_each_class 从最高往最低遍历：

stop_sched_class      (<- 最高)  迁移线程、hotplug、RCU 需要立即抢占某 CPU
      │
dl_sched_class        SCHED_DEADLINE，按截止时间 EDT 排序
      │
rt_sched_class        SCHED_FIFO / SCHED_RR，优先级 1..99
      │
fair_sched_class      SCHED_NORMAL / BATCH / IDLE，CFS
      │
idle_sched_class      (<- 最低)  每 CPU 的 idle task（swapper/N），halt 指令

注意 stop 与 idle 不可被用户设置：stop 是内核内部线程（migration/N），idle 是每 CPU 的 0 号 task。用户能选的是 FIFO/RR/NORMAL/BATCH/IDLE/DEADLINE。

3.5 SMP 负载均衡一句话

每个 CPU 有自己的 rq，如果一个 CPU 上有 5 个 runnable task，另一个 CPU 空闲，调度器会通过 load balance 把任务搬过去：周期性（tick 里 run_rebalance_domains）和 idle 时（newidle_balance）检查调度域（sched_domain：SMT → MC → DIE → NUMA）的负载差，超过 imbalance_pct 就迁移。迁移的目标 CPU 由 select_task_rq_fair 在唤醒时也能直接挑。

  • load 是权重（由 nice 映射），既用于算 CPU 份额，也用于负载均衡。
  • run_node 是红黑树节点，tasks_timeline 用它把实体串成树。需要说明的是，task_struct 里内嵌 se，所以“把 task 插入树”就是“把 &task->se.run_node 插进去”，没有额外分配。
  • vruntime 是本篇主角；sum_exec_runtime 是累计真实运行时间；prev_sum_exec_runtime 是“上次被选中时”的快照，用来算本次时间片已跑了多久（check_preempt_tick 里那个 delta_exec）。

  • parent / my_q / depth 只在开 CONFIG_FAIR_GROUP_SCHED（cgroup cpu 控制器）时存在：一个 cgroup 的 task_group 也有自己的 sched_entity，它的 my_q 指向该组的 cfs_rq，形成“实体树”。默认配置下这些字段不存在。

4.2 update_curr：记账发生的地方

kernel/sched/fair.c:1017-1049 update_curr

static void update_curr(struct cfs_rq *cfs_rq)
{
	struct sched_entity *curr = cfs_rq->curr;
	u64 now = rq_clock_task(rq_of(cfs_rq));
	u64 delta_exec;

	if (unlikely(!curr))
		return;

	delta_exec = now - curr->exec_start;
	if (unlikely((s64)delta_exec <= 0))
		return;

	curr->exec_start = now;

	schedstat_set(curr->statistics.exec_max,
		      max(delta_exec, curr->statistics.exec_max));

	curr->sum_exec_runtime += delta_exec;
	schedstat_add(cfs_rq->exec_clock, delta_exec);

	curr->vruntime += calc_delta_fair(delta_exec, curr);
	update_min_vruntime(cfs_rq);

	if (entity_is_task(curr)) {
		struct task_struct *curtask = task_of(curr);

		trace_sched_stat_runtime(curtask, delta_exec, curr->vruntime);
		cgroup_account_cputime(curtask, delta_exec);
		account_group_exec_runtime(curtask, delta_exec);
	}

	account_cfs_rq_runtime(cfs_rq, delta_exec);
}
  • rq_clock_task() 是“扣掉中断时间的任务时钟”，因为中断处理不应算进用户 task 的运行时间。这是“公平”在细节上的体现。
  • delta_exec 计算后立刻把 exec_start 推到 now，保证下次调用只算新增部分，不会重复记账。
  • calc_delta_fair(delta_exec, curr)（fair.c:778）就是那套 delta * NICE_0_LOAD / weight，其中 nice 0 走快速路径直接返回 delta。
  • update_min_vruntime(cfs_rq)（597 行）把 min_vruntime 推成“当前 curr 与树最左节点 vruntime 的较小者”，并保证单调递增。它给新任务/唤醒任务一个“当前进度基准”。
  • update_curr 在调度切换、tick、唤醒、cgroup 节流、设置优先级等多处被调用，是最高频的记账路径。

4.3 __enqueue_entity：把实体插进红黑树

kernel/sched/fair.c:648-676 __enqueue_entity

static void __enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	struct rb_node **link = &cfs_rq->tasks_timeline.rb_root.rb_node;
	struct rb_node *parent = NULL;
	struct sched_entity *entry;
	bool leftmost = true;

	/*
	 * Find the right place in the rbtree:
	 */
	while (*link) {
		parent = *link;
		entry = rb_entry(parent, struct sched_entity, run_node);
		/*
		 * We dont care about collisions. Nodes with
		 * the same key stay together.
		 */
		if (entity_before(se, entry)) {
			link = &parent->rb_left;
		} else {
			link = &parent->rb_right;
			leftmost = false;
		}
	}

	rb_link_node(&se->run_node, parent, link);
	rb_insert_color_cached(&se->run_node,
			       &cfs_rq->tasks_timeline, leftmost);
}
  • entity_before() 比较 vruntime：se->vruntime < entry->vruntime。走左子树表示“我更小”，走右子树表示“我更大”。
  • leftmost 是给 rb_root_cached 的优化：如果这次一路都走了右子树，新节点不可能成为“最小值”，leftmost 保持 false，插入时就不用更新缓存的最左指针；否则要更新。rb_first_cached() 因此可以 O(1) 取最小值，而不是 O(log n) 沿左链爬。
  • 红黑树的平衡修复在 rb_insert_color_cached 里，只涉及少量旋转，保证最坏 O(log n)。
  • “正在运行的 curr 不在树里”：切换出去时 __dequeue_entity() 把它摘掉，切回来时 enqueue_task_fair 再插回去。这样 pick 时树里全是“在等待”的实体。

4.6 pick_next_task：从最高的类开始问

kernel/sched/core.c:5314-5350 pick_next_task

static inline struct task_struct *
pick_next_task(struct rq *rq, struct task_struct *prev, struct rq_flags *rf)
{
	const struct sched_class *class;
	struct task_struct *p;

	/*
	 * Optimization: we know that if all tasks are in the fair class we can
	 * call that function directly, but only if the @prev task wasn't of a
	 * higher scheduling class, because otherwise those loose the
	 * opportunity to pull in more work from other CPUs.
	 */
	if (likely(prev->sched_class <= &fair_sched_class &&
		   rq->nr_running == rq->cfs.h_nr_running)) {

		p = pick_next_task_fair(rq, prev, rf);
		if (unlikely(p == RETRY_TASK))
			goto restart;

		/* Assumes fair_sched_class->next == idle_sched_class */
		if (!p) {
			put_prev_task(rq, prev);
			p = pick_next_task_idle(rq);
		}

		return p;
	}

restart:
	put_prev_task_balance(rq, prev, rf);

	for_each_class(class) {
		p = class->pick_next_task(rq);
		if (p)
			return p;
	}

	/* The idle class should always have a runnable task: */
	BUG();
}
  • 快路径：如果本 CPU 上所有 runnable task 都是 fair 类（nr_running == cfs.h_nr_running），直接调 pick_next_task_fair，跳过 4 次虚函数调用。这是绝大多数桌面/服务器场景。
  • 慢路径：for_each_class 依次调用，stop 的 pick_next_task 若发现有迁移线程待跑就返回它，否则返回 NULL 继续下一类。最后 idle 类一定返回 idle task，所以 BUG() 不该触发。
  • RETRY_TASK 是 newidle_balance 拉任务时的特殊返回：它曾经释放过 rq 锁，可能有更高优先级任务进来，必须重新选一遍。

  • signal_pending_state()：如果 task 是 TASK_INTERRUPTIBLE 且有待处理信号，则把它改回 TASK_RUNNING 不从队列摘——让它醒来去处理信号。这就是“Ctrl-C 能打断 read()”在内核侧的落点。
  • 非抢占且确实要睡眠时，deactivate_task(rq, prev, DEQUEUE_SLEEP) 会调 dequeue_task_fair，把 prev 的 se 从红黑树移除。

4.8 schedule() 与 need_resched 循环

kernel/sched/core.c:5651-5663 schedule

asmlinkage __visible void __sched schedule(void)
{
	struct task_struct *tsk = current;

	sched_submit_work(tsk);  /* 处理工作队列睡眠前的准备工作 */
	do {
		preempt_disable();  /* 禁用抢占 */
		__schedule(false);  /* 调用核心调度函数，false表示非抢占调度 */
		sched_preempt_enable_no_resched();  /* 重新启用抢占但不立即检查重调度 */
	} while (need_resched());  /* 如果仍需要重调度则继续循环 */
	sched_update_worker(tsk);  /* 更新工作队列状态 */
}
  • need_resched()（include/linux/sched.h:1895）就是 tif_need_resched()，检查 TIF_NEED_RESCHED 位。循环的意义是：一次切换回来之后，可能立刻又该切走（比如被更高优先级任务抢占），要把标志消化干净再返回调用者。
  • sched_submit_work 会在睡眠前把当前 task 的 workqueue 里的 pending work 推给 worker，防止“持有 work 睡死导致 worker 饿死”的死锁。
  • schedule() 是“主动让出”，典型调用点：read() 等 IO、mutex_lock 阻塞、wait_event 睡眠。内核里不能随便调它——必须确保自己不在原子上下文、不持不可睡眠的锁。

4.9 check_preempt_tick：时间片到点的判定

kernel/sched/fair.c:4745-4767 check_preempt_tick（开头）

static void
check_preempt_tick(struct cfs_rq *cfs_rq, struct sched_entity *curr)
{
	unsigned long ideal_runtime, delta_exec;
	struct sched_entity *se;
	s64 delta;

	ideal_runtime = sched_slice(cfs_rq, curr);
	delta_exec = curr->sum_exec_runtime - curr->prev_sum_exec_runtime;
	if (delta_exec > ideal_runtime) {
		resched_curr(rq_of(cfs_rq));
		/*
		 * The current task ran long enough, ensure it doesn't get
		 * re-elected due to buddy favours.
		 */
		clear_buddies(cfs_rq, curr);
		return;
	}
  • sched_slice()（831 行）：先算 __sched_period(nr_running)，再按 se->load.weight / cfs_rq->load.weight 的比例切一块。默认周期 sysctl_sched_latency = 6ms；runnable 数超过 sched_nr_latency = 6ms/0.75ms = 8 时，周期改为 nr_running × 0.75ms，保证单次不低于最小粒度。
  • 两个条件任一成立就置 NEED_RESCHED：跑超了理想时间片；或与最左节点差距超过 sysctl_sched_latency（防止某 task 独占太久）。
  • resched_curr()（core.c:714）如果目标就是本 CPU，直接 set_tsk_need_resched；否则发 IPI（RESCHEDULE_VECTOR）让对方 CPU 在中断返回时检查。
  • CFS 没有“固定时间片”概念——理想时间片是按权重算出来的比例值，任务数变了它就变。这正是它区别于 O(1)/RR 调度器的地方。

5. 动手验证

实验一：看 policy 与 nice。

$ ps -o pid,ni,pri,psr,policy,comm -p $$
  PID  NI PRI PSR POL COMMAND
 4001   0  19   2 TS  bash
$ chrt -p $$
pid 4001's current scheduling policy: SCHED_OTHER
pid 4001's current scheduling priority: 0

NI=0 表示 nice 0，PRI=19 是 ps 把 nice 换算成的“越小越高”的展示值（20 + nice）。POL=TS 即 SCHED_OTHER（fair）。

实验二：给 CPU 加负载，看 vruntime 与红黑树。

$ (for i in 1 2 3 4; do yes >/dev/null & done); sleep 1
$ grep -A3 "cpu#0" /proc/sched_debug | head -6
cpu#0, 2600.000 MHz
  .nr_running                    : 4
  .nr_switches                   : 123456
  ...
  cfs_rq[0]:/
    .nr_running                    : 4
    .min_vruntime                  : 123456.789
    .tasks                         : 4

/proc/sched_debug 需要 CONFIG_SCHED_DEBUG=y（多数发行版内核开启）。展开 cfs_rq 下的 .tg_load_avg 与每个 task 的 se.vruntime，你能直接看到红黑树里排着几个 yes，它们的 vruntime 只差几毫秒——因为它们权重相同，跑同样久就欠同样多账。清理：pkill yes。

实验三：nice 差异真的改变 CPU 份额。

$ nice -n 0  yes >/dev/null &
$ nice -n 10 yes >/dev/null &
$ sleep 5; ps -o pid,ni,time,comm -C yes
  PID  NI     TIME COMMAND
 6101   0 00:00:04
 6102  10 00:00:01

预期时间比约 5:1? 实际理论比是权重比 1024 : 110 ≈ 9.3:1。若两个任务都只在一个 CPU 上竞争，5 秒里 nice 0 的应拿到约 4.5s，nice 10 约 0.5s。上面的示例输出是粗略示意，实际以权重为准。清理 pkill yes。

实验四：chrt 切到 FIFO，看实时任务抢占一切。

$ sudo chrt -f 50 yes >/dev/null &
$ ps -o pid,ni,rtprio,policy,comm -C yes
  PID  NI RTPRIO POL COMMAND
 6201   0     50 FF  yes
$ top -b -n1 | grep yes      # 你会看到它 100% 占着一个 CPU
$ sudo chrt -o 0 -p 0 6201   # 切回 SCHED_OTHER（pid 换成实际的）
$ kill 6201

注意：FIFO 任务不主动让出 CPU 的话会一直跑（除非被更高优先级 RT 抢占）。生产环境慎用，否则可能饿死内核线程导致系统卡死。

实验五：用 perf 看调度延迟与迁移。

$ perf sched record -- sleep 1
$ perf sched latency | head -15
$ perf sched map | head -10

perf sched latency 列出每个 task 的“等待被调度”的最大/平均延迟以及运行时间；perf sched map 画成横向时间轴，能看到哪个 task 在哪个 CPU 上、什么时候迁移。需要 perf 可用且有 perf_event_paranoid 权限。

6. 自测

Q1. 为什么比较的是 vruntime 而不是实际运行时间？因为“公平”要按权重比例分配。如果比实际时间，nice -20 和 nice 19 会各拿一半，那 nice 就没意义了。把实际时间按 NICE_0_LOAD/weight 折算成 vruntime 后，“vruntime 最小者优先”自动等价于“CPU 份额与权重成正比”。
Q2. 为什么 CFS 用红黑树而不是数组或链表？需要频繁的“按 key 插入/删除/查最小”操作。链表查最小是 O(n)，任务多时不可接受；堆的“任意删除”代价高且需要附加索引；红黑树提供 O(log n) 的插入/删除，并用 rb_leftmost 缓存把“取最小”降到 O(1)。
Q3. 正在运行的 task 在红黑树里吗？不在。set_next_entity() 选中它时调用 __dequeue_entity() 把它摘掉，put_prev_entity() 在换出时再 __enqueue_entity() 放回去。所以 pick_next_entity() 拿到的“最左节点”一定是等待中的 task，不会选中自己。curr 另外由 cfs_rq->curr 指着。
Q4. need_resched 置位后立刻会切换吗？不会。它只是一个标志，真正的切换要等“抢占点”：中断/异常返回、系统调用返回、preempt_enable()（且 preempt_count == 0）、cond_resched()、或显式 schedule()。在持锁、关抢占、中断上下文里，即使标志置位也不能切——这正是“安全点”的意义。
Q5. 5.10 的 pick_next_task() 快路径为什么要求 prev->sched_class <= &fair_sched_class？因为如果 prev 是 rt/dl/stop 类的任务，可能还有同类的高优先级任务等着跑，直接走 fair 的快路径会漏掉它们（也失去从别的 CPU 拉活的机会）。只有当 prev 本身就在 fair 或更低、且 rq 里全是 fair 任务时，才可以安全地只问 CFS。
