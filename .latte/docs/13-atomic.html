⚛️ 原子操作与内存屏障

一条 lock addl 的来历、READ_ONCE 到底挡住了什么，以及“编译器重排 + CPU 乱序”这两层坑 · 预计阅读 23 分钟

1. 它在解决什么问题

超市收银台旁边有个柜台，上面放着“一瓶酱油”和“一瓶醋”。收银员要同时把两样东西递给顾客。如果他先递酱油、转身去拿醋、这时另一位店员看到柜台空了就把醋收走了——顾客手里就只剩酱油。“取酱油”和“取醋”必须合成一个不可分割的整体，这正是“原子性”的意思：要么两样都拿到，要么一样都拿不到，中间绝不能被别人插进来。

在单线程程序里这件事天经地义（没人会插进来）。但内核是多线程、多核、还带中断的。单看多核，还只是“原子性”问题；一旦把编译器也算进来，就变成两层完全不同的麻烦：

  • 第一层：编译器重排。你写的源码顺序不等于机器实际执行的顺序。GCC 看到 a = 1; b = 2; 两句没有数据依赖，完全可以先写 b 再写 a；甚至可以把 a 优化成寄存器里一直不放、直到函数返回才写回内存。这纯粹是编译器的“自作聪明”，跟硬件无关。
  • 第二层：CPU 乱序与可见性延迟。现代 CPU 为了跑满流水线，会把写先放进 Store Buffer 稍后再刷出去，于是“写 A”可能先于“写 B”对别的 CPU 可见；读也可能绕过还没到货的写（读到旧值），而且不同 CPU 之间看到同一份数据的时刻可能相差很久（缓存一致性协议不是瞬时的）。

内核因此准备了三个工具箱，各管一层：原子操作（保证“这个读-改-写不可分割”，顺便解决硬件层的乱序）、内存屏障（保证“某两件事的执行顺序/可见性顺序”）、READ_ONCE / WRITE_ONCE（只禁止编译器优化，不加任何 CPU 屏障——它是“只挡第一层”的轻量武器）。

还有一类问题连“原子”都不需要：per-CPU 变量。既然每个 CPU 各有一份、只有自己会改，那自然不需要任何锁——但必须保证“任务被调度到别的 CPU 上时，值被正确搬过去”。这就是 per-CPU 变量要解决的问题。

3. 整体结构

3.1 两层模型

你写的代码：            a = 1;  b = 2;  use(a);  use(b);

   ┌─────────────────────────────────────────────────────┐
   │ 第一层：编译器重排                                     │
   │   GCC 可能把 b=2 提到 a=1 之前                        │
   │   可能把 a=1 缓存在寄存器里、直到函数返回才写回        │
   │   ⇒ 工具：barrier() / READ_ONCE() / WRITE_ONCE()       │
   │      （靠 "memory" clobber 告诉编译器"内存被改过了"）  │
   └─────────────────────────────────────────────────────┘
                          │  编译后
                          ▼
   ┌─────────────────────────────────────────────────────┐
   │ 第二层：CPU 乱序与可见性                                │
   │   写先进 Store Buffer，晚点才刷出去                    │
   │   读可能绕过还没到达的写                                │
   │   ⇒ 工具：原子操作（lock 前缀）/ mfence / lfence / sfence│
   │      以及 smp_mb() / smp_rmb() / smp_wmb()              │
   └─────────────────────────────────────────────────────┘
关键区别：barrier()（编译器屏障）生成的是一条 CPU 指令都没有的空汇编；而 smp_mb() 在 x86 上会生成 lock addl $0,-4(%rsp)——真的会让 CPU 停下来把 Store Buffer 刷干净。两者的成本差着好几个数量级。

3.2 原子操作：四档内存序

档位后缀保证典型用途
relaxed_relaxed只有“不可分割”，不保证任何顺序纯计数器，比如统计中断次数
acquire_acquire之后的读写不会被重排到之前拿到指针后读它指向的数据
release_release之前的读写不会被重排到之后填好数据后再发布指针
fully ordered无后缀全部顺序保证（等价于 seq_cst）不确定该用哪档时的默认值

在 include/linux/atomic.h:14-25 里，内核把这件事写得很清楚：

 * We support four variants:
 *
 * - Fully ordered: The default implementation, no suffix required.
 * - Acquire: Provides ACQUIRE semantics, _acquire suffix.
 * - Release: Provides RELEASE semantics, _release suffix.
 * - Relaxed: No ordering guarantees, _relaxed suffix.

3.3 屏障速查

宏作用x86 上的实现
barrier()只挡编译器空汇编，零成本
READ_ONCE(x)只挡编译器（读）加 volatile 的普通 load
WRITE_ONCE(x,v)只挡编译器（写）加 volatile 的普通 store
smp_wmb()写屏障barrier()（x86 天然保序）
smp_rmb()读屏障barrier()（x86 天然保序）
smp_mb()全序屏障lock addl $0,-4(%rsp)

为什么 x86 上写屏障和读屏障是空的？因为 x86 是强序架构：所有写按程序顺序对所有核可见，所有读按程序顺序执行。唯一需要额外处理的是“读-改-写”（lock 前缀自带全序）。所以 x86 上只有 smp_mb() 真的要下指令。而 ARM/PowerPC/RISC-V 是弱序架构，三种屏障都要真下指令。

3.4 per-CPU 变量

普通全局变量：      ┌──────────────────┐
                    │   counter = 5     │   ← 所有 CPU 抢同一条缓存行
                    └──────────────────┘      要加锁，否则缓存行乒乓

per-CPU 变量：   CPU0      CPU1      CPU2      CPU3
                ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
                │  12 │  │  7  │  │  0  │  │  3  │  ← 各写各的，互不干扰
                └─────┘  └─────┘  └─────┘  └─────┘
                  ↑        ↑        ↑        ↑
               this_cpu_inc() 用当前 CPU 的偏移量定位到自己的那一份

代价：变量本身占 N 份内存；任务被调度到别的 CPU 时，
      它的值必须被“搬”过去（percpu 区的 __per_cpu_offset 机制）。

4. 源码走读

4.1 atomic_t：一个结构体一个 int

include/linux/types.h:166-170 atomic_t

typedef struct {
	int counter;
} atomic_t;

#define ATOMIC_INIT(i) { (i) }

之所以包成结构体而不是直接用 int，是为了让 sparse/编译器知道“这个变量只能通过原子 API 访问”，从而在你直接写 v.counter = 5 时给出警告。

4.2 atomic_inc 在 x86 上就是 lock incl

arch/x86/include/asm/atomic.h:93-98 arch_atomic_inc

static __always_inline void arch_atomic_inc(atomic_t *v)
{
	asm volatile(LOCK_PREFIX "incl %0"
		     : "+m" (v->counter) :: "memory");
}
#define arch_atomic_inc arch_atomic_inc

这就是全部魔法：lock incl (%rax)——lock 前缀让这条指令在多核上全局原子：在它执行期间，任何其他 CPU 对同一地址的读-改-写都会排队等待。代价是它要锁住总线/缓存行，周期数比普通指令高一个数量级。

加法版本：

arch/x86/include/asm/atomic.h:51-56 arch_atomic_add

static __always_inline void arch_atomic_add(int i, atomic_t *v)
{
	asm volatile(LOCK_PREFIX "addl %1,%0"
		     : "+m" (v->counter)
		     : "ir" (i) : "memory");
}

带返回值的版本用的是 xadd（x86 的“交换并相加”指令，本身就带隐式锁）：

arch/x86/include/asm/atomic.h:163-167 arch_atomic_add_return

static __always_inline int arch_atomic_add_return(int i, atomic_t *v)
{
	return i + xadd(&v->counter, i);
}
#define arch_atomic_add_return arch_atomic_add_return

注意返回值是 i + xadd(...)：xadd 返回的是加之前的旧值，所以要再加上 i 才是新值。

4.3 通用层：atomic_read 与 atomic_add

架构相关的 arch_atomic_* 之上还有一层通用 API。x86 定义了 ARCH_ATOMIC 宏，所以走的是 include/asm-generic/atomic-instrumented.h——这一层只做一件事：给操作加上 KASAN 插桩，然后转发给架构实现。

include/asm-generic/atomic-instrumented.h:60-65 atomic_add

static __always_inline void
atomic_add(int i, atomic_t *v)
{
	instrument_atomic_read_write(v, sizeof(*v));
	arch_atomic_add(i, v);
}

include/asm-generic/atomic-instrumented.h:237-242 atomic_inc

static __always_inline void
atomic_inc(atomic_t *v)
{
	instrument_atomic_read_write(v, sizeof(*v));
	arch_atomic_inc(v);
}

所以完整的调用链是：atomic_inc(&v) → arch_atomic_inc(&v) → lock incl (%mem)。中间那层 instrument_atomic_read_write() 在没开 KASAN 时是空函数，编译后完全消失。

而对于没有定义 ARCH_ATOMIC 的架构（比如某些 ARM、MIPS、RISC-V 老配置），走的是 include/asm-generic/atomic.h 这套纯软件回退实现：

include/asm-generic/atomic.h:163-187 atomic_read / atomic_set / atomic_add

/**
 * atomic_read - read atomic variable
 * @v: pointer of type atomic_t
 *
 * Atomically reads the value of @v.
 */
#ifndef atomic_read
#define atomic_read(v)	READ_ONCE((v)->counter)
#endif

/**
 * atomic_set - set atomic variable
 * ...
 */
#define atomic_set(v, i) WRITE_ONCE(((v)->counter), (i))

#include <linux/irqflags.h>

static inline void atomic_add(int i, atomic_t *v)
{
	atomic_add_return(i, v);
}

两个观察：

  • 回退版本里 atomic_read(v) 就是 READ_ONCE((v)->counter)。在 x86 上这确实安全（x86 的读本身是原子的，且 arch_atomic_read() 用的也是 __READ_ONCE）；但弱序架构上普通的 load 可能读到撕裂的值（8 字节变量读一半），所以那些架构必须覆盖这个定义。
  • 回退版本里 atomic_add() 是用 atomic_add_return() 实现的——明明天知道返回值用不上，还是多算了一遍。这是历史包袱：因为在多数架构上 add 和 add_return 本来就是同一条指令，懒得单独写一份。

4.4 refcount_t：给原子计数加上保险丝

include/linux/refcount.h:111-117 refcount_t

typedef struct refcount_struct {
	atomic_t refs;
} refcount_t;

#define REFCOUNT_INIT(n)	{ .refs = ATOMIC_INIT(n), }
#define REFCOUNT_MAX		INT_MAX
#define REFCOUNT_SATURATED	(INT_MIN / 2)

它和 atomic_t 的区别在于防呆：引用计数一旦下溢（有人多减了一次），普通 atomic_t 会从 0 变成 -1、-2……然后某次 dec_and_test() 返回 0 的时候就会提前释放还在被使用的对象——一个极难查的 use-after-free。refcount_t 的做法是：一旦检测到下溢或上溢，立刻 WARN，并把计数钉死在 REFCOUNT_SATURATED（一个很大的负数）上，让它再也不会被误判成 0。

取引用的关键接口：

include/linux/refcount.h:243-246 refcount_inc_not_zero

static inline __must_check bool refcount_inc_not_zero(refcount_t *r)
{
	return __refcount_inc_not_zero(r, NULL);
}

它是 atomic_inc_not_zero() 的“安全版”：只有计数不为 0 时才加一，返回 false 表示对象已经在被销毁，别碰。这是引用计数最常见的竞态——A 线程正要 free(obj)，B 线程同时想拿一个引用。

释放引用：

include/linux/refcount.h:331-334 refcount_dec_and_test

static inline __must_check bool refcount_dec_and_test(refcount_t *r)
{
	return __refcount_dec_and_test(r, NULL);
}

注释里写明了它的内存序：“Provides release memory ordering, such that prior loads and stores are done before, and provides an acquire ordering on success such that free() must come after.”——减到 0 的那个线程，会先 release（保证之前对对象的修改都已生效），再 acquire（保证自己后面看到的是最新数据），然后才能 free()。

4.5 READ_ONCE / WRITE_ONCE：只挡编译器

include/asm-generic/rwonce.h:43-62 READ_ONCE / WRITE_ONCE

#ifndef __READ_ONCE
#define __READ_ONCE(x)	(*(const volatile __unqual_scalar_typeof(x)) &(x))
#endif

#define READ_ONCE(x)							\
({									\
	compiletime_assert_rwonce_type(x);				\
	__READ_ONCE(x);							\
})

#define __WRITE_ONCE(x, val)						\
do {									\
	*(volatile typeof(x) *)&(x) = (val);				\
} while (0)

#define WRITE_ONCE(x, val)						\
do {									\
	compiletime_assert_rwonce_type(x);				\
	__WRITE_ONCE(x, val);						\
} while (0)

核心就是把变量“强转成 volatile”再访问。效果是：

  • 编译器不会把这个读取优化掉，也不会把它和相邻的读取合并成一次（普通情况下 if (a) { x = p->v; } if (b) { x = p->v; } 会被合并成一次 load）；
  • 编译器不会把对它的写入优化掉或延后；
  • 但是——它不产生任何 CPU 指令，也不做任何跨 CPU 的顺序保证。

所以 READ_ONCE 的典型用途是“读一个会被别人并发修改的标志位，我只关心这一刻的值，不关心它和别的内存访问的相对顺序”。真正需要顺序保证时，得用 smp_load_acquire() 或 rcu_dereference()。

4.6 barrier()：一条空汇编

include/linux/compiler.h:81-85 barrier

/* Optimization barrier */
#ifndef barrier
/* The "volatile" is due to gcc bugs */
# define barrier() __asm__ __volatile__("": : :"memory")
#endif

看懂这三段：

  • __asm__ __volatile__("")：生成一条空的汇编语句。之所以要 volatile，是因为 GCC 有一个已知 bug：非 volatile 的空汇编可能被删掉。
  • : : :"memory"："memory" 是clobber 列表，意思是“我这条汇编可能读了也可能写了任意内存”。编译器因此必须假设：barrier() 前后所有对内存的读写都可能互相影响，于是不敢把内存访问跨过这条屏障重排。
  • 注意它不产生 CPU 指令，所以对硬件层的乱序毫无约束力。

4.7 smp_mb / smp_rmb / smp_wmb

通用层在 include/asm-generic/barrier.h:65-73：

#ifndef smp_mb
#define smp_mb()	__smp_mb()
#endif

#ifndef smp_rmb
#define smp_rmb()	__smp_rmb()
#endif

#ifndef smp_wmb
#define smp_wmb()	__smp_wmb()
#endif

x86 的实现（arch/x86/include/asm/barrier.h:14-25）：

arch/x86/include/asm/barrier.h:14-25 mb / rmb / wmb

#ifdef CONFIG_X86_32
#define mb() asm volatile(ALTERNATIVE("lock; addl $0,-4(%%esp)", "mfence", \
				      X86_FEATURE_XMM2) ::: "memory", "cc")
#define rmb() asm volatile(ALTERNATIVE("lock; addl $0,-4(%%esp)", "lfence", \
				       X86_FEATURE_XMM2) ::: "memory", "cc")
#define wmb() asm volatile(ALTERNATIVE("lock; addl $0,-4(%%esp)", "sfence", \
				       X86_FEATURE_XMM2) ::: "memory", "cc")
#else
#define mb() 	asm volatile("mfence":::"memory")
#define rmb()	asm volatile("lfence":::"memory")
#define wmb()	asm volatile("sfence" ::: "memory")
#endif

x86_64 上：全序屏障 = mfence，读屏障 = lfence，写屏障 = sfence。这三条是 Intel 定义的真正的硬件屏障指令。

而内核真正用的是 __smp_mb()（arch/x86/include/asm/barrier.h:57-63）：

#ifdef CONFIG_X86_32
#define __smp_mb()	asm volatile("lock; addl $0,-4(%%esp)" ::: "memory", "cc")
#else
#define __smp_mb()	asm volatile("lock; addl $0,-4(%%rsp)" ::: "memory", "cc")
#endif
#define __smp_rmb()	dma_rmb()
#define __smp_wmb()	barrier()

lock addl $0,-4(%rsp) 是比 mfence 更老的“全屏障”写法（Intel 手册推荐 mfence，但 lock 前缀在老 CPU 上更可靠、且在 x86_32 上没有 mfence）。

同文件里还有一对更常用的“半屏障”：

arch/x86/include/asm/barrier.h:66-79 __smp_store_release / __smp_load_acquire

#define __smp_store_release(p, v)					\
do {									\
	compiletime_assert_atomic_type(*p);				\
	barrier();							\
	WRITE_ONCE(*p, v);						\
} while (0)

#define __smp_load_acquire(p)						\
({									\
	typeof(*p) ___p1 = READ_ONCE(*p);				\
	compiletime_assert_atomic_type(*p);				\
	barrier();							\
	___p1;								\
})

在 x86 上，acquire/release 只需要一个编译器屏障就够了——因为 x86 的硬件本身不会把读重排到写之后、也不会把写重排到读之前。这两个宏正是第 12 篇里 rcu_assign_pointer() 用的 smp_store_release() 的底层实现。

4.8 per-CPU 变量：this_cpu_inc

include/linux/percpu-defs.h:507-521 this_cpu_*

#define this_cpu_read(pcp)		__pcpu_size_call_return(this_cpu_read_, pcp)
#define this_cpu_write(pcp, val)	__pcpu_size_call(this_cpu_write_, pcp, val)
#define this_cpu_add(pcp, val)		__pcpu_size_call(this_cpu_add_, pcp, val)
/* ... */
#define this_cpu_sub(pcp, val)		this_cpu_add(pcp, -(typeof(pcp))(val))
#define this_cpu_inc(pcp)		this_cpu_add(pcp, 1)
#define this_cpu_dec(pcp)		this_cpu_sub(pcp, 1)

this_cpu_inc() 就是 this_cpu_add(pcp, 1)。它和 raw_cpu_add()（include/linux/percpu-defs.h:422）的差别在注释里写得很清楚：

/*
 * Operations for contexts where we do not want to do any checks for
 * preemptions.  Unless strictly necessary, always use [__]this_cpu_*()
 * instead.
 *
 * If there is no other protection through preempt disable and/or disabling
 * interupts then one of these RMW operations can show unexpected behavior
 * because the execution thread was rescheduled on another processor or an
 * interrupt occurred and the same percpu variable was modified from the
 * interrupt context.
 */
#define raw_cpu_read(pcp)		__pcpu_size_call_return(raw_cpu_read_, pcp)
#define raw_cpu_write(pcp, val)	__pcpu_size_call(raw_cpu_write_, pcp, val)
#define raw_cpu_add(pcp, val)		__pcpu_size_call(raw_cpu_add_, pcp, val)

翻译成人话：this_cpu_* 会先检查“当前是不是还在原来那颗 CPU 上”（靠 __this_cpu_preempt_check()），保证整个操作不会因为中途被抢占/迁移而落到别的 CPU 上；raw_cpu_* 不做这个检查，所以调用者必须自己保证（比如已经关了抢占和中断）。

“定位到当前 CPU 那一份”的动作由 this_cpu_ptr() 完成（include/linux/percpu-defs.h:246-253）：

#ifdef CONFIG_DEBUG_PREEMPT
#define this_cpu_ptr(ptr)						\
({									\
	__verify_pcpu_ptr(ptr);						\
	SHIFT_PERCPU_PTR(ptr, my_cpu_offset);				\
	...
#else
#define this_cpu_ptr(ptr) raw_cpu_ptr(ptr)
#endif

my_cpu_offset 就是“当前 CPU 在 percpu 区里的基址偏移”。percpu 区的所有变量都按 CPU 号排在一起，加上偏移量就得到“我这一份”的地址——不需要任何锁，因为只有这颗 CPU 会访问它。

4.9 一个真实的 per-CPU 计数器：中断统计

内核统计每个 IRQ 在每颗 CPU 上被触发多少次，用的正是 per-CPU 数组：

kernel/irq/proc.c:498-501 show_interrupts

	seq_printf(p, "%*d: ", prec, i);
	for_each_online_cpu(j)
		seq_printf(p, "%10u ", desc->kstat_irqs ?
					*per_cpu_ptr(desc->kstat_irqs, j) : 0);

每颗 CPU 各写自己那一份（用 this_cpu_inc()），打印时再逐颗读出来——全程无锁、无原子操作，因为每份数据只有一个主人。

5.3 亲眼看到 lock incl

写一个最小模块，然后 objdump 它的机器码：

// atomic_demo.c
#include <linux/module.h>
#include <linux/atomic.h>

static atomic_t counter = ATOMIC_INIT(0);

static int __init ad_init(void)
{
	atomic_inc(&counter);
	atomic_add(41, &counter);
	pr_info("counter = %d\n", atomic_read(&counter));
	return 0;
}

static void __exit ad_exit(void) { }
module_init(ad_init);
module_exit(ad_exit);
MODULE_LICENSE("GPL");
$ make -C /lib/modules/$(uname -r)/build M=$PWD modules
$ objdump -d atomic_demo.ko | sed -n '/<ad_init>/,/ret/p'
0000000000000000 <ad_init>:
   0:	55                    	push   %rbp
   1:	48 89 e5              	mov    %rsp,%rbp
   4:	f0 83 05 3f 00 00 00 01 	lock addl $0x1,0x3f(%rip)        # 1000 <counter>
   e:	f0 83 05 38 00 00 00 29 	lock addl $0x29,0x38(%rip)       # 1000 <counter>
  18:	8b 05 31 00 00 00    	mov    0x31(%rip),%eax           # 1000 <counter>
   ...

三条关键指令一目了然：atomic_inc() 变成 lock addl $0x1，atomic_add(41, ...) 变成 lock addl $0x29（41 的十六进制），而 atomic_read() 只是一条普通的 mov——因为 x86 的读本来就是原子的，不需要 lock。

关于 lock addl 和 lock incl：内核源码里写的是 lock incl（arch/x86/include/asm/atomic.h:95），但 GCC 常把它改写成 lock addl $0x1，两者语义完全等价。到底生成哪一条取决于编译器版本和优化选项——你用 objdump 看到的就是真相。

5.4 亲眼看到编译器重排（用户态小实验）

这个实验不需要内核，直接在普通 Linux 机器上跑，它演示的正是 barrier() 挡住的那一层：

// reorder.c
#include <stdio.h>

int a, b;

int no_barrier(void)
{
	a = 1;
	b = 2;
	return a + b;
}

int with_barrier(void)
{
	a = 1;
	__asm__ __volatile__("" ::: "memory");   /* 内核 barrier() 的等价物 */
	b = 2;
	return a + b;
}

int main(void)
{
	printf("no_barrier   = %d\n", no_barrier());
	printf("with_barrier = %d\n", with_barrier());
	return 0;
}
$ gcc -O2 -o reorder reorder.c
$ ./reorder
no_barrier   = 3
with_barrier = 3

$ gcc -O2 -S -o - reorder.c | sed -n '/no_barrier:/,/ret/p'
no_barrier:
.LFB0:
	.cfi_startproc
	movl	$1, a(%rip)
	movl	$2, b(%rip)
	movl	a(%rip), %eax
	movl	b(%rip), %edx
	addl	%edx, %eax
	ret
.LFE0:

看汇编：no_barrier() 里两条 store 的顺序被保留了——因为它们写的是两个不同的全局变量，编译器没有动力去换。但如果你把 b = 2; 换成“b 的值依赖于 a”或者把 a 放进一个循环里，编译器就会开始合并、消除、换序。barrier() 的 "memory" clobber 就是在告诉编译器“别动我周围的内存访问”。

更强的实验：把 no_barrier() 改成循环里反复 a = a + 1;，用 gcc -O2 编译后用 objdump 看，会发现编译器把它优化成了一条 addl（把多次加法合并成一次）——这就是“编译器合并访存”，也正是 READ_ONCE 要防的事。

5.5 经典例子：无锁计数器与顺序锁读侧

无锁计数器——最常见的原子操作用法：

static atomic_t irq_count[NR_IRQS];

/* 中断处理程序里 */
void irq_handler(int irq, void *dev)
{
	atomic_inc(&irq_count[irq]);      /* 一次 lock addl，别的 CPU 看不到中间值 */
	handle_event();
}

/* 读的时候 */
unsigned long count = atomic_read(&irq_count[irq]);

顺序锁（seqlock）的读侧——完全不加锁的读法，核心是“读序号 → 读数据 → 再读序号”：

	unsigned seq;
	int val;

	do {
		seq = read_seqcount_begin(&seqcount);   /* 读偶数序号 */
		val = READ_ONCE(data);                    /* 读数据 */
	} while (read_seqcount_retry(&seqcount, seq));  /* 序号变了就重来 */

这里 READ_ONCE 的作用是“禁止编译器把这个 load 提到循环外面去或者合并掉”——因为它每次都必须真的去内存里读一次。真正保证顺序的是 smp_rmb()（见 include/linux/seqlock.h:346-352 和 450-454，详见第 11 篇）。

6. 自测

Q1. atomic_inc() 在 x86 上编译出来是什么指令？为什么需要它？是 lock incl %mem（或编译器选择的等价形式 lock addl $1,%mem）。lock 前缀让这条读-改-写指令在多核上全局原子：执行期间总线/缓存行被独占，其它 CPU 对同一地址的读-改-写会排队。普通 incl 不是原子的——两个 CPU 可能同时读到旧值、各自加一再写回，结果只加了一次（lost update）。
Q2. barrier() 和 smp_mb() 有什么区别？barrier() 是编译器屏障：展开成 __asm__ __volatile__("": : :"memory")，不产生任何 CPU 指令，零成本，作用是告诉编译器“我前后对内存的访问别重排”。smp_mb() 是硬件屏障：在 x86_64 上生成 lock addl $0,-4(%rsp)（或 mfence），会真正让 CPU 把 Store Buffer 刷出去、挡住所有未完成的访存，代价是几十个周期。跨 CPU 的可见性顺序必须靠后者。
Q3. READ_ONCE() 到底防住了什么？它防不住什么？它防的是编译器把这次读取优化掉、延后，或与相邻的读取合并（比如两次 p->v 只读一次内存）——实现手法是把地址强转成 volatile。它不防：CPU 层面的乱序、其他 CPU 读到过期值、读到撕裂值（弱序架构上）。要跨 CPU 的顺序保证，得用 smp_load_acquire()、smp_mb() 或 rcu_dereference()。
Q4. 为什么要用 refcount_t 而不是直接用 atomic_t 做引用计数？因为 atomic_t 的下溢是静默灾难：计数从 0 减成 -1、-2，某次 dec_and_test() 误判为 0 就会提前 free() 一个还在被使用的对象，表现为极难复现的 use-after-free。refcount_t 在检测到下溢/上溢时立刻 WARN，并把计数钉死在 REFCOUNT_SATURATED 上，让它永远不会被误判为 0。另外它还提供正确的 release/acquire 内存序，保证减到 0 的那个线程之前的修改对后续读者可见。
Q5. per-CPU 变量为什么不需要锁？它的代价是什么？因为每个 CPU 各有一份副本（percpu 区里按 CPU 号排列），只有“当前 CPU”这一份会被访问它的代码修改，所以天然没有竞争。定位当前那一份靠 this_cpu_ptr()（用 my_cpu_offset 加偏移）。代价有三个：① 内存占用乘以 CPU 数；② 任务被调度到别的 CPU 时，它的值必须被搬运过去（这由 percpu 区的迁移机制负责）；③ 中断上下文访问同一份数据时要小心——所以 raw_cpu_* 不做抢占检查，调用者必须自己保证关好抢占/中断。
Q6. 为什么 x86 上 smp_rmb() 和 smp_wmb() 是空操作，只有 smp_mb() 要下指令？因为 x86 是强序架构：写按程序顺序对所有核可见，读按程序顺序执行，只有“读-改-写”需要额外保证（由 lock 前缀提供）。所以 smp_rmb()/smp_wmb() 退化成 barrier()（纯编译器屏障），而 smp_mb() 需要 lock addl 或 mfence 来真正拦住未完成的访存。ARM、RISC-V 等弱序架构上三种屏障都要真下指令——这也是为什么内核代码要用通用的 smp_* 宏而不是直接写 x86 汇编。
