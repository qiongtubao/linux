🧪 伪文件系统：procfs / sysfs / debugfs

没有真实存储，却能用 cat/echo 读写的“文件”：内核给用户开的窗口 · 预计阅读 10 分钟

1. 它在解决什么问题

内核里有一堆状态：当前哪些进程在跑、每个进程什么状态、CPU 有多少个、网卡收了多少包、某驱动内部计数器是多少。这些数据根本不存在磁盘上，都是内存里结构体的即时值。可用户又想查看甚至修改它们，怎么办？

若为每个数据开一个专门系统调用，内核会膨胀成几百个 syscall，用户态还要配几百个工具。Linux 的答案很巧妙：把内核数据“伪装成文件”。你 cat /proc/self/status，内核临时生成文本；你 echo 1 > /sys/...，内核解码字符串并改内部变量。这套机制叫伪文件系统：有 inode 和 dentry，却没有磁盘块。VFS 不知道也不关心背后有没有硬盘，它只看函数指针。

于是复用了现成的一切：权限用文件权限、查看用 cat、脚本用 shell 管道、远程用 ssh、编程用 open/read。文件成为内核与用户之间的通用接口。本篇讲三类最重要的：procfs（进程与内核状态）、sysfs（设备模型的结构化视图）、debugfs（调试用的“什么都往里塞”）。

2. 核心名词

术语英文一句话解释
伪文件系统pseudo fs用 inode/dentry 抽象暴露内核数据，但不在磁盘上存任何内容。
procfsproc filesystem挂在 /proc；/proc/[pid]/ 是进程视图，/proc/meminfo 等是全局状态。
sysfssysfs挂在 /sys；按“设备/总线/驱动/类”的目录层级展示 kobject 树。
debugfsdebugfs挂在 /sys/kernel/debug；驱动随意暴露调试信息，无稳定 ABI 保证。
kobjectkobject设备模型的基本节点（名字/父节点/引用计数），sysfs 目录就是它的投影。
kernfskernfssysfs 的底层实现：内核对象树与用户态文件树之间的映射层。
seq_fileseq_file输出较长文本的标准库：start/next/show/stop 逐条产生，自动处理翻页。
proc_opsproc_ops5.10 中 procfs 文件的操作表（取代旧 file_operations 用法）。

3. 整体结构

/proc                        /sys                      /sys/kernel/debug
├ self -> [pid]              ├ devices/  (设备清单)     ├ tracing/   (ftrace)
├ [pid]/status               ├ bus/      (总线)         ├ block/     (块层调试)
│   ├ Name/State/Pid...      │   └ pci/               ├ bdi/
│   └ 由 proc_pid_status     ├ class/    (按功能分类)    └ <驱动自建目录>
├ meminfo / cpuinfo          │   └ net/
├ sys/  (可写开关)           ├ block/    (每个块设备)
└ tty/                       └ module/   (模块参数)

三者共享同一条路：VFS 的 read()/write() 调到伪文件系统注册的回调。procfs 用 proc_ops（proc_read 实际是 single_open 包装的 seq 回调）；sysfs 用 kernfs 的 sysfs_ops（show/store），属性通过 DEVICE_ATTR 声明；debugfs 用普通 file_operations，实现最自由。cgroupfs 也是 kernfs 之上的一层，一句话：它用同样的目录/文件形式做“资源分组”，把 cpu.max、memory.max 这类限额写进文件。

读一个 proc 文件的流程：cat → vfs_read → proc_reg_read → seq_read → 反复调 proc_pid_status 里的 seq_printf 直到缓冲区够填。写则相反：proc_reg_write → 驱动自己的解析函数。

4. 源码走读

4.1 注册一个 proc 文件

fs/proc/generic.c:564-570 proc_create

struct proc_dir_entry *proc_create(const char *name, umode_t mode,
				   struct proc_dir_entry *parent,
				   const struct proc_ops *proc_ops)
{
	return proc_create_data(name, mode, parent, proc_ops, NULL);
}
EXPORT_SYMBOL(proc_create);

fs/proc/generic.c:549-562 proc_create_data

	p = proc_create_reg(name, mode, &parent, data);
	if (!p)
		return NULL;
	p->proc_ops = proc_ops;
	pde_set_flags(p);
	return proc_register(parent, p);   /* 挂进 parent 的子项链表并分配 inode */

驱动一行就能在 /proc 下建文件：proc_create("hello", 0444, NULL, &hello_ops)。它只分配 proc_dir_entry、记下 proc_ops，然后挂到父目录项列表；文件真正“出现”是在 VFS 下一次 lookup 时由 procfs 的 proc_lookup 按名字找到该 entry 并造 inode。

4.2 进程状态文本从哪来

fs/proc/base.c:3170 status 文件声明

	ONE("status",     S_IRUGO, proc_pid_status),

ONE 宏（base.c:144）把 proc_pid_status 包成 proc_single_file_operations 的 .proc_show。于是 /proc/[pid]/status 的读回调就是下面这个函数：

fs/proc/array.c:404-415 proc_pid_status（开头）

int proc_pid_status(struct seq_file *m, struct pid_namespace *ns,
			struct pid *pid, struct task_struct *task)
{
	struct mm_struct *mm = get_task_mm(task);

	seq_puts(m, "Name:\t");
	proc_task_name(m, task, true);
	seq_putc(m, '\n');

	task_state(m, ns, pid, task);
	// ... 省略后面几十行：内存、信号、capabilities 输出

它用 seq_file 逐行输出：先打名字，再打状态块。名字来源是 task_struct->comm（若为内核 worker 需特殊处理）。get_task_mm 拿内存描述符的引用，防止读取中被释放。

4.3 State 字段与状态数组

fs/proc/array.c:129-140 task_state_array

static const char * const task_state_array[] = {
	/* states in TASK_REPORT: */
	"R (running)",		/* 0x00 */
	"S (sleeping)",		/* 0x01 */
	"D (disk sleep)",	/* 0x02 */
	"T (stopped)",		/* 0x04 */
	"t (tracing stop)",	/* 0x08 */
	"X (dead)",		/* 0x10 */
	"Z (zombie)",		/* 0x20 */
	"P (parked)",		/* 0x40 */
	/* states beyond TASK_REPORT: */
	"I (idle)",		/* 0x80 */
};

task_state_index() 把 task_struct 的状态位（可能是多个位或）映射成这个数组的下标，再由 get_task_state() 返回字符串。这就是你 ps 看到的 R/S/D/Z 字母的真身：S = 可中断睡眠、D = 不可中断（一般在等 IO）、Z = 僵尸（已退出等父进程回收）。特殊状态如 I（idle 内核线程）在正常位图之外单独处理。

4.4 sysfs 属性：DEVICE_ATTR 与 device_create_file

include/linux/device.h:125-126 DEVICE_ATTR

#define DEVICE_ATTR(_name, _mode, _show, _store) \
	struct device_attribute dev_attr_##_name = __ATTR(_name, _mode, _show, _store)

这个宏只声明一个 struct device_attribute（内含名字、权限、show/store 回调）。要让它出现在 /sys/devices/... 下，还需注册：

drivers/base/core.c:2298-2312 device_create_file

int device_create_file(struct device *dev,
		       const struct device_attribute *attr)
{
	int error = 0;

	if (dev) {
		WARN(((attr->attr.mode & S_IWUGO) && !attr->store),
			"Attribute %s: write permission without 'store'\n",
			attr->attr.name);
		WARN(((attr->attr.mode & S_IRUGO) && !attr->show),
			"Attribute %s: read permission without 'show'\n",
			attr->attr.name);
		error = sysfs_create_file(&dev->kobj, &attr->attr);
	}

	return error;
}

两个 WARN 是权限自检：给了写权限却没 store、给了读权限却没 show，都是驱动 bug，会打出栈。真正的建文件是 sysfs_create_file(&dev->kobj, ...)：把属性挂到设备的 kobject 上，由 kernfs 在 /sys 目录树里生成对应文件。读时 kernfs 调 ->show(dev, attr, buf)，写时调 ->store(...)。

sysfs 的目录结构不是人工维护的，而是 kobject 树（include/linux/kobject.h:64：name、parent、sd 指向 kernfs_node）的投影：设备注册到总线/类，目录就自动出现。这就是“设备模型”的展示层。

4.5 debugfs 与 cgroupfs

debugfs 没有固定格式：debugfs_create_file(name, mode, parent, data, fops) 传一个普通 file_operations，读写出什么完全由驱动决定。它不承诺稳定 ABI，也不该在生产脚本里依赖。tracing/（ftrace 控制）、block/、bdi/ 都在这里。cgroupfs v2 则是 kernfs 之上的控制器框架：/sys/fs/cgroup/ 下每个目录表示一个资源组，文件如 cpu.max、memory.max 是控制接口，写入字符串即调控制器回调。

5. 动手验证

先看现成的伪文件。

cat /proc/self/status | head -8
ls -l /proc/self/fd                 # 每个 fd 都是一个“魔法符号链接”
cat /sys/class/net/$(ls /sys/class/net | head -1)/statistics/rx_bytes
ls /sys/bus/pci/devices/ | head -3; cat /sys/bus/pci/devices/*/vendor 2>/dev/null | head -3

/proc/self 是动态符号链接，指向当前 cat 进程的 pid 目录；/sys/class/net/eth0/statistics/ 下每个文件对应一个计数器的 show 回调；vendor 是 PCI 设备的 16 进制厂商号。

写一个模块创建 /proc/hello。（需内核头文件，可在 qemu 实验机或装了 headers 的本机做）

// hello_proc.c
#include <linux/module.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>

static int hello_show(struct seq_file *m, void *v)
{
    seq_printf(m, "hello from kernel, jiffies=%lu\n", jiffies);
    return 0;
}
static int hello_open(struct inode *i, struct file *f)
{ return single_open(f, hello_show, NULL); }

static const struct proc_ops hello_ops = {
    .proc_open = hello_open,
    .proc_read = seq_read,
    .proc_lseek = seq_lseek,
    .proc_release = single_release,
};

static int __init hello_init(void)
{
    proc_create("hello", 0444, NULL, &hello_ops);
    return 0;
}
static void __exit hello_exit(void) { remove_proc_entry("hello", NULL); }
module_init(hello_init); module_exit(hello_exit);
MODULE_LICENSE("GPL");
make -C /lib/modules/$(uname -r)/build M=$PWD modules
sudo insmod hello_proc.ko
cat /proc/hello          # 每读一次 jiffies 都不同 → 内容是“现算”的
sudo rmmod hello_proc

sysfs 属性同理：在模块里定义 static DEVICE_ATTR(hello, 0444, show_fn, NULL);，拿到 struct device * 后 device_create_file(dev, &dev_attr_hello)，文件就出现在该设备目录下；cat 它会调用 show_fn，返回缓冲区内容。若换成 0644 并实现 store，echo 1 > ... 会写到内核变量。

6. 自测

Q1. 伪文件系统的文件为什么没有磁盘块？它的 inode 由文件系统代码现场构造（如 proc_lookup），数据由 read 回调即时生成，不经过 page cache 的磁盘读路径。
Q2. /proc/[pid]/status 的内容由哪个函数产生？proc_pid_status（fs/proc/array.c），内部先调 proc_task_name 打名字，再调 task_state 打状态块；State 字符串来自 task_state_array。
Q3. DEVICE_ATTR 与 device_create_file 各自做什么？前者声明一个带名字/权限/show/store 的属性结构，后者把它挂到设备的 kobject 上，由 kernfs 在 /sys 生成文件。
Q4. sysfs 的目录结构怎么来的？由 kobject 树自动投影：设备/总线/驱动注册时建 kobject，kernfs 据此生成目录与属性文件，而不是手工 mkdir。
Q5. 为什么脚本不应依赖 debugfs？它没有稳定 ABI，接口随内核版本变化；生产脚本依赖它会在升级后失效。稳定接口应使用 sysfs/procfs 中已文档化的文件。
