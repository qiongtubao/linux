🐣 03 · 内核启动流程：从加电到第一个用户进程

把"按下电源"到"看到登录界面"这 3 秒钟拆成 5 个阶段，看清每一步是谁在干活 · 预计阅读 25 分钟

1. 它在解决什么问题

想象你在组装一台打印机：零件买了一堆（CPU、内存、硬盘、网卡），但它现在只是一堆零件，还不会打印任何东西。真正让它"活过来"的，是一条严格的装配流水线——先通电看灯亮不亮（硬件自检），再装驱动（让 CPU 学会和硬盘说话），最后装上应用（浏览器、编辑器）。哪一步顺序错了，要么开机黑屏，要么识别不出硬盘。

Linux 内核启动就是这条流水线。固件（BIOS/UEFI）先把 CPU 从"关机"唤醒并做最小自检，然后把控制权交给引导加载器（GRUB2）；GRUB2 把压缩的内核镜像和 initramfs 读进内存，交棒给内核；内核接管全部硬件，初始化内存、调度器、中断、文件系统，最后主动启动第一个用户态进程（/sbin/init，PID=1），把控制权彻底交出去，从此自己退居幕后当"后台管家"。

从操作系统视角看，这段代码要回答三个核心问题：① 硬件从谁手里接过来？（固件 → 引导器 → 内核，是一条单向的所有权移交链）；② 内核内部几十个子系统按什么顺序初始化？（有严格依赖：先有内存才能分配缓存，先有调度器才能开中断，先有 VFS 才能挂载根）；③ 什么时候算"启动完毕"？（内核自己不算，PID 1 的 init 跑起来才算，所以你会看到"启动 3 秒"其实是 init 报告的，不是内核报告的）。

本篇就把这条流水线拆开讲：汇编入口 head_64.S 做了什么、start_kernel() 里那两百多行初始化各自负责什么、initcall 分级机制为什么存在、rest_init() 怎么凭空造出 PID 0/1/2、以及根文件系统是怎么被挂上的。读完你应该能解释：为什么 dmesg 里第一条消息是内核版本，而第一条属于用户空间的消息往往是 init 打的。

3.2 为什么顺序不能乱？

内核初始化看起来是一长串函数调用，但顺序是被依赖关系严格约束的，不然就会当场 panic：

顺序约束原因
setup_arch() 必须在最前要先知道内存长什么样（e820 表）、CPU 支持哪些特性，才能决定后续怎么分配内存、要不要开某些指令。
build_all_zonelists() 在 mm_init() 之前内存区（zone）的划分依据是 e820 解析出来的物理内存布局。
vfs_caches_init_early() 在 mm_init() 之前它的注释写得很直白：这些缓存要"用大块启动内存（bootmem）分配"，必须在 slab 分配器就绪之前做完。
sched_init() 在 local_irq_enable() 之前中断一开，定时器中断就会来。如果那时调度器还没建好，会直接 oops。
console_init() 在中途太早打印，串口/显示器驱动还没准备好；太晚打印，前面出问题就什么都看不到了。
initcall 在 do_basic_setup() 里跑此时内存、调度器、中断都已就绪，驱动初始化函数才可以自由地分配内存、注册中断。
prepare_namespace() 在 kernel_execve() 之前用户态进程要有地方读自己的可执行文件，根文件系统必须先挂上。

3.3 initcall 分级表：驱动什么时候注册自己

驱动需要在正确的时机初始化自己（注册设备、申请中断、挂载文件系统）。但"正确时机"因驱动而异：内存相关的要最早，块设备驱动要晚一些。用宏 + 链接段表达这个顺序，是内核最经典的设计之一。

等级宏所在链接段运行时机典型使用者
earlyearly_initcall(fn).initcallearlySMP 启动之前（do_pre_smp_initcalls()）内存子系统、时序等极早期初始化
0pure_initcall(fn).initcall0do_initcalls() 最早只做变量初始化、无依赖
1core_initcall(fn).initcall1核心子系统
2postcore_initcall(fn).initcall2核心之后

4subsys_initcall(fn).initcall4一般子系统

rootfsrootfs_initcall(fn).initcallrootfs在 5 和 6 之间根文件系统相关

关键点：等级不是"优先级"，而是"跑在第几梯队"。同等级内的先后顺序由链接顺序决定（即 Makefile 里的 obj-y 顺序），跨等级则严格按表格从上到下。而且还有 _sync 变体（如 core_initcall_sync → .initcall1s），表示这个 initcall 必须同步执行完（不能丢到异步队列）。

3.4 module_init 与 initcall 的关系

这是新手最容易混淆的一点。module_init() 有两副面孔，取决于代码是编进内核还是编成模块：

场景module_init(x) 展开成什么时候被调用谁调用
编进内核（builtin，CONFIG_XXX=y）__initcall(x) → device_initcall(x) → 函数指针放进 .initcall6 段开机时do_initcalls() 遍历调用
编成模块（CONFIG_XXX=m，生成 .ko）生成一个叫 init_module 的函数（用 alias 属性指向你写的 init 函数）insmod / modprobe 时kernel/module.c:3604 的 do_init_module()

所以：同一个驱动源码，编译方式不同，初始化时机完全不同。编进内核它在开机第 6 梯队被调用；编成模块，它在被加载的那一刻被调用。这就是为什么"驱动明明 insmod 成功了却不工作"——可能它的 module_init 依赖某个只在内核启动早期才存在的东西。

3.5 谁是 PID 0、1、2？

  PID 0   swapper/0   ← 引导线程转世而来，就是那个跑 start_kernel() 的 CPU
                          永远待在 idle 循环里，CPU 没事干就跑它
                          它是所有进程的祖先（task_struct 的 parent 链最终指向它）

  PID 1   init        ← rest_init() 里第一个 kernel_thread 创建的
                          第一个用户态进程（由它 execve /sbin/init 而来）
                          回收僵尸进程、挂载文件系统、启动服务

  PID 2   kthreadd    ← rest_init() 里第二个 kernel_thread 创建的
                          所有内核线程的父进程（kworker/0、ksoftirqd/0 的爹）

为什么 init 必须是 PID 1？因为 PID 1 有特权：它回收不到父进程的僵尸（自己是父），忽略未被处理的信号（除了它显式注册的），并且是命名空间的初始化者——容器里的 PID 1 就是一个新的命名空间根。这个"特权"正是容器需要 --init 或特殊 init 的原因。

4. 源码走读

4.1 解压入口：arch/x86/boot/compressed/head_64.S

GRUB2 把 bzImage 读进内存后，CPU 还处于 16 位实模式（startup_32）。这段汇编先切换到 32 位保护模式、设置好栈，然后解压出真正的内核，最后跳到 64 位入口。注意 0x200 这个偏移是 ABI 约定，不能改——UEFI stub 依赖它。

arch/x86/boot/compressed/head_64.S:308-345 startup_64（压缩镜像里的 64 位入口）

	.org 0x200
SYM_CODE_START(startup_64)
	/*
	 * 64bit entry is 0x200 and it is ABI so immutable!
	 * We come here either from startup_32 or directly from a
	 * 64bit bootloader.
	 * If we come here from a bootloader, kernel(text+data+bss+brk),
	 * ramdisk, zero_page, command line could be above 4G.
	 * We depend on an identity mapped page table being provided
	 * that maps our entire kernel(text+data+bss+brk), zero page
	 * and command line.
	 */

	cld
	cli

	/* Setup data segments. */
	xorl	%eax, %eax
	movl	%eax, %ds
	movl	%eax, %es
	movl	%eax, %ss
	movl	%eax, %fs
	movl	%eax, %gs

	/*
	 * Compute the decompressed kernel start address.  It is where
	 * we were loaded at aligned to a 2M boundary. %rbp contains
	 * the decompressed kernel start address.
	 *
	 * If it is a relocatable kernel then decompress and run the kernel
	 * from load address aligned to 2MB addr, otherwise decompress and
	 * run kernel from LOAD_PHYSICAL_ADDR
	 *
	 * We cannot rely on the calculation done in 32-bit mode, since
	 * we may have been invoked via the 64-bit entry point.
	 */
	// ... 省略 KASLR 随机偏移计算（CONFIG_RELOCATABLE 下的 image_offset 处理）

逐点解释：

  • cld; cli：清方向标志、关中断。此刻中断向量表还没建好，任何中断都是灾难。
  • movl %eax, %ds/%es/%ss/%fs/%gs：把段寄存器清零。x86 上加载段寄存器会触发特权级检查，此时还在 ring 0，清零最省事。
  • "Compute the decompressed kernel start address"：解压出来的内核必须放在 2MB 对齐的物理地址上（因为要用 2MB 大页映射），所以要算出目标地址并存进 %rbp。
  • 注释里说的 "identity mapped page table being provided"：64 位路径要求引导器（或 EFI stub）已经建好了恒等映射页表，否则解压代码没法访问 4GB 以上的内存。

4.2 内核真正的入口：arch/x86/kernel/head_64.S

解压完成后，控制权交给未压缩的内核镜像里的 startup_64。这段汇编干的事可以概括为四步：建页表 → 切长模式 → 设好段/栈/IDT → 跳 C 代码。

arch/x86/kernel/head_64.S:73-107 startup_64（未压缩内核的 64 位入口）

	/* Set up the stack for verify_cpu(), similar to initial_stack below */
	leaq	(__end_init_task - SIZEOF_PTREGS)(%rip), %rsp

	leaq	_text(%rip), %rdi
	pushq	%rsi
	call	startup_64_setup_env
	popq	%rsi

	/* Now switch to __KERNEL_CS so IRET works reliably */
	pushq	$__KERNEL_CS
	leaq	.Lon_kernel_cs(%rip), %rax
	pushq	%rax
	lretq

.Lon_kernel_cs:
	UNWIND_HINT_EMPTY

	/* Sanitize CPU configuration */
	call verify_cpu

	/*
	 * Perform pagetable fixups. Additionally, if SME is active, encrypt
	 * the kernel and retrieve the modifier (SME encryption mask if SME
	 * is active) to be added to the initial pgdir entry that will be
	 * programmed into CR3.
	 */
	leaq	_text(%rip), %rdi
	pushq	%rsi
	call	__startup_64
	popq	%rsi

	/* Form the CR3 value being sure to include the CR3 modifier */
	addq	$(early_top_pgt - __START_KERNEL_map), %rax
	jmp 1f
SYM_CODE_END(startup_64)

逐点解释：

  • leaq (__end_init_task - SIZEOF_PTREGS)(%rip), %rsp：用 RIP 相对寻址算栈顶。为什么不写绝对地址？因为内核可能被加载到任意物理地址（KASLR），RIP 相对是位置无关的。
  • startup_64_setup_env：把引导器传来的 boot_params 地址等信息整理成 C 能用的形式。
  • pushq $__KERNEL_CS; lretq：这是 x86 汇编里的经典技巧——用 lretq 一次性装载 CS 和 RIP，比 jmp 更灵活（AMD 不支持 64 位偏移的远跳转）。
  • call verify_cpu：检查 CPU 的安全特性（NX、SMEP 等），把不支持的特性关掉。这是防止"内核被利用后跑用户态恶意代码"的第一道防线。
  • call __startup_64：真正建立内核页表（early_top_pgt），返回 %rax 是新的 CR3 值。
  • addq $(early_top_pgt - __START_KERNEL_map), %rax：把物理地址转成内核虚拟地址。内核被编译成链接在高地址（0xffffffff8xxxxxxx），但运行时页表里放的是物理地址，所以要加上这个偏移量。

arch/x86/kernel/head64.c:517-559 x86_64_start_kernel（跳入 C 世界的第一站）

	/* 初始化CR4控制寄存器的影子变量，用于追踪CR4状态（避免每次读取CR4） */

几个关键点：

  • clear_bss()：BSS 段是"未初始化的全局变量"。引导器加载内核时不会帮你清零 BSS，所以必须内核自己做。不清零的话，那些没显式赋初值的全局变量会带着内存里的垃圾值运行。
  • copy_bootdata()：把 boot_params（含 cmd_line、内存布局、initrd 地址）从引导器留下的低地址内存复制到内核自己的数据段。
  • init_top_pgt[511] = early_top_pgt[511]：只复制一项——内核高地址映射那一项。其余 510 项是恒等映射，属于启动蹦桥，用完就扔（reset_early_page_tables() 已经清掉了）。

4.4 rest_init()：凭空造出 PID 0/1/2

这是启动流程里最"魔法"的一段：一个函数凭空变出三个进程。

init/main.c:720-772 rest_init

noinline void __ref rest_init(void)
{
	struct task_struct *tsk;
	int pid;

	/* 启动RCU调度器，允许后续代码使用RCU读临界区 */
	rcu_scheduler_starting();
	/*
	 * We need to spawn init first so that it obtains pid 1, however
	 * the init task will end up wanting to create kthreads, which, if
	 * we schedule it before we create kthreadd, will OOPS.
	 */
	/* 创建 kernel_init 内核线程，它将成为用户空间的 init 进程(PID=1) */
	pid = kernel_thread(kernel_init, NULL, CLONE_FS);
	/*
	 * Pin init on the boot CPU. Task migration is not properly working
	 * until sched_init_smp() has been run. It will set the allowed
	 * CPUs for init to the non isolated CPUs.
	 */
	/* 将 init 线程固定在引导CPU上运行，直到SMP初始化完成后才允许迁移 */
	rcu_read_lock();
	tsk = find_task_by_pid_ns(pid, &init_pid_ns);
	set_cpus_allowed_ptr(tsk, cpumask_of(smp_processor_id()));
	rcu_read_unlock();

	numa_default_policy();
	/* 创建 kthreadd 内核线程(PID=2)，所有后续内核线程都由它 fork */
	pid = kernel_thread(kthreadd, NULL, CLONE_FS | CLONE_FILES);
	rcu_read_lock();
	kthreadd_task = find_task_by_pid_ns(pid, &init_pid_ns);
	rcu_read_unlock();

	/*
	 * Enable might_sleep() and smp_processor_id() checks.
	 * They cannot be enabled earlier because with CONFIG_PREEMPTION=y
	 * kernel_thread() would trigger might_sleep() splats. With
	 * CONFIG_PREEMPT_VOLUNTARY=y the init task might have scheduled
	 * already, but it's stuck on the kthreadd_done completion.
	 */
	system_state = SYSTEM_SCHEDULING;

	/* 通知 kernel_init 线程：kthreadd 已就绪，可以开始创建内核线程了 */
	complete(&kthreadd_done);

	/*
	 * The boot idle thread must execute schedule()
	 * at least once to get things moving:
	 */
	/* 至少调用一次 schedule()，让调度器选择 kernel_init 运行 */
	schedule_preempt_disabled();
	/* 进入CPU空闲循环，引导线程永久成为 idle 进程(PID=0)，永不返回 */
	cpu_startup_entry(CPUHP_ONLINE);
}

逐点解释：

  • rcu_scheduler_starting()：RCU（Read-Copy-Update）读侧无锁同步机制的调度器要开始了。
  • kernel_thread(kernel_init, NULL, CLONE_FS)：kernel_thread() 是"内核版的 fork"——创建一个只有内核空间的线程。顺序很关键：必须先创建 init（拿到 PID 1），因为 init 马上就想创建内核线程，如果那时 kthreadd 还不存在会 OOPS。
  • set_cpus_allowed_ptr(...)：把 init 钉在引导 CPU 上。因为此时 sched_init_smp() 还没跑，任务迁移机制还不完整。
  • kernel_thread(kthreadd, NULL, CLONE_FS | CLONE_FILES)：创建 kthreadd（PID 2）。
  • system_state = SYSTEM_SCHEDULING：系统状态推进到"可以调度了"，此时 might_sleep() 和 smp_processor_id() 的检查才被打开。
  • complete(&kthreadd_done)：这是两个线程之间的握手信号。kernel_init_freeable() 开头就在 wait_for_completion(&kthreadd_done) 等它。
  • schedule_preempt_disabled()：主动让出 CPU。第一次 schedule 是"交接"仪式——从此引导线程不再往下走，而是进入 idle 循环。
  • cpu_startup_entry(CPUHP_ONLINE)：永不返回。引导线程就此变成 PID 0 的 idle 进程。

4.5 kernel_init_freeable()：PID 1 干的活

现在把视角切到刚被创建出来的 PID 1（内核线程 kernel_init）。它的入口是 kernel_init()，真正的重活都在 kernel_init_freeable() 里。

init/main.c:1679-1747 kernel_init_freeable

static noinline void __init kernel_init_freeable(void)
{
	/*
	 * Wait until kthreadd is all set-up.
	 */
	/* 阻塞等待 kthreadd(PID=2) 完全就绪，确保后续内核线程可以被创建 */
	wait_for_completion(&kthreadd_done);

	/* Now the scheduler is fully set up and can do blocking allocations */
	/* 调度器已完全初始化，现在允许所有GFP内存分配标志 */
	gfp_allowed_mask = __GFP_BITS_MASK;

	/*
	 * init can allocate pages on any node
	 */
	/* 允许init进程从任意NUMA节点分配内存 */
	set_mems_allowed(node_states[N_MEMORY]);

	cad_pid = task_pid(current);

	/* 准备所有辅助CPU（非引导CPU），为SMP启动做准备 */
	smp_prepare_cpus(setup_max_cpus);

	/* 启动工作队列线程（kworker），使异步任务可以真正执行 */
	workqueue_init();

	init_mm_internals();

	do_pre_smp_initcalls();
	lockup_detector_init();

	/* 启动所有辅助CPU，实现真正的多核并行 */
	smp_init();
	/* 完成SMP感知的调度器初始化（负载均衡、CPU拓扑等） */
	sched_init_smp();

	padata_init();
	page_alloc_init_late();
	/* Initialize page ext after all struct pages are initialized. */
	page_ext_init();

	/* 触发所有 __initcall 级别的驱动初始化（设备驱动注册的核心时机） */
	do_basic_setup();

	kunit_run_all_tests();

	/* 打开 /dev/console，为init进程提供 stdin(0)/stdout(1)/stderr(2) */
	console_on_rootfs();

	/*
	 * check if there is an early userspace init.  If yes, let it do all
	 * the work
	 */
	if (init_eaccess(ramdisk_execute_command) != 0) {
		ramdisk_execute_command = NULL;
		prepare_namespace();
	}
	// ... 省略 integrity_load_keys() 之前的说明性注释
	integrity_load_keys();
}

逐点解释：

  • wait_for_completion(&kthreadd_done)：等 rest_init() 里的握手信号。没有它，init 可能比 kthreadd 先跑。
  • gfp_allowed_mask = __GFP_BITS_MASK：解锁所有 GFP 分配标志。之前调度器没好，睡眠类分配（会触发调度）是不允许的。
  • smp_prepare_cpus() → smp_init() → sched_init_smp()：三步走。准备 CPU 状态 → 真正启动其他 CPU（它们会走 secondary_startup_64）→ 让调度器感知多核拓扑。顺序也是依赖关系：先有 CPU 在线，才能做拓扑感知的负载均衡。
  • do_pre_smp_initcalls()：跑 early_initcall 那一档（见 4.6）。
  • do_basic_setup()：驱动初始化的总开关，见下一节。
  • console_on_rootfs()：打开 /dev/console 并 dup 成 0/1/2。这样用户态 init 的标准输入输出才有归宿。
  • prepare_namespace()：挂载根文件系统，见 4.8。

4.7 启动第一个用户态进程

根文件系统挂好后，内核就要"变出"第一个用户态进程。kernel_init() 会依次尝试若干路径。

init/main.c:1605-1647 kernel_init：寻找并执行 init

	/* 优先尝试运行ramdisk中指定的init程序 */
	if (ramdisk_execute_command) {
		ret = run_init_process(ramdisk_execute_command);
		if (!ret)
			return 0;
		pr_err("Failed to execute %s (error %d)\n",
		       ramdisk_execute_command, ret);
	}

	 * We try each of these until one succeeds.
	 *
	 * The Bourne shell can be used instead of init if we are
	 * trying to recover a really broken machine.
	 */
	if (execute_command) {
		ret = run_init_process(execute_command);
		if (!ret)
			return 0;
		panic("Requested init %s failed (error %d).",
		      execute_command, ret);
	}

	if (CONFIG_DEFAULT_INIT[0] != '\0') {
		ret = run_init_process(CONFIG_DEFAULT_INIT);
		if (ret)
			pr_err("Default init %s failed (error %d)\n",
			       CONFIG_DEFAULT_INIT, ret);
		else
			return 0;
	}

	/* 依次尝试标准init路径：/sbin/init → /etc/init → /bin/init → /bin/sh */
	if (!try_to_run_init_process("/sbin/init") ||
	    !try_to_run_init_process("/etc/init") ||
	    !try_to_run_init_process("/bin/init") ||
	    !try_to_run_init_process("/bin/sh"))
		return 0;

	/* 所有init路径均失败，内核无法继续运行，触发panic */
	panic("No working init found.  Try passing init= option to kernel. "
	      "See Linux Documentation/admin-guide/init.rst for guidance.");
}

优先级：ramdisk_execute_command（rdinit= 参数）→ execute_command（init= 参数）→ CONFIG_DEFAULT_INIT → /sbin/init → /etc/init → /bin/init → /bin/sh（急救用）。全失败就 panic，因为没有用户态进程的系统等于没有系统。

		return PTR_ERR(filename);

	bprm = alloc_bprm(fd, filename);
	if (IS_ERR(bprm)) {
		retval = PTR_ERR(bprm);
		goto out_ret;
	}

	retval = count_strings_kernel(argv);
	if (retval < 0)
		goto out_free;
	bprm->argc = retval;

	retval = count_strings_kernel(envp);
	if (retval < 0)
		goto out_free;
	bprm->envc = retval;

	retval = bprm_stack_limits(bprm);
	if (retval < 0)
		goto out_free;

	retval = copy_string_kernel(bprm->filename, bprm);
	if (retval < 0)
		goto out_free;
	bprm->exec = bprm->p;
	// ... 省略后面的 bprm_execve() 调用与错误处理路径
}

最终 bprm_execve() 会加载 ELF、切换到新的地址空间、跳到用户态入口。内核态的 kernel_init() 从此不再返回——它"变身"成了 PID 1 的用户态进程。

4.8 prepare_namespace()：挂上根文件系统

init/do_mounts.c:645-705 prepare_namespace

void __init prepare_namespace(void)
{
	if (root_delay) {
		printk(KERN_INFO "Waiting %d sec before mounting root device...\n",
		       root_delay);
		/* 等待指定秒数，给慢速存储设备（USB、eMMC）足够时间完成初始化 */
		ssleep(root_delay);
	}

	/*
	 * wait for the known devices to complete their probing
	 *
	 * Note: this is a potential source of long boot delays.
	 * For example, it is not atypical to wait 5 seconds here
	 * for the touchpad of a laptop to initialize.
	 */
	/* 等待所有块设备驱动完成设备探测，确保根设备已就绪 */
	wait_for_device_probe();

	/* 初始化软件RAID(md)设备，处理多磁盘阵列配置 */
	md_run_setup();

	if (saved_root_name[0]) {
		root_device_name = saved_root_name;
		if (!strncmp(root_device_name, "mtd", 3) ||
		    !strncmp(root_device_name, "ubi", 3)) {
			/* MTD/UBI闪存设备直接挂载（嵌入式系统常用） */
			mount_block_root(root_device_name, root_mountflags);
			goto out;
		}
		/* 将设备名（如/dev/sda1、UUID=xxx）转换为内核设备号 */
		ROOT_DEV = name_to_dev_t(root_device_name);
		if (strncmp(root_device_name, "/dev/", 5) == 0)
			root_device_name += 5;
	}

	/* 尝试加载initrd/initramfs，若成功则跳过块设备挂载 */
	if (initrd_load())
		goto out;

	/* wait for any asynchronous scanning to complete */
	if ((ROOT_DEV == 0) && root_wait) {
		printk(KERN_INFO "Waiting for root device %s...\n",
			saved_root_name);
		/* rootwait模式：持续等待直到根设备出现（适用于热插拔设备） */
		while (driver_probe_done() != 0 ||
			(ROOT_DEV = name_to_dev_t(saved_root_name)) == 0)
			msleep(5);
		async_synchronize_full();
	}

	/* 挂载根文件系统（NFS/CIFS/块设备） */
	mount_root();
out:
	/* 将devtmpfs挂载到/dev，提供设备节点访问 */
	devtmpfs_mount();
	/* 将根文件系统移动挂载到/，替换早期的rootfs */
	init_mount(".", "/", NULL, MS_MOVE, NULL);
	/* 切换进程根目录到新挂载的根文件系统 */
	init_chroot(".");
}

逐点解释：

  • wait_for_device_probe()：等所有设备探测完。这是启动慢的常见来源——笔记本的触摸板可能要 5 秒才应答。
  • ROOT_DEV = name_to_dev_t(root_device_name)：把命令行里的 root=/dev/sda2、root=UUID=xxx、root=LABEL=xxx 翻译成内核内部的主设备号/次设备号。
  • initrd_load()：如果给了 initramfs，先把它挂成根，成功了就 goto out——initramfs 里的 init 脚本会自己负责去挂真正的根盘。这正是"initramfs 里放磁盘驱动"的意义。
  • mount_root()：挂真正的根。支持三种：NFS（root= 是 IP 形式）、CIFS、以及块设备。
  • init_mount(".", "/", NULL, MS_MOVE, NULL) + init_chroot(".")：内核启动早期有个临时的 rootfs（内存里的空目录），挂载完真根后，用 MS_MOVE 把新根"搬"到 /，再把当前进程的根目录切过去。

init/do_mounts.c:414-449 do_mount_root（真正执行挂载）

static int __init do_mount_root(const char *name, const char *fs,
				 const int flags, const void *data)
{
	struct super_block *s;
	struct page *p = NULL;
	char *data_page = NULL;
	int ret;

	if (data) {
		/* init_mount() requires a full page as fifth argument */
		p = alloc_page(GFP_KERNEL);
		if (!p)
			return -ENOMEM;
		data_page = page_address(p);
		/* zero-pad. init_mount() will make sure it's terminated */
		strncpy(data_page, data, PAGE_SIZE);
	}

	ret = init_mount(name, "/root", fs, flags, data_page);
	if (ret)
		goto out;

	init_chdir("/root");
	s = current->fs->pwd.dentry->d_sb;
	ROOT_DEV = s->s_dev;
	printk(KERN_INFO
	       "VFS: Mounted root (%s filesystem)%s on device %u:%u.\n",
	       s->s_type->name,
	       sb_rdonly(s) ? " readonly" : "",
	       MAJOR(ROOT_DEV), MINOR(ROOT_DEV));

out:
	if (p)
		put_page(p);
	return ret;
}

关键的那行是 init_mount(name, "/root", fs, flags, data_page)——它先挂到 /root 这个临时位置，成功后再 init_chdir("/root") 把当前工作目录切过去，最后 prepare_namespace() 用 MS_MOVE 把它搬到 /。"先挂到临时点再搬走"是为了避免挂载过程中的路径混乱（挂载点必须存在，且不能在挂载过程中被当作路径解析的一部分）。

一句话总结本节：内核启动不是"一段代码"，而是一次有严格依赖关系的有序释放——每一步都在"交接"某样东西：固件交出硬件控制权，setup_arch() 交出内存布局知识，initcall 交出"驱动注册"的时机，prepare_namespace() 交出根文件系统，kernel_execve() 最后交出整个机器。

5. 动手验证

5.1 看看启动日志的三个"分水岭"

# 1) 内核第一条消息：内核横幅
dmesg | head -3
# 预期：
# [    0.000000] Linux version 5.10.0 (gcc ...) #1 SMP ...
# [    0.000000] Command line: BOOT_IMAGE=/vmlinuz root=UUID=... ro quiet

# 2) 根文件系统挂上的那一刻（VFS: Mounted root）
dmesg | grep -n "Mounted root"
# 预期： [    1.234567] VFS: Mounted root (ext4 filesystem) readonly on device 8:2

# 3) 交出控制权给用户态（Run /sbin/init as init process）
dmesg | grep -n "as init process"
# 预期： [    1.567890] Run /sbin/init as init process

# 整条时间线：内核从 0.000000 到 "Run ... as init process"
dmesg | head -60

这三条消息恰好对应本篇的三个阶段。时间戳还能告诉你启动慢在哪：如果 "Mounted root" 出现在 30 秒，说明卡在设备探测或磁盘上；如果 "Run /sbin/init" 出现在 40 秒，说明卡在 initcall（某个驱动初始化超时）。

5.3 用 init= 参数改"第一个用户进程"

这是最直观的实验：让内核启动时执行一个你自己的脚本，而不是 /sbin/init。

# 查看当前系统支持哪些内核参数（/proc/cmdline 就是解析结果）
cat /proc/cmdline

# 如果你用 GRUB2，在 linux 那一行末尾加：
#   init=/bin/sh
# 开机后你将直接得到一个 root shell（没有 systemd！）

# 用 qemu + busybox 复现这个实验（不需要改磁盘）
# --- 1) 造一个极简 initramfs ---
mkdir -p /tmp/rootfs/bin /tmp/rootfs/proc /tmp/rootfs/sys
busybox --install -s /tmp/rootfs/bin        # 需要本机已装 busybox
cat > /tmp/rootfs/init <<'EOF'
#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
echo "=== 我就是 init，PID 是 $$ ==="
ls /proc | head -5
exec /bin/sh
EOF
chmod +x /tmp/rootfs/init

# --- 2) 打包成 cpio.gz ---
cd /tmp/rootfs && find . | cpio -o -H newc 2>/dev/null | gzip > /tmp/initramfs.cpio.gz
cd -

# --- 3) 用 qemu 启动（-kernel 直接给内核，不经过 GRUB） ---
qemu-system-x86_64 -m 512M \
  -kernel arch/x86/boot/bzImage \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init panic=1" \
  -nographic
# 预期：先看到内核横幅（Linux version 5.10.0 ...），
#       接着看到 "=== 我就是 init，PID 是 1 ==="
#       最后进入 /bin/sh 提示符
# 按 Ctrl-A X 退出 qemu

这个实验把本篇的整条链路都跑通了：固件阶段被 qemu 代替、initramfs 代替根文件系统、rdinit=/init 代替 /sbin/init。你看到的"我就是 init，PID 是 1"，正是 rest_init() 造出来的那个 PID 1。

6. 自测

Q1. module_init(my_init) 在"编进内核"和"编成模块"两种情况下分别是谁调用？编进内核时，module_init(x) 展开为 __initcall(x) → device_initcall(x) → 函数指针放进 .initcall6.init 链接段，开机时由 do_initcalls() 遍历调用。编成 .ko 时，宏生成一个名为 init_module 的函数（alias 到 my_init），在 insmod/modprobe 时由 kernel/module.c 的 do_init_module() 调用。
Q2. 为什么 vfs_caches_init_early() 必须在 mm_init() 之前？因为它创建的是 dcache / inode 这些"大对象"，代码注释写明它们要使用 bootmem（启动内存）分配，而 bootmem 必须在 slab 分配器（kmem_cache_init()）初始化之前使用。放到 mm_init() 之后就晚了——那时 bootmem 已经被释放或不再可用。同理，sched_init() 必须在 local_irq_enable() 之前，否则定时器中断一来，调度器还没建好就会 oops。
Q3. early_initcall 和 device_initcall 的区别只是"早晚"吗？不只是早晚，运行的时机点也不同。early_initcall 在 do_pre_smp_initcalls() 中运行，此时 SMP 还没启动（只有引导 CPU），调度器也不完全就绪；device_initcall 在 do_initcalls() 中运行，此时多核已经启动、调度器完全可用。另外 early_initcall 只对内建代码有效（模块编译时它被重定义为 module_init）。
Q4. 内核自己怎么知道"启动成功了"？它不知道。内核的判定标准是"我已经把控制权交给用户态了"——kernel_execve("/sbin/init") 成功执行、且不返回，就意味着交接完成。所以在 dmesg 里，"Run /sbin/init as init process" 这行才是内核启动的终点；之后 systemd 还要再花几秒，那段时间内核已经在正常服务了，机器却还"没启动完"。
Q5. 为什么 init 必须是 PID 1，根文件系统又是怎么被"搬"到 / 的？因为 PID 1 有三样特权：① 它的父进程不存在，所以由它回收僵尸进程；② 它是命名空间的"根"，容器里的 PID 1 就是容器的 init，namespace 的建立依赖于它；③ 它忽略大部分默认信号。PID 编号由 rest_init() 中创建线程的先后顺序决定——先创建 kernel_init 拿到 1，再创建 kthreadd 拿到 2，而引导线程自己保留 0。
挂载方面：内核启动早期有一个内存里的空 rootfs 挂在 /。真正挂载时先挂到临时目录 /root（do_mount_root() 里的 init_mount(name, "/root", ...)），成功后 init_chdir("/root") 切进目录；最后 prepare_namespace() 用 init_mount(".", "/", NULL, MS_MOVE, NULL) 把这个挂载点整体移动到 /，再 init_chroot(".") 把进程根目录切过去。先挂临时点再 MS_MOVE，是为了避免挂载过程中 / 自身被当作路径解析的一部分而引起混乱。
