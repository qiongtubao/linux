# 主题二 · 一个字符的旅程：从 UART 中断到 `read()`

## 你已知的

在串口终端敲一个 `x`，屏幕立刻回显一个 `x`；敲回车，程序才拿到这一行。
中间要经过：硬件 → 驱动 → 行规程 → 用户缓冲区。

## 五跳

```
① UART 收到字节 → 触发 IRQ 4（上一站：request_irq）
② serial8250_interrupt() 读 RBR 寄存器，塞进 tty 的 flip buffer
③ tty_flip_buffer_push() → n_tty_receive_buf_common()   ← 行规程第一站（有打点）
④ 按 termios 处理：
     ├─ ISIG：0x03 == INTR_CHAR → isig(SIGINT) → __isig() → kill_pgrp()（有打点）
     ├─ ECHO：把字符打回输出（你看到的回显）
     └─ 规范模式：攒到换行 → 置位 canon_head，唤醒 read()
⑤ 用户态 read() 拿到一行（不含控制字符）
```

## 实测：敲一个 `x` 和一个 `Ctrl-C`

```
[latte] n_tty_rx: 1 bytes      ← 收到 'x'
x                              ← 回显（行规程打的，不是对方程序）
[latte] n_tty_rx: 1 bytes      ← 收到 0x03
[latte] isig: sig=2            ← 翻译成 SIGINT
[latte] __isig: sig=2 pgrp=set ← 找到前台进程组，投递
```

三行打点正好对应“收字节 → 认控制字符 → 投递信号”三个阶段。注意 `x` 的回显出现在
`n_tty_rx` 之后：**回显是内核替对端打的**，这也是为什么 `stty -echo` 一关，敲字就看不见。

## 为什么要有 flip buffer

中断上下文里不能长时间持锁、不能睡眠。所以驱动只做最少的活：把字节拷进一个
“翻转缓冲”（flip buffer），然后推给行规程；行规程再在合适的上下文里处理。

```
中断上下文：读寄存器 → memcpy 到 flip buffer → 推上去（尽快返回）
进程上下文：行规程处理（回显、攒行、发信号、唤醒 read）
```

## 规范模式 vs 非规范模式

| | 规范模式（默认） | 非规范/raw 模式 |
|---|---|---|
| 何时可读 | 一整行（遇 `\n`、EOF、或缓冲满） | 有多少读多少 |
| 行编辑 | 支持（退格、Ctrl-U） | 原样传给程序 |
| 典型用途 | shell、命令行工具 | `ssh`、`vi`、串口协议 |

`vi` 这类全屏程序会自己切到 raw 模式，因为退格、方向键必须原样交给它解析。
