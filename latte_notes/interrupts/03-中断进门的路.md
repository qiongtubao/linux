# 主题三 · 中断进门的路：从汇编桩到你的驱动

## 你已知的

IDT 里每个向量只填了一个“入口地址”。但设备五花八门，不可能每个 IRQ 各写一个处理
函数。内核的做法是：**所有外部 IRQ 共用一个入口桩，进门后再按向量号找对应设备**。

## 五跳

```
① CPU 查 IDT[vector] → irq_entries_start 里的桩（每个向量 16 字节）
② 桩：把向量号压栈，跳 common_interrupt
③ common_interrupt(regs)              arch/x86/kernel/irq.c:319
     → call_irq_handler(vector, regs)  → 按向量号取出 irq_desc
④ desc->handle_irq(desc)              kernel/irq/chip.c:686/825
     → handle_edge_irq() / handle_level_irq()   ← 流控（屏蔽/放行、边沿挂起）
⑤ handle_irq_event(desc)              kernel/irq/handle.c:250
     → 遍历 action 链，调 action->handler(irq, dev_id)   ← 你的驱动
```

返回路上还有两件事：

- `apic_eoi()`：告诉中断控制器“这条处理完了”，否则同类中断不再送来；
- `irq_exit()` → 跑 softirq（下半部），`/proc/softirqs` 统计的就是这里。

## `irq_desc` 是中枢

每个 IRQ 号对应一个 `struct irq_desc`（在 `irq_desc_tree` 或静态数组里），里面挂着：

| 字段 | 作用 |
|---|---|
| `handle_irq` | 流控函数：边沿 / 电平 / fasteoi |
| `action` 链 | 所有注册到这条 IRQ 的 handler（共享中断时多条） |
| 统计 | 计数、未处理次数（`/proc/interrupts` 的数据源） |

CPU 侧还有一份 per-CPU 的 `vector_irq[]`：向量号 → `irq_desc` 的映射，因为不同 CPU
可能把同一个 IRQ 分到不同向量。

## 为什么“共享中断”能工作

`request_irq()` 时传 `IRQF_SHARED` 的设备可以共用一条 IRQ 线：中断来了，
`handle_irq_event()` 会把 action 链上**每个** handler 都调一遍，谁认领谁处理
（靠 `dev_id` 和状态寄存器判断）。本次日志里 `ata_piix` 的两个口
（IRQ 14/15）就带着 `flags=0x80`（`IRQF_SHARED`）。

## 为什么 handler 不能睡眠

进入 `common_interrupt` 时 CPU 已经关中断、且可能持有中断控制器的锁；此时睡眠会
导致“等不到的唤醒”。所以规则是：

| 能做 | 不能做 |
|---|---|
| 读设备寄存器、清中断标志 | `kmalloc(GFP_KERNEL)`、`mutex_lock`、`msleep` |
| 拷数据到预分配缓冲 | 等 I/O、等用户态响应 |
| 调度下半部（`raise_softirq`、`schedule_work`） | 长时间计算 |

## 代码位置

| 位置 | 内容 |
|---|---|
| `arch/x86/entry/entry_64.S` | `irq_entries_start` 桩的生成（宏） |
| `arch/x86/kernel/irq.c:319` `common_interrupt()` | 设备 IRQ 的 C 入口 |
| `arch/x86/kernel/irq.c` `call_irq_handler()` | 向量 → `irq_desc` → `handle_irq` |
| `kernel/irq/chip.c:686` `handle_level_irq()` | 电平触发流控 |
| `kernel/irq/chip.c:825` `handle_edge_irq()` | 边沿触发流控 |
| `kernel/irq/handle.c:250` `handle_irq_event()` | 遍历 action 链 |
