# 主题二 · `ps` 到底有没有显示僵尸：一个 `head` 造成的误判

## 问题回顾

`exit/04` 里写的是：“本次没有用 `ps` 的输出来判断（busybox `ps` 的列表里没看到那一行
——可能被过滤或位置靠后）”。

## 复查旧日志：`ps` 其实列出了

把 `exit/04` 那次启动的完整日志拿出来，只看 `ps` 那一段：

```
--- ps ---
PID   USER     COMMAND
    1 0        /bin/sh /init nokaslr
    2 0        [kthreadd]
    ...
   59 0        [busybox]        ← 僵尸在这里
   ...
```

`ps` **确实列出了** pid 59，只是：

- 显示成 `[busybox]`（**带方括号**）——busybox `ps` 对“没有 cmdline 的进程”
  （内核线程、以及已经退出的僵尸）都用方括号显示；
- 它在列表的第 59 行附近，而我当时用 `head -40` 截断后查看，于是没看到。

## 结论

**这是我自己的测量失误，不是 busybox `ps` 的缺陷。** 两条教训：

1. 判定“某进程在不在”时，用精确匹配（`ps | grep 59`、或直接读 `/proc/59/stat`），
   不要用 `head` 截断后肉眼扫；
2. 僵尸的 `cmdline` 是空的，所以 `ps` 只显示名字（这里还加了方括号），
   不会显示成 procps-ng 那种 `defunct` —— **不同 `ps` 实现的措辞不同，但状态字母读的是
   同一个 `/proc/PID/stat` 第三列**。

## 校正后的证据链

| 证据 | 值 |
|---|---|
| `/proc/59/stat` 第三列 | `Z` |
| `ps` 列表里的那一行 | `59 0 [busybox]` |
| `do_exit` / `release_task` 打点 | 118 次 / 118 次 |

三条独立证据一致：进程确实进入了僵尸状态，并且最终被回收。`exit/04` 已按此更正。

## 代码位置

| 位置 | 内容 |
|---|---|
| `fs/proc/array.c:127` `task_state_array[]` | `Z (zombie)` 的名字来源 |
| `fs/proc/array.c` `proc_pid_stat()` | `/proc/PID/stat` 的输出 |
| `fs/proc/base.c` | `/proc/PID/cmdline`（僵尸为空，故 `ps` 只剩名字） |
