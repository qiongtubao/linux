# 主题六 · 按名字匹配不可靠：改用地址追 dentry

## 目标

`05` 已经回答了“新建 dentry 为什么不进 LRU”（`DCACHE_DONTCACHE`）。剩下的问题是：
**它们的引用计数为什么降不到 0**（`nr_dentry` 不回落）。

追这个问题需要“盯住某一个 dentry”，最自然的办法就是按名字过滤 trace。

## 先把 `d_name` 的偏移从反汇编里确认

`__d_alloc` 里会把名字拷进新 dentry，所以它必然写 `d_name`：

```
$ objdump -d --disassemble=__d_alloc vmlinux | grep -E "0x2[0-9a-f]\(%r12\)"
mov %edx,0x20(%r12)      ← d_name.hash
mov %eax,0x24(%r12)      ← d_name.len
mov %rax,0x28(%r12)      ← d_name.name（指针）
movq $0x0,0x30(%r12)     ← d_inode
lea  0x38(%r12),%rcx     ← d_iname（内联名字缓冲）
```

所以 `+0x28(%di):string` 读的就是名字——偏移是对的。

## 但按名字过滤行不通

实测 trace（净化过，原始字节里有非 UTF-8）：

```
kd: (dput+0x4) nm=".........|2.....k1" cnt=0x3 fl=0x200080
kd: (dput+0x4) nm=".........|2.....k1" cnt=0x2 fl=0x200080
```

名字前面**多出 16 个脏字节**才到 `k1`。原因是短名字存在 dentry 的**内联缓冲**
`d_iname` 里，而 dentry 对象来自 SLUB 缓存、**被复用**——`d_iname` 里残留着上一个
使用者的内容。所以：

- `nm=` 打出来的字符串可能带前缀垃圾（甚至不是合法 UTF-8，`sed`/`grep` 会直接报错）；
- 按 `grep k1` 匹配会**误配**到别的 dentry（任何内联缓冲里残留 "k1" 的都会命中）。

## 这一轮采到的数据（供后续参考）

| 实验 | 动作 | 相关 `dput(cnt, fl)` | `d_lru_add` | `nr_dentry` |
|---|---|---|---|---|
| kp5 | `touch /k1`，等 2 秒 | `(3, 0x200080)` → `(2, 0x200080)` | 1（不变） | 721 不回落 |
| kp6 | `touch /k1` → `rm /k1` | `(2, …)`、`(2, …)`、`(2, …)` | 2 | 623 → 624 → **625** |

两个现象都说明：**这些 dentry 的计数没有降到 1**（最后一次 `dput` 从未发生或被推迟），
所以 `DONTCACHE` 的“最后一次 dput 就销毁”也就没有触发。

## 方法上的结论（下次怎么做）

1. **不要用名字做 key**：内联名字缓冲会复用，按名字会误配。
   应改为**按 dentry 地址**（`%di`）做 key：先探 `__d_alloc` 打出 `d=+0x0(%si)` 之类的
   地址，再用地址过滤后续 `dput`。
2. **trace 可能含非 UTF-8**：`sed`/`grep` 会报 “stream did not contain valid UTF-8”。
   取数据前先净化：`tr -c '\11\12\40-\176' '.' < log`。
3. **偏移仍从反汇编拿**（`05` 的方法），别按源码手推。
