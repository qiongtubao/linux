# 主题五 · 从反汇编里拿结构体偏移，再用 kprobe 读引用计数

## 问题

`04` 里想用 kprobe 读 `struct dentry` 的引用计数和名字，但把 `qstr->name` 的偏移写成了
`+8`，采到的是乱码（`sed: stream did not contain valid UTF-8`）。

内核是 `CONFIG_DEBUG_INFO_NONE=y`：`vmlinux` 里既没有 DWARF 也没有 BTF，
`gdb -ex 'ptype struct dentry'` 没有输出、`pahole` 也无从下手。

## 办法：让编译器自己告诉你偏移

结构体成员的偏移会**印在反汇编里**。`dput()` 里必然要访问 `d_lockref`（引用计数），
所以直接看它：

```bash
$ objdump -d --disassemble=dput vmlinux | head -20
ffffffff814edef0 <dput>:
...
ffffffff814edf04:  lea    0x80(%rbp),%r12        ← &dentry->d_lockref 在 0x80
ffffffff814edf18:  call   <lockref_put_return>
ffffffff814edf30:  cmpq   $0x0,0x10(%rbp)        ← d_unhashed()：d_hash.pprev 在 0x10
ffffffff814edf52:  mov    0x84(%rbp),%eax        ← 读 count：0x84（lockref 里 count 在后 4 字节）
ffffffff814edf3a:  test   $0xa8,%al               ← DONTCACHE(0x80)|...|OP_DELETE(0x8) 的快路径判断
ffffffff814edf3e:  and    $0x40040,%eax           ← LRU_LIST(0x40000)|REFERENCED(0x40)
```

于是得到两个可靠偏移：

| 字段 | 偏移 | 依据 |
|---|---|---|
| `d_flags` | `0x0` | 结构体第一个成员（源码可确认） |
| `d_hash.pprev` | `0x10` | `cmpq $0x0,0x10(%rbp)` 对应 `d_unhashed()` |
| `d_lockref` | `0x80` | `lea 0x80(%rbp),%r12` 后立刻 `lockref_put_return` |
| `d_lockref.count` | `0x84` | `mov 0x84(%rbp),%eax` 后判 `test %eax,%eax`（判是否为零） |

**这比按源码手动推结构体布局可靠得多**——编译器已经把答案写在指令里。

## 用偏移做 kprobe

```sh
T=/sys/kernel/tracing
echo 'p:kd dput cnt=+0x84(%di):x32 fl=+0x0(%di):x32' >> $T/kprobe_events
echo 1 > $T/events/kprobes/enable
touch /k1
grep 'kd:' $T/trace | head
```

实测采到的 `(fl, cnt)` 组合（`touch /k1` 一次调用的窗口内）：

| 次数 | `cnt`（dput 入口的引用计数） | `fl`（d_flags） | 解读 |
|---|---|---|---|
| 3 | `0x11` | `0x108080` | 目录 + MOUNTED + **DONTCACHE(0x80)** |
| 2 | `0x4` | **`0x200080`** | **普通文件 + DONTCACHE** |
| 2 | `0x3` | `0x200080` | 同上 |
| 1 | `0x3` | `0x20000c` | 普通文件 + OP_DELETE + OP_REVALIDATE |
| 1 | `0x4` | `0x100000` | 目录，无 DONTCACHE |

## 这解释了“为什么不进 LRU”

`fl` 里那个 **`0x80` = `DCACHE_DONTCACHE`**（`include/linux/dcache.h` 的枚举：

```c
DCACHE_DONTCACHE = BIT(7),   /* Purge from memory on final dput() */
```

而 `retain_dentry()` 的开头就有：

```c
if (unlikely(d_flags & DCACHE_DONTCACHE))
	return false;            /* 直接不进 LRU，最后一次 dput 就销毁 */
```

`retain_dentry()` 返回 false → `dput()` 走销毁路径，**根本不会调用 `d_lru_add()`**
→ `nr_dentry_unused` 永远不会加。这与 `04` 的 kprobe 计数完全一致
（`d_lru_add` 在创建窗口恒为 1，一点没涨）。

**至此，“为什么新建的 dentry 不进 LRU”这个问题有了直接原因：tmpfs 给它的 dentry 打了
`DCACHE_DONTCACHE` 标记。**

## 还剩下一个矛盾（未解释）

如果 `DONTCACHE` 的 dentry 在最后一次 `dput` 就销毁，那么 `nr_dentry` 应该在 `touch`
退出后回落；但实测一直是 `721`（基线 621 + 100），**不回落**。

从 kprobe 看，`dput` 入口的 `cnt` 仍是 3~4（不是 1），说明**最后一次 `dput` 还没发生**——
有别的持有者没放手。是谁？`cnt` 的具体来源需要按 dentry 区分（本次没做到，见下）。

## 仍未做到的

- **名字没取到**：`+0x28(%di):string` 没采到 `nm=k1` 的记录，说明 `d_name`（qstr）
  不在 0x20。要确定它，可以同样反汇编 `d_lookup` / `__d_alloc` 里访问 `d_name` 的位置，
  或用 `d_instantiate` 的代码路径推。
- 有了名字，就能把“某个 dentry 的 cnt 从几降到几”逐条追出来，彻底定位“谁不放手”。
  **这一路在 [06](06-按名字匹配不可靠改用地址.md) 上撞了墙**：名字存在内联缓冲
  `d_iname` 里，dentry 对象被 SLUB 复用后会残留旧内容，`nm=` 打出来带脏前缀、
  按名字过滤会误配。下一次要按 dentry **地址**匹配。

## 方法论小结

1. **没有调试信息也能拿偏移**：反汇编里找“lea offset”/“mov offset”。
2. **kprobe 的内存取值语法**：`+0x84(%di):x32` 表示“以 %di 为基址、偏移 0x84、读 4 字节为
   十六进制”；`%si`/`%di` 是寄存器名，`$si` 不支持。
3. **flag 值要从源码枚举核对**：`0x80` 是 DONTCACHE 还是别的，取决于版本。
