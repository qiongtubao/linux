# 主题七 · 按地址追踪：引用卡在 1，`dput` 的计数语义先要搞对

## 上一轮的教训怎么修

`06` 说明按名字匹配不可靠（内联缓冲 `d_iname` 会被 SLUB 复用污染）。这一轮改成
**按 dentry 地址**：

```sh
T=/sys/kernel/tracing
echo 'p:di d_instantiate d=%di nm=+0x28(%di):string' >> $T/kprobe_events
echo 'p:kd dput d=%di cnt=+0x84(%di):x32 fl=+0x0(%di):x32' >> $T/kprobe_events
echo 'p:kk __dentry_kill d=%di' >> $T/kprobe_events
echo 'p:kl d_lru_add' >> $T/kprobe_events
```

- `d_instantiate` 是“新建文件绑定 inode”的必经点，`%di` 就是那个 dentry 的地址；
- 拿到地址后在 trace 里按 `d=` 精确匹配，不再依赖名字。

## 一个必须先搞对的语义

`dput()` 入口读到的 `cnt` 是**减一之前**的值：

```
dput 入口 cnt=3  →  执行后 2
dput 入口 cnt=2  →  执行后 1
dput 入口 cnt=1  →  执行后 0 → 走 retain_dentry/kill 分支
```

所以“看到 `cnt=1` 的那次 `dput`”才是最后一次。

## 实测（`touch /k1` + 等 2 秒 + `cat /k1`）

`d_instantiate` 给出了地址：

```
di: (d_instantiate) d=0xffff888003c5fa80 nm="........"
```

按这个地址过滤 `dput`：

```
kd: (dput) d=0xffff888003c5fa80 cnt=0x3 fl=0x200080   ← 普通文件 + DONTCACHE(0x80)
kd: (dput) d=0xffff888003c5fa80 cnt=0x2 fl=0x200080
（之后再也没有这个地址的 dput）
```

**减完之后剩 1 个引用**，且 `fl` 带 `DONTCACHE` → 不进 LRU、也不销毁 → `nr_dentry` 不回落。

## 对照组：`cnt=1` 的 dentry 确实会被杀

同一段 trace 里还有别的 dentry，可以看到“入口 `cnt=1` → 立刻 `__dentry_kill`”：

```
kd: (dput) d=0xffff888003c5f9c0 cnt=0x1 fl=0x80
kk: (__dentry_kill) d=0xffff888003c5f9c0        ← 紧跟着就销毁
kd: (dput) d=0xffff888003c5f600 cnt=0x1 fl=0x10000c
kk: (__dentry_kill) d=0xffff888003c5f600
```

**这说明销毁机制本身是好的**：只要真的走到最后一次 `dput`（`cnt=1`），
`DONTCACHE` 的 dentry 就会被立刻销毁。我们那个 `/k1` 的问题只是**没走到那一步**。

## 结论

| 问题 | 状态 |
|---|---|
| 为什么新建 dentry 不进 LRU | ✅ 已结案（`DONTCACHE`，`05`） |
| 为什么 `nr_dentry` 不回落 | ⚠️ 缩小到：**有 1 个引用一直没释放**（不是销毁机制的问题） |
| 谁持有那 1 个引用 | ❓ 仍未定位 |

## 下一步（方法已明确）

1. `dget()` 是内联函数，`System.map` 里没有符号，**探不到**；
2. 可行的是给 `dput` 加 `$stack`（栈回溯）+ 地址过滤器：

```sh
# 已知地址后
echo 'd == 0xffff888003c5fa80' > $T/events/kprobes/kd/filter
echo 'p:kd dput d=%di:x64 $stack' >> $T/kprobe_events
```

3. 或者反过来探“加引用”的路径：`d_find_alias` / `d_find_any_alias` 是真实符号
   （`System.map` 里是 `T`），可以探它们是否被调用。
