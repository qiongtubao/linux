# 主题二 · 作业控制：shell 到底做了什么

## 你已知的

shell 里 `cmd &` 放后台、`Ctrl-Z` 挂起、`fg` 拉回前台、`jobs` 看列表。
这些不是 shell 的“特效”，每一步都对应内核机制。

## 三个内核概念

| 概念 | 作用 | 谁维护 |
|---|---|---|
| 进程组（pgrp） | 作业的单位：一个 `cmd | cmd` 管道是一个 pgrp | `setpgid()`，shell 在 fork 后调用 |
| 会话（session） | 一个“终端登录”的范围，最多一个控制终端 | `setsid()` |
| 控制终端的前台组 | `tty->ctrl.pgrp`：谁现在“占着”终端 | `tcsetpgrp()`（`TIOCSPGRP`） |

`Ctrl-Z` 的完整路径（与本系列两站接上）：

```
终端收到 0x1a
 └─ n_tty 行规程 isig() → SIGTSTP        （tty/01、tty/02）
     └─ 发给 tty 的前台进程组
         └─ do_signal_stop() → 进程状态 T  （本站主题一、三）
             └─ shell 收到子进程停止的通知（waitpid 的 WUNTRACED）
                 └─ 打印 "[1]+ Stopped ..." 并把作业记进 job 表
```

## `fg` / `bg` 的实质

| 命令 | 做的事 |
|---|---|
| `fg %1` | `tcsetpgrp(终端, 作业的pgrp)` + `kill(-pgrp, SIGCONT)`，然后 shell 自己让开终端 |
| `bg %1` | 只发 `SIGCONT`（作业留在后台），然后 shell 继续用终端 |
| `jobs` | 读自己的 job 表（用户态结构），不涉及内核查询 |

所以“把作业放前台”= 改控制终端的前台进程组；“继续运行”= 发 `SIGCONT`。两件事经常一起做，
但不是一回事。

## 为什么需要 `set -m`

脚本默认不开作业控制（因为脚本可能没有终端）。`set -m`（monitor mode）会：

1. 给每个命令建新的进程组；
2. 把终端前台组设成它；
3. 这样 `Ctrl-C`/`Ctrl-Z` 才能定向到“当前前台作业”。

**前提是 shell 必须有控制终端**，否则 ash 会打印：

```
can't access tty; job control turned off
```

这句话我们在 `tty/04` 与本次实验里都见过——**没有控制终端就没有前台组，
也就没有作业控制**。

## 没有作业控制时会发生什么（本次实测）

1. `set -m` 失败；
2. 子进程和 shell 留在**同一个进程组**；
3. 这个进程组是“孤儿”（shell 的父进程不在同会话），于是
   **`SIGTSTP` 被内核丢弃**，只有 `SIGSTOP` 生效；
4. 结果就是“`kill -TSTP` 没反应、`kill -STOP` 立刻变成 T”。

## 代码位置

| 位置 | 内容 |
|---|---|
| `kernel/signal.c:2551` `do_signal_stop()` | 停止的实现 |
| `drivers/tty/n_tty.c:1075` `isig()` | Ctrl-Z → SIGTSTP（tty 站） |
| `drivers/tty/tty_jobctrl.c` | `tcsetpgrp` / 会话与前台组 |
| `kernel/exit.c` | `wait4()` 报告“已停止”的子进程（`WUNTRACED`） |
