# 主题一 · 进程状态与停止信号

## 你已知的

任务管理器里能把程序“挂起”，之后又能“恢复”。Linux 里对应的是**进程状态**与
**停止信号**：`ps` 的 `STAT` 列会从 `S`（睡眠）变成 `T`（停止）。

## 状态字母（`/proc/PID/stat` 第三列）

| 字母 | 含义 | 什么时候 |
|---|---|---|
| `R` | running / runnable | 正在跑或在运行队列里 |
| `S` | 可中断睡眠 | 等事件（`sleep`、等键盘） |
| `D` | 不可中断睡眠 | 等 I/O，连 `kill` 都叫不醒 |
| `T` | 停止 | 收到停止信号，或被调试器停住 |
| `t` | 被调试器停住 | `ptrace` |
| `Z` | 僵尸 | 已退出但父进程还没 `wait` |
| `I` | idle 内核线程 | 空闲线程 |

字母表就在 `fs/proc/array.c:127` 的 `task_state_array[]` 里。

## 五个与“停/继续”有关的信号

| 信号 | 编号 | 能否捕获/忽略 | 谁常发 |
|---|---|---|---|
| `SIGSTOP` | 19 | **不能** | 内核/管理员强制暂停 |
| `SIGTSTP` | 20 | 能（shell 把它转成 Ctrl-Z） | 终端 `Ctrl-Z` 时行规程发 |
| `SIGTTIN` | 21 | 能 | 后台进程读终端时内核发 |
| `SIGTTOU` | 22 | 能 | 后台进程写终端时内核发 |
| `SIGCONT` | 18 | 能 | `kill -CONT`、`fg`/`bg` |

`SIGSTOP` 不可捕获、不可忽略，所以“杀不死也停不了”的进程，`SIGKILL` 才是最后一招（同理
`SIGKILL`(9) 不可捕获）。

## 一个反直觉的规则：孤儿进程组的停止信号会被丢弃

POSIX 规定：**发给“孤儿进程组”成员的停止信号（SIGTSTP/SIGTTIN/SIGTTOU）
被内核直接丢弃**，只有 `SIGSTOP` 不受影响。内核源码里写得很直白
（`kernel/signal.c:2974` 附近）：

```c
/* The job control signals do nothing in an orphaned pgrp,
 * but SIGSTOP always works. */
if (signr != SIGSTOP) {
	...
	if (is_current_pgrp_orphaned())
		goto relock;
}
```

为什么要这样？因为“孤儿进程组”意味着**没有前台作业能把它恢复**（父进程在别的会话里），
停住就永远停住，还会泄漏资源。所以干脆不停。

本次实验正是撞上了这条规则（主题四）。

## 停止与继续在内核里怎么实现

```
信号投递 → get_signal()                       fs/... kernel/signal.c:2808
 ├─ 是停止信号？
 │   ├─ 非 SIGSTOP 且 pgrp 是孤儿 → 丢弃（不调用下一步）
 │   └─ do_signal_stop()                      kernel/signal.c:2551（打点）
 │        └─ 设置 JOBCTL_STOP_PENDING，然后 schedule() 睡下
 │             → 进程状态变成 T（直到 SIGCONT）
 └─ 是 SIGCONT → 清掉停止标记、唤醒 → 状态回到 R/S
```

## 代码位置

| 位置 | 内容 |
|---|---|
| `kernel/signal.c:2808` `get_signal()` | 信号处理的总出口 |
| `kernel/signal.c:2551` `do_signal_stop()` | 组停止的实体（打点） |
| `kernel/signal.c:2974` 附近 | 孤儿进程组丢弃停止信号的检查 |
| `fs/proc/array.c:127` `task_state_array[]` | 状态字母表 |
| `kernel/exit.c` | 退出与僵尸（`Z`）的维护 |
