# 主题五 · 信号投递：内核怎么把信号“摆”到用户栈上

`tty/04` 讲了 `Ctrl-C` 的两种命运，`jobs/01`~`04` 讲了停止信号与进程状态。
这篇补最后一段：**信号从“被发出”到“真的跑到你的 handler 里”，中间差了什么**。
答案有点反直觉：差一次“进程要回用户态”。

## 你已知的

- 终端按下 `Ctrl-C`，行规程把它变成 `SIGINT`（`tty/04`）；
- `SIGSTOP`/`SIGTSTP` 让进程进 `T` 状态，`kill -CONT` 让它继续（`jobs/01`、`jobs/03`）；
- `execve` 的最后一跳是 `iretq` 回到用户态（`execve/05`）。

## 内核里对应什么：**发信号**和**投递信号**是两件独立的事

**发**（谁都能发，随时可发，甚至从内核里发）：

```
kill(pid, SIG) / tgkill / raise
 └─ kill_pid_info → group_send_sig_info
     └─ __send_signal_locked()            kernel/signal.c:1043      ← 打点
         ├─ legacy_queue()：sig < SIGRTMIN 且该位已 pending → 直接短路
         │   （`kernel/signal.c:1037`，返回 TRACE_SIGNAL_ALREADY_PENDING）
         └─ 实时信号：sigqueue_alloc() → list_add_tail() → 真的入队
```

**投递**（只发生在“进程即将从内核回到用户态”那一刻）：

```
系统调用返回 / 中断返回 → exit_to_user_mode_loop
 └─ 若 _TIF_SIGPENDING 置位 → arch_do_signal_or_restart()   kernel/entry/common.c:40
     └─ get_signal()                                       kernel/signal.c:2808
         └─ handle_signal()                                arch/x86/kernel/signal.c:259  ← 打点
             └─ setup_rt_frame()                           arch/x86/kernel/signal.c:237  ← 打点
                 └─ x64_setup_rt_frame()                   arch/x86/kernel/signal_64.c:165 ← 打点
                     └─ __unsafe_setup_sigcontext()        arch/x86/kernel/signal_64.c:99
                         → 用户栈上出现 rt_sigframe：
                            ucontext + sigcontext + 掩码 + pretcode(=sa_restorer)
```

所以：**阻塞中的信号不会“执行”，它只是躺在 pending 位上等着**；
下一个系统调用返回时才会被搬上用户栈。这也解释了为什么信号 handler
总是在某条指令之间“突然插入”——不是异步打断内核，而是内核在返回前替它摆了现场。

## 4 个打点

| 打点 | 位置 | 记什么 |
|---|---|---|
| `send_signal: sig=… shared=…` | `kernel/signal.c` `__send_signal_locked()` | 每发一次就一条（哪怕被去重） |
| `handle_signal: sig=…` | `arch/x86/kernel/signal.c` `handle_signal()` | 真的要投递时一条 |
| `setup_rt_frame: sig=…` | `arch/x86/kernel/signal.c` `setup_rt_frame()` | 开始摆 frame |
| `setup_sigcontext: sig=… sp=…` | `arch/x86/kernel/signal_64.c` `x64_setup_rt_frame()` | 写入用户栈的位置（`sp` 是栈顶） |

## 实测：标准信号发两次只投递一次，实时信号发两次投递两次

探针程序：装两个 handler，先把信号**阻塞**、`kill` 自己两次、查 pending 位，
再解除阻塞看 handler 被调用几次。

```
[sig] pid=57 rt=34
[latte] send_signal: sig=10 shared=1        ← kill(SIGUSR1) 第一次
[latte] send_signal: sig=10 shared=1        ← 第二次（照样走完整入口）
[sig] blocked: SIGUSR1 pending=1            ← pending 只有一位
[latte] handle_signal: sig=10               ← 解除阻塞后只投递 1 次
[latte] setup_rt_frame: sig=10
[latte] setup_sigcontext: sig=10 sp=7fffe2d70610
[sig] after unblock: usr1_cnt=1

[latte] send_signal: sig=34 shared=1        ← kill(SIGRTMIN) 第一次
[latte] send_signal: sig=34 shared=1        ← 第二次
[sig] blocked: SIGRTMIN pending=1
[latte] handle_signal: sig=34               ← 投递 2 次（队列里两个）
[latte] setup_rt_frame: sig=34
[latte] setup_sigcontext: sig=34 sp=7fffe2d70610
[latte] handle_signal: sig=34
[latte] setup_rt_frame: sig=34
[latte] setup_sigcontext: sig=34 sp=7fffe2d70610
[sig] after unblock: rt_cnt=2
```

计数对照：

| 信号 | `send_signal` | `handle_signal` | handler 实际执行 |
|---|---|---|---|
| `SIGUSR1`（标准） | 2 | **1** | **1**（`usr1_cnt=1`） |
| `SIGRTMIN`（实时） | 2 | **2** | **2**（`rt_cnt=2`） |

日志里还有一批 `send_signal: sig=17`——那是 `SIGCHLD`：`init` 里每跑完一个命令，
shell 都会收到一次子进程退出的通知，同一个打点顺手看到了。

## 三个结论

1. **发信号与投递是两条链**：`__send_signal_locked()` 在“发”的那一侧、
   `handle_signal()` 在“回用户态”的那一侧。阻塞期间两侧都不动，
   所以 `pending=1` 之后要等解除阻塞、系统调用返回，handler 才跑到。
2. **标准信号只有一位 pending**：连发两次，第二次在 `legacy_queue()`
   （`kernel/signal.c:1037`：`sig < SIGRTMIN && sigismember(pending, sig)`）处就被短路，
   但打点仍在，所以日志能直接看到“发 2 投 1”。
   实时信号走 `sigqueue_alloc()` + `list_add_tail()`，是真队列，“发 2 投 2”。
3. **handler 的现场是内核在用户栈上摆的**：两次投递的 `sp` 完全相同
   （`0x7fffe2d70610`），说明每次都从同一处栈顶扣出 `rt_sigframe`；
   frame 里的返回地址指向 handler、`pretcode` 是 `sa_restorer`，
   handler 一 `ret` 就走 `rt_sigreturn` 系统调用恢复被打断的现场——
   这正好接上 `execve/05` 那个 `iretq`：一次进程从内核回用户态，
   可能是继续执行，也可能是跳进 handler。

## 复现

```c
/* sigprobe.c: 标准信号 vs 实时信号，看“发几次、投几次” */
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static volatile int usr1_cnt, rt_cnt;

static void on_usr1(int sig) { (void)sig; usr1_cnt++; }
static void on_rt(int sig) { (void)sig; rt_cnt++; }

int main(void)
{
	struct sigaction sa;
	sigset_t set, pend;
	int rt = SIGRTMIN;

	memset(&sa, 0, sizeof(sa));
	sigemptyset(&sa.sa_mask);
	sa.sa_handler = on_usr1;
	sigaction(SIGUSR1, &sa, NULL);
	sa.sa_handler = on_rt;
	sigaction(rt, &sa, NULL);

	printf("[sig] pid=%d rt=%d\n", getpid(), rt);

	/* 标准信号：连续发两次，只有一个 pending 位 */
	sigemptyset(&set);
	sigaddset(&set, SIGUSR1);
	sigprocmask(SIG_BLOCK, &set, NULL);
	kill(getpid(), SIGUSR1);
	kill(getpid(), SIGUSR1);
	sigpending(&pend);
	printf("[sig] blocked: SIGUSR1 pending=%d\n", sigismember(&pend, SIGUSR1));
	sigprocmask(SIG_UNBLOCK, &set, NULL);
	printf("[sig] after unblock: usr1_cnt=%d\n", usr1_cnt);

	/* 实时信号：连续发两次，两个都进队列 */
	sigemptyset(&set);
	sigaddset(&set, rt);
	sigprocmask(SIG_BLOCK, &set, NULL);
	kill(getpid(), rt);
	kill(getpid(), rt);
	sigpending(&pend);
	printf("[sig] blocked: SIGRTMIN pending=%d\n", sigismember(&pend, rt));
	sigprocmask(SIG_UNBLOCK, &set, NULL);
	printf("[sig] after unblock: rt_cnt=%d\n", rt_cnt);
	return 0;
}
```

## 代码位置

| 位置 | 函数 | 做什么 |
|---|---|---|
| `kernel/signal.c:1043` | `__send_signal_locked()` | 发送落点：去重（标准）/入队（实时） |
| `kernel/signal.c:1037` | `legacy_queue()` | 标准信号的去重判据：`sig < SIGRTMIN` 且该位已 pending |
| `kernel/entry/common.c:40` | `exit_to_user_mode_loop()` | 投递时机：`_TIF_SIGPENDING` 才进信号处理 |
| `kernel/signal.c:2808` | `get_signal()` | 取信号、处理 stop/ptrace/默认动作 |
| `arch/x86/kernel/signal.c:259` | `handle_signal()` | syscall 重启规则（`EINTR` 或重试）+ 摆 frame |
| `arch/x86/kernel/signal.c:237` | `setup_rt_frame()` | 按 ABI 选 32/64 位 frame 构造函数 |
| `arch/x86/kernel/signal_64.c:165` | `x64_setup_rt_frame()` | 64 位 `rt_sigframe`：ucontext/sigcontext/掩码/pretcode |
| `arch/x86/kernel/signal_64.c:99` | `__unsafe_setup_sigcontext()` | 把 16 个通用寄存器 + ip/flags/cs/ss 写进 sigcontext |

## 一句话收尾

信号是“**先把话记在 pending 位上，等你回用户态时再摆现场**”：
标准信号只有一位（会丢），实时信号排队（不丢），
而现场是内核用 `rt_sigframe` 在你自己栈上摆的——
handler 不是被“调用”的，是被 `iretq` 跳进去的。
