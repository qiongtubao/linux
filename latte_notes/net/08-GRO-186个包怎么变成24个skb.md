# 主题八 · GRO：186 个包怎么变成 24 个 skb

`net/04` 里有一句话只有代码依据：“GRO 把这批包聚成了 **skb 列表**，所以走 `ip_list_rcv`”。
这篇实测一次 256KB 传输，把数量对清楚——顺便修正那句话：
**合并主要发生在 skb 内部**（长度涨、包数不涨），不是把很多 skb 串成链。

## 你已知的

- NAPI 一次轮询批量收（`net/02`），`budget=64`；
- `netif_receive_skb` → `ip_rcv_core` → 协议栈（`net/04`）；
- TCP 段有 MSS，通常 1440 字节载荷（`net/07`）。

## 内核里对应什么：合并发生在“段 → skb”这一步

```
virtnet_poll（一次轮询，budget=64）
 └─ 每个收到的帧 → napi_gro_receive → dev_gro_receive()      net/core/gro.c:463  ← 打点
     ├─ 按流（5 元组哈希）在 gro_list 里找同一条流
     ├─ 找到 → 把新段的载荷**追加到已有 skb 的 frags**，长度涨、包数不涨
     └─ 找不到 → 自己成为一个新的候选
     （轮询结束/凑够就 flush）
 └─ flush → netif_receive_skb_list → ip_list_rcv()           net/ipv4/ip_input.c:656 ← 打点
     └─ 每个 skb 走 ip_rcv_core（`net/04` 的打点）
```

关键点：`gro_list` 里存的是**正在长大的 skb**。所以“合并”体现在
`skb->len` 变大（1480 → 10120 → …），而不是 list 变长。
`ip_list_rcv` 的 `n` 之所以常常是 1，就是因为它拿到的这个 skb 已经装了好几段。

## 2 个打点

| 打点 | 位置 | 内容 |
|---|---|---|
| `dev_gro_receive: len=…` | `net/core/gro.c` | 每个待合并的段（`len` 是单段长度） |
| `ip_list_rcv: n=…` | `net/ipv4/ip_input.c` | 一批里有几个 skb（合并后的批大小） |

配合 `net/04`/`net/07` 已有的 `virtnet_poll`、`netif_receive_skb`、`tcp_v4_rcv` 就能对账。

## 实测：宿主机发 256KB 原始 TCP 流给 guest

宿主机 `socat -u FILE:/tmp/big.bin TCP-LISTEN:10080,reuseaddr,fork`，
guest 里 `nc 10.0.2.2 10080 > /dev/null`（slirp 的 `10.0.2.2` 就是宿主机）。

```
nc rc=0
  eth0:  272202     186  ...              ← RX 272202 字节 / 186 个包

virtnet_poll=25  dev_gro_receive=186  ip_list_rcv=23  netif_receive_skb=24  tcp_v4_rcv=23
```

186 个设备包，进了 186 次 GRO，最后只有 **24 个 skb** 交给协议栈：

| 阶段 | 数量 | 平均 |
|---|---|---|
| 设备收到的包（`/proc/net/dev`） | **186** | —— |
| 进 GRO 的段（`dev_gro_receive`） | 186 | 1 段/次 |
| NAPI 轮询（`virtnet_poll`） | **25** | **7.4 包/轮** |
| 上送的 skb（`netif_receive_skb`） | **24** | **7.75 段/skb** |
| `ip_list_rcv` 批次数 | 23（每次 `n=1`） | —— |

有序片段最能说明问题（同一时刻的 14 个段 → 1 个聚合包）：

```
[    3.840689] [latte] dev_gro_receive: len=1480   ← ×14 行，时间戳完全相同
...
[    3.840735] [latte] netif_receive_skb: len=10120 proto=0x0800 dev=eth0
```

`10120 = 7 × 1440 + 40`：**7 个段合成一个 skb**（40 是 IP+TCP 头）。
上送 skb 的长度分布也都是这个形状：

```
      1 netif_receive_skb: len=10120      1 netif_receive_skb: len=14440
      2 netif_receive_skb: len=11560      2 netif_receive_skb: len=15880
      1 netif_receive_skb: len=13000      2 netif_receive_skb: len=17320
                                          4 netif_receive_skb: len=18760
                                          1 netif_receive_skb: len=21640
```

`1440×N + 40`，N 从 7 到 15——最大的 21640 是 15 个段合在一起。
`tcp_v4_rcv` 看到的也是这些大段（`len=2900`、`5780`、`8660`…），
说明合并发生在 **TCP 层之前**，TCP 白白少处理了 160 多次。

## 三个结论

1. **GRO 合并的是 skb，不是 list**：186 段 → 24 个 skb，实现方式是往同一个 skb 的
   `frags` 里追加。`ip_list_rcv` 的 `n=1` 与 `len=21640` 并不矛盾，
   前者说“这批只有 1 个 skb”，后者说“这个 skb 装了 15 段”。
   `net/04` 里“聚成 skb 列表”的措辞要改成“合并进同一个 skb”。
2. **合并的前提是“同一轮 NAPI 里有多个同流段”**：本次 25 次轮询吃掉 186 个包
   （平均 7.4 个/轮），所以合得很充分。`net/04` 的 ping 场景一轮只有 1~2 个包，
   自然看不到合并——那不是 GRO 没工作，是没东西可合。
3. **收益是“协议栈少跑”**：`netif_receive_skb` 24 次、`tcp_v4_rcv` 23 次，
   而不是 186 次；每省一次就是一次 `ip_rcv_core` + TCP 段处理。
   代价是延迟：GRO 会把数据攒到一个轮询结束才上送。

## 三个实验坑（都花了一轮才定位）

1. **busybox `dmesg` 是消费式读取**：同一个 ring buffer 连读两次，第二次是空的。
   我前面几次统计结果全是 0，就是因为它：第一次 `grep -oE` 把缓冲读了，
   后面的 `grep -c`/`awk` 读到的都是空。正确做法是**先 `dmesg > /dmesg.txt`，再反复 grep 文件**。
2. **`socat -u` 的方向是“地址1 → 地址2”**：写成 `socat -u TCP-LISTEN:...,FILE:big.bin`
   就变成“把收到的数据写进文件”，guest 那边永远等不到数据。
   正确写法是 `socat -u FILE:/tmp/big.bin TCP-LISTEN:10080,reuseaddr,fork`。
3. **这个 rootfs 没有 `/tmp`**：`nc ... > /tmp/got.bin` 直接报
   “can't create: nonexistent directory”，根本没发起连接。重定向到 `/dev/null` 即可。

## 复现

```bash
cd /home/dong/Documents/github/linux
head -c 262144 /dev/urandom > /tmp/big.bin
make -j16 bzImage
rm -rf /tmp/net8 && cp -a bb_rootfs /tmp/net8
cat > /tmp/net8/init <<'EOF'
#!/bin/sh
B=/bin/busybox
mount -t proc none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev
$B ip link set eth0 up
$B ip addr add 10.0.2.15/24 dev eth0
$B nc -w 5 10.0.2.2 10080 > /dev/null; echo "nc rc=$?"
$B grep eth0 /proc/net/dev
$B dmesg > /dmesg.txt          # 只 dump 一次，后面都读文件
$B awk '/virtnet_poll:/{p++} /dev_gro_receive:/{g++} /ip_list_rcv:/{l++} \
        /netif_receive_skb:/{r++} /tcp_v4_rcv:/{t++} \
        END{printf "virtnet_poll=%d dev_gro_receive=%d ip_list_rcv=%d netif_receive_skb=%d tcp_v4_rcv=%d\n", p+0,g+0,l+0,r+0,t+0}' /dmesg.txt
$B grep -oE "ip_list_rcv: n=[0-9]+" /dmesg.txt | $B sort | $B uniq -c
$B grep -oE "netif_receive_skb: len=[0-9]+" /dmesg.txt | $B sort | $B uniq -c
$B awk '/netif_receive_skb: len=1[0-9]{4}/{for(i=1;i<=14;i++) printf "%s\n", a[i]; print; exit} \
        {for(i=14;i>1;i--) a[i-1]=a[i]; a[14]=$0}' /dmesg.txt
echo "=== net8 done ==="
exec /bin/sh
EOF
chmod +x /tmp/net8/init
( cd /tmp/net8 && find . | cpio -o -H newc --quiet ) > /tmp/bb_net8.cpio

socat -u FILE:/tmp/big.bin TCP-LISTEN:10080,reuseaddr,fork >/tmp/socat8.log 2>&1 &
sleep 1
timeout 30 qemu-system-x86_64 -kernel arch/x86/boot/bzImage \
  -initrd /tmp/bb_net8.cpio \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
  -append "console=ttyS0 earlyprintk=serial nokaslr loglevel=3 panic=1" \
  -nographic -m 1G -no-reboot > /tmp/latte-net8.log 2>&1 || true
pkill -f "TCP-LISTEN:10080"
tr -d '\r' < /tmp/latte-net8.log | sed -n '/nc rc=/,/net8 done/p'
```

`loglevel=3` 在这里是必须的：186 个 `dev_gro_receive` 打到串口会把传输拖到超时。

## 代码位置

| 位置 | 函数 | 做什么 |
|---|---|---|
| `net/core/gro.c:463` | `dev_gro_receive()` | 按流查找并合并（追加到已有 skb 的 frags） |
| `net/core/gro.c:633` | `gro_skb_finish()` | 决定“继续攒”还是“flush 上送” |
| `net/ipv4/ip_input.c:656` | `ip_list_rcv()` | 批量入口，`n` 是这批 skb 数 |
| `net/ipv4/ip_input.c:460` | `ip_rcv_core()` | 两条路径（`ip_rcv`/`ip_list_rcv`）的汇合点 |
| `net/core/dev.c` | `netif_receive_skb_list_internal()` | list 版本的上送（GRO flush 调用它） |
| `.config` | `CONFIG_NET_GRO` / virtio-net 的 `NETIF_F_GRO` | 本次两者都开，所以能合并 |

## 一句话收尾

GRO 的全部秘密是“**在协议栈之前，把同一个流的多个段粘成一个 skb**”：
186 个包、25 次轮询、24 个 skb。判断它有没有生效，看 `netif_receive_skb` 的 `len`
（`1440×N+40`）比看批大小更直接。
