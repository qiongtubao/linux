# 主题二 · 磁盘、分区、文件系统，以及“根”

## 你已知的

一块硬盘 → 分成几个分区（Windows 里是 C:/D:）→ 每个分区格式化成一个文件系统
（NTFS/FAT32/ext4）→ 里面才有目录和文件。想访问某个分区里的文件，得先让它“出现
在系统里”。

Linux 里同样三件事，只是内核对象的叫法不同。

## 三件事在内核里叫什么

| 你说的 | 内核里的东西 | 说明 |
|---|---|---|
| 硬盘 / U 盘 | 块设备（block device） | 按块随机读写；用“主设备号:次设备号”区分 |
| 分区 | 分区表 + `block_device` | 分区表在磁盘开头；每个分区自己也是一个设备 |
| 文件系统 | `super_block` | 打开分区后先读超级块，才知道里面是 ext4 还是 xfs |
| 目录与文件 | `dentry` / `inode` | 文件系统的内部结构，挂载之后接进全局目录树 |

与块设备相对的是字符设备（键盘、串口）：只能按字节流顺序读写，没有“第 N 块”的概念。

## 为什么必须“挂载”才能用

Linux 只有**一棵**目录树，起点是 `/`。磁盘上的文件系统不会自动出现在树里：
必须 `mount` 到某个目录（挂载点），之后访问那个目录才会落到那个文件系统上。
这也是为什么内核里“打开磁盘上的根”必须等同于“把某个文件系统挂到某个目录”。

## “根文件系统”特殊在哪

所有路径查找都从 `/` 开始，所以 `/` 上必须先已经有一个文件系统。于是问题变成两级：

1. 启动最早期，`/` 上是**内存里的 rootfs**（ramfs 或 tmpfs，主题三）——一定有，不依赖任何磁盘；
2. 之后要不要把 `/` 换成磁盘上的根，取决于 `/init` 是否存在（主题四）。

`root=` 就是回答第 2 问的参数：告诉内核“磁盘上的根在哪”。

## `root=` 两种写法，对应两套分支

| 写法 | `ROOT_DEV` 变成什么 | 后续 |
|---|---|---|
| `root=/dev/sda2` | 真实设备号（`dev_t`） | 按块设备挂（主题五） |
| `root=/dev/nfs` | 伪值 `Root_NFS` | 走 NFS 客户端挂载，带重试 |
| `root=/dev/ram` | 伪值 `Root_RAM0` | 把 ramdisk 直接当根 |
| `root=mtd…` / `ubi…` | 伪值 `Root_Generic` | 交给通用查找 |

解析发生在 `parse_root_device()`；真正打开设备时，`mount_block_root()` 会先
`create_dev("/dev/root", ROOT_DEV)` 造一个临时设备节点（`/dev/root` 只是个名字，
指向 `ROOT_DEV` 那个主:次设备号），再逐个文件系统类型去试挂。

## 本次为什么“根本没有根可挂”

命令行里没给 `root=`，于是 `ROOT_DEV == 0`。内核仍然尽职地造了一个 0:0 的
`/dev/root`，打开它必然失败：

```
/dev/root: Can't open blockdev
VFS: Cannot open root device "" or unknown-block(0,0): error -6
```

完整日志与结论见主题七。这里的重点是：**没有 `root=` 不等于“用内存里的根”，而是
“没有磁盘根可挂”**——内存根那条路要靠 `/init` 走（主题四）。

## 代码位置
