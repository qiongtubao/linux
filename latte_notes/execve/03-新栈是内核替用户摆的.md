# 主题三 · 新栈是内核替用户摆的

## 你已知的

C 程序的 `main(argc, argv, envp)` 从哪拿到参数？不是从寄存器，而是从**栈**上：
进程刚启动时，栈顶依次放着 `argc`、`argv[]` 指针数组、`NULL`、`envp[]`、`NULL`，
再往后是 `auxv`（给动态链接器用的键值对）。这是 ABI 约定，谁来摆？——**内核**。

## 为什么必须是内核摆

`execve` 成功之后，用户态**一行代码都还没跑**，没有 `main`、没有 `libc`，
自然没有谁能去执行“把参数压栈”这件事。于是内核在切换前就把这一切做好：

| 步骤 | 谁做 | 说明 |
|---|---|---|
| 建一个临时栈 | `bprm_mm_init()`（`fs/exec.c:256`） | 在很高的地址 `STACK_TOP_MAX` 建一页栈，先当参数暂存区 |
| 把字符串压进去 | `copy_string_kernel()` / `copy_strings()` | 从栈顶**往下**增长，和用户程序压栈方向一致 |
| 记下新的栈顶 | `bprm->p` | 压完所有字符串后，这就是用户态 `RSP` 的初值 |
| 补 `auxv` | `create_elf_tables()`（`fs/binfmt_elf.c`） | `AT_PAGESZ`、`AT_RANDOM`、`AT_EXECFN`、`AT_ENTRY`… |
| 把栈搬到最终位置 | `setup_arg_pages()`（`fs/exec.c:598`） | 参数栈从临时位置搬到真正的用户栈顶（可能偏移随机化） |

所以 `bprm->p` 一路被传递，最后出现在 `START_THREAD(elf_ex, regs, elf_entry, bprm->p)`
里，变成新程序的 `RSP`。

## 实测：每次 execve 都换一份新栈

镜像 A 日志里的 `sp`（同一次启动内的四次 execve）：

| 被执行的程序 | 新栈顶 `sp` |
|---|---|
| `/init`（1 号进程） | `0x7fff4ade2b70` |
| `/bin/mount` | `0x7ffe937260a0` |
| `/proc/self/exe` | `0x7ffc593f04e0` |
| `/bin/sh` | `0x7fff6f950670` |

四个值都在用户栈的高地址区（`0x7ff…`），但各不相同的——因为每次 `execve` 都重建了
栈（含地址随机化）。同时 `ip` 都是 `0x40b300`：它们全是同一个 busybox 的入口
（`/bin/mount` 等只是它的符号链接）。

## 一个细节：脚本的参数是“拼”出来的

`/init` 是脚本 `#!/bin/sh`。内核加载的其实是 `/bin/sh`，但 `argv` 会被改写成：

```
argv = [ "/bin/sh", "/init", ...原来的参数 ]
```

这就是 `binfmt_script` 干的活：把解释器路径塞到 `argv[0]`、把脚本路径塞到 `argv[1]`，
然后 `bprm->argc++`。实测 `/init` 那次 `argc=2`（脚本 + `nokaslr`），而
`/bin/sh` 那次是 `argc=1`（脚本里 `exec /bin/sh` 没有额外参数）。

## 代码位置

| 位置 | 内容 |
|---|---|
| `fs/exec.c:256` `bprm_mm_init()` | 建临时栈 |
| `fs/exec.c:598` `setup_arg_pages()` | 把参数栈搬到最终用户栈 |
| `fs/binfmt_elf.c` `create_elf_tables()` | 摆 `argc/argv/envp/auxv` |
| `fs/binfmt_script.c` `load_script()` | 脚本改写成 `[解释器, 脚本, …]` |
