# 主题四 · 内存紧张时发生什么：水位、kswapd、直接回收

## 你已知的

内存快用完时系统会变慢、风扇转、有时卡死；极端情况下有进程被“OOM killer”杀掉。
这些现象背后是一套**三级响应**：后台回收 → 同步回收 → 压缩 → 杀进程。

## 三级响应

| 级别 | 触发条件 | 谁在做 | 代价 |
|---|---|---|---|
| 1 后台回收 | zone 的 free 低于 **low** 水位 | `kswapd` 内核线程 | 异步，正常情况用户无感 |
| 2 直接回收 | free 低于 **min** 水位，且快路径分配失败 | 当前进程自己（`direct reclaim`） | 同步变慢，等 I/O |
| 3 压缩 / OOM | 回收也凑不出连续块 | `compaction` / `oom_killer` | 搬页很慢 / 杀进程 |

每个 zone 有三个水位（`/proc/zoneinfo` 里的 `min` `low` `high`），差值就是“提前量”。
`min` 是关键：**低于 min 的分配必须自己下场回收**，不许再等后台线程。

## `kswapd` 是谁

`kswapd` 是每个内存 node 一个的内核线程（本次实测 2.2 秒就绪）：

```
kswapd()                       mm/vmscan.c:7330    ← 睡眠等你叫醒
 └─ balance_pgdat()            mm/vmscan.c:7001    ← 一次回收循环
     └─ shrink_node()          mm/vmscan.c:6074    ← 扫 LRU、回收页
         └─ shrink_slab()                          ← 顺手收缩内核对象缓存
```

它带 `PF_MEMALLOC` 标志：回收途中自己申请内存不会被再拉进回收，避免递归。

## 直接回收

快路径（`get_page_from_freelist()`）失败 → 进慢路径：

```
__alloc_pages_slowpath()        mm/page_alloc.c:4647
 ├─ 唤醒 kswapd（希望它赶紧干活）
 ├─ __alloc_pages_direct_reclaim()
 │    └─ __perform_reclaim()  → try_to_free_pages()  ← 自己同步扫一遍
 ├─ compaction（腾连续块）
 └─ OOM killer（再不行就杀）
```

`try_to_free_pages()` 与 kswapd 的 `balance_pgdat()` 干的是同一类活，区别是有量：
它只求“扫够 `SWAP_CLUSTER_MAX`（32）页”，不追求回到水位——因为它是在**别人等分配**的
路径上，不能无限扫。

## 回收“回收什么”

| 页类型 | 回收手段 | 备注 |
|---|---|---|
| 干净文件页 | 直接丢弃（还在磁盘上） | 最快，等于释放页缓存 |
| 脏文件页 | 先回写再丢弃 | 慢，靠 `writeback` |
| 匿名页（堆/栈） | 换出到 swap | 本机没 swap，`CONFIG_SWAP=y` 但没有交换设备 |
| slab 对象 | `shrink_slab()` | 释放 dentry/inode 缓存等 |

因为没有 swap，本机的匿名页**回收不掉**——这也是小内存机器上“内存一满就 OOM”的原因。

## `/proc/vmstat` 里的读数

| 计数 | 含义 |
|---|---|
| `pgscan_kswapd` | kswapd 扫描了多少页 |
| `pgsteal_kswapd` | kswapd 真正回收掉多少页 |
| `pgscan_direct` / `pgsteal_direct` | 直接回收扫了多少 / 收了多少 |
| `allocstall_*` | 分配被迫停下等回收的次数 |
| `pgalloc_dma32` / `pgfree` | 页分配/释放总量 |

**本次实测（无压力启动）：全是 0**。这不是 bug——内核启动自己只用了几十 MB，远没到
水位。真正的压力要用户态去制造（主题五）。
